# WP-266 — the findings of the fuzzing budget on the 1.0 candidate

Landed: two classes of the fuzz harness, each on evidence gathered for
the seed in the run (`spec/harness.md` "Random programs", "Set apart"
and "Set apart (seeds)"; `spec/dwarf.md` §5.10, last paragraph). No
change under `crates/`: hod's code and line rows stay as they are.

The budget's run on the candidate (hod 02fe2d02, 62 slices, 26,250
seeds) exited 1 with two findings and one error of the harness.

## Findings 1 and 2: `dead-store`

| seed | slice | pair | statement |
|---|---|---|---|
| 220612 | x86-64 LLVM 22 debug, csmith `c` | func_1 prog.c:713 | `l_2459 \|= (&g_1494[0] == &g_1494[2]);` |
| 220916 | x86-64 LLVM 22 debug, csmith `c-float` | func_23 prog.c:718 | `(*l_161) = (g_168 = 0x8.564011p+55);` |

The IR of 713: `icmp eq ptr @g_1494, getelementptr (... @g_1494, 0, 2)`,
`zext`, a load of `%277`, `zext`, `or`, `trunc`, a store to `%277`. The
IR of 718 (an out-of-range float-to-integer conversion):
`store i32 poison, ptr @g_168`, a load of `%57`, `store float poison`
through it.

`is_stmt` rows at the pair (`llvm-dwarfdump-22 --debug-line` of each
object, `llc-22 -O0 -relocation-model=pic`):

| seed | hod | SelectionDAG | FastISel | GlobalISel |
|---|---|---|---|---|
| 220612 | 1 (713:43) | 0 | 1 (713:43) | fell back on func_1 (0 rows, SelectionDAG's) |
| 220916 | 1 (718:31) | 0 | 1 (718:31) | fell back on func_23 (0 rows, SelectionDAG's) |

What each wrote at the line (`llvm-objdump -d`):

- hod: 713, `leaq`/`leaq`/`cmpq`/`sete`/`movzbl` (the compare) and
  `movzbl`/`movzbl`/`orl`/`movb` (the `or` and the store); 718, `movl $0x0`
  to `g_168` and `movl $0x0` through the reloaded pointer.
- `FastISel`: the same statements (`cmpq`/`sete` ... `orl`/`movb`; a
  `movl %eax` and a `movss %xmm0` of whatever the registers held).
- `GlobalISel`: fell back to `SelectionDAG` on both functions (below).
- `SelectionDAG`: nothing. Its rows go from the store of line 712
  straight to line 715 (seed 220612), and line 718 has only the
  function's line-0 row: it folds the compare to 0 and the `or` away,
  then deletes a store of a value just loaded from the same address and
  a store of `undef`.

**A correction, as it happened.** The first reading took
`global-isel.o`'s missing rows for `GlobalISel` deleting the statements
too (rows 1/0/1/0), and a class was agreed on that reading
("`GlobalISel` built, no fallback, 0 rows"). The re-run of the two seeds
under it still found both: `GlobalISel` had printed `warning:
Instruction selection used fallback path for func_1` (a call with a
`byval` argument at line 346, `-pass-remarks-missed=gisel`) and `...
for func_23` (a `volatile` 24-bit load at line 789), so the rows of
those functions in `global-isel.o` were `SelectionDAG`'s, and the
candidate's harness had rightly refused `selector-split` for want of
evidence. The two statements alone in a function `GlobalISel` selects
(`x |= (&a[0] == &a[2]); *p = (g = 0x8.564011p+55);`, clang `-O0 -g`,
`llc -O0`, LLVM 22 and 19 alike) have rows under `FastISel` (3:15, 4:11)
and `GlobalISel` (the same) and none under `SelectionDAG`: a selector
split, 1/0/1/1, hidden by the fallback.

hod is right: the stores change nothing in memory, deleting them is
allowed and keeping them is too, and a row names code hod really
writes. Moving the rows to another line would misattribute that code;
deleting the stores changes machine code, not a line rule. So the
difference is set apart by a new narrow class, not fixed:
`case::dead_store`, with `permitted::IrFacts::dead_store` for the IR.
Its evidence, all of it required: a hod-only pair left unclassified and
not a selector split; `FastISel` built and linked with a row at it;
`GlobalISel` built, and its `stderr` holding the fallback warning for
that very function (a fallback elsewhere does not count; a `GlobalISel`
that selects the function decides alone: a row is a selector split, no
row a finding); and the line's instructions loads, stores, compares,
casts and binary operations, none `volatile` or `atomic`, with a store of
`poison`/`undef` or a store to the pointer a load of the line reads. The
IR condition stands in for `GlobalISel`'s row only where `GlobalISel`
gave no answer of its own. The pair is printed (`dead-store: seed S F at
prog.c:L: rows hod H selection-dag 0 fast-isel A global-isel fell back
("warning: Instruction selection used fallback path for F"); the IR:
...`), counted with the selector splits, and in the budget under its own
name.

## Item 3: `llc19-int128-last-register` at `--mix`'s self-check

Seed 226098 (x86-64 LLVM 19 `abi` `--mix`) was an ERROR: "llc's two
halves disagree with the whole module: stdout differs at byte 268". The
module has the class's shape: `call @callee_0(sret ptr, i8, x86_fp80,
ptr, i32, i64, i128, ...)`, variadic, the `i128` as argument 7 with only
`r9` left. Built by hand (`clang-19 -O0`, `llc -O0 -global-isel=0
-fast-isel=0`, x86-64 gcc `-O0 -pie`, run under qemu):

| program | bytes | status | output |
|---|---|---|---|
| gcc -O0, prog.c | 1377 | 0 | reference |
| llc-22, the module | 1377 | 0 | the same as gcc's |
| llc-19, the module, run 1 | 1387 | 0 | differs at byte 266 |
| llc-19, the module, run 2 | 1387 | 0 | differs from run 1 |

`llc` 19's callee reads with `va_arg` the `r9` its caller left unset, so
its output is garbage that changes from run to run; its halves and its
whole module print different garbage, which the self-check saw before
hod was asked. `int128::decide_self_check` now sets such a seed apart
when gcc's and `llc` 22's programs agree with each other and `llc` 19's
whole module does not; otherwise the error stays and says why the class
did not apply.
