# WP-260: the trees of an optimized unit

Spec: `spec/dwarf.md` §6.37 (and the notes in §6.7 and
`spec/harness.md` "Trees"). hod's output is unchanged: no file under
`crates/` was edited. The binary measured is the 1.0 candidate, hod
02fe2d02 (sha256 5c1e181d...c3633d), with kiln 8f93304ee's corpus.

## The open item

`cargo xtask debug trees` exited 1 at the candidate. On AArch64 it gave
8 same, 8 `realigned frame` and 2 differ; on x86-64, 16 same and 2
differ. The two that differed were one test,
`class.temporary/lifetime-markers-O2-g-fpic-run.cpp`, in both its LLVM
22 and LLVM 19 corpus entries. It is an `-O2 -g -fPIC` unit, so kiln's
IR is optimized and its locals are described by `#dbg_value` records.
hod's object passes `--verify`, and the program passes strict L6.

The tree comparison found these kinds of difference. The three listed
first were recorded by WP-244; the others were hidden behind the first
`DIFFERS`:

| kind | hod | `llc` | target |
|---|---|---|---|
| value locations | `DW_AT_location` list, or none | single expression, `DW_AT_const_value`, list, or none | both |
| unit list bases | `DW_AT_rnglists_base` | `DW_AT_loclists_base` | both |
| block ranges | `DW_AT_ranges` (2 ranges) | `low_pc`/`high_pc` | both (already equal by §6.7) |
| placeless concrete `this` | DIE with only `abstract_origin` | none | both |
| call-site return addresses | hod's code | `llc`'s code | both |
| frame base | `DW_OP_reg6` (`rbp`) | `DW_OP_reg7` (`rsp`; the IR asks for no frame pointer) | x86-64 |
| sibling order | variables and types in another order | | both |

## (A) Is hod's information correct?

Yes, for every kind, on both targets. The tools and transcripts are in
the work directory `.build/findings/wp-260/`, outside the repository:
`tools/walk.py`, `tools/summarize.py`, `tools/callpc.py`,
`tools/run-remote*.sh` and `work/`.

1. **Instruction walk** (`walk.py`). gdb has a breakpoint on every
   instruction of the module's six functions. At each stop it prints
   the frame (inlined frames by name), the line and every variable
   visible in the scope chain. The program is run natively on AArch64
   and under `qemu-x86_64 -g` with `gdb-multiarch` on x86-64. Stops on
   hod's programs: AArch64 300 (LLVM 22) and 304 (LLVM 19); x86-64 368
   and 373. The distinct values shown (`walk-hod-*.sum`) are identical
   for the two LLVM dialects on each target, and identical between the
   targets apart from the counts. Every value shown is the program's:
   - `may_throw`'s `n` = 3;
   - `make`'s `n` = 3, 4 and 0;
   - `a` and `__range1` are the argument, and `__end1` = `a`+24;
   - `__begin1` = `a`+12 over the first two instructions of the loop's
     code, which is what the IR's last record before them says. From
     the next record on (a `DIArgList` and a folded `getelementptr`,
     which have no home) it is `<optimized out>`, never stale;
   - `g1`..`g6` have ids 1, 2, 4, 5 and 6, and `argc` = 1;
   - `r` = `@0x0` only before `make` returns. That is the IR's
     `ptr null` record, and `llc` says `DW_OP_lit0` there too.

   Everything else is `<optimized out>`.
2. **Line sessions** (`gdb-lines-{hod,llc}-{a64,x64}.txt` and
   `lldb-lines-{hod,llc}-a64.txt`; a breakpoint on every source line,
   `info args`/`info locals` or `frame variable`). Comparing hod
   against `llc` 22's program, every line is equal, or hod has
   `<optimized out>` / `<variable not available>` where `llc` has a
   value (the session class `value-range`). There is one exception:
   `__range1` in `total`, where hod prints the array and `llc` prints
   `Cannot access memory at address 0x0`. That is `llc`'s error, not
   hod's. `llc` writes `DW_AT_const_value 0`, taken from the first of
   the two records `#dbg_value(ptr null, ...)` and
   `#dbg_value(ptr %0, ...)` at the same point; the later record holds.
   lldb 19 reads hod's lists, which have `DW_FORM_sec_offset` and no
   `loclists_base`, the same as gdb:
   `image lookup -va` shows each range and expression.
3. **Static checks** against the disassembly (both targets). Each home
   slot named by a list (`fbreg +16/+24/+64/+88` on AArch64,
   `-32/-48/-64/-32/-56` on x86-64) is stored by the instruction just
   before its range and never stored inside it. `guarded` reuses its
   argument's slot for the `sdiv` result, and hod gives `n` no range
   there. Each list entry ends at the next record of its variable, or
   at its block's end.
4. **Unit bases.** hod's location lists are `DW_FORM_sec_offset`
   (absolute, §6.23), so they need no `DW_AT_loclists_base`. Its
   `DW_AT_rnglists_base` is the base of the one `DW_FORM_rnglistx`
   `DW_AT_ranges`, which `llvm-dwarfdump` decodes as `indexed (0x0)
   rangelist`. gdb and lldb read both (item 2). Nothing a consumer
   could misread.
5. **Block ranges.** `guarded`'s inner block is
   `[0x130,0x15c) [0x184,0x18c)` on AArch64 and the same shape on
   x86-64. The second range is the landing pad's two stores of the
   exception pointer and selector. Its IR location is `!112` (line 43,
   scope the block `!85`), so the range belongs to the scope.
6. **Call sites** (`callpc.py`). On each target all 13
   `DW_AT_call_return_pc` values are the address after a call
   instruction, and each call's relocation names the `DW_AT_call_origin`
   callee.
7. **Placeless `this`.** Its records are all `poison` or `undef`. hod's
   concrete DIE has no location; gdb prints `this=<optimized out>` from
   the abstract instance under both programs.

No release finding.

## (B) The classes

`xtask/src/debug/trees.rs` adds:
- the facts `described_by_values` (the names of the variables of value
  records, "" for an unnamed one) and `without_frame_pointer` (defined
  functions without a `"frame-pointer"` of `all`, `non-leaf...` or
  `reserved`);
- the classes `value records`, `no frame pointer` and
  `unit range lists`, exactly as §6.37 states them;
- the sibling comparison by identity, only in modules with value
  records;
- the relocation rules: `llc`'s `loclists_base` one, hod's one per value
  list, and hod's `rnglists_base` one;
- `DW_AT_call_return_pc` and `DW_AT_call_pc` added to the masked
  attributes, as §6.7 already said.

Unit tests (module `optimized_units`):
- `the_shapes_of_an_optimized_unit_are_permitted`;
- `what_the_classes_do_not_cover_differs`, nine negative cases: a
  declared variable, a module without value records, a function with a
  frame pointer, hod's own single expression, another attribute
  differing, an extra DIE with a location, a DIE of `llc`'s hod lacks,
  a relocation beyond the lists, `rnglists_base` without more ranges;
- `value_variables_and_frameless_functions_of_a_module` (`DIArgList`,
  the old intrinsic, an unnamed variable, a `#dbg_declare` left out,
  attribute groups and quoted names);
- `call_site_addresses_are_masked`.
