# WP-351: a first open-source lane for i386

Landed: `scripts/oss/i686/` (the compiler wrapper `i686-cc` with its
`i686-c++` link, the driver `i686-oss.sh`, the summaries
`i686-report.py`), the status page `docs/status/oss-i686.md`, and the
first results: zlib, zstd and bzip2 for `i686-unknown-linux-gnu`, each
built in control, hybrid and strict mode and tested under `qemu-i386`.

## The compiler pair and the control

kiln has no i686 target, so the lane uses clang 22 as the front end with
hod as the back end, as the libc++ i686 lane does (WP-330, WP-339;
`i686-cc` is derived from `scripts/libcxx-i686-clang.sh`). Every
invocation gets `--target=i686-linux-gnu`; clang finds the cross GCC
installation, its linker and `/usr/i686-linux-gnu` itself.

- A compile of a source (`.c .cc .cpp .cxx`) is split in two. clang
  writes the module (`-S -emit-llvm`) with the invocation's own flags
  plus `-Xclang -disable-llvm-passes`. The project's `-O2` still steers
  the front end (`__OPTIMIZE__`, no `optnone`/`noinline`, lifetime
  markers, TBAA), but no LLVM pass runs: the module is the front end's,
  before optimization, which is what kiln hands hod. Then the back end
  writes the object from that module.
- The modes differ only in the back end, on the same `.ll`:
  control = `llc -O0 -global-isel=0 -fast-isel=0` (the reference, as on
  every hod lane); hybrid = hod (`HOD_CENSUS=1`) with the wrapper itself
  as `--fallback`, which `exec`s the control's `llc` (so a declined
  module is built exactly as in the control, WP-339); strict = `hod
  --strict` (`HOD_CENSUS=1`): a refusal fails that compile, `make -k`
  builds the rest. All get `-relocation-model=pic` when the module has a
  "PIC Level" flag. Check: on bzip2 the `.ll` files of the control and
  strict trees are byte-identical and the objects differ.
- Links, assembly files and probes go to clang unchanged (with the
  target). During the build (`HOD_I686_LAUNCH=1`) an executable is
  linked to `<out>.i686` and `<out>` becomes a script that runs it
  under `qemu-i386 -cpu pentium2,-mmx -L /usr/i686-linux-gnu -R
  0x40000000` (hod_testutil's I686_EMULATED_CPU: no SSE, no MMX), so
  ctest and the lane's own tests run the programs unchanged. Configure
  runs in control mode without launchers (CMake reads its probe
  executables), so the three builds configure alike.
- Builds are the projects' release builds at -O2:
  `CMAKE_BUILD_TYPE=Release`, `CMAKE_C_FLAGS_RELEASE="-O2 -DNDEBUG"`;
  bzip2 with its own Makefile's `-Wall -Winline -O2
  -D_FILE_OFFSET_BITS=64`.

## Projects

Chosen from the 64-bit lanes' list for plain C, tests that run in
minutes under qemu, and sources already in the workspace (nothing was
fetched): zlib 1.3.2 and zstd 1.5.7 (the 64-bit lanes' cached clones,
`.build/oss/src`, at `projects.toml`'s tags) and bzip2 1.0.8 (the copy
in CMake's sources, `.build/oss3/src/cmake/Utilities/cmbzip2`; lua,
sqlite, xz and libpng are not in the cache).

- zlib: shared and static library, `ZLIB_BUILD_TESTING=ON`; tests as the
  64-bit row: ctest (`-j1`, without the install / find_package /
  add_subdirectory tests) then six minigzip round trips of `libz.a`.
- zstd: library, programs and tests (`build/cmake`, the row's
  configure flags); tests: ctest without playTests (fullbench -i1,
  fuzzer -T60s, zstreamtest -T60s and the rest).
- bzip2: libbz2.a, bzip2, bzip2recover; 32 tests of the lane's own
  (bzip2's sample files are not in CMake's copy): for six inputs
  (the library, the bzip2 program, text, an empty file, one byte
  repeated, random bytes) and `-1`, `-9`, `-s`: a round trip whose
  stream must also equal the host bzip2 1.0.8's byte for byte; the host's
  stream decompressed by the lane's; `bzip2 -t` of the host's stream; a
  corrupted stream detected; bzip2recover's blocks decompress to the
  input.

## Results (2026-11-17, hod built from `8b8844f4`, sha256 `462f2d728ce2...`; clang 22.1.8, qemu-i386 10.0.13)

| project | mode | units | by hod | refused | build | tests pass / fail |
|---|---|---:|---:|---:|---|---|
| bzip2 | control | 9 | - | - | ok | 32 / 0 |
| bzip2 | hybrid | 9 | 9 | 0 | ok | 32 / 0 |
| bzip2 | strict | 9 | 9 | 0 | ok | 32 / 0 |
| zlib | control | 37 | - | - | ok | 11 / 0 |
| zlib | hybrid | 37 | 37 | 0 | ok | 11 / 0 |
| zlib | strict | 37 | 37 | 0 | ok | 11 / 0 |
| zstd | control | 118 | - | - | ok | 3 / 0 |
| zstd | hybrid | 118 | 118 | 0 | ok | 3 / 0 |
| zstd | strict | 118 | 118 | 0 | ok | 3 / 0 |

(zlib's 11: example, example64 and their static builds, infcover, six
minigzip round trips; zstd's 3: fullbench -i1, fuzzer -T60s,
zstreamtest -T60s.) Every object of the hybrid and strict trees is
hod's (the coverage log), and differs from the control's (checked on
zstd: 118 of 118).

- Suspected miscompiles: none. No test passes in control and fails
  in hybrid or strict.
- Census: nothing refused at the lane's flags. One refusal outside
  them: zlib asks for `-coverage` on infcover, whose link needs an i686
  `libclang_rt.profile.a` the container does not have (it fails in
  every mode, the control included), so the lane drops the flag
  (`HOD_I686_DROP_FLAGS`). With the flag, hod refuses the module:
  `named-metadata:llvm.gcov` (one module; `llc` ignores the metadata).
  With `-disable-llvm-passes` the GCOV pass never runs, so the module
  carries only that named metadata, no counters. Saved:
  `.build/findings/oss-i686/census/infcover-coverage.ll` and its
  reduction `gcov-reduced.ll` (one function, `!llvm.gcov`).
- Back-end time, the same modules, one at a time, fastest of three
  (`i686-time.sh` on the control trees, which hold the kept modules;
  the counts include one or two CMake probe modules):

  | project | modules | llc | hod | hod / llc |
  |---|---:|---:|---:|---:|
  | bzip2 | 9 | 256 ms | 191 ms | 0.74 |
  | zlib | 38 | 836 ms | 889 ms | 1.06 |
  | zstd | 120 | 4991 ms | 2084 ms | 0.42 |

  zlib's modules are small (about 20 ms each for either back end, mostly
  process start), and single runs on the loaded machine vary by more
  than the difference. The wrapper's own `time.tsv` (inside the parallel
  builds) gives hod / llc 1.24 (zlib), 0.95 (bzip2), 0.74 (zstd) for
  strict.
- Test time: zstd's fuzzer ran 253 s in control and about 400 s with
  hod's code (both modes): run-time speed is not hod's goal, and the
  `-T60s` limits keep the step bounded.

## Lane fixes found on the way

- An option's value is kept whole in the IR step (`-MT
  CMakeFiles/x.dir/a.c.o` is not an object to drop; dropping it made
  `-MT` swallow `-MF` and every CMake compile fail).
- `i686-oss.sh` runs from a copy of the lane taken when it starts
  (`<root>/.lane-<pid>/`), as `oss-run.sh` does: editing the scripts
  during a build does not change the running one.

## Rerun

    cd hod && source scripts/env.sh
    scripts/oss/i686/i686-oss.sh <zlib|zstd|bzip2> <control|hybrid|strict> [--force] [--prune]
    python3 scripts/oss/i686/i686-report.py table "$CARGO_TARGET_DIR/oss-i686"
    scripts/oss/i686/i686-time.sh "$CARGO_TARGET_DIR/oss-i686/<project>/control"

The table command also lists the tests that pass in control and fail
with hod (the suspects) and the back-end time from `time.tsv`. To bisect
a suspect: each tree keeps every `<object>.ll` and object in place, so
one object at a time is copied from the control tree into the hod tree
and the program relinked there (`make` in the tree's build directory).
