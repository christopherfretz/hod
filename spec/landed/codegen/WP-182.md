# WP-182: one-leaf arrays across calls on AArch64

The one refusal WP-160's ABI fuzzing met (`docs/status/fuzz.md`): 11 of
300 programs of the `abi` profile on AArch64 refused with
`abi:one-leaf-array`. The C type is a packed structure of one
`long double`, which clang 19 and 22 and kiln all write as
`[1 x fp128] alignstack(8)`; the same frontends write
`[1 x fp128] alignstack(16)` for an ordinary one (supported before) and
`[1 x double] alignstack(8)` for a packed `struct { double x; }`
(supported before). In the corpus: 56 parameters of
`[1 x fp128] alignstack(16)` and 16 of `[1 x double] alignstack(8)`,
none of the refused shape.

## Why it was refused

WP-034 (`spec/landed/abi-a64/WP-034.md`) cross-checked every signature
against GlobalISel (plain `llc -O0`) and SelectionDAG (`llc -O2`): for a
one-leaf array whose stack alignment `A` (§3.3) is not the leaf's own
slot size, SelectionDAG passes a block aligned to `A`, GlobalISel an
ordinary leaf in its slot. With two oracles that disagree it refused.
Since then the project's oracle is SelectionDAG at `-O0`
(`docs/VALIDATION.md` "Oracles").

## What LLVM does

`llc -O0 -global-isel=0 -fast-isel=0` and `llc -O2`, LLVM 19 and 22,
place `[1 x fp128] alignstack(8)` behind eight `double`s, eight `i64`s
and one stack `i64` at `sp+8`; GlobalISel (19 and 22) at `sp+16`. The
two versions never differ. gcc (`-O1`) reads the packed
`struct { long double x; }` from `sp+8` too, and clang 22 at `-O1` does;
clang 22 at `-O0`, whose AArch64 back end selects with GlobalISel, reads
it from `sp+16`: an LLVM inconsistency between optimization levels, not
something hod can agree with both sides of. AAPCS64 C.12/C.13 round
NSAA to the alignment of the composite (at least 8), which is
SelectionDAG's answer.

## What is implemented

- `crates/hod_a64/src/abi.rs`: a one-leaf array is a block like any
  other (§3.3): the leaf's register, or the stack aligned to `A`. The
  refusal is gone; `ONE_LEAF_ARRAY` stays as a `pub const` for the
  coverage log's history, out of `UNSUPPORTED` (now 22 names).
- The same rule for the one-leaf `i128` arrays of WP-101
  (`wide_int_array`): on the stack, an `alignstack` below 16 makes
  `[1 x i128]` a block aligned to `A` instead of an ordinary 16-aligned
  `i128`. Found by the random grid once the new shapes were drawn
  (`[1 x i128] alignstack(8)` read 8 bytes off by both SelectionDAG
  configurations); latent before, as nothing drew it.
- No change in the call and return lowerings (`call.rs`, `vcall.rs`,
  `term.rs`): they place what `assign` says, and a one-leaf block on the
  stack is one part (or two merged pieces for `i128`).
- Returns were already supported and are unchanged (§5).

Refused, unchanged: `abi:bfloat-array` (llc 19 is not a block where
llc 22 is; a `[1 x bfloat]` with no register left is refused as before),
`abi:wide-int-array` (`[1 x i128]` at an odd NGRN with registers left,
and `n` ≥ 2 that do not fit), `abi:vector-array`.

## Evidence

- `grid::one_leaf_arrays` (new, in the systematic grid): 18 leaf types
  (`i8`, `i32`, `i33`, `i48`, `i64`, `ptr`, `i65`, `i128`, `half`,
  `bfloat`, `float`, `double`, `fp128`, `<2 x i32>`, `<1 x i64>`,
  `<4 x i32>`, `<3 x float>`, `<16 x i8>`) × lengths 1, 2 (3, 4, 5, 8, 9
  under `HOD_ABI_GRID=full`) plus `[1 x [1 x T]]`, `[1 x { T }]`,
  `{ [1 x T] }`; each as argument and result; `alignstack` none, 8, 16;
  in registers, with one register of each class left, on the stack at
  offsets 8 and 12 bytes past a slot boundary, beside `sret` and two
  `byval`s. Run by execution in both directions (hod calls LLVM, LLVM
  calls hod) under llc 19 and 22: systematic grid 4,409 signatures in
  the quick grid (was 2,970), 5,689 under `HOD_ABI_GRID=full`; random
  grid 8,000 (seeds 1 to 4), all agree. A case with a one-leaf array
  whose `A` is not the leaf's slot runs under SelectionDAG only
  (`Case::has_one_leaf_block`, `run::runs`): about 220 signatures of
  the quick grid skip GlobalISel.
- `errors::every_name`: the four former refusals now assign.
- Seed test `tests/ir/one_leaf_array.ll`: one-leaf arrays of `fp128`,
  `float`, `double`, `i64`, nested, and `[2 x fp128] alignstack(8)`, in
  registers and on the stack, returned `[1 x fp128]` and `[1 x double]`.
- `cargo xtask fuzz --profile abi --seed 1 --count 300` on AArch64
  (LLVM 22, `-j 3`), as WP-160 ran it: whole, 300 of 300 agree, 0
  refused (was 289 and 11 `abi:one-leaf-array`); `--mix`, 300 of 300
  agree, 0 refused, no finding.
- Mutation: giving a one-leaf block its leaf's slot (GlobalISel's rule)
  in `abi.rs` fails the systematic grid with 284 failures; reverted.

## x86-64

hod_x64 has no array-specific refusal name, but it declines every
parameter `alignstack` as `attr:alignstack` (the support matrix's
`todo(X64)` row, `crates/hod_ir/src/classify/matrix.rs`), so the seed
test carries `unsupported(x86_64): *`. Frequency: clang 22 and kiln
write no parameter `alignstack` for x86-64 (none in the probes of this
package), and the x86-64 `abi` fuzz profile met no refusal in WP-160
(300 of 300); the refusal is met only by IR written for AArch64. Left
as it is.

The seed test also runs split (`llvm-extract`: `main` by hod and the
callees by `llc -O0 -global-isel=0 -fast-isel=0`, and the other way
round): the same output.

## Sweep: the other `abi:*` names on AArch64

Probes compiled with clang 19 and 22 (`--target=aarch64-linux-gnu`) and
kiln (`-O0 -S -emit-llvm`), and a scan of the corpus's 6,454 modules.

| name | written for ordinary C/C++? |
|---|---|
| `abi:cc` | only by explicit attributes: `preserve_most`, `preserve_all`, `aarch64_vector_pcs` give `preserve_mostcc`, `preserve_allcc`, `aarch64_vector_pcs` (corpus: kiln's `dcl.attr.cconv` conformance test, both LLVMs). **Next package candidate.** |
| `abi:invalid-signature` | no (verifier-invalid IR) |
| `abi:type-x86_fp80` | no (x86 only) |
| `abi:scalable-vector` | only SVE ACLE types (`svint32_t`) with `+sve`; not in the corpus |
| `abi:target-ext-type` | no |
| `abi:addrspace` | no (none in the corpus) |
| `abi:vector-element` | `ext_vector_type` of `_BitInt(N)`, N odd; rare, not in the corpus |
| `abi:mask-wide` | `_Bool __attribute__((ext_vector_type(128)))` gives `<128 x i1>`; clang extension, not in the corpus (largest mask parameter there: `<16 x i1>`) |
| `abi:wide-int-array` | no: clang and kiln pass `__int128` members and `_BitInt(65..128)` structures as `i128`, larger ones indirectly |
| `abi:bfloat-array` | **yes**: `struct { __bf16 a, b; }` and `_Complex __bf16` are `[2 x bfloat] alignstack(8)`; refused when fewer than two vector registers are left (corpus: kiln's `ext.complex/complex-bf16.cpp`, both LLVMs, which fits). **Next package candidate** (llc 19 and 22 differ: a precise rule per version, or the llc 22 rule with llc 19 named) |
| `abi:vector-array` | no: an HVA of 16-byte vectors is `[N x <4 x float>]` (one register each); a 32-byte vector member makes the aggregate indirect |
| `abi:attribute-after-empty-argument` | no: an empty structure is `i8` (clang 19, C) or `i64` (clang 22 and kiln, C++), never `{}` |
| `abi:inreg`, `abi:swiftself`, `abi:swifterror`, `abi:swiftasync`, `abi:inalloca`, `abi:preallocated` | no (x86 or Swift only; none in the corpus) |
| `abi:elementtype` | on inline-asm operands (`"=*m"(ptr elementtype(i32) …)`), which do not go through `assign`; never on a call |
| `abi:byval-align` | no: clang and kiln never write `byval` on AArch64 (aggregates over 16 bytes travel as a pointer to a copy); none in the corpus |
| `abi:too-many-pieces`, `abi:size-limit` | no (indirect above 16 bytes) |
