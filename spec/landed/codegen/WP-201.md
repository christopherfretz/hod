# WP-201 — the target features of real `-march=` settings

Landed: `crates/hod_x64/src/features.rs` (`AVAILABLE`, `tuning`, four new
reasons, `of_function`'s implications and CPU tables),
`crates/hod_a64/src/features.rs` (the rest of LLVM's instruction
features, `tuning`, `attr:target-feature-thread-pointer`),
`spec/codegen.md` §5.6.2 (rewritten in place), `spec/abi-x64.md` §1.3.
Tests: `crates/hod_x64/tests/features_census.rs` with its data
`crates/hod_x64/tests/features/{x64_census,x64_features,x64_cpus}.tsv`,
`crates/hod_a64/tests/features_census.rs` with
`crates/hod_a64/tests/features/a64_census.tsv`, and the unit tests of both
`features` modules.

The finding: a module built with `-march=haswell` was refused whole as
`attr:target-feature-unknown` (`+fsgsbase` first, then `+invpcid`,
`+pclmul`, `+rdrnd`, `+xsaveopt`; 134 of 136 simdjson objects, second
real-project lane).

## Census

A one-function C file at `-O0 -S -emit-llvm`, its `"target-cpu"`,
`"tune-cpu"` and `"target-features"` collected, on the AArch64 host:

- x86-64: `-march=<cpu>` for every CPU of `--print-supported-cpus` of
  clang 19 (137 names) and 22 (140), and kiln at the clang 22 list, plus
  no flag and `-march=native`. The 32-bit-only CPUs (`i386` to
  `pentium4`, `athlon*`, `k6*`, `geode`, `winchip*`, `c3*`, `lakemont`)
  and the underscore aliases are refused by all three for x86-64. 75
  distinct `target-cpu` values, 112 feature names (121 with the AArch64
  names below), 107 distinct strings.
- AArch64: `-mcpu=<cpu>` for every CPU of clang 19 (80 names) and 22
  (107), kiln at the clang 22 list; `-march=armv8-a` .. `armv9.6-a` (9.6:
  clang 22 and kiln) with no extension and with `+crypto`, `+sve`,
  `+sve2`, `+sme`, `+lse`, `+nolse`, `+crc+aes+sha2`, `+fp16`,
  `+bf16+i8mm`, `+memtag`, `+pauth`, `+nofp`, `+nosimd`, `+sve2+sme2`,
  `+dotprod+rcpc`; no flag and `-mcpu=native`. 83 `target-cpu` values,
  129 feature names, 529 distinct strings.

kiln against clang 22 (the binary before pin 21caaf874; the 505 kiln runs
repeated at 21caaf874 give the same output): the same strings
for every x86-64 CPU but `novalake` and `wildcatlake` (kiln writes the
CPU with the baseline features only; `llc` 22 derives the rest from the
CPU, and hod assumes AVX and AVX-512 for a CPU it has no row for, so it
only refuses), and `-march=native` (kiln: no `target-cpu`, the baseline;
clang: `x86-64` with the *host's AArch64* features `+neon`, `+lse`,
`+crc`, `+aes`, `+sha2`, `+sha3`, `-rand`, `-sve` — a clang quirk when
cross-compiling, left unknown). AArch64: kiln refuses `-mcpu=cortex-r82`
and `cortex-r82ae` (clang writes `+v8r`, refused `attr:target-feature-profile`),
and its `-mcpu=native` writes the baseline where clang writes the host's
`+aes,+crc,+ete,+lse,+sha2,+sha3,+trbe`.

## x86-64 judgement

Every feature of `llc -mattr=help` 19 and 22 (199 names) and of the
census, `+` and `-`: 122 accepted as instructions only (`AVAILABLE`), 63
tuning, 14 refused when on and 5 when off, each by name
(`x64_features.tsv`):

| item | reason |
|---|---|
| `-sse`, `-sse2` | `attr:target-feature-no-sse` |
| `-x87` (function with an `x86_fp80`; `-mattr`) | `attr:target-feature-no-x87` |
| `+soft-float` | `attr:target-feature-soft-float` |
| `+x32` | `attr:target-feature-x32` (new) |
| `+16bit-mode`, `+32bit-mode`, `-64bit`, `-64bit-mode` | `attr:target-feature-mode` (new) |
| `+tagged-globals` | `attr:target-feature-tagged-globals` (new) |
| `+seses` | `attr:target-feature-seses` (new) |
| `+retpoline*`, `+harden-sls-*`, `+lvi-*` | as before |

Every census string but the cross `-march=native` ones is accepted
(`x64_cpus.tsv`: 219 CPU/tool rows, all `accepted`).

**Evidence by `llc`'s convention.** `llc -O0 -stop-after=finalize-isel`
gives, per function, where its arguments arrive (`liveins`, fixed stack
objects), where its result leaves (the return's implicit uses), and per
call its register mask and result registers (and the variadic call's
uses, `al` among them). 26 probes (see `SIGS` in the test) under: every
census string and its CPU alone; every feature enabled alone on
`x86-64`; every feature disabled on `x86-64-v4`, `sapphirerapids`,
`diamondrapids`, `znver5`, `haswell`, `x86-64` — 1,324 configurations
under `llc` 19 (it does not know `diamondrapids`, `novalake`,
`wildcatlake`), 1,526 under 22; configurations hod refuses by the
feature, or with `-x87` (`llc` stops on an `x86_fp80` there), are left
out. Against the function without features:

- 7,864 (19) and 9,647 (22) probe/configuration pairs differ; every one
  is a signature hod refuses under the configuration's `of_function`
  (`x64:wide-vector-abi`: a vector over 128 bits under AVX, a vector of
  `i1` under AVX-512), or `preserve_allcc` (below).
- Found and fixed: `+sha512`, `+sm3`, `+sm4` imply AVX in `llc` 19 and 22
  (`<8 x float>` in `ymm0`) without `avx` in their names; `of_function`
  said no AVX for them, which would have placed the vector in two `xmm`
  registers. They now set `avx`.
- Nothing else changes a signature or a mask: not `cx16`, `mmx`, `x87`
  on, APX (`egpr`, `ndd`, `ppx`, `push2pop2`, `ccmp`, `cf`, `nf`, `zu`:
  same masks, `r16`..`r31` caller-saved), AMX, `evex512`, any tuning
  name. The masks of `ccc` calls stay `csr_64` under every feature;
  `preserve_mostcc`'s does not change.
- `preserve_allcc`: under AVX the call's mask keeps all of
  `ymm0`..`ymm15` (`CSR_64_AllRegs_AVX`; the same under AVX-512, no
  `zmm`). hod's callee keeps their low halves (§5.6.23). `llc`'s own
  callee saves and restores the whole registers but then returns through
  `vzeroupper` whenever it called anything (and saves nothing it does not
  touch when a leaf), so under `llc` too the caller's upper halves are
  lost: `preserve_all_under_avx_is_llc_s` runs a caller that keeps an
  `<8 x float>` in `ymm0` across the call and gets `2 3 4 5 0 0 0 0` with
  `llc`'s callee and with hod's, `llc` 19 and 22. Not refused.

**AVX-512.** Judged per signature, not per function: a function with
`+avx512f` compiles unless a signature it touches has a wide vector or a
vector of `i1`. What was proved for the rest: the register masks of its
calls are `csr_64` (no `zmm`/`k` register is callee-saved); hod writes
no `ymm`/`zmm` upper half and no mask register, so no `vzeroupper` is
owed and nothing it keeps can be clobbered behind its back that a
baseline call would not clobber; a 64-byte-aligned value is aligned by
its IR alignment, not by the feature. APX likewise.

**`cx16`.** hod uses `lock cmpxchg16b` inline with `+cx16` and
libatomic's `__atomic_*_16` without (`atomic.rs`), the same choice as
`llc`. libatomic on x86-64 picks `cmpxchg16b` itself on a CPU that has
it, so mixed objects agree on lock-freedom. Note: `atomic::has_cx16`
reads only `"target-features"`, while `llc` also takes `cx16` from
`"target-cpu"`; every census string with a `cx16` CPU spells `+cx16`, so
the two agree on what clang and kiln write (`crates/hod_x64/src/atomic.rs:183`).

**Execution.** `march_strings_mix_with_llc`: hod's functions with
`double`, `float`, `<4 x float>`, `<2 x double>`, `{ double, double }`,
`i128` signatures, built with clang 22's `haswell`, `skylake` and
`znver4` strings, call `llc`'s and are called by them (`llc` 19 and 22,
`znver4`'s `llc` side with `znver3`'s string: the emulator has no
AVX-512), under `qemu-x86_64 -cpu max`, linked by bfd, lld and mold:
the output equals the all-`llc` build's.

## AArch64 judgement

The census's names hod did not know: `clrbhb`, `hcx`, `specres2`
(instructions and system registers, written for current cores by clang
22) and `zcm*`/`zcz*` (zero-cycle moves, tuning). Added with the rest of
LLVM 19's and 22's instruction features and a tuning family list;
`+tpidr-el1`/`-el2`/`-el3`/`+tpidrro-el0` (the thread pointer in another
register than the one hod's TLS reads) are refused as
`attr:target-feature-thread-pointer`. In the census only `+v8r`
(`attr:target-feature-profile`), `-fp-armv8` and `-neon` (from `+nofp`,
`+nosimd`) are refused. Convention evidence: `llc -O0 -global-isel=0
-fast-isel=0 -stop-after=finalize-isel` 19 and 22, each feature of their
lists enabled alone on `generic`, 17 probes (integers, `i128`, `fp128`,
`half`, `bfloat`, 64-/128-/256-bit vectors, vectors of `i1`, HFAs, stack
arguments, `preserve_mostcc`, `preserve_allcc`): only `call-saved-*`
changes a mask and only `reserve-x1`..`x7` stop `llc`; both were refused
already (a script run, not a test: `hod_a64` has no `llc` harness of
this shape).

`fastjson_dom.cpp`, `fastjson.cpp`, `fastjson2.cpp` and `min.ll`, built
