Generated by `scripts/oss/oss-report.py status` from the lane's reports (docs/VALIDATION.md "Real projects (L9)"): each project built through its own build system with kiln at `-O0` (flavour `O0`) and `-O0 -g` (`O0g`), three ways: `llc` (kiln's LLVM back end, the control), `hod` (kiln with hod, falling back to llc where hod declines), `strict` (no fallback). `TUs`: the translation units of the build step (the compile wrapper's log). `objects`: the object jobs (`-c`) in kiln's statistics log of the hybrid build, which covers the build and the test steps, so it counts a TU compiled for several targets once per target and the compiles a project's tests run (compile-failure tests, package tests); `no backend` among them: jobs kiln's front end rejected before any back end ran (a compile-failure test's expected rejection), counted in no later column. Compile-and-link jobs (`kiln++ x.cc -o prog`) are not objects and are not counted. `built by hod`: objects whose `backend` is `hod`; `fell back`: offered to hod and declined or failed; `not offered`: kiln took the LLVM route itself (an `opt` trigger). Every build, the control's included, ends with one of its 528 links failing, hence `failed (0 TUs)`.
2. Boost (`boost_tmpl`): one of the 528 links fails in every build, the control's included: `multi_index-test_serialization` (undefined `test_serialization2()`, `test_serialization3()` and Boost.Serialization symbols). The lane's Jamfile shim reads only the first line of a multi-line `run` rule and Boost.Serialization is not in the subset; not a compiler difference.
3. range_v3: one translation unit (`view/tokenize.cpp`) fails to compile upstream in every build, the control's included (clang 19 rejects it too); every object the strict build makes is hod's.
4. glaze: kiln's front end rejects three translation units in every build, the control's included (`cbor_test.cpp`, `cli_menu_test.cpp`, `msgpack_test.cpp`), and with `-g` the compile of `json_test.cpp` runs out of memory twice in every build as well, hence `failed (3 TUs)` and `failed (5 TUs)`; every object the strict build makes is hod's, and its tests equal the control's test by test.
5. A test that runs an x86-64 program itself rather than through ctest (a death test re-executing `/proc/self/exe`, a python test script) fails under qemu in the control and in hod's builds alike: the comparison with the control holds, the absolute count does not (googletest's 45 of 63).
6. scnlib: `scn_stdin_test` is such a test (a python script that starts the x86-64 program itself). It failed in the control and in the hybrid build of 2026-11-15, where the host could not start the program ("rosetta error: failed to open elf at /lib64/ld-linux-x86-64.so.2"), and passes in the strict build at a68a0d5d of 2026-11-17: 25 of 25 against 24 of 25. The difference is the host's between the two days, not hod's; why the host starts the program now was not looked into.
7. mold: mold's ctest list has 1,362 tests on the lane host of 2026-11-17 against 929 on 2026-11-15 (433 `i686-*` tests more: mold adds them when it finds an i686 cross compiler and qemu-i386), so the control was built again on 2026-11-17 at kiln 8f93304ee and the row compares the same 1,362 tests in both trees. Most of them fail in both, the cross-built mold running under qemu-x86_64: 237 pass in the control. `-O0`: equal test by test. `-O0 -g`: one test, `aarch64-sort-debug-info-merged-str`, passes in the strict build and fails in the control; it was not looked into.
8. zlib (the one stated exception of the lane rows, docs/RELEASE.md section 5): one of 37 objects, `infcover.c`, is compiled with `--coverage`, and kiln never offers such a translation unit to hod (skip reason `coverage`: the gcov instrumentation runs in kiln's LLVM pipeline), so 36 of 37 objects are hod's and the strict build is marked `failed`; the owner's decision of 2026-11-15: not hod's fault, does not block 1.0 (BACKLOG WP-279). `infcover` links in neither build (the linker does not find `libclang_rt.profile.a`, LLVM's profile runtime, on the lane host): 7 of 8 links. Both flavours measured at a68a0d5d against the kiln 8f93304ee controls of WP-278, serial ctest: 5 of 6 tests, the control's. The `-O0 -g` difference seen at e98267c0 is a race in zlib's own tests: `zlib_example` and `zlib_static_example` write the same `foo.gz`; under `ctest -j2` it fails 27 to 36 of 40 runs in the control and in strict alike, serially 0 of 20 (WP-278).
