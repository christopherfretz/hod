# WP-010 — `hod_obj`: object model and ELF64 relocatable writer

The contract is `spec/object.md`. This file records what the work package
did, what it measured, and what it left.

## What landed

- `crates/hod_obj/src/model.rs`: `Object` and its tables (sections,
  symbols, relocations, groups), all addressed by `u32` ids.
- `crates/hod_obj/src/reloc.rs`: `A64Reloc`, `X64Reloc`, `RelocKind`.
- `crates/hod_obj/src/names.rs`: the section name interner.
- `crates/hod_obj/src/error.rs`: `Error`, `Limit`, `SymbolProblem`,
  `WriteError`.
- `crates/hod_obj/src/elf.rs`: `elf::write`, `elf::to_vec`,
  `elf::file_size`, and the public `SHT_*`/`SHF_*` constants.
- Tests: unit tests in the sources; `tests/common/mod.rs` (an independent
  ELF reader and the fixture programs); `tests/structure.rs`;
  `tests/tools.rs`; `tests/link.rs`; `examples/throughput.rs`.
- `spec/object.md`.

No third-party crate; no `unsafe`.

## Decisions and why

- **One relocation vector for the object, chained per section.** The code
  generator emits into `.text.<fn>`, `.rodata`, `.eh_frame` and debug
  sections in interleaved order. A vector per section would be an
  allocation per section (100 000 of them with function sections); the
  chain costs four bytes per relocation and keeps the entry at 32 bytes.
- **Symbol names are not deduplicated.** The arena is the `.strtab` image,
  so emitting it is one `write_all`. A hash lookup per symbol would cost
  more than the duplicate bytes save: C++ symbol names are nearly all
  distinct. Section names are interned because they repeat (`.text.<fn>`
  and `.rela.text.<fn>` share bytes, and group members repeat names).
- **Layout first, then one forward pass.** `Layout::new` validates and
  sizes everything, so a bad object writes nothing and the writer never
  seeks. The section header table goes last so that nothing before it
  depends on its size.
- **Section header order** (groups, sections, stack marker, relocation
  sections, tables) makes a section's ELF index `1 + group_count + id`, so
  no index table is needed for symbols.
- **Relocations are emitted sorted by offset.** The model tracks whether a
  section's relocations were added in order; the sort (stable, on a
  scratch vector of indices) runs only for sections where they were not.
- **Calls on the hot path do not return `Result`.** Their failures (a
  relocation kind of the wrong architecture, a bad alignment for padding,
  index-space exhaustion) are recorded and reported by the writer.
- **Sections without file space are not padded in the file.** A `.bss`
  aligned to 4096 costs no bytes. Linkers, `readelf` and `llvm-readelf`
  accept it (`bss_is_zero_and_aligned` links and runs).
- **`ELFOSABI_GNU` only when needed** (`STT_GNU_IFUNC`, `SHF_GNU_RETAIN`),
  as GNU as and LLVM do.

number in `src/reloc.rs` and seeing `readelf_names_every_relocation_kind`
fail, then restoring it.

## Throughput

`cargo run --release -p hod_obj --example throughput`, fastest of five,
`elf::write` into a sink that counts and discards, on the host above (24
cores, shared with other work; the example is single-threaded). Not a
gate.

| | 100 000 functions of 64 bytes, each in its own `.text.<fn>`, 5 relocations each | the same in one `.text` (`HOD_OBJ_MODE=one-text`) |
|---|---|---|
| sections / symbols / relocations | 100 001 / 100 001 / 500 000 | 1 / 100 001 / 500 000 |
| build the model | 15.6 ms | 8.6 ms |
| `elf::write` | 15.3 ms (2 640 MiB/s) | 4.1 ms (5 680 MiB/s) |
| `elf::to_vec` | 19.3 ms | 5.7 ms |
| file size | 40.51 MiB | 23.36 MiB |
| resident memory with the model built | 45.7 MiB | 29.8 MiB |
| peak resident memory through `write` | 49.5 MiB | 31.8 MiB |
| peak resident memory through `to_vec` | 89.9 MiB | 55.1 MiB |

Allocation pattern: building allocates the growing tables (symbols,
relocations, names, section records) and one buffer per section with
contents; nothing per symbol or relocation. `write` adds about 4 MiB of
resident memory in the first case: 12 bytes per section, 4 per symbol, the name plan and the
64 KiB buffer. `to_vec` adds the file itself, allocated once.

With function sections, most of the file and most of the writer's time is
section headers and `.rela` headers (128 bytes per function before any
content), and most of the model's memory is one small heap buffer per
section.

## Left for later

- TLS sections and TLS relocations are written and read back by the tools,
  but no test links and runs a thread-local access.
- `.init_array`/`.fini_array` are written; no test runs a constructor, and
  priority-suffixed names (`.init_array.<n>`) are only the caller's naming.
- Mergeable sections are written with their flags and entry size; no test
  checks that a linker merges them.
- `.note.gnu.property` (BTI/PAC, CET) has no helper; a caller can write it
  with `SectionKind::Note` and raw bytes.
- Groups: no test of a group with debug sections, of `GroupKind::Plain`
  through a linker, or of a relocation from outside a discarded group.
- `SHF_LINK_ORDER` (needed by some metadata sections) is rejected because
  the model cannot express a caller's section's `sh_link`.
- x86-64 link-and-run needs an x86-64 host or an emulator.
- One heap buffer per section is the dominant memory cost with function
  sections; a shared arena for small sections is a possible change behind
  the same API if memory tracking shows it matters.
