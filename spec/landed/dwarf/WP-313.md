# WP-313 — the module-only DIEs ahead of the last chunk: measured, not built

Item 1 of WP-303 step 3's list (`spec/landed/ll/WP-303.md`, "What
remains"): could a granted thread write the part of the DIEs that
depends on the module alone while the workers compile, so that only the
part that depends on generated code is left after the last chunk? Base
`7848ce3c`. The result is the measurement: the part that can be moved
ahead is about 80% of the type DIEs, but what it saves after the last
chunk is 0.1 to 0.8 ms, inside the noise of the `object` phase on both
`stl-heavy-g` and `templates-g`. No code changed.

## Method

Temporary timers (on a scratch branch, never on this one) around the
steps of `DebugLines::finish` (`hod_cg`), the plan's construction
(`UnitPlan::for_functions`, at `ModuleEmitter::new`), `write_debug_info`
and the depth-first walk of `Writer::unit` (`hod_dwarf`), the walk's time
split by what each DIE is: type DIEs, namespaces / global variables /
imported entities, and the whole subtree of a subprogram (a clock read at
each change of category only: 857 changes on `stl-heavy-g`). `hod --strict
-O0 -filetype=obj -relocation-model=pic`, bench inputs produced as
`cargo xtask bench --generate` does (clang 22), both targets, 1 and 8
threads (the split is after the join, the same at every thread count),
15 interleaved runs, medians in ms. Load average 20 to 23 of 24 cores.

DIE counts on `stl-heavy-g`: 51,631, of which 34,681 types (252 KB of
`.debug_info`), 525 namespaces / globals / imports, 16,424 in subprogram
subtrees (197 KB); 13,843 strings, 4,109 `.debug_addr` entries, 27,092
forward references patched.

What each part needs:

- **Types** (and namespaces): the module alone for their content; but
  28,520 of `stl-heavy-g`'s DIEs exist when the plan is built (from the
  unit's globals, enumerations and retained types), and the rest are made
  by `add_function` (the classes of member functions, as the code is laid
  out) and by `seal` (return and variable types, §6.4). Types are 0 on
  `tiny-functions-g`.
- **Global variables and template parameters with an address**: their
  `DW_OP_addrx` index depends on the address pool's order, which the
  functions' `low_pc`s fill first (WP-296).
- **Subprogram subtrees**: code offsets, sizes, frame offsets, block
  ranges, call sites: generated code.
- **Patches, contributions, abbreviations, sections**: the whole unit.

## Where byte identity constrains a design

- **DIE order.** The walk interleaves the parts: in DIE order, only the
  first 16 DIEs of `stl-heavy-g` come before a DIE made by a function, and
  27,920 of the type DIEs that exist before the first function are written
  after one (the plan's children are in discovery order, and a namespace
  made for a global later holds the functions and types made in it). So
  no prefix of `.debug_info` is module-only; every module-only DIE's
  offset depends on the size of the function DIEs before it.
- **String indices.** `DW_FORM_strx` is a ULEB of the string's index in
  the unit's `.debug_str_offsets`, numbered in first use by the walk
  (§6.3); `.debug_str` is laid out in the same first-seen order. A DIE
  written ahead cannot know its indices, nor their widths.
- **Address indices.** As strings, in first use by the walk (§6.4).
- **References.** `DW_FORM_ref4` to unit offsets: fixed width, patchable.
- **Abbreviation codes.** The table is fixed (§6.1) and written from the
  set of codes used, so the order does not matter; but a code depends on
  whether the DIE has children, and the family chosen does too (an array
  type without children is another family), and children are added until
  `seal`.

The invariant a design must rely on: a DIE written ahead is the serial
DIE's bytes with holes for every `strx`, `ref4` and abbreviation code,
the holes filled by the final walk in the serial order (so that every
index is assigned as the serial walk assigns it), and it is used only if
its children-or-not assumption still holds after `seal` and it took no
address; anything else is written by the walk as before.

## The first experiment (decides: not built)

A prototype of exactly that (scratch branch): a tape mode of the DIE
writer (`strx`, `ref4` and `abbrev` record holes instead of writing; an
address marks the DIE as not taken), the module-only DIEs that exist when
the plan is built rendered to a tape from that plan, and the final walk
splicing a taped DIE (copying its bytes and filling its holes through
the ordinary `strx`/`ref4`/`abbrev`) instead of writing it. The objects
were byte-identical to the base on 16 `-g` inputs of both targets
(after one fix: the abbreviation code depends on the children, which the
tape takes from the plan as built and the splice checks). On
`stl-heavy-g` 28,162 DIEs were taped (21 refused).

To measure the most any threaded version could gain, the tape was
rendered serially (its cost not counted) and only the walk after the
last chunk was timed. That bounds the wall gain from above: on a thread
the tape costs code generation the thread's time as well.

| input, a64 / x64 (ms) | walk, base | walk, tape free | gain | the tape's own cost |
|---|---|---|---|---|
| stl-heavy-g, 1 thread | 8.05 / 7.67 | 7.53 / 7.20 | 0.52 / 0.48 | 2.2 / 2.3 |
| stl-heavy-g, 8 threads | 7.45 / 7.25 | 6.69 / 6.86 | 0.77 / 0.39 | 1.6 |
| templates-g, 1 thread | 2.37 / 2.33 | 2.24 / 2.27 | 0.12 / 0.06 | 0.5 |
| templates-g, 8 threads | 2.30 / 2.37 | 2.11 / 2.18 | 0.19 / 0.19 | 0.35 |
| containers-g, 8 threads | 1.35 / 1.39 | 1.21 / 1.24 | 0.13 / 0.15 | 0.3 |

Splicing a DIE costs about 85% of writing it: of the type DIEs' 4.2 ms
on `stl-heavy-g` with the tape, 2.3 ms is `DebugStrings::index` (a
variant that skipped the string lookups, bytes wrong, took the types to
1.95 ms). What the walk spends on a type DIE is the string pool, not
the node's decode or the type graph's logic, and the pool's order is the
walk's. Even with the string lookups free, the bound on `templates-g`
is 0.37 to 0.45 ms.

The noise of the `object` phase at the base (same runs, 15 per point,
interquartile range): `stl-heavy-g` 0.6 to 1.1 ms at 4 and 8 threads,
`templates-g` 0.4 to 0.8 ms. The bound is inside it on both inputs,
before the tape's cost to code generation (0.35 to 2.3 ms of one
thread's work) and its memory (the tape and a copy of the plan for the
thread, since `add_function` changes the plan while the workers run).
No threaded prototype was built: it cannot gain more than the bound.

## What remains (in order)

1. **The string pool by the store's string id** (WP-311's item 3): the
   one large cost inside the type DIEs, 2.3 ms of `stl-heavy-g`'s walk,
   and serial at every thread count. `hod_ir` interns names; a pool
   indexed by that id would replace a hash of the bytes with an array
   read, at one thread as well. Needs `DiView`/`DiNode` to hand out the
   id (`crates/hod_ir`) and `crates/hod_dwarf/src/strings.rs`.
2. **The plan built while the workers compile.** `UnitPlan::for_functions`
   (1.6 to 1.9 ms on `stl-heavy-g`, 0.7 to 1.2 on `templates-g`) depends
   on the module alone and runs before any code is generated, at every
   thread count; the lay-out needs it only at the first `add_chunk`. On
   a granted thread it would overlap code generation; a refusal of the
   plan must still be the answer before any function's (join the plan
   before reporting). The plan is built in `DebugLines::new`
   (`crates/hod_cg/src/emit/lines.rs`, not this package's) from
   `ModuleEmitter::new`; the scheduling is `crates/hod/src/back.rs`.
3. `seal` (1.5 to 1.7 ms on `stl-heavy-g`) needs every function; the
   subprogram subtrees (2.8 to 3.0 ms) need the code. Rendering a
   function's subtree as it is laid out (already overlapped with the
   workers) and splicing it after meets the same string-pool cost.
