# WP-086 — `attr:convergent`

Landed:
- `spec/ir.md` §5.7: `convergent` is a kept function flag and call-site
  flag, with the argument for accepting it (below) and what stays
  refused; §5.4 and the `CallSite` accessor list: `convergent` on calls;
  §9.4 (printer): written on calls.
- `spec/ll.md` §6 (calls): `convergent` is one of the kept call-site
  attributes.

## The argument

The LLVM Language Reference defines `convergent` ("Function Attributes")
as a restriction on transformations: a convergent call may not be made
control-dependent on more values than it is in the input (no duplicating
into branch arms, sinking, hoisting across control flow, unswitching
around it); "Convergent Operations" leaves the set of threads that
execute it together to the implementation when no convergence control
token is given. hod makes none of those transformations: code generation
is one walk per body in layout order that emits each call once, in its
block (`spec/codegen.md` §1), and its only reordering, deferral (§4.6),
never moves anything past a terminator. So the attribute is satisfied
by construction. It is kept (not dropped) so that a module hod prints
forbids what its input forbade. What would need real semantics stays
refused by name: the `convergencectrl` bundle (`bundle:convergencectrl`,
row unchanged) and the token-producing
`llvm.experimental.convergence.{entry,anchor,loop}` (`intrinsic:<name>`,
`Intrinsic::Other`, plus `type:token`).

## What it did

| where | change |
|---|---|
| `hod_ir` `attrs.rs` | `FnAttrs::CONVERGENT` (bit 19, `FLAG_NAMES` grows to 20); the table row `convergent` is `Kept` |
| `hod_ir` `builder.rs`, `body.rs` | `CallDesc::convergent`, `CallSite::is_convergent` (call flag bit 5) |
| `hod_ir` `print/body.rs` | ` convergent` after `returns_twice` on a call |
| `hod_ir` `classify/matrix.rs` | row `attr:convergent`, `ON` on both targets (it is checked on bodies' functions, like every flag row) |
| `hod_ll` `call.rs`, `hod_bc` `inst.rs` | the call-site mask keeps `CONVERGENT` (both readers dropped it silently before the mask was widened: the round-trip test caught it) |
| `hod_ir` `random.rs` | generated calls carry `convergent` one time in eight |

Interface: `CallDesc` has a new public field (`convergent`, default
`false` in `CallDesc::new` / `intrinsic`); `CallSite::is_convergent`.

## Found elsewhere

`llvm.is.constant` of a literal aggregate (`{ i32, i32 } { 1, 2 }`,
`[2 x i32] [1, 2]`): `llc` folds it to true (`isManifestConstant` recurses
into `ConstantAggregate`), hod to false
(`crates/hod_a64/src/intrinsic.rs:205`, the `IsConstant` arm, which
says "aggregates included"). Clang and kiln never emit it (the front end
folds `__builtin_constant_p` of a non-scalar), so no C++ program reaches
it. `xtask/tests/data/known/is_constant_aggregate.ll` is the reproducer,
run by the `#[ignore]`d `is_constant_of_an_aggregate_literal` in
`xtask/tests/known_differences.rs` (the seed corpus `tests/ir` must
pass in hybrid mode, so it cannot hold an `xfail`).

`llvm.is.constant` of a computed operand: hod folds it to false as
`llc -O0` does, but still emits the operand's computation; `llc`'s
`LowerConstantIntrinsics` deletes it when it becomes dead
(`RecursivelyDeleteTriviallyDeadInstructions`). GCC's `bcp-1.c` relies on
that (`__builtin_constant_p(p[123456])`, an operand C does not evaluate,
which clang still emits as a load): hod's program faults, `llc`'s exits
0 (`crates/hod_a64/src/intrinsic.rs:205`; the IR has undefined behavior,
so both are allowed, but `llc` is the oracle).
`xtask/tests/data/known/is_constant_dead_operand.ll` is the reproducer,
run by the `#[ignore]`d `is_constant_drops_its_dead_operand`. It
does not touch libc++'s uses (operands that are plain loads of valid
objects), as the 37 runs above show.
