# WP-115 — variable arguments typed in the call ABI

Two items left open by WP-064 (`spec/landed/ir/WP-064.md`, follow-ups).

## What it did

| item | where | change |
|---|---|---|
| 1 typed variable arguments | `crates/hod_cg/src/abi.rs` | `TargetStackArgs::of_call` types the variable arguments of a variadic call (those it lists before a forwarded `...`) by their values in the call's body, as the call sequence does, and gives `assign` the whole signature with the effective attributes of every argument. A `musttail` call with such arguments is judged now, not `musttail:stack-args-unknown`: in registers it compiles, on the stack it is `musttail:stack-args-grow` (the caller's area holds only its named arguments) (`spec/codegen.md` §7.1 "The `musttail` hook") |
| | `crates/hod_ir/src/body.rs` | `CallSite::body()`, the body a call is in (the hook is given only the call site; outside the brief's ownership, additive) |
| | AArch64 | nothing to change: `forward_variadic_registers` reloads the forwarded registers, then the call sequence writes every argument, the variable ones included, over them, as `llc` does (`spec/abi-a64.md` §8.5) |
| | `crates/hod_x64/src/call.rs` | refused, `x64:musttail-variable-arguments`: `llc` 19 and 22 write the forwarded registers over the variable arguments and pass `al` as it arrived, so the callee gets the caller's own arguments; nothing to follow (`spec/abi-x64.md` §8.5). The facade gives x86-64's `classify` no stack-argument rule, so every x86-64 `musttail` call is still `musttail:stack-args-unknown` there first |
| 2 address-taken blocks | `crates/hod_cg/src/driver.rs` `mark_reachable`, `cx.rs` (one field) | a function with an address-taken block and no `indirectbr` records `block_offsets` (`ConstPool::has_address_taken_block`), so a `blockaddress` in data of it is placed, no longer `init:blockaddress-unplaced`. Of its unreachable blocks only the address-taken ones (`is_address_taken`) get the trap and a row. `llc` deletes such a block and writes `1` for its address in code and data; hod writes the trap's (`spec/codegen.md` §9.6) |

## Evidence

- `crates/hod_a64/tests/musttail_varargs.rs`: 180 generated variadic
  thunks (3 seeds), named `i64`/`double` parameters, some on the
  stack, 0 to 6 extras of every class (`i8`, `i16`, `i32`, `i64`
  constant or computed, `i128`, `float`, `double`, `fp128`,
  `[2 x i64]`, `[2 x double]`, `[3 x float]`), a third behind a call
  that sets every argument register. `classify` with the hook agrees
  with an AAPCS64 model written in the test on every case: 110 compile
  (36 with extras and named stack arguments), 70 are
  `musttail:stack-args-grow`. The 110 run with a C callee reading them
  by `va_arg`, hod plain and stress, `llc` 19 and 22, under bfd, lld
  and mold (12 runs per seed). The named and extra values are checked
  against the generator's, the forwarded stack words (canaries just past
  the caller's named area) exactly, the rest of the output against
  `llc`'s; the caller checks canaries in its frame and callee-saved
  values. Every class of extra ran 12 to 27 times.
- `crates/hod/tests/musttail_forward.rs`: WP-064's ignored test runs
  (text and bitcode 19, 22 give one object; 6 runs agree with `llc`),
  and the refusal test now checks what compiles, what grows and the
  x86-64 facade's `musttail:stack-args-unknown`.
- `crates/hod_x64/tests/musttail_varargs.rs`: the refusal for three
  classes, the thunk without extras compiling, and `llc` 19 and 22
  under `qemu-x86_64` (6 runs) printing the caller's `7 2.50 8` where
  the thunk passed `42 1.50`.
- `crates/hod_a64/tests/block_address_taken.rs`: a table of block
  addresses in data against the same addresses formed in code, hod
  plain and stress and `llc`, under every linker; a trap only for an
  address-taken unreachable block.
- `crates/hod_a64/tests/call.rs` `the_stack_args_hook_decides_musttail`:
  its variadic case now expects compile (registers) and grow (stack).
- Corpus: the 100 modules of `.build/corpus` and `.build/corpus-x64`
  with a `musttail` or a `blockaddress`, compiled by the binary before
  and after: 79 objects byte-identical, 21 refusals unchanged (12
  `musttail:stack-args-unknown`, all x86-64, which has no hook). No
  corpus `musttail` call lists variable arguments before `...` (8, all
  forwarding alone), and no corpus module was
  `init:blockaddress-unplaced`.
- Mutations, each caught then reverted: `of_call` without the
  variable arguments (the hook test: case 3 compiles where the model
  says grow); the copy over the incoming area 8 bytes too long (a
  stack canary changes; 16 bytes crash the caller); variable arguments
  assigned one vector register late (the extras printed differ); the
  address-taken mark dropped (`init:blockaddress-unplaced`); every
  unreachable block given the trap (`only_an_address_taken_...`).
- The interpreter is not used: the callees are C.

## Follow-ups

- `crates/hod/src/session.rs:108`: the facade gives x86-64's
  `classify` no stack-argument rule, so every x86-64 `musttail` call is
  `musttail:stack-args-unknown` (12 corpus modules). `hod_x64` lowers
  `musttail` (WP-125); handing it `TargetStackArgs` needs a decision on
  the per-function features `X64::assign` reads (a static hook has the
  default ones).
