# WP-227 — the attributes of optimized modules

Landed: `"alloc-family"` is a dropped string attribute (`spec/ir.md`
§5.7, `crates/hod_ir/src/attrs.rs`, one row of `ATTRIBUTES`); both
readers take it through the shared table (`hod_ir::kit::string_attr`),
so neither `hod_ll` nor `hod_bc` changed. Seed `tests/ir/alloc_family.ll`;
tests `crates/hod/tests/alloc_family.rs`, `crates/hod_ir/tests/attr_table.rs`,
a row of `crates/hod_ll/tests/syntax/rows.rs`. Every other attribute the
audit met was already kept or dropped; nothing else is refused by name.

## The audit

Inputs:

- **Compiled for this package**: 292 sources (hod's 49 C and C++ test
  programs under `tests/`, every 50th of kiln's conformance tests,
  every 10th of kiln's C tests, every 20th of the GCC C torture
  `execute` tests, and four library-heavy programs: containers and
  strings, threads and streams, a coroutine, the C allocation
  functions), each with `clang-19`, `clang-22` and `kiln++`/`kiln`, at
  `-O0`, `-O1`, `-O2` and `-O2 -g`, for `x86_64-unknown-linux-gnu` and
  `aarch64-unknown-linux-gnu`: 7,008 compilations, 5,277 modules (the
  others are kiln tests that are meant not to compile, or need options
  the sweep did not pass).
- **The optimized `-g` modules of WP-225's census** (894 files,
  `-O1`/`-O2 -g`, kiln over libc++ tests and hod's debug programs).
- **The saved refused modules** under `.build/findings/` (706 files).
- **Both corpora** (6,460 AArch64 and 6,456 x86-64 entries, `-O0`).

Each module was read twice: every attribute name of its attribute
groups (and the rejected keywords and string attributes on `define`,
`declare` and call lines) classified against the base table, and base
`hod --strict` (686ff25b) run with `HOD_CENSUS=1`, which lists every
unsupported construct, not only the first. Of the 706 saved findings
the census ran on 283; the other 423 (389 `highway` and 28
`simdjson` modules, which take seconds each, and 6 others) were read
for their attribute groups only, the census being cut short for time.

| attribute | modules (compiled / WP-225 census / findings / corpora) | decision |
|---|---|---|
| `"alloc-family"` | 36 / 26 / 1 / 0 | ACCEPT (dropped) |
| `elementtype` (kept; matrix row `attr:elementtype` LATER on AArch64) | 0 / 0 / - / 2 | STAYS REFUSED |

No other name was refused. The 36 compiled modules are two sources
(`libc.c` and kiln's `expr.delete/destroying-operator-delete-virtual.cpp`)
under all three compilers, `-O1`, `-O2` and `-O2 -g`, both targets: a
module has the attribute only when a declaration of a C allocation
function survives optimization. No `-O0` module has it. The family
seen is `"malloc"` throughout (90 groups); `operator new` and
`delete` carry none in this output.

The text reader also met strings in call lines that are not attributes
(inline-assembly templates and constraints, operand-bundle tags of
`llvm.assume` such as `"align"` and `"separate_storage"`, a section
name); the census confirms none of them is refused.

### `"alloc-family"`: ACCEPT

LangRef ("Function Attributes"): `"alloc-family"="FAMILY"` "indicates
which 'family' an allocator function is part of ... Matching
malloc/realloc/free calls within a family can be optimized, but
mismatched ones will be left alone." In the LLVM source tree at hand
(`cd708029`, January 2025) it is written by `BuildLibCalls.cpp`
(`setAllocFamily`, on `malloc`, `calloc`, `realloc`, `free`,
`aligned_alloc`, `memalign`, `valloc`, `strdup`, `strndup`, and the
`vec_` variants) and read in one place, `MemoryBuiltins.cpp`
(`getAllocationFamily`), whose only callers are in InstCombine
(removal of an allocation whose only uses are frees of the same
family). Nothing under `lib/CodeGen` or a target reads it. It changes
no symbol, section, ABI, frame or unwind property.

`llc` agrees, byte for byte (objects of each module and of the same
module with every `"alloc-family"="..."` removed, `-filetype=obj`):

| input | `llc-19` | `llc-22` |
|---|---|---|
| hand module (declarations, a definition of its own family, call-site groups), both targets, `-O0`/`-O1`/`-O2` | 6/6 same | 6/6 same |
| the 36 compiled modules, `-O0` and `-O2` | 24/24 same (the 12 clang-19 modules; `llc-19` cannot read the 24 LLVM 22 ones) | 72/72 same |
| the 26 WP-225 census modules, `-O0` | not readable (LLVM 22 dialect) | 26/26 same |

The test `crates/hod/tests/alloc_family.rs` checks the same for hod:
the seed with the attribute in eight groups (declarations, two
definitions, call sites) is accepted on both targets, its object is
byte-identical to the object without it, and the `llvm-as` 19 and 22
bitcode gives that object. `cargo xtask irdiff --witness` on the seed:
PASS on aarch64 and x86_64, LLVM 19 and 22 (3 results each, one per
linker found, 0 FAIL/ERROR).

After the change, `reduced.ll` of the finding builds; of the 26 census
modules, 8 build and 18 are refused for debug-value constructs
(`debug:dbg-value-expr` 10, `-arglist` 4, `-fragment` 2,
`debug:fragment` 2: WP-225's scope); of the 36 compiled modules, 27
build and 9 are refused for `module-flag:debug-info-assignment-tracking`
(8, clang `-O2 -g`) and `debug:dbg-value-expr` (1).

### `elementtype`: STAYS REFUSED

Two corpus modules (kiln's `target.acle/exclusive-sysreg-run.cpp`, LLVM
19 and 22, AArch64 corpus) carry `elementtype(i8)` on the pointer
argument of `llvm.aarch64.ldxr.p0` and `llvm.aarch64.stxr.p0`. It is a
kept attribute: there it is the width of the exclusive access (`ldxrb`
for `i8`), so a lowering of these intrinsics has to read it. The row
stays `LATER` on AArch64 (row text: "on an inline-assembly or
intrinsic argument"); it is not an optimizer attribute.

### Byte identity

Every 10th module of each corpus (646 AArch64, 646 x86-64) built with
base release hod (686ff25b) and with this branch's release hod,
`--strict -O0 -relocation-model=pic -filetype=obj`: AArch64 608
objects identical and 38 declined with the same message, x86-64 605
identical and 41 declined the same; 0 differ.

### Matrix and support page

A dropped attribute has no matrix row: the `attr` rows are exactly the
kept attributes (asserted by
`crates/hod_ir/tests/classify_matrix.rs`), because `classify` never
sees a dropped one. `docs/status/support.md` is unchanged
(`HOD_BLESS=1 cargo test -p hod_ir --test classify_support_doc` wrote
no difference).
