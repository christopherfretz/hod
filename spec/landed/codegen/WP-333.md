# WP-333: stack-passed arguments of a protected function (64-bit targets)

## The finding (WP-324) and its reproduction

In a protected function (`ssp`, `sspstrong`, `sspreq`, `spec/codegen.md`
§5.6.24) hod kept an argument passed wholly on the stack at its incoming
location (`hod_cg::driver::enter_arguments`, "Wholly on the stack") and
read it there, above the guard, after the function's buffer had been
written. Reproducer: a `sspstrong` function with eight `i64` and then a
`ptr %dst` (the 9th argument, on the stack on both targets) that fills a
16-byte buffer with 200 bytes and then stores through `%dst`
(`tests/ir/stack_protector_stack_args.ll`, `@victim`). Built at `baa19ddb`
and run (PIE, glibc): hod x86-64 under `qemu-x86_64` SIGSEGV, hod AArch64
SIGSEGV (the store went through `0x4141414141414141`); `llc -O0
-global-isel=0 -fast-isel=0` 22 on both, `*** stack smashing detected
***` and SIGABRT.

## What llc does (measured, 19 and 22, x86-64 and AArch64, `-O0`)

- Every used non-`byval` stack argument is loaded at entry, BEFORE the
  guard store (`movq 64(%rsp), %rax` · `movq %rax, 8(%rsp)` then `movq
  %fs:40, %rax`; AArch64 `ldr x8, [sp, #64]` · `str x8, [sp, #8]` then
  the `__stack_chk_guard` load), into a virtual register that lives in a
  register or a spill slot below the guard. This is SelectionDAG's
  argument lowering: unprotected functions do it as well. A part that is
  not used is not loaded (only the low half of an `i128` used through
  `trunc`).
- A `double` beyond the eight FP registers: the same (`movsd 48(%rsp)`,
  `ldr d0, [sp, #64]` at entry).
- `byval`: the address of the caller's copy; the fields are read in place
  after the buffer is written (`movq 32(%rsp), %rdi` after `call fill`;
  `ldr x0, [sp, #48]` after `bl fill`), above the guard.

## What hod does now

`spec/codegen.md` §5.6.24 rule 10. In a protected function that is not a
coroutine body, an argument wholly on the stack in one part is copied at
entry (`FnCx::enter_guarded_stack_arg`, from `enter_arguments`, before
the guard's entry code, as `llc` orders it) into a home slot outside the
guarded block, hence below the guard, and that home is its location from
then on. Integers and pointers through a scratch register (`home_bytes`
wide), `Mem`-class values by a memory copy (then their odd leaves
cleared). Values in several parts already had homes of their own
(`enter_mem`); masks are gathered into a register at entry.

- Equal to `llc`: `byval` stays in place (above the guard in both).
- Stricter than `llc`: hod copies the whole value even where `llc` loads
  only the used part.
- Unchanged: unprotected functions (byte-identical), protected coroutine
  bodies (not measured, not changed), the `va_start` overflow area, a
  `musttail` call's writes into the incoming area, CFI.
- Debug info: a `#dbg_value` of such an argument now names the copy
  (`DW_OP_fbreg -72` instead of `+32` on x86-64 in the probe); `llc`
  names the incoming slot (`DW_OP_fbreg +64`). Both hold the same value
  in bounds; hod's is what the program reads. kiln's parameters are
  `#dbg_declare`d allocas, which this does not touch; the debug lanes
  compare the location's form (`DW_AT_location list` in both builds),
  which does not change.

## Tests

- `tests/ir/stack_protector_stack_args.ll` (irdiff, both targets, against
  `llc`): in bounds, a 7th to 11th integer (pointer, `i32`, `signext
  i8`), a `double` and a `float` beyond the FP registers, an `i128` on
  the stack, a `byval` struct, a protected variadic function with its
  last named argument on the stack (`va_start`, `vprintf`), `sspreq`
  without a buffer, a dynamic `alloca`; then the overflow of `@victim`,
  which must end in SIGABRT ("smashing" printed, nothing after), never
  in the SIGSEGV of a store through the overwritten pointer.
- `crates/hod/tests/stack_protector_stack_args.rs`: on both targets, each
  protected function of the seed reads the incoming area before the
  guard and (but for `va_start`) never after it; without the attributes
  `@victim` still reads its pointer in place after its call.

The seed is kept off i686 (`lp64-abi`: `%ld` of an `i64`, the
`va_list`'s address to `vprintf`); its row is in `spec/harness.md`
"Kept off a target".

## Evidence

- compare-binaries, `baa19ddb` (own target directory) against the head,
  over `tests/ir`, `.build/corpus/kiln`, `.build/corpus-x64/kiln`, `-j 4`:
  14114 comparisons, 4 different, 0 changed outcome. The 4 are the new
  seed (aarch64 and x86_64, plain and pic), in which 7 functions change
  per target (`ints`, `fps`, `wide`, `va`, `req`, `dyn`, `victim`;
  `byval` does not). No corpus object changes: no kiln-built module of
  the corpus has a protected function with a stack-passed argument.
- irdiff (all tier), head: aarch64 465 PASS with LLVM 22 and 19, x86_64
  475 PASS with 22 and 19; 0 FAIL, 0 ERROR. Base (`baa19ddb`, the same
  tests): 460 and 470 PASS, 5 FAIL each, all five the new seed (one per
  linker: the base program dies of SIGSEGV where `llc`'s aborts).
- bench counts: AArch64 4649.3 M (baseline 4649.1 M), x86-64 4768.8 M
  (baseline 4769.0 M): +0.0% both, 20 inputs ok each.
