# WP-025 — x86-64 programs run under emulation

Landed: `spec/harness.md` "Cross runs", "Cross targets", "The oracle",
"Child processes", "In the gate", "Seed corpus", "Toolchain for tests" and
the test lists. On this AArch64 host, `cargo xtask irdiff --target x86_64`
links every seed's programs with the x86-64 cross toolchain and runs them
under `qemu-x86_64`; the gate runs a few seeds that way (quick) or all of
them with both oracles (full). hod has no x86-64 code generator yet, so
for now this checks the reference side and the toolchain.

## The emulated CPU

qemu's default CPU for `qemu-x86_64` is `max`: AVX2, BMI, POPCNT,
CMPXCHG16B and more. A program that uses any of them would pass here and
die on an older machine, so the runner passes
`-cpu qemu64,-sse3,-cx16,-lahf-lm`, which is x86-64-v1. A CPUID probe
under it reports `sse2=1 sse3=0 cx16=0 popcnt=0`. `popcnt` dies with
SIGILL 4, and so does `cmpxchg16b` once `cx16` is off. LLVM 19 and 22
call `__atomic_compare_exchange_16` for an `i128` `cmpxchg` at the default
CPU, so `cx16` costs the reference nothing. AArch64 under emulation would
use `cortex-a53`; that path is not exercised on this host.

Without `-L /usr/x86_64-linux-gnu`, a dynamic program does not start:
"Could not open '/lib64/ld-linux-x86-64.so.2'". qemu runs fine under the
harness's 1 GiB `ulimit -v`.

## Linkers

The cross gcc selects a linker with `-B<dir>`, where `<dir>` holds it as
`ld.<name>`, plus `-fuse-ld=<name>`. The `.comment` signatures confirm the
choice. `-B` is needed for lld because there is no plain `ld.lld` on
`PATH`. With bfd (`x86_64-linux-gnu-ld.bfd`), lld 19, lld 22 and mold
2.37.1, all of these link and run under the emulator:

- PIE, non-PIE, static and static PIE C programs;
- C++ programs with exceptions, `thread_local` and `std::thread`;
- `llc` 19 and 22 objects, both PIC and static.

None needs compiler-rt: the soft-float `fp128`, `half` conversions and the
`x86_fp80` support all come from libgcc. wild is not installed and was
left alone.

## The x86-64 reference

The question was whether the x86-64 reference should be plain `-O0`
(FastISel) or `-fast-isel=0`. Four stand-in hods were run in hybrid mode
over every seed for x86-64: LLVM 22 and 19, each with `llc -O0` and with
`llc -O0 -global-isel=0`. They build the same objects that plain `-O0` and
the FastISel path would. Each program was compared with the reference
(`-fast-isel=0`) under the emulator with bfd, lld and mold.

**No behaviour differs.** The only FAILs were the two `coro/` seeds. The
stand-in hod runs `llc` without `opt`, and those seeds need the coroutine
passes first. Rebuilt by hand after `opt -passes=default<O0>`, both match
under both selectors with LLVM 19 and 22. The code does differ: with
LLVM 22, 43 of 43 seeds give different assembly under FastISel. So the
equal behaviour is evidence, not an accident of identical code.

There is no LLVM difference to reduce. The reference stays
`-O0 -global-isel=0 -fast-isel=0` on both targets, set in one place,
`tools::reference_selector`.

The witness (`--witness --target x86_64`) agreed on every seed: 24 s with
LLVM 22, 26 s with LLVM 19.

## Measurements

All measurements were taken on the 16-core AArch64 host at load average
19 to 26, with `-j 4`.

| run | wall |
|---|---|
| every seed (50), x86-64 emulated, the real hod declining, LLVM 22 / 19 | 4.2 to 17.9 s / 4.3 to 16.4 s (three runs each) |
| every seed (50), AArch64 native, hod building 48 of 49, LLVM 22 / 19 | 5.7 to 12.8 s / 5.9 to 6.1 s |
| every seed (44), x86-64 emulated, the same, first measurement | 15.2 s / 14.9 s |
| every seed (45, 46), x86-64 emulated, hybrid stand-in (`llc` builds both sides, so twice the programs) | 28 to 33 s |
| every seed (45), x86-64 emulated, with the witness | 24 to 26 s |
| the quick cross seeds (4), x86-64 emulated, LLVM 22 / 19 | 0.9 s / 0.5 s |

The spread of one run's wall time is the machine's: with `-j 4` under a
shared jobserver at load 20, a run waits for tokens. It is larger than any
difference between emulated and native.

Per test and per linker, each seed's `llc` 22 program was linked and run
serially (`exp/cost.py`, not in the tree):

| target | linker | link per test | run per test |
|---|---|---|---|
| AArch64 native | bfd | 54 ms | 3 ms |
| AArch64 native | lld 22 | 59 ms | 3 ms |
| AArch64 native | mold | 30 ms | 3 ms |
| x86-64 emulated | bfd (cross) | 57 ms | 26 ms |
| x86-64 emulated | lld 22 | 56 ms | 27 ms |
| x86-64 emulated | mold | 25 ms | 28 ms |

An emulated run costs a median of 9.5 times a native one (1.8x for
`exit_control.ll` up to 16x for `tls.ll`). It is still about 25 ms, mostly
qemu's start-up and the dynamic loader. Across 150 programs at `-j 4`
that is about a second of a run: a run's wall time is set by compiling
and linking (and by the load), not by emulation. Today the x86-64 run
links one side only, because hod declines there. Once hod builds x86-64
objects, a run will link and run twice as many programs, which is the
hybrid stand-in's 28 to 33 s.

The quick gate runs a fixed handful, `xtask::ci::QUICK_CROSS_SEEDS`, in
about a second, well under the minute it was allowed. The full set would
fit in that minute too. The handful was kept so that the quick gate stays
the same size as hod's x86-64 coverage grows. The full gate runs every
seed for x86-64 with both oracles, in under a minute.
Program limits under emulation are six times the native ones. No test
reads wall time.

## Debuggers

Ways to debug an emulated x86-64 program from this AArch64 host, found
with `qemu-x86_64 -g <port>`:

- **gdb.** The host's gdb 16.3 is built for AArch64 only: `set
  architecture` lists only arm and aarch64. Against qemu's stub it fails
  with "Target description specified unknown architecture
  i386:x86-64 ... Truncated register 55 in remote 'g' packet". It needs
  `gdb-multiarch` (Debian package `gdb-multiarch`, 16.3-1), which is not
  installed and was not installed.
- **lldb.** `lldb-19` with `gdb-remote <port>` works, for non-PIE and PIE
  programs alike (it finds the PIE slide). Working: breakpoints by name
  and by `file:line`, `bt`, `frame variable`, `finish` with the return
  value, `register read`, and continuing to exit. Missing: shared
  libraries, because qemu's stub sends no library list. `image list`
  shows only the executable, so there are no symbols in libc or
  libstdc++. At a breakpoint on a function's entry, the arguments read 0
  until the prologue has stored them, as natively at `-O0`. There is no
  `lldb-22`.

`cargo xtask debug` (L7) therefore stays native-only. A cross L7 would
need either `gdb-multiarch` or an LLDB that handles a remote without a
library list.

## Mutations

Each was applied, caught, and reverted:

1. **The runner drops `-L <sysroot>`** (`Target::emulator_args`). Caught
   by all four `link_cross` tests (the program does not start) and by the
   fakes `cross_target_runs_under_the_emulator` and
   `cross_runs_need_the_emulator_and_the_system_root` (the fake qemu
   requires `-L`).
2. **The x86-64 reference built for the host triple**
   (`engine.rs`, the reference's `-mtriple`). Caught by
   `irdiff_real::the_seed_corpus_runs_for_the_other_target`: every
   linker refuses an AArch64 object in an x86-64 link, which is an ERROR
   per test. Also caught by the fake `cross_target_runs_under_the_emulator`,
   which now checks both compilers' `-mtriple`. Before that check was
   added, the fakes missed it.
3. **LLVM 19 dropped from the full gate's cross runs**
   (`ci::irdiff_runs`). Caught by `ci::tests::the_gates_irdiff_runs`.
