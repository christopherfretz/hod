# WP-015 — `hod` command line, fallback, coverage log, kiln shim

Landed: `spec/cli.md` (all sections) and `spec/harness.md` "shim".

## What it did

- `crates/hod`: the facade the tool programs against: `Options` (one field
  per `llc` option hod accepts), `compile(&[u8], &Options)`,
  `CompileError`, `Unsupported { construct, function }`, `Construct` with
  the first four reasons, and the header helpers `InputKind::detect`,
  `module_triple`, `effective_triple`, `target_supported`. `compile`
  declines everything, with a deterministic reason.
- `crates/hod_cli`: the `hod` binary. `args.rs` (the `llc` grammar),
  `driver.rs` (one invocation: read, compile, write or fall back),
  `coverage.rs` (the log line and its single-`write` append).
- `xtask`: now a library plus the binary, so tests can build a shim.
  `xtask::shim` and `cargo xtask shim`.
- `hod_testutil`: `write_script` / `Scratch::write_script` (a script that
  can be executed at once), and `run_with` retries a spawn that fails with
  "text file busy". See "ETXTBSY" below.

## Decisions, and why

- **The command line was checked against the real `llc`** (LLVM 22.1.8):
  `-x` and `--x` are the same; `-O0`, `-O=0`, `-O 0`; a value option takes
  the next argument whatever it is; a boolean flag takes a value only
  joined; duplicates are allowed and the last wins; errors exit 1.
- **Hybrid mode falls back on everything `compile` can return**, including
  `MalformedInput` and `InvalidOptions`. The alternative (hod reports its
  own error) would let a hod bug in the IR reader break a build that `llc`
  compiles. The log line carries the reason, so a disagreement is visible.
- **A rejected command line falls back without reading the input.** hod
  cannot know what an option it does not know does to the input or the
  output. The cost is a log line without the input's kind and size.
- **An unusable coverage log is an error**, not a warning: coverage numbers
  from a log that may have dropped lines mean nothing.
- **Exit status 2** for "unsupported, and nothing fell back" is hod's own
  (`llc` uses 1 for everything), so a strict-mode harness can separate the
  remaining work from failures.
- **`fallback` as an outcome says only that the fallback ran.** Its exit
  status is the process's exit status and is not in the log.
- **`-march` is declined** (`unsupported-target`) rather than interpreted:
  mapping LLVM architecture names onto a triple is `llc`'s business until
  a target needs it. kiln does not pass it.
- **`--time-trace*` is accepted and ignored.** kiln adds these when the
  user asks for a trace and merges the child's file if it exists; a
  missing file costs the trace its backend events and nothing else.
- **The shim's `bin/llc` is a shell script**, not a link to hod: it has to
  carry the fallback path, and a link cannot. This costs one `sh` exec per
  translation unit; a build-time-configured or `argv[0]`-relative fallback
  in hod itself would remove it and is a follow-up once it is measurable.
- **The shim mirrors with links**, top-level entries as single links and
  `bin/` entry by entry, because kiln only ever looks at `bin/<tool>`,
  `lib/clang/<N>` and `include/c++/v1` beneath the directory.
- **kiln never runs `llc --version`.** `--version` still appends the
  fallback's version text for the scripts that do grep for it.

## ETXTBSY

A test that writes a script and runs it at once can fail with "text file
busy" in a multi-threaded test binary: another thread's `fork` holds a copy
of the still-open write descriptor at the moment of the `exec`. Two
measures, both in `hod_testutil`: scripts are written by a child `sh` (the
test process never holds a write descriptor to them), and `run_with`
retries a spawn that fails this way.
