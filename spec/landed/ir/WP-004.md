# WP-004 — hod_ir function bodies: values, instructions, the function builder, use facts, verification

Landed: `spec/ir.md` §5.1 to §5.6 (delivery, stack objects, values,
instructions, intrinsics, use facts), and two sections the spec did not
have: §5.8 (what the builder checks and what `verify` checks) and §5.9 (the
API code generation reads a body through). Not here: the symbol table and
function attributes (§2.2, §5.7: WP-003), debug nodes and expressions (§6:
WP-005), `classify` (§8: WP-009), the printer (§9: WP-006), any parser.

## What it did

New modules of `crates/hod_ir`; `lib.rs` and `error.rs` gained only
appended lines.

| module | contents |
|---|---|
| `value` | `Value` (4 bytes: 3-bit tag, 29-bit index), `ValueKind`, `InstId`, `SlotId` |
| `inst` | `Opcode` (67), `IntPredicate`, `FloatPredicate`, `AtomicOrdering`, `SyncScope`, `RmwOp` (21), `TailKind`, `MemFlags`, the 20-byte instruction record, `aggregate_field` |
| `intrinsic` | `Intrinsic` (133 members and `Other(name)`), `resolve_intrinsic`, `Intrinsic::mangled_name`, `no_code_intrinsic`, `no_code_names`, `NoCode` |
| `body` | `Body`, `UseFacts`, `Slot`, `SlotVar`, `Clause`, `Callee`, `Bundle`, and the read views `Block`, `Inst`, `InstKind`, `PtrAdd`, `Phi`, `Switch`, `CallSite`, `LandingPad` |
| `builder` | `FunctionBuilder`, `CallDesc` |
| `verify` | `Body::verify` |
| `random` (tests only) | a generator of random well-formed bodies and of damage to finished ones |

`IrErrorKind` gained `UndefinedValue`, `BadBlock` and `UseFactsMismatch`.

Sizes, asserted in unit tests: an instruction record 20 bytes, `Value`,
`InstId`, `SlotId` and `UseFacts` 4, `MemFlags` 2, `Opcode` 1, a block
record 12, `Slot` 16, `SlotVar` 12, `Clause` 8, a call record 40, a bundle
record 16, a landing-pad record 16.

A body is these tables and nothing else: instructions, use facts (one per
instruction, one per argument), locations (only with debug information),
three operand pools (values, 32-bit words, types), bundle-tag bytes, blocks,
the layout, slots, slot variables, calls, parameter attributes, bundles,
landing pads, clauses.

## Decisions where the spec was silent

Delivery (§5.1):

- **Instruction ids are layout positions.** A block's instructions are a
  range of ids; the terminator is the last; "the next instruction" is `id +
  1`. Blocks are created in any order and *begun* in layout order, one
  open at a time. A producer that emits blocks out of order begins them in
  the order it wants them laid out, which is the order it emits them in.
- **The builder holds no borrow of the module.** It reads the parameter
  count in `new` and afterwards is told every result type. This is what
  lets one module feed builders on many threads, and it is why the builder
  cannot check types: `verify` does.
- **A failed append changes nothing; a failed `finish` drops the storage.**
  `abandon()` returns the storage of a function the producer gives up on.
- **`Body: Eq`**, comparing every table. A body built in recycled storage
  equals the one built in fresh storage, which is how recycling is tested.
- **Limits**: 2^28 instructions and 2^28 placeholders per body (they share
  the 29-bit instruction index space of `Value`), 2^29 of anything else a
  `Value` names. All `TableFull`.

Values (§5.3):

- **`reserve` returns a placeholder, and `resolve` defines it**, instead of
  the spec's "hands out instruction ids ahead of definition". With ids as
  layout positions an id cannot be promised before the instructions ahead
  of it exist. `finish` rewrites the operands; a finished body has no
  placeholders. A placeholder may resolve to any operand (a constant, an
  argument, another placeholder), which is what a producer needs when a
  forward-referenced LLVM value turns out to be something it folds.
- **Every placeholder must be resolved**, used or not, or `finish` fails
  with `UndefinedValue`. A cycle of placeholders is `UndefinedValue` too.
- **The type given to `reserve` is advisory**: it answers
  `FunctionBuilder::value_type` and is not compared with the definition's
  type. `verify` sees only the definition.
- `Value::NONE` is the operand of `ret void` and the callee value of an
  intrinsic call. An instruction without a result still returns a `Value`
  from its append method; using it is `InvalidOperand` in `verify`.

Instructions (§5.4):

- **`ptrtoaddr` is an opcode**, the fourteenth cast. The spec's table had
  thirteen; LLVM 22 has it and `clang` 22 emits it.
- **`AtomicRmw` has 21 operations**, LLVM 22's (`xchg add sub and nand or
  xor max min umax umin fadd fsub fmax fmin uinc_wrap udec_wrap usub_cond
  usub_sat fmaximum fminimum`). The spec said 17.
- **`CallBr` is a call**: it has a call record, with the fallthrough and
  the indirect destinations in it.
- **`Alloca` states its result type** (a pointer type; the producer picks
  the address space), the element size in bytes and the alignment; the
  count is the operand. It is not typed otherwise.
- **`ExtractValue`/`InsertValue` carry a byte offset**, not an index path.
  `aggregate_field` is the one resolver. `verify` accepts an offset and a
  field type when some path reaches that type at that offset; two paths to
  the same offset and type (through a zero-sized field, say) are the same
  instruction. An `InsertValue` offset is limited to 2^32 - 1
  (`TypeTooLarge`), because its third operand word holds it; an
  `ExtractValue` offset is 64 bits.
- **Shuffle masks are words in the pool**, `SHUFFLE_UNDEF` for an
  undefined element.
- **The funclet opcodes carry no operands.** `funclet(op, ty)` appends
  one; the terminators among them have no successors. They exist to be
  rejected.
- **Not kept**, beyond what the spec lists: `samesign` on `icmp`, `nneg`
  on `zext`/`uitofp`, `nuw`/`nsw` on `trunc`, `inbounds`/`nuw`/`nusw` on
  address arithmetic. None changes unoptimized code.
- **Call attributes are stored only for calls that have any**: a call
  whose return and arguments all have `ParamAttrs::NONE` has no attribute
  entries.
- **Operand bundles** are a tag (bytes in the body's name pool) and input
  values. Nothing interprets them here.

Intrinsics (§5.5):

- **The list is the intersection of what can be asked for and what is
  generic.** It was drawn from two sources: every intrinsic name kiln's
  lowering can emit, and a survey of what `clang++` 22 emits at `-O0` over
  C++ exercising builtins, exceptions, coroutines, atomics, variadics,
  vectors and the standard library's math. Both give the same set, apart
  from the names below.
- **Left out**, so `Other`: target-specific names; intrinsics with
  metadata arguments (the constrained floating-point family,
  `llvm.read_register`/`write_register`), because a metadata argument is
  not a `Value`; the `llvm.masked.*` family, whose signatures differ
  between LLVM 19 and 22; `llvm.get.dynamic.area.offset`.
- **A name resolves to a member only if it is exactly the mangled name for
  the overload types its function type gives.** `llvm.ctlz.i64` declared
  as `i32 (i32, i1)` is `Other`. The alternative, trusting the base name,
  would let two producers disagree about what a call means.
- **`llvm.thread.pointer` without a suffix is accepted** as the member:
  LLVM 19 writes it so, and LLVM 22 upgrades it to `.p0`.
- **Overloads are read from fixed positions of the function type** (the
  return type, a parameter, a field of the returned struct), one table row
  per intrinsic, and the same row drives name mangling. A vector overload
  mangles as `v4i32` or `nxv2f32`, a pointer as `p0`, as LLVM does.
- **The no-code rule is a function, not a convention**: producers call
  `no_code_intrinsic` and do what the answer says.

Use facts (§5.6), including the supervisor's additions:

- **A use is an operand position**: `add %x, %x` is two uses of `%x`. The
  callee of an indirect call and the inputs of operand bundles are uses.
- **Arguments have use facts**: the count, and whether any use is outside
  the entry block. `only_use_is_next` is never set for an argument.
- **A `phi` use is located at the end of its incoming block.** It is
  "outside" exactly when the incoming block is not the defining block,
  and it never satisfies `only_use_is_next`.
- **`only_use_is_next` is stored as "count is 1 and that use was by the
  next instruction"**; a second use clears its meaning because the
  accessor compares the whole word.
- The count saturates at 2^30 - 1.
- Uses through a placeholder are attributed in `finish`, by the same rules.

Verification (§5.8):

- **The split is by cost.** The builder checks what keeps the tables sound
  (a few compares per operand, no type table); `verify` checks everything
  else and re-checks the structure from the tables, so it also judges a
  body that was not built by the builder (the damage tests rely on this).
- **`verify` does not check dominance.** LLVM permits anything in
  unreachable code, a dominator tree is a real cost, and nothing in the
  location policy depends on it.
- **`verify` does not check that a symbol or inline-assembly id exists**,
  and takes every symbol address as `ptr` in address space 0: the tables
  to check against were not in this branch.
- A body whose storage was abandoned or cleared has function type `void`
  and fails `verify` with `InvalidType`.

Read API (§5.9):

- **`Inst::operands()` is one slice for every opcode**, so that passes
  that only care about values (liveness, the use recount in `verify`)
  need no match. `Inst::kind()` is the typed view for instruction
  selection.
- **`Block::has_phis()` and `Block::phis()`**, and **`Body::calls()`**
  iterating the call table without walking instructions, were asked for by
  the supervisor for edge copies and for the outgoing-argument area. No
  per-body maximum is precomputed.

## What LLVM does that was not expected

All observed with LLVM 22 unless noted; each is pinned by a test in
`tests/body_llvm.rs`.

- **`ptrtoaddr` must yield exactly the address width** of the pointer's
  address space (`ptrtoaddr ptr %p to i32` is rejected on a 64-bit
  target), where `ptrtoint` yields any integer.
- **A `cmpxchg` failure ordering may be stronger than the success
  ordering** (`monotonic seq_cst` is accepted). Only `unordered`,
  `release` and `acq_rel` are refused as failure orderings.
- **Atomic `load` and `store` of a scalable vector are accepted** when the
  minimum size is a power of two of at least 8 bits (`<vscale x 2 x i32>`
  yes, `<vscale x 3 x i8>` and `<vscale x 4 x i1>` no). hod follows; a
  target will reject them in `classify`.
- **Atomic `load`/`store` take any integer, float, pointer or vector of
  power-of-two size**: `i128`, `half`, `<2 x ptr>` are accepted; `i1`,
  `i24`, `x86_fp80`, `<3 x i8>`, structs and arrays are not.
- **`atomicrmw xchg` takes no vector**, `atomicrmw fadd` takes a fixed
  vector of floats but no scalable one, and the integer operations take
  neither pointers nor vectors. `cmpxchg` takes integers and pointers
  only.
- **In text, an atomic `load` or `store` needs an explicit alignment.**
- **LLVM renames an intrinsic declared under the wrong suffix** instead of
  rejecting it (`llvm.ctlz.i13` of type `i32 (i32, i1)` becomes
  `llvm.ctlz.i32`), and keeps a non-overloaded name with a spurious suffix
  (`llvm.trap.i64`) as an ordinary function. hod resolves both to `Other`:
  the first cannot reach a producer that reads LLVM's output, and the
  second is not an intrinsic.
- **`llvm.lifetime.start`/`end` take one argument** in LLVM 22, and it
  must be an `alloca` or `poison`.
- **A `llvm.dbg.value` call is a `#dbg_value` record once read**; no call
  remains to be dropped.
- **An `extractvalue` with no index is a syntax error**, not a no-op, and
  an index path never enters a vector.
- **A `phi` needs one entry per predecessor edge**: a `switch` or `br i1`
  with both edges to one block needs two entries, with equal values.
- **A landing-pad block may only be entered by unwind edges**, and the
  entry block may be neither a landing pad nor a branch target.
- `opt -passes=instsimplify` does not fold a `ptrtoint` of a constant
  `getelementptr`; the offsets test reads them from the `.data` that
  `llc` writes for a table of such expressions.

## Tests

`cargo test -p hod_ir`: 83 unit tests in `src` (17 of them this work
package's), 18 in `tests/body_build.rs`, 6 in `tests/body_llvm.rs`, and
WP-002's four differential files unchanged.

**`tests/body_build.rs`** (no tools). Every instruction group is built and
read back through the read API; each test names its spec section. The
use-fact rules have one test per rule: results, arguments, uses through
placeholders, and `use_facts_across_a_block_boundary` (an `invoke` result
used by the first instruction of the next block, by a `phi` there, directly
and through a placeholder; a self-loop `phi`; a `phi` input arriving from a
third block). Every `IrErrorKind` this work package produces is produced:
the builder's in `builder_errors` and `reserved_values_resolve_or_fail`,
`verify`'s in `verify_type_rules` and `verify_call_and_control_rules`.

**The `random` module** (no tools; 1500 seeds, own splitmix64 generator):

- `random_bodies_verify`: 1500 bodies, 43244 instructions, every opcode
  but the five funclet ones; 9672 results used outside their block, 1679
  used only by the next instruction, 1926 arguments used outside the entry
  block. Placeholders are resolved early, late, to each other and to
  non-instructions; `phi` inputs are added after the fact.
- `random_bodies_in_recycled_storage_are_the_same`: each body built again
  in the previous body's storage equals the fresh one, and the allocation
  stops growing.
- `random_bodies_with_an_undefined_value_do_not_finish`: `UndefinedValue`.
- `damaged_bodies_do_not_verify`: 26 kinds of damage to one table entry of
  a finished body (use facts; operands, ids and side-table links; block
  ranges and `phi` lists; a duplicated `switch` case), each applied at
  least 25 times, each refused by `verify` with the kind §5.8 gives.

**Sensitivity.** Three bugs were put into the use-fact bookkeeping on
purpose (a `phi` use through a placeholder allowed to count as "next"; a
direct `phi` incoming judged "outside" by the wrong block; "next" set for
a use in another block). At first `body_build.rs` caught none of them, no
test at all caught the first, and a single random seed caught the third.
`use_facts_across_a_block_boundary` was written from that, and all three
are now caught by `body_build.rs` alone.

**`tests/body_llvm.rs`** (LLVM 22's `llvm-as`, `llvm-dis`, `llc`; skipped
without them, failing with `HOD_REQUIRE_TOOLS=1`). hod and LLVM answer the
same question for every case of a grid, and any disagreement fails:

| test | cases | accepted by both | rejected by both |
|---|---|---|---|
| `cast_rules_are_llvms` (14 opcodes, 100 type pairs) | 1400 | 92 | 1308 |
| `atomic_rules_are_llvms` (orderings, 28 types, 21 operations) | 327 | 120 | 207 |
| `aggregate_paths_are_llvms` (4 aggregate types) | 250 | 50 | 200 |
| `terminators_are_llvms` | 67 opcodes | 12 end a block | 55 do not, and are accepted before a terminator |

Also `aggregate_paths_are_llvms` compares the 50 byte offsets with the
ones `llc` computes; `intrinsic_names_are_llvms` round-trips one
declaration of each of the 133 intrinsics (names kept), and 108 with a
wrong suffix (all renamed by LLVM, all `Other` to hod);
`no_code_intrinsics_generate_no_code_in_llvm` compares `llc -O0` assembly
for 13 calls with the assembly of what the rule makes of each.

These grids found two rules hod had wrong, both fixed here: `ptrtoaddr`'s
width, and atomic access to scalable vectors.

Not covered against LLVM, and why:

- Whole random bodies are not assembled by LLVM. That needs the printer
  (WP-006); `tests/body_support` has a debugging dump, not LLVM text.
- The call rules (argument counts and types) and the `phi` and
  landing-pad rules are tested against `verify` only. LLVM's facts about
  them above were observed by hand.
- The no-code comparison is AArch64 only.
- LLVM 19 is not an oracle here: it lacks `ptrtoaddr` and four `atomicrmw`
  operations and spells some intrinsics differently.

## Measurements

`cargo run --release -p hod_ir --example body_throughput`, fastest of
five, on the shared development host (an AArch64 container with other
work running beside it). The mix per block of 13 instructions is 4 `load`, 3
`store`, 2 `PtrAdd` (one with a constant offset, one with a scaled index),
1 `add`, 1 `icmp`, 1 `call` with two arguments, 1 branch (one in four
conditional), on values kept in 24 stack slots.

| | one body of 1 000 001 instructions | 5000 bodies of 197 |
|---|---|---|
| build, fresh storage | 15.1 ns/instruction | 16.7 ns/instruction |
| build, recycled storage | 10.5 ns/instruction | 10.5 ns/instruction |
| `verify` | 25.9 ns/instruction | |
| read every instruction (type, use facts, operands) | 4.6 ns/instruction | |
| table bytes | 31.1 bytes/instruction | |
| allocated, fresh storage | 36.7 bytes/instruction | 8336 bytes held in all when recycling |

The 31.1 bytes are 20 for the record, 4 for use facts, and about 7 for
this mix's share of blocks (16 each), call records (40 and 12 of
operands) and pooled `PtrAdd` operands. With debug information add 4.

Bytes per instruction for real IR were not measured: there is no parser
yet. For orientation, the opcode mix of the `-O0` survey (about 8000
instructions of `clang++` 22 output) was `load` 1713, `store` 1357,
`alloca` 1150 (slots in hod, not instructions), `br` 790, `call` 742,
`getelementptr` 539, `ret` 375, `extractvalue` 157, `icmp` 156, `phi` 117,
`zext` 98, `add` 74: more calls and fewer address computations per block
than the synthetic mix, so somewhat more than 31 bytes.

## For the next work packages

- WP-003 (symbols): `verify` should check `Value::sym` and `Value::asm`
  ids against the module's tables and take a symbol's pointer type from
  its address space (`verify.rs`, `Verifier::value`). `FunctionBuilder::new`
  takes the function type as an argument; with a symbol table it can read
  it from the symbol.
- WP-005 (debug): `SlotVar` (`body.rs`) is where a `#dbg_declare`'s
  expression attaches; `Body::dbg_records` of §6 does not exist; per
  instruction locations are `set_loc` on the builder and `Body::loc`.
- WP-006 (printer): `Intrinsic::mangled_name` gives the declaration name;
  `tests/body_support::type_text` and `dump` are test helpers, not a
  printer. Once bodies print, the random generator's bodies should go
  through `llvm-as` and `opt -passes=verify`.
- WP-009 (`classify`): the funclet opcodes, `Intrinsic::Other`, operand
  bundles, `CallBr`, scalable types and atomic accesses of unusual types
  are all representable and all need an answer.
- Code generation: read §5.9. `Inst::uses().only_use_is_next()` is the
  fusion test for compare-and-branch; `Block::phis()` and `has_phis()`
  serve edge copies; `Body::calls()` serves the outgoing-argument area.
- Producers: call `no_code_intrinsic` before `resolve_intrinsic`; fold
  constant `getelementptr` indices into `PtrAdd`'s offset; turn entry-block
  constant-size `alloca`s into slots; resolve `extractvalue` paths with
  `aggregate_field`.
