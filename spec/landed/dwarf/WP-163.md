# WP-163 — debug follow-ups: rnglistx, the tail branch's end, two x86-64 rows

The contracts are `spec/dwarf.md` §6.4 (block ranges), §6.15 (split
block lists), §6.20 (DWARF 4), §6.21 (DWARF 4 tail call `low_pc`) and
§6.17 ("Fused compares", "Permitted differences on x86-64"). This file
records what the package found and did.

## 1. `DW_FORM_rnglistx` in every DWARF 5 unit

What `llc` writes (19 and 22 agree): every `DW_AT_ranges` of a DWARF 5
unit is `DW_FORM_rnglistx`, an index into the offsets table of the
unit's `.debug_rnglists` contribution. The scopes' lists are numbered in
DIE order, the unit's own list (more than one code span) is last, and
the unit has `DW_AT_rnglists_base`. A unit with one code span and scope
lists has `low_pc`/`high_pc`, `addr_base` and `rnglists_base`. hod wrote
`DW_FORM_sec_offset`, one relocation per list, outside split DWARF.

What changed: `crates/hod_dwarf/src/die.rs` records each list's start
(`block_list`) and writes the offsets table in `contributions`; families
38, 75 and 76 (`lexical_block`, `inlined_subroutine`, the abstract
`lexical_block`) take `DW_FORM_rnglistx` in place of `sec_offset`;
family 106 (`compile_unit (scope lists)`, base 11480) is the
one-span unit with `rnglists_base`. `UnitPlan::scope_lists` counts the
lists before the unit DIE is written; a count that disagrees is the
internal error "a scope range list the plan did not count". Split DWARF
(`split.rs`) no longer rewrites forms: its `.debug_rnglists.dwo` is the
same contribution. DWARF 4 (`dwarf4.rs`) resolves each index through the
offsets table to the version 5 list it transcodes.

Evidence, objects of hod before and after (`-O0`, PIC):

| set | `.rela.debug_info` | of them against `.debug_rnglists` | bytes | `.debug_info` | `.debug_rnglists` |
|---|---|---|---|---|---|
| `-g` corpus and `tests/debug`, AArch64 (90 objects) | 1694 = | 20 = (each a unit base) | 700528 = | 62428 = | = |
| same, x86-64 (78 objects) | 1610 = | 14 = | 620640 = | 58555 = | = |
| modules with scope lists, AArch64 | 42 → 38 | 10 → 6 | 89632 → 89560 | 4796 → 4786 | 326 → 350 |
| same, x86-64 | 32 → 28 | 8 → 4 | 24976 → 24896 | 1224 → 1214 | 145 → 169 |

The first two sets are byte-identical: at `-O0` none of their units has
a scope range list. DWARF 4 objects: 42 of 42 byte-identical. Every
object verifies (`llvm-dwarfdump-22 --verify`). The modules with scope
lists are the four test-data modules with interrupted inlined code or
blocks, with and without `-function-sections` (`kiln_types` is refused
on x86-64 before and after). Their offsets tables equal `llc`'s.

Tests: `crates/hod_x64/tests/rnglistx.rs` (forms, indices and
`offset_entry_count` against `llc` 19 and 22, one relocation, the unit's
list resolves to its functions' ranges; DWARF 4 resolves each index to
the same ranges), `split.rs` `every_range_list_is_rnglistx`, the
`hod_dwarf`, `hod_a64` `dies*`/`lines*` and `hod` `split_dwarf`,
`dwarf4`, `dwarf_scope_survey` tests. Mutations caught: the unit's
index 0 in place of last; the transcoder reading table entry 0 for
every index; the unit's own list first in the offsets table.

## 2. The tail branch's end

`DebugCallRow` has `end`: the target calls `FnCx::tail_branch_ends_here`
once it has written a tail call's branch (`hod_x64`, `hod_a64`
`frame.rs`), and `map_debug_calls` maps `end` with `offset` through the
shrink pass. `tail_branch_len` (a per-target assumed length) is gone.
Evidence: 168 of 168 objects byte-identical before and after;
`hod_cg` `a_tail_branch_end_moves_with_the_code`,
`crates/hod_x64/tests/tail_branch_end.rs` (a direct and an indirect
`musttail` after relaxed branches; each site is the end of a decoded
`jmp`). Mutation caught: x86-64 reporting the end before the `jmp`
(refused as `debug:call-site-pc`).

## 3. `key_multiline.c`, lldb `finish` on x86-64

Cause: `llc`'s instruction at `add`'s return address is its register
allocator's spill of the result (`movl %eax, 0xc(%rsp)`), with a line 0
row; lldb reports the next row with a line, 19:15. hod copies the result
out of `rax` under the call's location: 17:11. Not a bug on either
side; classified as `line 0 after a call` (§6.17), outside the
`return-column` class, which permits columns only. The test keeps not
using `finish` (a comment says why).

## 4. A fused `zext` feeding a store on x86-64

Cause: WP-157 put the cast's `setcc` at the cast's line; `llc` puts it
at the compare's, with every consumer, and only the `movzx` (`neg`) at
the cast's. Fixed in `crates/hod_x64/src/int.rs` (the `setcc` inside
`control::at_compare`). No code byte changes: 166 of 168 objects
byte-identical, the other two (`dwarf4_shapes.cpp`, x86-64, clang 19
and 22) differ only in `.debug_line`. Classified residual: a `zext i1`
to `i8` stored is `setl (%rdx)` at the store's line for `llc`, no row at
the cast's; hod's `movzx` has the cast's line. Test:
`crates/hod_x64/tests/zext_lines.rs` (fails with WP-157's placement).
