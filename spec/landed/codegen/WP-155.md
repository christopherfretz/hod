# WP-155: x86-64 on real hardware

What the hosted lane's x86-64 runner showed and `qemu-x86_64` hid
(`spec/landed/harness/WP-145.md`, "Findings of the x86-64 runner"), each
reproduced here first, then proved on the runner (run 43452390364, the
x86-64 `test` job restricted to these tests by a temporary commit that
was reverted).

## `kiln_e2e` `integers-hod-O0` printed `2 1 3` for `2 1 253`

Not a code generation fault. The C driver printed
`accumulate(1000)` and `g_counter` in one `printf`: the order in which a
call's arguments are evaluated is unspecified, and gcc for x86-64 reads
`g_counter` before it calls `accumulate` (gcc for AArch64 the other way).
Built here for x86-64 with kiln (`--target=x86_64-unknown-linux-gnu`),
hod's object and `llc -O0 -fast-isel=0`'s both print `3` under qemu.
The driver now calls `accumulate` first. `hod_builds_integers` builds
the program for both targets on every host (the other one with
`kiln --target`, the cross toolchain and its emulator), so this AArch64
host builds and runs the x86-64 program: the old driver fails here in
`integers-x86_64-hod-O0`. The x86-64 ignore is removed.

## `fpintr`: 66 `half` results differ from `llc` 22 natively

`fma` of `half`: hod computes `a * b + c` in `double` (`mulsd`, `addsd`:
the product is exact, one rounding, as `fma` of the widened values);
`llc` widens to `double` and calls the C library's `fma`, which runs
`vfmadd` on a CPU with FMA. With several NaN operands they return
different ones (`fma_h(0xfe00, 0x7e01, 0x3c00)`: hod `0xfe00`, the first
operand as `mulsd` returns it; `llc` `0x7e01`). The rule that decides is
the LLVM language reference's "Behavior of Floating-Point NaN values": a
NaN result with NaN operands is a quieted operand NaN or the preferred
NaN, chosen freely, so both are correct. The test matches `fma_h` and
`fma_aab_h` against `llc` NaN for NaN (`float_gen::Func::nan_open`); all
other bits are still compared. qemu hid it: its SSE returns the NaN with
the larger significand when both are quiet, not the first operand (hod's
own `mulsd` returns `0x7e01` under qemu). So qemu cannot catch a NaN
choice that depends on SSE operand order; the hosted lane can. The
x86-64 ignore is removed.
