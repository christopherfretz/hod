# WP-334 — a `hod` process that hung with `--threads`

## Facts given

A process `hod -filetype=obj --threads=4 clang22.tiny-functions-g.ll` was
found asleep with no CPU for 7.5 hours. Its binary was a development build
of WP-304 (since deleted). The main thread waited in `pthread_join` of the
first helper (`helper.join()` in `crates/hod/src/back.rs`); the three
helpers waited to lock one futex mutex in the binary's writable data
(`.bss` offset `0xb08` of the one-page RW mapping), value 2.

## What the core shows

- The `.bss` of the deleted binary has the same layout as a release build of
  `baa19ddb` with the same toolchain (rustc 1.95.0): the words around the
  lock hold `ARGC` = 6 (the six words of its command line), `ThreadId`'s
  counter = 4 (main and three helpers), `PAGE_SIZE` = 4096. At the lock's
  offset that build has `std::io::stdio::stderr::INSTANCE` + 8: the futex
  word of stderr's `ReentrantLock`. In the core, that lock reads owner = 1
  (the main thread's `ThreadId`), futex = 2, count = 1.
- The helpers' frame-pointer chain runs thread start → the worker closure →
  a function that calls `std::io::_eprint` (the routine that locks
  `0x…b08` and calls `lock_contended`) with the format template
  `"WP304C {} chunk={} fns={} us={}\n"`: a timer line of WP-304's
  diagnosis ("temporary timers in `hod::back` (per chunk, per thread, ...)",
  `spec/landed/harness/WP-304.md` "Method"), printed by a worker.

## Cause

`crates/hod_cli/src/main.rs` locked `stdin`, `stdout` and `stderr` for the
whole run and passed the guards to the driver. A worker's `eprintln!` then
waits for the main thread to release stderr, which it does only after the
run, and the run waits in `join` for the worker. The panic hook does not
take the lock (it writes to the raw stream), so a worker's panic did not
hang; only a write through `std::io::stderr()`/`stdout()` does.

`main` at `baa19ddb` has no such write on a worker (no `eprint!`, `print!`,
`dbg!` or `io::stderr()` outside tests and examples), so the released
binary does not hang this way; the lock was a trap for the next diagnostic
print on any thread hod starts (code generation, body reading, the index
scan). `--threads=1` never hangs: no other thread exists.

## Reproduced

- Stress on `baa19ddb` (release, unchanged): `hod -filetype=obj
  --threads=N` for N in 2..8 over the clang 22 bench inputs
  `tiny-functions-g` (in three of four loops), `huge-function-g`,
  `templates-g`, `stl-heavy-g`, `tables-g`, `interp-g`, `tiny-functions`;
  4 loops in parallel, 15 750 runs, host load 18 to 28 of 24 cores, part
  of it during a `cargo test` build: 0 hangs, 0 failures.
- The same tree with one `eprintln!` added after a worker's loop: 7 of 7
  runs (N = 2..8) hang. Main in `pthread_join` (`compile_bodies`), each
  live helper in `Stderr::lock` ← `_eprint` ← `Work::work`, the lock at
  `.bss` `0x5c0b08` = `stderr::INSTANCE` + 8: the shape of the original.
  With the print inside the loop (before posting a chunk), the main thread
  waits on the board's condition variable instead.

## Fix

`with_process_io` in `crates/hod_cli/src/main.rs` hands the driver the
unlocked `Stdin`, `Stdout`, `Stderr`: each read or write locks for itself
(`spec/cli.md` "Threads"). Objects are written with one `write_all`, so
the per-call lock costs nothing measurable.

## Test

`other_threads_can_write_while_the_driver_runs` (`crates/hod_cli/src/main.rs`):
inside `with_process_io`, a spawned thread writes to stderr and stdout
(directly, not through `eprint!`, which the test harness captures) and
signals. Before the fix it waits for the guards and the test fails at its
60 s bound (observed: `FAILED ... 60.00s`); after it passes at once. The
bound is reached only on the deadlock, never on a passing run.
