# WP-167: a lone `<1 x i128>` across calls on AArch64

The one module of 7,365 the native libc++ sweep refused on the AArch64
runner (`spec/landed/harness/WP-164.md`),
`std/algorithms/alg.nonmodifying/alg.find/find.pass.cpp`, refused with
`abi:vector-element`. libc++ 22's `std::__load_vector` lambda, instantiated
for `unsigned __int128` and `__int128`
(`_ZZNSt3__113__load_vector…IDv1_oPoE…` and `…IDv1_nPnE…`), returns
`<1 x i128>`, and `__find_vectorized<unsigned __int128>` calls it. The test
source of the tree used here (libc++ `llvmorg-22.1.8`, Debian's 22 headers)
refused the same way as the runner's.

## What `llc` does

`llc -O0 -global-isel=0 -fast-isel=0` of LLVM 19 and of LLVM 22 pass a lone
`<1 x i128>` exactly as an `i128`: two general registers under the
even-register rule (after one `i64`, in `x2`/`x3`), or two 8-byte stack slots
from a 16-aligned offset, and return it in `x0`/`x1`. The two versions agree
for arguments, results and the stack (LLVM 19 detours the result through
`d0`, but the place is the same). AAPCS64 has no 16-byte vector of one
128-bit integer; this is LLVM's legalization.

## What is implemented

- `abi.rs` (`lone_leaf`): the two pieces of the `i128` row, each a `Lanes`
  part `{ bits: 64, lane: 8, len: 2, first: limb }`, `offset` 0, `size` 8.
  The value is a `Q` register (`spec/codegen.md` §2) and a `Value` part
  cannot move it into general registers; a `Lanes` part goes through the
  target's `lanes_out`/`lanes_in`.
- `vcall.rs` (`limb_of`, `limb_out`, `limb_in`): `umov xN, vM.d[i]` and
  `ins vM.d[i], xN`, through `x16`/`x17` for a stack slot.
- `hod_cg` (outside the package's crates, one token each): the call
  sequence's argument (`call.rs` `place_part`), result and `place_return`
  paths and the function entry (`driver.rs` `enter_lanes`) gather or
  produce a register value with `Lanes` parts in the scratch register of
  the value's class instead of always the general one. Masks are `Gpr` on
  both targets, so nothing else changes.

Inside an aggregate the value is memory and travels as `Value` bytes as
before (WP-101).

## What stays refused

`abi:vector-element` for vectors of integers whose width is not 1, 8, 16, 32,
64 or 128 (`<2 x i7>`, `<4 x i24>`, `<2 x i96>`, `<1 x i256>`) and of
`x86_fp80`: no C or C++ type has them, AAPCS64 does not define them, and hod
lowers no value of them (`a64:vector-odd-element`, `a64:vector-wide-element`).
LLVM 19 and 22 were seen to place `<2 x i7>`, `<1 x i7>`, `<4 x i24>`,
`<2 x i96>`, `<1 x i256>` and `<1 x i65>` alike; that is noted in
`spec/abi-a64.md` §4.3 for a package that lowers such values.

## Evidence

- `find.pass.cpp`: kiln++ to LLVM IR, `hod --strict` builds it, linked
  statically against libc++ 22 and run natively: exit 0.
- `vcall::lone_i128_vectors_cross_calls`: 81 signatures (lone `<1 x i128>`
  after 0 to 8 general arguments, around `i32`, after full vector
  registers, in a structure, beside `<2 x i128>`, `<3 x i128>`, `i128` and
  the byte vectors; through a pointer, `invoke` and `musttail`; as a named
  argument of a variadic callee), 28,560 leaves compared over hod against
  `llc` 22 both ways under bfd, lld and mold, hod (stress options) against
  `llc` 19 both ways, and hod against hod.
- `table::vectors`: the assignment at an odd register, on the stack, as a
  result. `errors::every_name` now produces `abi:vector-element` from
  `<2 x i7>` and a `<1 x i256>` result.
- Mutations, each caught by the cross-call test and reverted: the limbs
  swapped in `limb_out` (1,872 disagreements); no even-register rule
  (`split` 0, 960); every limb inserted into lane 0 in `limb_in` (2,112).

## x86-64

The same 81 signatures, one module per caller and per callee, through
`hod --strict` for `x86_64-unknown-linux-gnu`: 112 of 162 modules build;
39 are `x64:vector-i128-split` (an `i128`-element vector, lone
`<1 x i128>` included, partly in registers and partly on the stack, or on
the stack at an offset that is not a multiple of 16: `llc` 19 and 22
differ, WP-152), 8
`call:part-register-class` (`<1 x i64>`, unrelated to `i128`), 3
`musttail:stack-args-unknown`. AArch64 builds all of them. `hod_x64` is
unchanged.
