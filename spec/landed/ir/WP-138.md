# WP-138 — x86-64 readiness of the target-neutral half

Landed:
- `spec/interp.md` §3 (`Val::X86Fp80`), §4 (a function's address is
  aligned to its `align`), §5.8 (`byval` copies), new §5.11 (`x86_fp80`),
  §8 (`type:x86_fp80` only for vector lanes, `intrinsic-x86_fp80`,
  `attr:byval` only for calls of functions without a body), §11, §12.
- `spec/harness.md` "x64census": the command.

## What it did

| where | change |
|---|---|
| `hod_interp` `x87.rs` (new) | a soft-float of the x87 at 64-bit precision, round to nearest even: add, sub, mul, div (correctly rounded), `fmodl`, compare, conversions to and from `float`, `double` and integers; denormals, invalid encodings, NaN propagation as the 387 does it. No dependency |
| `hod_interp` `interp.rs`, `value.rs`, `ops.rs` | `Val::X86Fp80`: 10-byte loads and stores, constants, initializers, arithmetic, `fneg`, `fcmp`, casts, `fabs`/`copysign`. `byval(T)` arguments copied into the callee's frame. Function addresses aligned to the function's `align` |
| `hod_interp` `memory.rs` | `alloc_function(sym, align)` |
| `hod_ir` `tests/common` | layout edge types `{i64, x86_fp80}`, `__va_list_tag` and `[1 x __va_list_tag]`, and pointers of address spaces 270..272: `layout_diff` compares them with `llc` for x86-64 on LLVM 19 and 22 |
| `hod_bc` `tests/x86_64.rs` (new) | both readers and the printer on the x86-64 constructs, and the two named refusals |
| `xtask` `x64census.rs` (new), `main.rs`, `lib.rs`, `Cargo.toml` | `cargo xtask x64census` |
| `hod_a64` `tests/common/aggr_gen.rs` | one match arm for the new `Val` variant (outside the package's crates; unavoidable) |

What needed no change: the readers already handled `x86_fp80` (type,
`0xK` constants, aggregates, initializers), the x86 calling conventions
(as numbers), the `byval`/`inreg`/`nest`/`preallocated`/`inalloca`
attributes, the target strings, address spaces 270..272, `llvm.x86.*` as
`Intrinsic::Other`, `inteldialect` and x86 constraints, and the module
flags `Code Model`, `cf-protection-*`, `RtLibUseGOT`,
`direct-access-external-data` and `kcfi`. The layouts matched `llc`.
Nothing outside the code generator assumes AArch64.

## Evidence

- Sample: 371 modules recompiled for `x86_64-unknown-linux-gnu` (kiln++
  and clang 19/22 over the corpus: a stride per source and major, design
  0006's `targeted.txt`, a `-g` stride, kiln tests that throw), plus 4
  probe modules. 375 jobs, 4 capture failures (3 multi-unit tests, one
  `arm_neon.h` test).
- `hod_bc` differential, bodies and debug tests over the sample: the text
  and bitcode readers agree on LLVM 19 (185/185) and LLVM 22 (185/185;
  one module has no `llvm-dis` oracle).
- `cargo xtask x64census --shipped --interp -j 4`: 375 modules.
  - 370 are ready: they read, verify, print, are accepted by `llvm-as`,
    print to a fixed point, and give the same reasons on both routes, all
    of them the code generator's.
  - 3 are `facade:front-refuses`, all by calling convention: `cc:78` (the
    two probes) and `cc:79`, `cc:92`, `cc:80` (kiln's `dcl.attr.cconv`
    test).
  - 2 are `ll:ParserUnsupported`: `type:x86_mmx` and
    `global-metadata:kcfi_type` (probes only).
  - Interpreter against `llc -O0` + `qemu-x86_64`: 140 agree and 0
    differ. 10 trap `uninitialized-load` on reads of initializer padding
    or uninitialized values (§12; they trap the same way on the AArch64
    builds). The rest are unsupported: `call:variadic` (147),
    `extern:<libc or C++ runtime>`, `call:inline-asm` (8), half, bfloat
    and fp128 types.
- `tests/x87_oracle.rs`: about 44,000 operations on random operands
  (normals, denormals, near overflow, specials, short significands) have
  the same bits as the x87 under `qemu-x86_64`.

## Refused by name, with proposed BACKLOG rows

| name | where | row |
|---|---|---|
| `type:x86_mmx` | both readers (LLVM 19; LLVM 20 removed the type) | keep refused: no front end of interest emits it |
| `global-metadata:kcfi_type` | both readers | read `!kcfi_type` and the `kcfi` operand bundle when `-fsanitize=kcfi` is wanted |
| `cc:64` .. `cc:92` | classify, x86_64 column (WP-116) | `x86_64_sysvcc` (78) is `ccc` on x86-64 Linux: accept it there. Give the other x86 conventions rows that are refused by design. With rows, `CallConv::keyword` can name them and the printer writes keywords instead of `cc N` (the `classify_matrix` completeness test requires a row for each keyword) |
| `intrinsic-x86_fp80` | `hod_interp` | `llvm.sqrt`, the rounding intrinsics and `fma` on `x86_fp80` |
| `call:variadic`, `intrinsic:llvm.va_start` | `hod_interp` | a model of the SysV `va_list` (`gp_offset`/`fp_offset`/overflow area) |
| `attr:byval` (host or extern callee) | `hod_interp` | when host functions take aggregates |
| `attr:inalloca`, `attr:preallocated` | `hod_interp` | never on x86-64 Linux (they are Win32 conventions) |

Two reader findings, neither met by kiln's or clang's output:
- LLVM auto-upgrades some old `llvm.x86.*` intrinsics when it reads them,
  and `hod_ll` does not. `llvm.x86.sse2.psrl.dq`, for example, becomes a
  `shufflevector` in `llvm-as`'s bitcode but stays a call in `hod_ll`'s
  reading.
- `llvm-as` gives an `llvm.x86.*` declaration the attributes of LLVM's
  intrinsic table (`nounwind`, ...). `hod_ll` has those attributes only
  for the intrinsics `hod_ir` knows. `tests/x86_64.rs` masks them.
