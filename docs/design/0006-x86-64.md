# Design 0006: x86-64 code generation

Status: accepted 2026-11-12 with the changes of section 10 (WP-110). A design; no product code. Written
after the operator made x86-64 the target that ultimately matters
(AArch64 stays supported), with up to about eight implementers in
parallel. The package split (section 7) is therefore cut for the
**shortest path to the corpus sample, then libc++, on x86-64**.

Paths are hod's unless marked `kiln:`. Experiments ran on the shared
aarch64 host (load 16-27), with LLVM 19 and 22 from `/usr/lib/llvm-*`,
the cross toolchain `x86_64-linux-gnu-gcc`/`g++` 14 and
`qemu-x86_64 -L /usr/x86_64-linux-gnu`. Times are proportions on a loaded
host. Scripts, IR and the outputs quoted are in `docs/design/0006-data/`
(below, `data/`); bulky intermediates are under
`.build/target-wp-110/x64/` and are regenerated by the scripts.

## Question

What does it take to give hod a second target, x86-64 SysV Linux, that
builds the corpus and then libc++'s test suite correctly, with as little
new code and as little re-gating of AArch64 as possible, by up to eight
implementers at once?

**Answer.** The driver (`hod_cg`), the object writer, the EH and DWARF
writers and the x86-64 encoder are already target-neutral or already
have x86-64 entries; `hod_x64` is written as a sibling of `hod_a64`
with the same module layout and the same group contract. Before it
starts, **one** refactoring package (R1, about 1,000 lines) moves into
`hod_cg` the semantic tables that would otherwise be written twice and
drift (runtime-function names, switch and memory-intrinsic plans, the
argument walk). Everything that is instruction selection is duplicated
on purpose. A second move (R3, the lane loop) is deferred until just
before x86-64 vectors, off the critical path. x86-64 code keeps every
value in memory, in the save-set pool (`rbx`, `r12`-`r15`) or in an
argument register it arrived in. `rax`, `rcx` and `rdx` never hold a
value, so the fixed registers of division, shifts and returns cost
nothing. It never folds loads, never uses the red zone, and holds
`x86_fp80` only in memory. `llc -O0 -fast-isel=0` for x86-64 is a
trusted oracle (756 random programs and 42 seeds agree in all six
configurations). Emulation costs about +42% per corpus test and 7.3x
on compute; a real x86-64 host is needed first at the L8 libc++ gate
used as a release criterion (section 6.4).

### 1.3 Why this little, and what is cheaper to duplicate

The rule from the operator: move only what would otherwise be written
twice **with real drift risk**, since every move re-gates AArch64.

**Real drift risk** means a table or plan where a silent difference
is a wrong answer that no x86 test would notice, because both targets
must give the same observable result. R1's contents are all of that kind.
The worst one is already a bug waiting to happen: the libm names for
`fp128`. On AArch64 `long double` is `fp128`, so `sinl` is right. On
x86-64 an explicit `fp128` (`__float128`) must call `sinf128`, and
`x86_fp80` must call `sinl` (`data/abi/12-libcalls.llc{19,22}.s`, both
versions alike). The tables in `hod_cg/src/sym.rs:123-283` and in
`hod_a64/src/fpintr.rs:153-174` are keyed by IR type alone. A copy for
x86-64 would get this wrong in one of the two places. Moved once, with a
`(type, target)` key, it is right in both.

**Cheaper to duplicate:**

- instruction kernels: carry chains, min/max with NaN and ±0, saturation,
  funnel shifts;
- dead-instruction emulation;
- odd-leaf clearing;
- the dispatch.

These are *sequences*, not decisions. Their rules are specified in
`spec/codegen.md` §5.5 and the x86 version is a rewrite in another
instruction set anyway. A shared abstraction over two instruction sets
costs more than the ~1,500 lines it saves, and it re-gates AArch64 on
every change. Drift is caught instead by **shared seeds**: each such rule
gets an IR seed in `tests/ir/` that runs on both targets. The 17 drift
points found by reading the groups (listed in section 8, risk 7) each
become one seed in X-together.

**Gate for R1:** byte-identical AArch64 objects for the IR corpus and
the AArch64 seeds, before and after (`hod` with `--emit obj`, `cmp`).
R1 changes no output, so any difference is a bug in the move.

## 2. What x86-64 changes in the group contract

The contract (`spec/codegen.md` §2-4, §8) stays. These are the points
where x86-64 fills it differently. Each becomes text in `spec/codegen.md`
§5.6, written by S0.

### 2.1 Registers

| role | AArch64 (§5.5) | x86-64 (proposed) |
|---|---|---|
| general pool | `x9`-`x14`; the save set is empty | the **save set** `rbx`, `r12`, `r13`, `r14`, `r15`, saved in every function (spec §2.1, §5.6) |
| holdable (besides the pool) | `x0`-`x8`, `x15` | `rsi`, `rdi`, `r8`, `r9` |
| never holds a value (fixed-register temporaries) | — | `rax`, `rcx`, `rdx` |
| scratch | `x16`, `x17` | `r11`, `r10` |
| vector pool / holdable | `v16`-`v29` / `v0`-`v7` | `xmm8`-`xmm13` (SysV has no callee-saved xmm: displaced at calls by §4.4) / `xmm0`-`xmm7` |
| vector scratch | `v30`, `v31` | `xmm14`, `xmm15` |
| landing-pad data | `x0`, `x1` | `rax`, `rdx` (stored at once by the landing pad) |
| frame pointer | `x29` | `rbp` |

**The fixed registers.** x86-64 has them where AArch64 has none:

- division uses `rax`/`rdx`;
- variable shifts use `cl`;
- wide multiply uses `rdx:rax`;
- returns use `rax`/`rdx`/`xmm0`/`xmm1`;
- variadic calls set `al`.

The proposal makes them cost nothing by taking `rax`, `rcx` and `rdx`
out of the holdable set. A lowering may then clobber them without asking
the driver. Incoming arguments in `rcx`/`rdx` go to their homes in the
prologue (§4.8), as any argument does that the policy does not hold.

**One rule for deferral (§4.6).** An operand evaluated straight into an
argument register must not clobber an argument already placed.
`rcx`/`rdx` are argument registers, so an instruction whose lowering
uses a fixed register (`udiv`/`sdiv`/`urem`/`srem`, variable shifts,
wide multiply) is **not deferrable** into a call argument on x86-64. It
is computed before the argument window. S0 states this as a `Target`
query, `defers(inst) -> bool`, or the equivalent the driver already has.

**Pins and `nest`.** A lowering may pin at most four general registers
of the pool (§4.2's minimum, satisfied: the pool has five). `rep movs`
is not used, since a large `memcpy` is a call (R1's plan), so `rsi`/`rdi`
need no claim. `nest` (r10) is refused as `x64:nest`, which resolves
spec §5.6's open point: the corpus samples have no real use of it
(`data/corpus/census.out`, one false match).

### 2.2 Two-operand instructions

`dst = a op b` becomes `mov t, a; op t, b; [mov dst, t]`. The group
helpers take care of the aliasing:

- if `dst` is `b` and `op` does not commute, compute in a temporary;
- for `sub`, `shl`/`shr`/`sar` and `div`, the operand order is fixed by
  the instruction;
- `lea` gives a three-operand `add` with no flags, and a three-operand
  scaled index.

This adds one `mov` per binary operation at worst. At `-O0` `llc` emits
the same `mov`.

### 2.3 Flags

`cmp`/`test` and the `jcc`/`setcc`/`cmovcc` that read them may be fused
(§4.6, as on AArch64). The rule for x86-64:

- between the instruction that sets the flags and the one that reads them,
  only flag-preserving glue may be emitted: `mov`, `lea`, `movzx`,
  `push`/`pop`;
- **not** `xor r, r` to zero a register (use `mov r32, 0`), and not
  `inc`/`dec`/`add`/`sub`/`neg`/`shl`;
- the zeroing idiom `xor` is allowed only where no flags are live.

A group test that disassembles every fused pair checks this.
`setcc` writes 8 bits; `movzx r32, r8` follows it.

### 2.4 Memory operands: not folded in v1

Measured with `llc 22 -O0` for x86-64 on the 70 sampled modules
(`data/fold/fold.out`, script `data/fold/fold.py`):

- 7,003 instructions, of which 1,008 are ALU instructions;
- only **124** of those have a memory operand: 12% of ALU instructions,
  1.8% of all instructions;
- for comparison: 954 frame loads, 1,113 frame stores, 1,020 IR loads;
- 24,955 text bytes in all.

Even `llc` folds rarely at `-O0`. Folding would save at most about 2%
of the instructions. In exchange it would complicate the use-site
rules of §4.2 (an operand that is an address rather than a register).
**Decision:** no load folding in v1. It is a later option, measured
against these numbers. Stores of immediates (`mov [m], imm32`) and
compares with an immediate are not folding, and are used.

### 2.5 Narrow registers

The width invariant (spec §2.2: bits above the width are unspecified)
carries over unchanged. Three x86 facts the helpers must respect:

1. 32-bit operations zero bits 32-63; 8- and 16-bit operations do
   **not**. So `movzx`/`movsx` extend where the invariant requires it, as
   AArch64's `uxtb`/`sxtb` do.
2. The byte registers `spl`, `bpl`, `sil` and `dil` need a REX prefix.
   `ah`, `bh`, `ch` and `dh` are never used: an encoder test must show
   that `hod_mc_x64` emits REX for byte registers 4-7.
3. 16-bit operations need `0x66`. They are avoided where a 32-bit
   operation gives the same low 16 bits (add, sub, logic, shifts left).

### 2.6 Value classes by type

| type | class | lowering |
|---|---|---|
| i1-i64, ptr | Gpr | as above |
| i128 | Mem (as on AArch64) | limb pairs; `mul` inline (`data/abi/04-i128.llc*.s`); `sdiv`/`udiv`/`srem`/`urem` call `__divti3`/`__udivti3`/`__modti3`/`__umodti3` (R1's table) |
| float, double | Fpr (`xmm`, low lane) | SSE2 scalar: `addsd`, `ucomisd`, `cvtsi2sd`, ... ; constants through a GPR (`movabs` + `movq`), no island |
| half, bfloat | Fpr | through float with `__extendhfsf2`/`__truncsfhf2` (`data/abi/12-libcalls`), passed in xmm (`data/abi/02-fp`) |
| fp128 | Fpr (an xmm holds 128 bits) | runtime calls only (`__addtf3`, ..., `sinf128`); constants from a 16-aligned island, RIP-relative |
| **x86_fp80** | **Mem** (16-byte slot, 10 used) | `fld` → x87 operation → `fstp` within one lowering; the x87 stack is empty between lowerings; a call result in `st0` is stored at once (`fstp`) |
| vectors (no AVX) | Fpr up to 128 bits, Mem above | SSE2 packed operations; the lane loop for the rest (R3) |

**x87 in memory only** is the core simplification. Every `x86_fp80`
operation loads its operands onto the x87 stack, operates and stores the
result. No x87 register lives across a lowering, so the x87 stack never
needs modelling and nothing is displaced at calls.

The same approach covers conversions:

- `fptosi` saves the control word, sets truncation (`fnstcw`/`fldcw`),
  does `fistp` and restores the control word (`data/abi/03-x87.llc*.s`);
- compares use `fucomip`, as llc does.

Its cost is about 2 memory operations per x87 instruction. Corpus
counts are in 7.2: `x86_fp80` is in 10 of the 39 targeted modules and in
none of the 70 random ones.

### 2.7 Atomics

What `kiln` and clang write for x86-64 enables `+cx8` but **not
`+cx16`**. The attribute groups of all 109 sampled modules read
`+cmov,+cx8,+fxsr,+mmx,+sse,+sse2,+x87` with cpu `x86-64`
(`data/corpus/census.out`, "target attributes"). So:

- **1-8 bytes:** `mov` for load; `xchg` for a `seq_cst` store (llc 19 and
  22, `data/abi/12-libcalls`); `lock xadd`/`lock add`/... for
  `atomicrmw`; a `lock cmpxchg` loop for `nand`/`min`/`max`; `mfence`
  for a `seq_cst` fence.
- **16 bytes:** `__atomic_*_16` calls from libatomic, as llc does without
  cx16 (`data/abi/12-libcalls`). `cmpxchg16b` is used only with `+cx16`.
  Until a package needs it, `+cx16` is refused as `x64:feature:+cx16`;
  the encoder already has the instruction.

libatomic for x86-64 exists on the host
(`/usr/lib/gcc-cross/x86_64-linux-gnu/14/`).

### 2.8 Thread-local storage

These are `llc`'s choices (`data/abi/13-tls*.llc*.s`, 19 = 22). The
model choice is `hod_cg/access.rs`'s, which is already tested for x86-64.

| model | when (PIE) | sequence |
|---|---|---|
| LE | `dso_local`, internal | `mov rax, fs:0; lea rax, [rax + x@TPOFF]`, or the `%fs:x@TPOFF` operand |
| IE | external | `mov rax, [rip + x@GOTTPOFF]` (`R_X86_64_GOTTPOFF`), then `fs:[rax]` |
| GD | DSO, external | `data16 lea rdi, [rip + x@TLSGD]; data16 data16 rex64 call __tls_get_addr@PLT`: exactly these bytes, which linkers relax |
| LD | DSO, local | `lea rdi, [rip + x@TLSLD]; call __tls_get_addr@PLT`; then `x@DTPOFF` |

GD and LD are calls. They are lowered as a call that displaces every
caller-saved register (§4.4), just as `llvm.threadlocal.address` is
lowered on AArch64. TLSDESC is not used: llc does not use it on x86-64
by default.

**Debug info:** a TLS variable location on x86-64 is refused today
(`crates/hod_dwarf/src/global.rs:99`). It needs
`DW_OP_const8u x@DTPOFF; DW_OP_GNU_push_tls_address` with
`R_X86_64_DTPOFF64`. That is a small part of X-debug.

### 2.9 Frame, red zone, alignment, probes, PIC, code models

**Frame.** The frame of spec §5.6, unchanged:

- `push rbp; mov rbp, rsp`;
- `push rbx, r12, r13, r14, r15`, always all five;
- `sub rsp, imm32`, patched.

With the return address, the six pushes are 56 bytes, so the patched
size is ≡ 8 (mod 16). `llc` saves only the registers it uses
(`data/abi/14-frame.llc*.s`). hod saves all five so that the prologue
and the CFI keep one shape. That costs at most 18 bytes and 10
instructions per function (`push rbx` is 1 byte, `push r12`-`r15` are 2
each, and the pops are the same).

**Red zone: not used.** Decided:

- llc uses it only in leaf functions with small frames (seen in the
  variadic callee, `data/abi/08-varargs.llc*.s`);
- hod's frame is always `rbp`-based and patched;
- the saving (one `sub rsp`) is not worth a second frame shape;
- a leaf function that is later instrumented, or a signal handler, makes
  it a correctness risk.

`noredzone` is therefore accepted and changes nothing.

**Stack alignment.** `rsp` is 16-aligned at every `call`.

**Refused by name, all with 0 uses in the samples:**

| construct | refusal |
|---|---|
| `"probe-stack"` | `x64:probe-stack` |
| `"stackrealign"`, and an `alloca` aligned above 16 | `x64:stackrealign` |
| `cf-protection` module flags (IBT/SHSTK) | `x64:cf-protection` |
| a `"Code Model"` module flag other than small | `x64:code-model` |

The census found none of the four in the samples (grep in
`data/corpus/census.py`'s inputs: 0 matches). A frame larger than 2 GiB
is `limit:frame-size`.

**PIC/PIE.**

- Every module carries "PIC Level" and "PIE Level".
- Calls are `call x@PLT` (`R_X86_64_PLT32`) unless dso-local.
- Addresses: `lea r, [rip + x]` for dso-local, else
  `mov r, [rip + x@GOTPCREL]` with `R_X86_64_REX_GOTPCRELX`, so that
  linkers may relax it.
- Data: `R_X86_64_64` (or PC32 in `.eh_frame`).

**Code model:** small only. A RIP-relative `rel32` reaches everything.

### 2.10 Branches and constants

- **Branches:** `jcc rel32` and `jmp rel32` reach ±2 GiB, so there is
  **no far mode** on x86-64 and the §6.3 retry never fires. The short
  forms are covered in section 5.
- **Data islands** (§7.5) are kept for vectors and `fp128`, loaded with
  RIP-relative `movaps` (the island is 16-aligned).
- **Integer constants:** `mov r32, imm32`, which zero-extends;
  `mov r64, simm32`; `movabs` otherwise.

## 3. ABI outline for `spec/abi-x64.md`

At the IR level, as LLVM's x86-64 backend applies it. Each rule was
checked by compiling `data/abi/NN-*.ll` with `llc` 19 and 22
(`-mtriple=x86_64-unknown-linux-gnu -O0 -fast-isel=0
-relocation-model=pic`, `data/abi/run.sh`). The two versions agree on
every rule. They differ in two places, both with no ABI effect:

- the padding byte: `0x90` vs the default;
- the `ctlz` sequence: LLVM 19 uses `bsr` + `cmov`; LLVM 22 preloads 63
  and relies on `bsr` leaving its destination unchanged for a zero source.

The outline below is what the X-abi package turns into the spec.

**Integers and pointers** (`01-int`, `11-i1`):

- `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`, then 8-byte stack slots in
  order.
- `zeroext`/`signext` on i1/i8/i16: the producer extends to 32 bits. On
  the stack, a narrow value is written by a 32-bit store into its 8-byte
  slot.
- A plain `i1` argument is passed as is, and the callee masks
  (`and $1`). A plain `i1` return is masked by the caller.
- Returns are **not** extended beyond their width by the callee, even
  with `signext i8`: `movb` only. With `zeroext i1` the callee does
  `andb $1` and the caller extends.

**Floating point** (`02-fp`):

- `xmm0`-`xmm7`, then 8-byte stack slots (a float takes a 32-bit store).
- `half`, `bfloat` and `fp128` travel in `xmm`. An `fp128` on the stack is
  16 bytes, 16-aligned.

**`x86_fp80`** (`03-x87`):

- An argument goes in memory: 16 bytes, 16-aligned, never in a register.
- The return value is in `st0`; `{x86_fp80, x86_fp80}` returns in `st0`,
  `st1`.

**i128** (`04-i128`):

- An argument takes a GPR pair in order, **never split** between
  registers and the stack. With five i64 arguments before it, an i128
  goes to the stack and `r9` stays unused.
- The return value is in `rax:rdx`.

**Aggregates passed directly** (first-class `{...}`/`[...]`, `05-aggr`):

- Each leaf takes the next register of its class. When the registers run
  out, the leaf goes to the stack. A `{i64, i64}` may be split between
  `r9` and the stack: only i128 is kept whole.
- `{i128}` takes a pair.

**Returns** (`05-aggr`):

| IR return type | where |
|---|---|
| `{double, double}` | `xmm0`, `xmm1` |
| `{i64, double}` | `rax`, `xmm0` |
| `{float × 4}` | `xmm0`, `xmm1`, then `st0` (element 2), `st1` (element 3) |
| `{double × 3}` | `xmm0`, `xmm1`, `st0` |
| `{i64, i64, i64}`, `[3 x i32]` | `rax`, `rdx`, `rcx` |
| `{ptr, i32}` | `rax`, `edx` |
| `{float × 5}`, 4 × i64 | **demoted to sret**: hidden pointer in `rdi`, returned in `rax` |

The x87 parts are why `{float×4}` must be refused or lowered with care.
kiln and clang never return such a type: C structs come back coerced or
through `sret`. Proposal: implement the x87 return parts in X-x87, and
refuse them as `x64:ret-x87-part` until then.

**Pointer attributes** (`06-ptrattrs`):

- `sret`: in `rdi`; the callee returns it in `rax`. The caller does not
  rely on that.
- `byval(T)`: copied into the outgoing area at T's alignment (at least
  8).
- `nest`: `r10` (refused, 2.1). `inreg`: ignored.
- `swiftself`: `r13`. `swifterror`: `r12` (refused unless `swiftcc`; 0
  in the corpus).

**byval appears on x86-64 where AArch64 passes a pointer.** In the
targeted sample, 4 of 11 torture modules and 2 of 28 kiln modules
(`data/corpus/census-targeted.out`) use `byval` on x86-64. It is part of
X-call, not a later package.

**Vectors, without AVX** (`07-vec`):

- 128-bit vectors in one `xmm`. `<2 x i32>` and `<2 x float>` are widened
  into one `xmm`.
- `<8 x float>` takes 2 `xmm`. `<4 x i1>` is promoted to `<4 x i32>`.
- A `<1 x i64>` is a scalar in a GPR (`rdi`/`rax`).
- The ninth vector goes to the stack, 16-aligned.
- Return: `<16 x float>` in `xmm0`-`xmm3`; `<32 x float>` is demoted to
  sret.
- Complex `float` is coerced to `<2 x float>` by both front ends (14
  mentions in the targeted sample), and complex `bf16` to `<2 x bfloat>`.
  **So vectors reach calls on x86-64 in code with no vector source.** This
  is the main reason X-vector is on the libc++ path (7.2).

**Varargs** (`08-varargs`):

- The caller sets `al` to the number of vector registers used (an upper
  bound is allowed; llc writes the exact count).
- `x86_fp80` varargs go on the stack; i128 in a pair.
- The callee's prologue saves the register save area: 6 GPRs (48 bytes),
  then 8 xmm (128 bytes), the xmm part only if `al ≠ 0` (`test al, al;
  je`).
- `va_start` writes `{gp_offset, fp_offset, overflow_arg_area,
  reg_save_area}` as `{i32, i32, ptr, ptr}`, with gp_offset = 8 × named
  GPRs and fp_offset = 48 + 16 × named xmm.
- The `va_arg` instruction is handled by llc but **never written** by
  clang or kiln for x86-64 (census: 0 in 109 modules): they expand it in
  IR. Refuse `inst:va_arg` on x86-64 as on AArch64.

**musttail** (`09-musttail`): a variadic thunk becomes
`jmp target@PLT`, with `al` and the argument registers untouched. The
`TargetStackArgs` hook of `hod_cg/src/abi.rs` serves it.

**Edge cases** (`10-edges`, where several of the rules above were
checked):

- `{i64, i64}` after five i64 is split: `r9` and `8(%rsp)`;
- `{i128}` after one i64 takes `rsi:rdx`;
- `<3 x float>` and `<2 x i64>` take one `xmm`;
- a `<32 x float>` argument takes `xmm0`-`xmm7`, while its return is
  demoted to sret (`movaps` to `(%rdi)`, `rdi` returned in `rax`);
- `fp128` after eight doubles and a float goes on the stack, 16-aligned;
- a plain `i1` argument is passed unextended (`pass_i1`).

**Runtime routines** (`12-libcalls`), one column of R1's table:

| type | routines |
|---|---|
| fp128 | `__addtf3`, `__multf3`, `__lttf2`, ..., and the libm names `sinf128`, `fmodf128` |
| x86_fp80 | `sinl`, `fmodl`, ...; `fsqrt` inline; `__trunctfxf2`/`__extendxftf2`; `__floattixf`/`__fixxfti` |
| i128 | `__divti3`, `__udivti3`, `__modti3`, `__umodti3` |
| half | `__extendhfsf2`, `__truncsfhf2` |
| float, double | `floor`, `ceil`, ... are libcalls without SSE4.1 (llc: `call floor@PLT`) |

llc tail-calls a libcall with `jmp` when it is in tail position. hod
does not have to.

**Cross-checks for L5.** The generated caller/callee grid of
`spec/harness.md` with clang for x86-64 (`clang-22 --target=x86_64-...`
links with the cross gcc). Each side runs under qemu.

## 4. EH, unwind tables and DWARF

**Already in place** (`crates/hod_eh/src/target.rs:77-95`, the
`X86_64` table), and checked against llc
(`data/abi/15-eh-encodings.out`, `eh_invoke.ll`, llc 19 and 22, PIC and
static):

| item | value | matches llc |
|---|---|---|
| code alignment factor | 1 | yes |
| data alignment factor | -8 | yes |
| return address column | 16 (rip) | yes |
| CIE initial instructions | `def_cfa rsp(7), 8; offset r16 at cfa-8` | yes (`data/abi/14-frame`) |
| FDE pointer encoding | 0x1b (pcrel \| sdata4) | yes |
| personality encoding | 0x9b (indirect \| pcrel \| sdata4) | yes, **PIC only**: static llc writes 0x03 (udata4) and LSDA 0x03 |
| LSDA encoding | 0x1b | yes, PIC (static: 0x03) |
| relocations | `R_X86_64_PC32` | yes |
| section type | `SHT_X86_64_UNWIND` | yes |

**The static case.** hod always writes the PIC encodings. A PC-relative
pointer is valid in a non-PIC executable too: the linker resolves it
either way. So the static difference is byte parity with llc, not
correctness. It is recorded as a known difference in X-call's
`spec/landed/` record, not implemented.

**CFI rows for the hod frame** (as llc writes them,
`data/abi/14-frame.llc*.s`):

- `push rbp` → `def_cfa_offset 16; offset rbp(6), -16`;
- `mov rbp, rsp` → `def_cfa_register rbp(6)`;
- after that, each push gets one `offset` row: `rbx(3)` at -24, `r12`
  at -32, `r13` -40, `r14` -48, `r15` -56;
- epilogue: `pop rbp` → `def_cfa rsp(7), 8`.

Because the CFA is `rbp + 16` after the second instruction, nothing
changes when the frame grows. It is the same shape as on AArch64 (one
row set per function).

**DWARF register numbers** (SysV psABI, figure 3.36):

| registers | DWARF numbers |
|---|---|
| rax, rdx, rcx, rbx, rsi, rdi, rbp, rsp | 0-7 |
| r8-r15 | 8-15 |
| rip (return address) | 16 |
| xmm0-15 | 17-32 |
| st0-7 | 33-40 |

They belong in `spec/abi-x64.md`. `hod_x64::reg` maps `PReg` to them.

**Frame base:** `DW_OP_reg6` (rbp), given by the `frame_base` parameter.
Variables are `DW_OP_fbreg -n`.

**Hard-wired to AArch64 (to change), file:line:**

  (2.8);
- `crates/hod_cg/src/emit/mod.rs:300`: single-byte padding. Use

- `crates/hod_cg/src/label.rs:98-110`: the displacement convention

The subagent's reading of `hod_dwarf` and `hod_obj` found nothing else

## 5. What `hod_mc_x64` lacks

**Present** (`crates/hod_mc_x64/src/`, L1-tested in `tests/l1`):

- every integer ALU, shift, bit-test, `imul`/`mul`/`div`, `movzx`/`movsx`
  and `cmov`/`setcc` form;
- SSE2 scalar: `movss`/`movsd`/`movq`/`movd`, arithmetic, `ucomis`,
  `cvt*`;
- `call`/`jmp` direct and indirect; `jcc`/`jmp` rel8 and rel32;
- `push`/`pop`, `lea`, RIP-relative operands, `fs`/`gs` segments;
- `lock`, `xchg`, `xadd`, `cmpxchg`, `cmpxchg8b`/`16b`, fences;
- `ud2`, `int3`, `endbr64`, `nop` of 1-15 bytes;
- the TLS GD and LD sequences;
- `Site{offset, fixup, addend}` and `Fixup::patch`.

**Nothing blocks S0 or the four core groups.**

**Branch policy (no relaxation pass).** This replaces relaxation:

- **backward branches** (the label is bound) use rel8 when the distance
  fits, rel32 otherwise;
- **forward branches** use rel32.

The policy needs no relaxation, no second pass and no far mode (2.10).
Its cost: a forward `jcc` is 6 bytes instead of 2, and a `jmp` 5 instead
of 2. Measured on llc 22's `-O0` objects for the sampled modules
(`data/fold/branches.py`, `branches.out`, 82 objects, 38,042 text
bytes): llc wrote 409 forward rel8, 16 forward rel32, 29 backward rel8
and 9 backward rel32 branches. Making the 409 forward rel8 branches
rel32 adds 1,427 bytes, **+3.8% of text**.

A later option, measured then, is a per-function relaxation in the
chunk. It is not needed for correctness.

**Patch convention.** `label.rs` hands `patch` the distance from the
fixup's offset. For x86-64 the encoded displacement is from the end of
the instruction, which is the end of the field here. So
`hod_x64::fixup_field` patches `disp = target − (at + field_size)`. This
is a target-side rule; `label.rs` does not change.

**Missing, and when it is needed:**

## 6. Oracle and validation on an AArch64 host

### 6.1 Is x86-64 `llc -O0` trusted?

On AArch64, FastISel was caught miscompiling (design 0001, §10.1: the
`i1` and `zext` reproducers). For x86-64:

| experiment | result | data |
|---|---|---|
| §10.1 reproducers on x86-64 | FastISel and SelectionDAG both right (exit 0; exit 224 expected); x86 GlobalISel crashes llc 19 and segfaults llc 22 (experimental; irrelevant) | `data/oracle/repro.out`, `fastisel-i1.ll`, `globalisel-zext.ll` |
| the 42 `tests/ir` seeds × LLVM 19, 22 × {`-O0`, `-O0 -fast-isel=0`, `-O2`} under qemu | **all 252 match** their expected output | `data/oracle/seed-oracles.tsv`, script `seed-oracles.py` |
| `hod_interp`'s 13 random batches (756 programs: default, sized, vector), retargeted to x86-64 | all 78 builds print **exactly** the native aarch64 SelectionDAG output | `data/oracle/batches.out`, `batches.sh` |

**Decision.** x86-64 FastISel showed no bug class, but the oracle stays
`llc -O0 -fast-isel=0`, as on AArch64. The reasons:

- one rule for both targets;
- SelectionDAG is the selector `-O2` uses, so it is the more exercised
  path;
- it costs nothing measurable.

x86-64 FastISel output is accepted as a **second opinion** in
investigations.

### 6.2 What emulation costs

| measurement | native aarch64 | qemu x86-64 | ratio | data |
|---|---:|---:|---:|---|
| one seed run (mean, 42 seeds) | 0.0027 s | 0.028 s | ~10x, +25 ms | `seed-oracles.tsv` |
| kiln corpus test: build (llc + link) | 0.069 s | 0.075 s | 1.09x | `emu-cost.out` (15 tests) |
| kiln corpus test: run | 0.002 s | 0.026 s | +24 ms | `emu-cost.out` |
| kiln corpus test: build + run | 0.071 s | 0.101 s | **1.42x** | `emu-cost.out` |
| compute-heavy loop (`emu-loop.c`) | 0.76 s | 5.56 s | **7.3x** | `emu-loop.out` |

**Per-test start-up.** The +24 ms is qemu's start-up (loading the guest
`ld.so` and libc through `-L`). It dominates every small test. For the
corpus (3,347 modules per LLVM version: 1,777 torture and 1,570 kiln,
`docs/status/corpus.md`) it adds about 80 s
of CPU, which is 20 s of wall time at `-j 4`. All 15 tests printed the
same output and exited alike on both targets.

**libc++.** The AArch64 baseline takes 3,176 s at `-j 3`, mostly in
building. Projected for x86-64:

| part | added cost |
|---|---|
| per-test start-up | 9,247 runs × 24 ms ≈ 220 s CPU, about 75 s of wall time at `-j 3` |
| compute | ×7.3 on the time tests spend running, not measured per test |

So emulation adds roughly 5-15% to a libc++ run. Timeouts are scaled by
**8** (`--timeout 20` becomes 160) so that compute-bound tests do not
fail as timeouts.

### 6.4 When a real x86-64 host becomes necessary

**Not before the L8 libc++ gate is used as a release criterion.** Every
gate up to and including "libc++ hybrid and strict on x86-64 equal to
the x86-64 baseline" can be run emulated, because:

- the oracle is differential: both the llc build and the hod build run
  under the same qemu, so emulation artefacts cancel;
- the cost is 1.4x on corpus tests and about 1.1x on libc++.

A real host becomes **necessary** for these:

1. **The release-candidate gate (L8 strict as a release criterion, and
   L9).** qemu-user is not the CPU:
   - it does not model memory ordering: x86 TSO is emulated on a weaker
     host with barriers, so atomics tests pass for qemu's reasons;
   - signal and `ucontext` details;
   - timing-sensitive tests (`std::thread`: 130 libc++ test sources
     mention `thread`; `condition_variable::wait_for`);
   - CPU feature detection (`cpuid` is qemu's model).

   A pass under qemu is evidence, not a release proof.
2. **Debugger tests against real `ptrace`** (L7 full tier), unless the
   operator accepts `gdb-multiarch` plus the qemu gdbstub as the L7
   oracle.
3. **Measuring hod's own speed when hod runs on x86-64.** hod is a cross
   compiler here: its speed numbers on this host are AArch64 numbers.
   The project's performance targets (`docs/VALIDATION.md`
   "Performance") for users on x86-64 need an x86-64 machine.

Until then, x86-64 status is reported as "emulated".

### 6.5 Corpus capture for x86-64

The corpus is captured by intercepting kiln++ (`HOD_CORPUS_CAPTURE`) and
has no `--target`. For this design a sample was recompiled:

- `data/corpus/capture-sample.py` takes every Nth LLVM-22 manifest entry,
  with the entry's own arguments plus `--target=x86_64-unknown-linux-gnu`
  (kiln++ in the kiln repository, or `clang-22` for torture);
- 70 of 75 modules were captured, 46 kiln and 24 torture. The 4 kiln
  multi-command tests and 1 torture test failed;
- a targeted list of 40 (`targeted.txt`) was chosen for fp128, `va_start`,
  atomics, TLS, vectors and half/bfloat. 39 were captured.

For the real corpus, H1 adds `xtask corpus capture --target x86_64`. It
is the same interception with the target passed through. The expected
outputs come from the llc + qemu run, and **must equal the AArch64
expected outputs** for tests without target-dependent output. That is a
free cross-check of kiln's x86-64 lowering, and differences go to the
kiln agents.

### 7.1 The critical path

```
day 1 ─┬─ S0 skeleton ──┬─ X-int ─────┐
       │                ├─ X-mem ─────┤ (first vertical slice, 7.3)
       │                ├─ X-control ─┤
       │                └─ X-call ────┴─┬─ X-float ──┐
       │                                ├─ X-aggr ───┼─ X-together: corpus sample gate ─┐
       │                                └─ X-intr ───┘                                  │
       ├─ H1 harness ─────── (needed by the slice gate) ─────────────────┘              │
       ├─ A1 ABI spec + abi.rs ─ (needed by X-call)                                     │
       ├─ R1 shared tables ─── (needed by X-float, X-intr, X-control's switch)         │
```

**The critical path is S0 → X-call → {X-float, X-aggr, X-intrinsic} →
X-together → {X-x87, X-vector} → libc++.** Everything off it is sized to
finish before its consumer:

- H1, A1 and R1 finish before S0's dependants need them;
- E1 and E2 before X-x87 and X-vector;
- L0 before libc++.

### 7.3 The first vertical slice

**Goal.** A C function with integers, memory (locals, globals, a
pointer argument), a loop and a branch, and a call to a function of the

**What the slice is:** S0 + X-int + X-mem + X-control + X-call (without

- the encoder's bytes, the relocations and the frame;
- the call sequence, the linker matrix and qemu;
- the harness, end to end.

**The seed** is `tests/ir/x64-slice.c` (compiled by clang to `.ll`, then
committed as a seed), with `;@ args`, `;@ exit` and the expected output.
The gate also runs the AArch64 seeds that use only these groups and
compares their output on both targets.

### 7.5 Parallelism with eight implementers

**Day one, before the skeleton**, with no dependency between them:

| slot | package |
|---|---|
| 1 | S0 |
| 2 | H1 |
| 3 | A1 (against R1's interface, stated in R1's first commit) |
| 4 | R1 |
| 5 | E1 |
| 6 | E2 |
| 7 | L0 |
| 8 | free, or a second H1 hand on capture |

**When S0 lands:** X-int, X-mem, X-control and X-call run in four slots.
X-aggr can start at once too, since it does not need R1.

**As E1, E2 and R1 finish:** their slots take X-float, X-aggr and
X-intrinsic. R3 starts as soon as R1 is merged.

**After X-together:** X-x87, X-atomic, X-tls and X-vector run in
parallel. X-libcxx needs all of them and L0.

**Ownership.** `hod_x64` gets the `hod_a64` rule (`lib.rs` header):

- one module per group;
- the dispatch in `target.rs` is final after S0;
- shared helpers are added to `common`, each in its own function;
- one line per group in the harness's groups file.

`hod_cg` is touched only by R1, R3 and S0's facade lines, so the groups
never conflict there.

## 10. Review (2026-11-12): accepted, with these changes

1. **Target features that only permit instructions are accepted and
   ignored, not refused.** hod's x86-64 code uses the base instruction set
   (SSE2), which runs on every x86-64 CPU, so `+sse3` ... `+sse4.2`,
   `+popcnt`, `+lzcnt`, `+bmi`, `+bmi2`, `+fma`, `+f16c`, `+movbe`,
   `+avx`, `+avx2` and any `target-cpu` are correct to accept without
   using them: a module built with `-march=x86-64-v3` or `-march=native`
   must not be declined as a whole. This replaces the refusals
   `x64:feature:+popcnt` and `+lzcnt` of 7.4 and risk 11. What is still
   refused, by name, is what changes the ABI or the meaning:
   - a vector wider than 128 bits as an argument or return value of a
     function whose features include AVX (it travels in `ymm`/`zmm`):
     `x64:wide-vector-abi`;
   - AVX-512 mask or 512-bit facts with the same rule;
   - `-sse`, `-sse2`, `+soft-float`, `-x87` with an `x86_fp80` use,
     `+retpoline*`, `+harden-sls*`, and the like, as on AArch64
     (`spec/codegen.md` 5.5.2);
   - a feature hod has not judged stays `attr:target-feature-unknown`.
   The judged list is a table in `hod_x64::features` with one line of
   reason per feature; S0 writes it, each group may extend it.
2. **`+cx16` is implemented, not refused.** A program built with `-mcx16`
   is not linked with libatomic, so a call to `__atomic_*_16` would not
   link. With `+cx16` X-atomic uses `lock cmpxchg16b` inline as `llc`
   does; without it, the libatomic calls of 2.7.
3. **L0 starts as an investigation** that builds libc++ for x86-64 under
   `.build/`, finds exactly what `kiln:xtask/src/libcxx/` needs (a target
   triple and an executor prefix), and ends in one precise request to the
   kiln agents, or a hod-side wrapper if the request is refused.
4. **A1 does not wait for R1.** It writes the spec, the rule tests against
   `llc` and `assign` with a private copy of the leaf walk, marked for
   replacement; it adopts `hod_cg`'s walk when R1 has landed.
5. **`gdb-multiarch`** is provisioned (container-local, in
   `scripts/provision.sh` of the context repository) when X-debug starts;
   lldb through the qemu gdbstub is the fallback.
6. **`cf-protection`** stays refused for now (0 in the samples), but it is
   a known default of some distributions' compilers: the first census of
   the full x86-64 corpus and of the operator's real environment decides
   whether IBT (`endbr64`, `.note.gnu.property`) becomes a package.
7. A real x86-64 host: the operator's decision (2026-11-12) is to go as
   far as possible under qemu; the request is made again when the gates of
   6.4 are reached, with the measured cost.
