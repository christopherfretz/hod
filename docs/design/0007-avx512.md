# Design 0007: AVX-512

Status: proposed with WP-208, which implements its first steps. A design
first: what hod needs to build the AVX-512 code of real x86-64 programs at
`-O0`, how each piece is checked on a host that cannot execute AVX-512,
and in which order the work goes.

Measurements ran on the shared AArch64 host with `llc`, `llvm-mc` and
`llvm-objdump` 19 and 22, clang 19 and 22 and `qemu-x86_64` 10.0.13.
The census is the second real-project lane's (WP-200): the portable SIMD
library highway, its 28 core tests built for x86-64 at `-O0` by kiln with
the library's default targets; after WP-201 and WP-202 hod refuses 318
names there, 27 of the 40 objects fall back to `llc` whole, and 20 of
the 24 distinct modules refuse at least one intrinsic. The scripts that
count it (`docs/design/0007-data/families.py`, `gen_calls.py`,
`llc_mnemonics.py`) read the lane's saved modules, which stay outside
the repository.

## Question

What is the smallest set of pieces that lets hod write correct code for
the AVX-512 intrinsics and the generic 512-bit IR a portable SIMD
library reaches, and what evidence can each piece get here?

**Answer.**

1. An **EVEX encoder** in `hod_mc_x64` (`src/evex.rs`): `zmm0`-`zmm31`,
   the three vector lengths, opmask registers with merging or zeroing,
   embedded broadcast, embedded rounding and SAE, and compressed
   displacements; plus the opmask instructions (`kmov*`, `kand*`, ...,
   which are VEX-encoded). Checked against `llvm-mc` 19 and 22 like
   every other encoder (L1).
2. **No new value representation.** A 512-bit vector is already a
   `Mem`-class value in a frame slot, a mask `<N x i1>` (N ≤ 64) is
   already a `Gpr`-class bit image (`mask.rs`, WP-132). AVX-512 code
   moves values in and out of scratch registers that no hod value ever
   lives in: `zmm16`-`zmm31` and `k1`-`k7`.
3. **Generic IR stays generic.** `select`, `icmp`, `bitcast`,
   `shufflevector` on 512-bit vectors and masks already compile in an
   AVX-512 function by the lane loops. The generic `llvm.masked.load`,
   `masked.store`, `masked.compressstore` and `masked.expandload` are
   written without any AVX-512 instruction at all (a lane loop over the
   mask's bits), at every width and with or without the feature. So they
   execute under `qemu-x86_64 -cpu max` and are checked by execution
   against `llc` (at a feature level the emulator runs).
4. **The `llvm.x86.avx512*` names are `llc`'s instruction**, one
   EVEX instruction per intrinsic between loads from and stores to the
   operands' slots, gated per function by the feature of clang's header.
5. **Evidence without execution.** No emulator on this host executes
   AVX-512 (section 4). Each intrinsic's lowering is checked by a
   *dataflow comparison* with `llc` 19 and 22 (section 4.2): the
   expression stored to the result is the same tree of instructions over
   the same input bytes. The harness runs the same tests by execution
   when a runner for AVX-512 code is named (`HOD_X64_AVX512_RUNNER`).
   **A real x86-64 host with AVX-512 is needed for execution evidence.**

## 1. Encoding: EVEX in `hod_mc_x64`

### 1.1 The prefix (measured)

`62 P0 P1 P2`, then opcode, ModRM, SIB, displacement, immediate (SDM
Vol. 2, 2.7):

| byte | bits |
|---|---|
| P0 | `R` `X` `B` `R'` `0` `mmm`: `R`, `X`, `B`, `R'` inverted; `mmm` the map (1 `0F`, 2 `0F38`, 3 `0F3A`, 5 and 6 the FP16 maps) |
| P1 | `W` `vvvv` (inverted) `1` `pp` (0 none, 1 `66`, 2 `F3`, 3 `F2`) |
| P2 | `z` `L'L` `b` `V'` (inverted) `aaa` |

- The `ModRM.reg` register's number is `R' R reg`: five bits, 0..31.
  A `k` destination (compares, `vfpclass`) or a general register leaves
  `R'` 1 (inverted 0).
- `vvvv` and `V'` are the second source's five bits; an unused `vvvv`
  is `1111` with `V'` 1.
- A register in `ModRM.rm` uses `B` for bit 3 and **`X` for bit 4**
  (there is no index); with memory, `X` and `B` extend the index and the
  base as in REX.
- `L'L` is the vector length (0 128, 1 256, 2 512), except in a
  register-register form with `b` set, where it is the rounding control
  (`{rn-sae}` 0, `rd` 1, `ru` 2, `rz` 3) and the length is 512; `{sae}`
  alone is `b` with `L'L` ignored by the processor; LLVM writes `00`
  there (measured: `vcvttpd2qq zmm0, zmm1, {sae}` is `62 f1 fd 18 7a
  c1`), and so does hod. An instruction without a `W` meaning (`WIG`)
  is written with `W` 0, as LLVM (`vpshufb`).
- `b` with a memory operand is the **embedded broadcast** `{1toN}`: one
  element read and repeated.
- `aaa` is the opmask register; **`k0` means "no mask"** (it can still
  be a destination or a source of the opmask instructions). `z` set is
  zeroing-masking `{z}` (lanes off are zeroed), clear merging (lanes off
  keep the destination's old value). `{z}` without a mask, and `{z}` on a
  store, are invalid: refused by the checked forms, rejected by
  `llvm-mc`.

`llvm-mc` 19 and 22 agree byte for byte on every form tried, and both
encode an instruction that has a VEX form with VEX when its operands
allow (`vpaddd xmm0, xmm1, xmm2` is `c5 f1 fe c2`). hod's EVEX
constructors always write EVEX (`62 f1 75 08 fe c2`); their L1 text
spells `{evex}` where a VEX form exists. The lowering decides which
encoding it asks for, not the encoder.

Examples (both majors):

| instruction | bytes |
|---|---|
| `vpaddd zmm0, zmm1, zmmword ptr [rax+64]` | `62 f1 75 48 fe 40 01` (disp8 1 = 64/64) |
| `vpaddd zmm0, zmm1, zmmword ptr [rax+32]` | `62 f1 75 48 fe 80 20 00 00 00` (32 is not a multiple of 64: disp32) |
| `vpaddd zmm0 {k1}{z}, zmm1, dword ptr [rax+4]{1to16}` | `62 f1 75 d9 fe 40 01` (disp8 1 = 4/4) |
| `vaddps zmm0, zmm1, zmm2, {rn-sae}` | `62 f1 74 18 58 c2` |
| `vpaddd zmm31, zmm30, zmm29` | `62 01 0d 40 fe fd` |
| `vmovdqu64 zmm16, zmmword ptr [rsp+128]` | `62 e1 fe 48 6f 44 24 02` |
| `vpmovusqb qword ptr [rax+8], zmm1` | `62 f2 7e 48 12 48 01` (N 8: an eighth of 64) |
| `vcvtph2pd zmm0, xmm1` | `62 f5 7c 48 5a c1` (map 5) |
| `kmovw k1, eax` | `c5 f8 92 c8` |
| `kmovq k1, rax` | `c4 e1 fb 92 c8` |

### 1.2 Compressed displacement (disp8*N)

The classic source of wrong bytes. With EVEX, an 8-bit displacement is
scaled by `N`: a displacement is written as `disp8 = disp / N` exactly
when `disp % N == 0` and the quotient fits in `-128..=127`; otherwise
`disp32` (never a `disp8` of the unscaled value). `disp == 0` with a base
other than `rbp`/`r13` has no displacement, as without EVEX; an absolute
field is always `disp32`. `N` comes from the instruction's **tuple
type** (SDM Vol. 2, 2.7.5, tables 2-34 and 2-35), the vector length and,
with broadcast, the element:

| tuple | `N` |
|---|---|
| full (FV), broadcast allowed | `VL/8` bytes; with `{1toN}` the element (4 or 8 by `W`, 2 for FP16) |
| full memory (FVM), no broadcast | `VL/8` |
| half (HV), broadcast allowed | `VL/16`; with broadcast the element (4) |
| half, quarter, eighth memory (HVM, QVM, OVM) | `VL/16`, `VL/32`, `VL/64` |
| quarter with broadcast (FP16 `vcvtph2pd`) | `VL/32`; with broadcast 2 |
| tuple-1 scalar (T1S), `vpcompress*`, `vcompressp*` | the element |
| 128-bit memory (M128: shift counts in an `xmm`) | 16 |

The encoder states `N` per member as `(divisor, fixed, broadcast
element)` and has one routine for the ModRM/SIB/displacement of an EVEX
memory operand (the non-EVEX routine of `inst.rs` with the scaling). The
L1 sweep of EVEX memory operands takes every form of "Memory operands"
plus the displacements `±N`, `±127N`, `±128N`, `128N`, `N ± 1`, `N/2`
through one member of each tuple at each length, and through a
broadcast, against `llvm-mc`.

### 1.3 The encoder API

It extends the VEX one (`src/avx.rs`) and keeps the crate's rules
(`const fn`, `Inst`, checked forms through `checked!`):

- `Zmm`: a vector register `0..=31` (`Zmm::new(n)`, `Zmm::from(Xmm)`,
  `.code()`); the length is an operand `Vl` (`X` 128, `Y` 256, `Z`
  512), so `Zmm(3)` with `Vl::X` is `xmm3`. `Xmm` stays `0..=15` for
  every non-EVEX constructor.
- `K`: `K0`..`K7`. `Masking { k, zero }` with `Masking::NONE`,
  `Masking::merge(k)`, `Masking::zero(k)`; `{z}` with `k0` is refused
  by the checked forms.
- Families by operand shape, each member `(map, pp, W, opcode, lengths,
  tuple, mnemonic)`: `E3` (`op dst{k}, a, b`), `E3Imm`, `E2` (`op
  dst{k}, src`), `E2Imm`, `EShift` (`op dst{k}, src, imm8` with `dst` in
  `vvvv` and a `/digit`), `ECmp` (a `k` destination: `vpcmp*`,
  `vfpclass*`, `vptestm*`), `ECvt` (a destination of another length:
  the conversions), `EStore` (`op m/dst{k}, src`: `vpmov*` truncations,
  `vpcompress*`, `vcompressp*`), `EMov` (`vmovdqu8/16/32/64`,
  `vmovups`, `vmovupd`: load, store, register), and the mask moves
  `vpmov*2m`/`vpmovm2*`.
- Operand forms are suffixes as elsewhere: `_rrr`, `_rrm`, `_rrb` (a
  broadcast memory operand), `_rrr_round` (512-bit register form with
  `{er}`/`{sae}`), each taking `(op, vl, masking, ...)`. The checked
  forms refuse a length the member lacks, broadcast on a member without
  it, rounding on one without it, and `{z}` without a mask.
- The opmask instructions (VEX, `src/evex.rs` too): `kmov_kk`,
  `kmov_kr`, `kmov_rk`, `kmov_km`, `kmov_mk` with a `KSize` (`B` needs
  DQ, `W` F, `D`/`Q` BW: the encoder does not check features);
  `k3_kkk(op: K3, size, dst, a, b)` for `kand`, `kandn`, `kor`,
  `kxor`, `kxnor`, `kadd` and `kunpck` (`kunpckbw`/`wd`/`dq` as
  sizes `W`/`D`/`Q`); `k2_kk(op: K2, ...)` for `knot`, `kortest`,
  `ktest`; `kshift_kki(op, size, dst, src, imm8)`.

Each family gets a sweep in `tests/l1/evex.rs` (groups `evex`,
`evex-memory-operands`, `opmask`): every member at each length it has
(the others refused, also by `llvm-mc`), every register position over
registers on both sides of bits 3 and 4 (`0, 7, 8, 15, 16, 23, 24,
31`), masking none / merge / zero with `k1` and `k7`, broadcast where
allowed, every rounding mode where allowed, immediates at the
boundaries, the sampled memory operands; rows in `tests/l1/table.rs`.

## 2. Values at `-O0`

### 2.1 Where a 512-bit value lives

A `<16 x i32>`, `<8 x double>`, `<32 x i16>`, `<64 x i8>` is a `Mem`
value (class by size, §2.6 of design 0006), in a frame slot of 64 bytes.
Value slots are aligned to `min(align, 16)` (`hod_cg::policy::value_slot`):
**hod never realigns the stack**, for 32-byte values today (WP-202 moves
them with `vmovdqu`) or for 64-byte ones, and every EVEX move of a value
slot is unaligned (`vmovdqu64`/`vmovups`). `llc -O0` does the same for its
own spills: measured on 19 and 22, a function that keeps two `zmm` values
across a call spills them with `vmovups` to `rsp`-relative slots after
`subq $248, %rsp`, with no `and rsp, -64`. An `alloca` with `align 64`
is the IR's request and hod already serves it by its dynamic over-aligned
slots (§5.1); nothing changes there.

### 2.2 Scratch registers

`zmm16`-`zmm31` are outside the ABI (caller-saved, never arguments or
results, `csr_64` masks keep no `zmm`, WP-201) and outside the VEX
space, so no value of hod's is ever in one and no WP-202 lowering uses
one: they are the natural scratch set, and using them needs no save and
no `vzeroupper` (which does not touch them). The lowering of one
intrinsic:

1. each vector operand loaded from its slot into `zmm16`, `zmm17`, ...
   (`vmovdqu64` at the operand's length; a 128-bit `Fpr` operand used
   in place from its `xmm` register, since EVEX reaches `xmm0`-`xmm15`
   directly);
2. a merge source (a masked intrinsic's pass-through) loaded into the
   destination register first; a mask operand moved from its general
   register into `k1` (`kmovw` for up to 16 lanes, `kmovd`/`kmovq` for
   32/64 lanes, which only BW functions reach), or no mask when it is the
   constant all-ones (as `llc`);
3. the instruction;
4. the result stored to its slot (`vmovdqu64`), or for a 128-bit result
   written straight into its `xmm` register (`EVEX.128` zeroes the
   upper bits, which hold none of hod's values), or for a mask result
   `kmovw`/`kmovd`/`kmovq` from `k0`/`k1` into the result's general
   register (zero-extended, which a mask's unspecified upper bits allow).

No general register but the mask's and the result's, no `xmm0`-`xmm15`
but the operands' own, no flags.

### 2.3 Masks

Unchanged: `<N x i1>` for `N ≤ 64` is a `Gpr` bit image (`mask.rs`),
so `bitcast <16 x i1> to i16` and back, `load`, `store`, `phi`, `select`
on a mask (bitwise), `and`/`or`/`xor` of masks need nothing new. A mask
of 2 or 4 lanes is the low bits of a `k` register written by `kmovw`;
the instruction reads only its lanes, and the bits above are unspecified
in both representations. `k` registers never hold a value across
instructions of different IR operations. Masks passed or returned by
value (where `llc` uses `k` registers or `vpmov*2m`) are WP-203's ABI
work and stay refused (`x64:wide-vector-abi`).

### 2.4 Generic IR on 512-bit types

Already compiled by the lane loops in an AVX-512 function (WP-201 judges
signatures, not bodies): `load`/`store`, element-wise arithmetic,
`icmp`/`fcmp` (to a `Gpr` mask), `select` on a mask, `shufflevector`,
`bitcast`. They use no AVX-512 instruction, which costs speed only.

The masked memory intrinsics arrive as generic IR too, from clang's
`_mm512_mask_loadu_*` and from highway's `MaskedLoad`/`BlendedStore`/
`CompressStore`. Their signatures differ between majors (LLVM 22 moved
the alignment from an `i32` operand to the pointer's `align`
attribute):

| intrinsic | LLVM 19 | LLVM 22 |
|---|---|---|
| `masked.load` | `(ptr, i32 align, <N x i1>, passthru)` | `(ptr align A, <N x i1>, passthru)` |
| `masked.store` | `(val, ptr, i32 align, <N x i1>)` | `(val, ptr align A, <N x i1>)` |
| `masked.compressstore` | `(val, ptr, <N x i1>)` | same |
| `masked.expandload` | `(ptr, <N x i1>, passthru)` | same |

hod lowers each as a loop over the lanes, unrolled for `N ≤ 64`: test
mask bit `i` (`bt`), skip or do lane `i`'s scalar load/store (and for
compress/expand, advance the packed pointer by the element size). A lane
whose bit is clear is not accessed (the guarantee programs rely on to
read up to the end of a buffer); a load's result starts as the
pass-through's image. This is correct whatever the features, so it is
also what an AVX2 or SSE2 function gets (the 18 `<4 x float>`/`<8 x
float>`/... names of the census are refused today even without AVX-512).

## 3. The feature gate

Per function, as WP-201/WP-202 (§5.6.33): the last item of
`"target-features"` naming a feature decides; a `target-cpu` alone does
not count. The need of each name is clang's header attribute:

| need | names |
|---|---|
| `avx512f` | the `.512` forms of F (`avx512.*` without `.128`/`.256`, `avx512.mask.*.512`), `rcp14.sd`/`rsqrt14.sd` |
| `avx512f` + `avx512vl` | F's `.128`/`.256` forms |
| `avx512bw` (+ `vl` for 128/256) | the word/byte names (`*.w.*`, `*.b.512`, `pack*.512`, `psad.bw.512`, `pmul.hr.sw.512`, `permvar.hi.*`, `vpermi2var.hi.*`, `dbpsadbw.*`) |
| `avx512dq` (+ `vl`) | `fpclass.*`, `cvt*qq*`, `cvt*uqq*`, `cvtqq2ps`, `cvtuqq2ps` |
| `avx512vbmi` (+ `vl`) | `permvar.qi.*`, `vpermi2var.qi.*`, `pmultishift.qb.*` |
| `avx512vbmi2` (+ `vl`) | `mask.compress` of `i8`/`i16` lanes |
| `avx512fp16` (+ `vl`) | `avx512fp16.*` |
| `avx512bf16` (+ `vl`); `avxneconvert` | `avx512bf16.*`; `vcvtneps2bf16128`/`256` |
| `vaes` (+ `avx512f` for 512) | `aesni.*.256`, `aesni.*.512` |
| `vpclmulqdq` (+ `avx512f` for 512) | `pclmulqdq.256`, `.512` |
| `gfni` + `avx512f` (+ `bw` as clang) | `vgf2p8*.512` |

Implications, measured by clang's own header check (a function with
`__attribute__((target("X")))` calling one header function of each
need; `llc` is no test here, since it emulates a missing feature with
other instructions, `avx512.pshuf.b.512` as two `ymm` `vpshufb` under
`avx512f`): every `avx512*` feature implies `avx512f`; `avx512vbmi`,
`vbmi2`, `bitalg`, `fp16`, `bf16` imply `avx512bw`; under clang 19
`avx512fp16` also implies `dq` and `vl` and `avx10.1-512` implies all of
them, under clang 22 neither does. hod counts an implication only when
both majors have it, so `dq`, `vl`, `vbmi`, `vbmi2` and `fp16` are each
on only by their own name (clang 19 and 22 write the implied names into
`"target-features"` themselves, so this refuses nothing they write).
Turning off `avx512f` turns off every one of them; turning off `avx2` or
anything below turns off `avx512f`.

`evex512` (measured): clang 19 writes `+evex512` with every AVX-512 CPU,
clang 22 and kiln write neither. `llc` 19 with `+avx512f,-evex512` aborts
on a 512-bit intrinsic ("Do not know how to split the result"); `llc` 22
ignores `-evex512`. hod refuses a **512-bit** name in a function whose
last `evex512` item is `-evex512`, and builds the 128/256-bit forms.
`prefer-vector-width`, `prefer-256-bit`, `min-legal-vector-width` are
tuning: they change what the vectorizer and `llc`'s type legalization
prefer, not what an intrinsic means; hod ignores them.

Without the feature a name is refused by its name (`intrinsic:<name>`,
`classify`'s rule for every `llvm.x86.*` row whose feature is off), as
§5.6.29/§5.6.33. AArch64 refuses every one.

## 4. Oracle and execution

### 4.1 Nothing here executes AVX-512

`qemu-x86_64` 10.0.13, a static program whose first instruction is one of
`vpaddd zmm0, zmm1, zmm2`, `vpaddd ymm16, ymm17, ymm18` (VL, no `zmm`),
`kmovw k1, eax`: **SIGILL** under `-cpu max`, `Icelake-Server`,
`Skylake-Server`, `Cascadelake-Server`, `GraniteRapids` and `EPYC-Genoa`
(qemu warns "TCG doesn't support requested feature:
CPUID.07H:EBX.avx512f"; it has no `Sapphire-Rapids` model). TCG has no
AVX-512, and there is no other x86-64 emulator on the host. So:

- **Generic IR** (the masked memory intrinsics, section 2.4) is checked
  by execution: hod's code has no AVX-512 instruction, so it runs under
  `-cpu max`; the reference is `llc` 19 and 22 on the same module with
  `"target-features"` lowered to `+avx2` (the IR's meaning does not
  depend on the features), linked and run the same way. WP-202's legs
  (hod plain bfd and lld, hod stress, `llc` 22 and 19) and its
  mutations.
- **AVX-512 intrinsics** are checked by the dataflow comparison below
  on this host, and by execution where a runner exists.
- **AVX2-executable twins: none.** A VL form on `xmm`/`ymm` still needs
  an EVEX instruction (and a `k` register for its mask), and the
  512-bit forms need `zmm`; no census name has a lowering without
  AVX-512 that would be `llc`'s.

### 4.2 The dataflow comparison

The test function of one intrinsic call is

```llvm
define void @t(ptr %out, ptr %a, ptr %b, ptr %c, i64 %m) #0 {
  ; each vector operand loaded from its pointer, each mask operand
  ; truncated from %m (and bitcast to <N x i1> where the signature says),
  ; the immediates constant, the call, the result stored to %out
}
```

compiled by hod and by `llc -O0` 19 and 22, and disassembled
(`llvm-objdump -M intel`). A small symbolic interpreter runs each
listing from the entry to `ret`:

- the leaves are the bytes of `*%a`, `*%b`, `*%c` (an operand loaded
  from a pointer argument) and the bits of `%m`;
- registers and memory hold symbolic bytes: a move, load or store of
  any width (`mov`, `movzx`, `movups`/`movdqu`, `vmovdqu*`/`vmovdqa*`/
  `vmovups`/`vmovaps`/`vmovapd`, `kmov*`, `lea` of a frame address,
  `push`/`pop`, `sub`/`add rsp`) copies bytes; frame memory is keyed by
  its offset from the entry `rsp`, so hod's slots and `llc`'s spills are
  both just places;
- any other instruction makes a new node: its mnemonic, its immediate,
  its rounding or SAE, its masking (`{k}` with the mask register's
  content as an input, `{z}`), its broadcast, and its inputs **in
  operand order** (with the destination as an input when the
  instruction reads it: merging-masking, and the tied forms
  `vpermt2*`, `vpermi2*`, `vfmadd*`/`vfmaddsub*`, `vpternlog*`);
- the result is the bytes stored to `*%out` (or returned).

The check: the result of hod's listing equals `llc` 19's and 22's, as
trees. **What it catches:** a wrong instruction or opcode (by its
disassembled mnemonic), a wrong immediate, rounding or masking, swapped
operands, a mask taken from the wrong place, a wrong pass-through, a
result of the wrong width or partly stored, an operand read from the
wrong slot or with the wrong length, a missing zero-extension of a mask
result. **What it cannot catch:** an encoding that disassembles to the
intended text but runs differently (L1 covers the encoding against
`llvm-mc`), the instruction's semantics (hod writes `llc`'s, so both are
right or both wrong), and any difference that only shows when the
instruction executes (`MXCSR` state, faults, denormals). It is strict:
an equivalent but different sequence fails, so hod must write `llc`'s
instruction (a documented rewrite rule may be added where `llc` itself
writes one of two forms, e.g. `vpermt2*` versus `vpermi2*`). Mutations
show the comparison bites: swapped sources, a wrong immediate, merge
instead of zero, the mask from `k0` (no mask), a 256-bit store of a
512-bit result.

### 4.3 The same test by execution

`crates/hod_x64/tests/x86_avx512.rs` builds, for each case, WP-202's
executable shape too (edge and random inputs, hod's object and `llc`'s
linked into one program that prints both results). With
`HOD_X64_AVX512_RUNNER` unset it only compares listings. Set, it names
how to run an x86-64 executable that may use AVX-512 (`native` on an
x86-64 host with AVX-512, or a command prefix such as an emulator
`sde64 -spr --`); the harness then also runs every case and requires the
outputs to agree, skipping a function by `__builtin_cpu_supports` as
WP-202 does. The command for the supervisor on such a host:

```sh
HOD_REQUIRE_TOOLS=1 HOD_X64_AVX512_RUNNER=native \
  cargo test -p hod_x64 --test x86_avx512
```

## 5. Order of work

### 5.1 The census by family

Names refused after WP-202 (317 intrinsics), by family, in how many of
the 20 modules that refuse an intrinsic, and the modules freed when the
families up to that line are built (a module is freed only when every
name it refuses is built; 2 further modules are refused by
`x64:wide-vector-abi`, WP-203):

| family | names | in modules | freed (cumulative) | `llc`'s instructions |

### 5.2 The packages

1. **WP-208 (this one), in order:**
   (a) this note; (b) the EVEX encoder and the opmask instructions with
   their L1 sweeps (about 95 mnemonics for F/VL/BW/DQ/VBMI/VBMI2, about
   220 member/length forms, 15 opmask forms); (c) the generic masked
   memory intrinsics by execution (54 census names, all widths); (d) the
   harness of section 4.2 and the F/VL names by census count (110 rows),
   then BW (35) and DQ (23). The cut: what is not reached keeps its
   refusal, counted in `spec/codegen.md` §5.6.35.
2. **Follow-up A:** VBMI, VBMI2, VAES, GFNI 512, VPCLMULQDQ (26 names,
   12 instructions) and the F gathers/scatters (16 names; VSIB
   encoding, `V'` as index bit 4, the mask register written by the
   instruction).
3. **Follow-up B:** FP16 and BF16 (45 names; maps 5 and 6, the `half`
   and `bfloat` lanes, `vfpclassph` with its own N).
4. **WP-203** (planned): 512-bit vectors and masks by value; then the
   two modules refused for `x64:wide-vector-abi` and every module freed
   above link.

Lowering rows per family follow the census one-for-one: one row per
name, each a call of one encoder member (or two: a `vpermt2` with the
index operand placed where `llc` puts it). The masked memory intrinsics
are four rows generic over the type.
