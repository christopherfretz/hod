# WP-176 — the lexer's per-token path (`hod_ll`)

Landed: five cuts to the text reader's lexer and `Parser::expect`, one
commit each with its counts in its message, on `crates/hod_ll/src/lexer.rs`
and `crates/hod_ll/src/parser.rs` only. No change to emitted bytes,
refusals, error messages or error positions (below), none to `spec/ll.md`
(§2.8 says what a replaying lexer gives, which is unchanged). Safe Rust,
no new dependency, no edit outside those two files and their tests. Base:
`786e96aa` (main).

## Method

As WP-168: Callgrind instruction counts, `HOD_THREADS=1`, the release
profile (`debug = 1`, fat LTO, one code unit), self cost per function
(`callgrind_annotate --inclusive=no`); `hod --strict -O0 -filetype=obj
-relocation-model=pic -mtriple=T -o out.o in.ll` over the bench inputs
of `cargo xtask bench --generate` (clang 22, both targets). The host is
AArch64 Linux, so the instructions counted are AArch64's for both
targets. "Lexer" is the sum of the functions named `hod_ll::lexer::`
(the keyword hash inlined into `word` included). Hot spots were read
from `--dump-instr=yes` profiles against `objdump`. Base and each cut
were built in their own build and kept as separate binaries.

AArch64 objects move the same way within 0.5M a step (base → after:
stl-heavy-g 1291.15 → 1183.92, huge-function 383.53 → 359.19).

- **replay** (the parked note's cut): `Lexer::src` is the source up to
  the offset of the next token to replay, `Lexer::bytes` the whole
  source, read by the token rules. The blank skip and the first byte
  look only at `src`, so the replay test is no longer paid per token:
  it is made in `at_end`, where the end of `src` is met, with the end
  of the source and the 4 GiB case. A blank or comment that runs past
  the bound stops at it and goes to `at_end` with the lexer's own
  `pos`, which replays the recorded token if one was looked for there
  and otherwise lexes over the whole source; an unterminated `/*` inside
  the bound goes there too, so its error is the lexer's.
- **dispatch**: `next_token` loads one byte, a second after a space,
  and dispatches by a 256-entry table (`DISPATCH`: word, one-byte token,
  `%`, `@`, number, blank, other; `SIMPLE` gives a one-byte token's
  kind). LLVM had folded the old `match` so that letters and digits
  left its jump table for range tests; any other white space or a
  comment now goes out of line (`after_blank`) and dispatches again.
- **label**: a word before a colon (the field names of metadata nodes,
  `line:`, `scope:`) is the label of the word and the colon in `word`'s
  fast path; it went through `word_rule` and the label scan (366,000
  words on stl-heavy-g). Inputs without `-g` do not change.
- **expect**: `Parser::expect` is inline, its failure out of line
  (`unexpected`, cold): the Ok path no longer builds a `PResult<Token>`
  and copies the token through the stack in a frame of its own. The
  binary grows by 62 KB (0.2%).
- **`!`**: tested first in the dispatch's last arm and lexed by
  `exclaim`, without `compound`'s frame and second jump table (474,000
  of `compound`'s 537,000 calls on stl-heavy-g).

## Exactness

The token rules are unchanged; what moved is which bytes the blank skip
and the dispatch look at and in what order. `DISPATCH` and `SIMPLE` are
built at compile time from the character classes and tested against the
sets of §2 for every byte value (`classes_are_the_sets_of_section_2`).
The label fast path takes only a word of the fast path (at most 15
bytes, sixteen bytes of source, not `u0…`/`s0…`/`cc`-digit) whose next
byte is `:`: the run of label characters ends there, which is what
`word_rule` and `label_tail` give; it skips `label_run_end`'s memo,
which only ever records a run, so later answers are the same
(`keyword_labels`: keywords and integer types before a colon, with and
without sixteen bytes of source). The replay bound is invisible
(`replay_bounds_are_invisible`: 400 random recordings, at the offset the
lexer stopped at or at the token's start, over blanks and comments that
run past a recorded offset and an unterminated comment, every token and
the error text as lexed), and `replayed_tokens_are_the_lexed_ones`
still holds.

## Tried and dropped

- `!` as a dispatch entry of its own: an eighth case deepened the
  compare tree LLVM makes of the dispatch `match` for every token
  (+1.07M on huge-function, +0.8M on stl-heavy against −5.3M on
  stl-heavy-g); kept as a test in the last arm instead.
- `Token` as a scalar pair (`{ span: u64, tag: u16 }`, the parked note's
  finding 2) was not made. Every lexer function returns the 12-byte
  token through memory (sret), but on the hot path that is two or three
  stores the token needs anyway: the copies that cost were `expect`'s,
  which the inline `expect` removed. The change would turn some 500
  field reads across the reader (75 in the debug metadata reader) into
  accessors, and `Tok`/`Kw` would have to be rebuilt from a `u16` with
  a test per token; left until a measurement says the remaining few
  instructions a token are worth that.

## Where the rest is

On stl-heavy-g (x86-64 objects, head), of the lexer's 226M:
`next_token` 71.0M (3.3M tokens, about 21 each: the bound and space
tests, the table load and LLVM's compare tree over the seven cases, the
one-byte tokens stored in place), `word` 57.2M (the length loop, a
table test per byte, then the key, the multiply and the compare of the
keyword hash, about 35 a keyword), `number` 26.1M, `exclaim` 15.9M,
`after_blank` 10.6M (line feeds and indentation), `compound` 9.7M,
`at_end` 9.3M (320,000 tokens reach the replay bound: the recorded
token is taken there), `global` 8.1M, `local` 7.3M, `word_rule` 5.6M.
Next, in order of promise: a jump table instead of the compare tree in
the dispatch (LLVM did not make one for seven cases; not tried), the replay entries read without
`replayed`'s loop when the next one is at `pos`, and the per-byte word
length. On huge-function the cost named `Lexer::number_rule` (8.2M) is
the label scan of `body.rs` (§11.3) under a folded symbol, not the
lexer.
