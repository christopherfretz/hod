# WP-034 — `spec/abi-a64.md` and `assign` for AArch64 Linux

Landed: all of `spec/abi-a64.md` (§1 to §12), and `hod_a64::abi` and
`hod_a64::reg` that implement it. `hod_cg/src/abi.rs` and
`spec/codegen.md` are unchanged: the interface fixed there was enough.

## What it did

- `crates/hod_a64/src/reg.rs`: `x(n)`, `v(n)`, `X0`..`X30`, `V0`..`V31`,
  `FP`, `LR`, `SP`, `is_gpr`, `is_fpr`, `number`, in the `PReg` numbering
  `hod_cg` documents for this target.
- `crates/hod_a64/src/abi.rs`:
  - `assign(types, sig, out) -> Result<(), AbiUnsupported>` (§3 to §6,
    §9, §10);
  - `cc_is_c(cc)` (§1.2), `ARG_REGS`, `INDIRECT_RESULT` (`x8`), `NEST`
    (`x15`), `MAX_PIECES`, `UNSUPPORTED` (the 23 names of §10);
  - `Extension`, `produced_extension(bits, attrs)` and
    `assumed_extension(bits, attrs, place)` (§7), so that the code
    generator and the tests read the extension duties from one place.
- `crates/hod_a64/tests/abi/`: the cross-check against `llc` and its
  tool-free companions (below).
- `spec/README.md`: the `abi-a64.md` row.

## Decisions, and why

- **The spec states what all four configurations do, and names the rest
  unsupported.** `-O0` (GlobalISel) is what a debug build of clang uses
  and `-O2` (SelectionDAG) what everything else uses; code compiled
  either way may be on the other side of a call. Where the two disagree
  there is no right answer to implement, and a wrong guess is a silent
  miscompile, so each disagreement got a name (§12) instead of a choice.
- **Structures are passed leaf by leaf, with no size limit**, because
  that is what LLVM does with a first-class structure. It is not what
  AAPCS64 says about a C structure, and the spec says so (§12); the
  frontend's coercions are what make the two meet.
- **One stack part for a dense block.** `[1000000 x i64]` on the stack
  is one `Part` and costs one step, not a million. `Part` merging (§3.4)
  is specified rather than left as an optimization so that the tables in
  the tests can be exact.
- **`stack_size` is not rounded**, as `hod_cg::abi` documents; `VaInfo::
  stack_offset` is rounded to 8, because that is where the first
  variable argument is.
- **The extension tables live in the library** (`produced_extension`,
  `assumed_extension`), although the brief asked only for `assign`: the
  duty is part of the ABI, the code generator needs it as code, and the
  grid then tests the very function the code generator will call.
- **The producer's duty is the same in a register and on the stack**
  (extend to 32 bits), although LLVM's callee would be content with less
  on the stack for `i1`/`i8`/`i16`. One rule; the cost is nothing. The
  consumer's table is the narrow one, because it has to hold against
  LLVM's callers.
- **The test emitter is driven by `Assignment` alone** and knows no
  register names of its own beyond its scratch registers. It is a small
  model of what WP-038 has to do (§8), and its being generic is what
  makes the grid a test of `assign` rather than of a second copy of the
  rules.
- **Junk everywhere.** hod's side fills every bit this document calls
  unspecified with a pattern (register bits above a part, unused
  argument registers, stack bytes between parts, padding of a memory
  return). Several findings below only showed because of it.
- **`llc` at both `-O0` and `-O2`, 19 and 22, in one test run**, batched
  so that a grid of 3,000 signatures is four `llc` runs, one assembler
  run and four links per 400 cases. A signature `llc` itself crashes on
  is left out and reported, not hidden.

## What LLVM does that the grid had to learn

- **A plain `i1` argument is a `_Bool`.** LLVM's callee assumes an `i1`
  parameter without attributes is zero-extended to 8 bits
  (`AArch64ISD::ASSERT_ZEXT_BOOL`), and clang passes `bool` exactly so,
  with no `zeroext`. A producer that leaves junk in bits 1 to 7 breaks
  LLVM-compiled callees. For a returned `i1` LLVM's caller does not rely
  on it, but LLVM's callee does it.
- **With `zeroext`/`signext`**, values below 32 bits are extended to 32
  bits, wider ones to the next multiple of 64; on the stack LLVM's
  callers store one byte for `i1`/`i8` and two for `i16`, so a callee
  may rely on less there.
- **GlobalISel reads parameter attributes at the wrong index after a
  zero-sized argument**: `lowerFormalArguments` skips the argument
  without advancing its attribute index, so a later `signext`, `sret`
  or `byval` is applied to the wrong parameter at `-O0`.
  → `abi:attribute-after-empty-argument`.
- **`[1 x i128]` after one `i64`** is in `x2`, `x3` at `-O0` and in `x1`,
  `x2` at `-O2`. → `abi:wide-int-array`. (clang never emits such an
  array; it passes `i128`.)
- **An array of vectors that need more than one register each**
  (vectors LLVM splits or passes element by element) is assigned
  registers differently by the two selectors. → `abi:vector-array`.
- **A one-leaf array whose stack alignment is not the leaf's slot size**
  (`[1 x double] alignstack(16)`, `[1 x float] alignstack(16)`): one
  selector treats it as a block and one as a plain value, and they
  differ in the stack offset. → `abi:one-leaf-array`. What clang emits
  for one-member aggregates (`[1 x float] alignstack(8)`, `[1 x double]`,
  `[1 x fp128]`, `[1 x i64]`) is supported; an over-aligned one-member
  structure becomes `[2 x i64]`.
- **llc 19 against llc 22**: `nest` moved from `x18` to `x15`;
  `[N x bfloat]` became a block. Nothing else differs in 11,000
  signatures.
- **`fastcc`, `swiftcc` and `cxx_fast_tlscc` are `ccc`** to the last
  byte of assembly on this target; `coldcc` is rejected by LLVM itself
  ("unsupported calling convention"); `tailcc` and `preserve_mostcc`
  differ.
- **The verifier** refuses `sret` on a function that returns a value,
  and variadic `fastcc`; it accepts a `musttail` pair that differs in
  `nest`.
- **A variadic `musttail` thunk** forwards `x8` as well as the argument
  registers.
- **LLVM's own `va_arg` instruction is not AAPCS64's** on this target:
  it reads `__stack` and nothing else. clang never emits it.
- **A returned-in-memory value** is stored by LLVM's callee leaf by leaf,
  assuming the buffer has the type's preferred alignment, and LLVM's
  caller allocates it so.
- **GlobalISel's legalizer crashes** on a few odd types; the harness
  isolates such a function. After the unsupported names above were in
  place, the grids meet none.
- Vectors that are not 8 or 16 bytes are widened, split or passed
  element by element, and integer elements narrower than 64 bits in a
  short power-of-two vector are *promoted* (`<2 x i8>` travels as two
  32-bit lanes), which a `Part` cannot express. → `abi:vector-promoted`.

## What x86-64 will need from the interface

`hod_cg::abi` looks sufficient for System V x86-64, with two points to
settle when `abi-x64.md` is written:

- `x86_fp80` returns in `st0` (and `{ x86_fp80, x86_fp80 }` in `st0`,
  `st1`): `Place::Reg` needs `PReg` numbers for the x87 stack, or a new
  `Place`.
- The extension duties of §7 are target rules that are not in
  `Assignment`; here they are two functions of the target crate.
  x86-64 has the same need, so a `Target` method may be the better home
  once there are two.

`vector_regs_used` (`al`), `sret_returned_in` and `RetMemory::
returned_in` (`rax`), and `VaInfo` (the offsets of `va_list` and the
overflow area) are already there for it.

## Open questions

- `spec/codegen.md` §5.5 says `abi-a64.md` states the entry sequences of
  branch protection. It does not yet (§1.1); that was outside this WP.
- WP-038 lists the `VaArg` instruction. There is no LLVM behavior to
  match for it on this target (see above). Either `classify` rejects it
  (clang and, as far as known, kiln expand `va_arg` in the frontend), or
  §9 grows AAPCS64's "The `va_arg()` macro" for IR types with C as the
  oracle, as `variadic::variadic_against_c` already does for
  `va_start`.

## Follow-ups

- `crates/hod_a64/src/abi.rs:794`..`804`: the four unsupported arrays.
  None is something clang emits. Any of them could be supported by
  following one selector, which is a policy decision (which LLVM-built
  code is on the other side), not a technical one.
- `crates/hod_a64/src/abi.rs:153`: `abi:attribute-after-empty-argument`
  likewise follows from a GlobalISel defect; an upstream fix would let
  it go.
- `crates/hod_a64/src/abi.rs:27` and
  `crates/hod_a64/tests/abi/run.rs:186`: `nest` follows llc 22 and is not
  cross-checked against llc 19.
- `crates/hod_a64/src/abi.rs:441`: `abi:vector-promoted` needs a way to
  say "this element, widened, in that lane"; not worth a new `PartKind`
  until a frontend emits such a vector as an argument.
- `crates/hod_a64/src/abi.rs:738`: `byval` aligned above 16.
- `crates/hod_a64/src/abi.rs:88`: `tailcc`, `swifttailcc`,
  `preserve_mostcc`, `preserve_allcc`, `preserve_nonecc`, `ghccc` and
  the vector PCS conventions are all `abi:cc`.
- `crates/hod_a64/src/abi.rs:186`: the producer's duty on the stack could
  be narrowed to what LLVM's callee needs (§7), if the extra instruction
  ever matters.
- The harness in `crates/hod_a64/tests/abi/` (`ty.rs`, `sigs.rs`,
  `ir.rs`, `run.rs`, `grid.rs`, `variadic.rs`) is target-neutral apart
  from `emit.rs` and the triple; `abi-x64.md` can reuse it by moving it
  to a shared test-support crate.
