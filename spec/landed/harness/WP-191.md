# WP-191 — the real-project lane on x86-64

Landed: WP-177's lane (`scripts/oss/`) takes the target as a parameter
(`--target aarch64|x86_64`, default `aarch64`, the native build it had)
and cross-builds its projects for `x86_64-unknown-linux-gnu` on the
AArch64 development host, running their tests under `qemu-x86_64`;
`scripts/oss/oss-reduce.py` reduces every kept refusal to its smallest
module; the layer is `docs/VALIDATION.md` "Real projects (L9)".

## What changed

| file | change |
|---|---|
| `oss-build.sh` | `--target`; for `x86_64`: CMake's cross settings (`CMAKE_SYSTEM_NAME`/`PROCESSOR`, `CMAKE_C_COMPILER_TARGET` for a clang C row, `CMAKE_FIND_ROOT_PATH` the system root with programs from the host, `CMAKE_CROSSCOMPILING_EMULATOR` = `qemu-x86_64 -L <sysroot>`), `HOD_OSS_TARGET_TRIPLE` for the wrappers, links capped at 16 GB, the test timeout times 4, trees under `<root>/x64-build/` and `<root>/x64-install/`; dependencies built for the same target |
| `kiln-cxx` (and so `kiln-cc`) | `--target=$HOD_OSS_TARGET_TRIPLE` first when set; `KILN_OSS_LINK_VMEM_KB` caps an invocation that is not a compile |
| `projects.py` | the report's `target` |
| `oss-report.py` | `--target` before the command: the target's trees, its findings under `<findings>/x64/`, its title |
| `oss-run.sh` | `--target` (census `<findings>/X64-CENSUS.md`, regressions `<findings>/x64/TEST-REGRESSIONS.txt`); `--strict` runs the strict build even after a fallback; `--modes` (WP-177's spelling) runs only the modes named; each project's kept refusals are reduced |
| `oss-report.py` (collect) | a refused module is kept under every reason of its census (hod's coverage log, matched by output and size), not only its first |
| `oss-report.py` (census) | "Strict builds": each strict build by kiln's `backend` field per object |
| `projects.py` | `emulate-tests`: a cross build's CTestTestfile.cmake commands that are x86-64 programs get the emulator (CMake adds it only for a command naming a target; googletest names paths), and so do a `cmake -P` test's `-D<var>=<program>` (doctest's `COMMAND`, glog's `LOGCLEANUP`) and CTestCustom.cmake's pre- and post-test commands (CLI11); the census of a reason that is never a module's first (it raised `KeyError`) |

| `oss-reduce.py` | new: `llvm-extract` of the refused function, then `llvm-reduce` while hod's census still holds the reason; `min.ll` beside the kept module |

## Decisions

- **A parameter, not a copy.** The native lane and the cross lane are the
  same scripts; the target decides the CMake settings, the wrapper's
  `--target`, and where the trees and findings go. The sources are
  shared (`<root>/src/`).
- **kiln finds the cross toolchain.** `kiln++ --target=x86_64-unknown-linux-gnu`
  finds the distribution's cross GCC (`/usr/lib/gcc-cross`) and its
  system root, and links with mold; the lane adds nothing else to the
  command line. The wrapper puts `--target` first, so a project's own
  `--target` (none of the rows has one) would still decide.
- **ctest under the emulator.** `CMAKE_CROSSCOMPILING_EMULATOR` makes
  CMake's `add_test` (and `gtest_discover_tests`) run the test programs
  under qemu; the host has no `binfmt_misc` entry that runs x86-64 Linux
  programs with the system root, so a program a test starts itself (a
  death test re-executing `/proc/self/exe`, a python script running a
  test binary) fails alike in the three builds. Those tests fail in the
  control too, so the comparison with the control is unchanged.
- **Strict after a fallback.** The native lane runs the strict build only
  when the hybrid build fell back nowhere. On x86-64 googletest itself
  holds a refusal (`int3` in inline assembly) and every test binary links
  it, so `--strict` runs the strict build anyway for the refusals still
  open; its failed compiles are the refusals, the rest builds (`make -k`).
- **The reproducer.** The kept module is the exact text kiln gave hod;
  `min.ll` is what is left of it after `llvm-reduce` with "hod refuses it
  with this reason somewhere in its census" (`HOD_CENSUS=1`, the
  coverage log) as the test, so a reason that is not the module's first
  still gets one.

Notes on these rows:
- mold: 682 of the 929 tests cannot run here, in the control and in strict
  alike. mold's arena reserves 8 GB of address space (`lib/arena.cc`), and
  the test phase runs under a 16 GB `ulimit -v` that also has to hold qemu.
  The evidence is therefore the 163 passing tests plus the identical status
  map. At hod 02fe2d02, strict had no `mold` binary: two oneTBB TUs were
  refused with `intrinsic:llvm.x86.tpause`, so its link failed. The tests'
  `cc -B.` then used the system linker, which is why the counts differed.
- glog: the two sources that stop in the front end are glog's
  expected-to-fail compile checks. O0g's `logging` is the known qemu race.
- zlib: once, O0g's `zlib_static_example` failed with `gzread err:`. The
  shared and static examples both write `test/foo.gz` under a parallel
  ctest. Run alone under qemu, it passes in 5 of 5 runs.

### Kiln 21b9110a4, hod main 3b14f8ff (wave 17)

Built with the lane's scripts at eb93d8ee. In every strict build, every
object was built by hod (kiln's `backend` field), with no refusal:

|---|---|---|---|

| glog | O0 | 45 hod + 2 with no back end | 22/24 / 22/24 |
| glog | O0g | 45 hod + 2 with no back end | 23/24 / 23/24 |
| protobuf | O0, O0g | 627 | 2/4 / 2/4 (the build runs the x86-64 `protoc`) |
| fmt | O0, O0g | 50 | 20/21 / 20/21 |
| googletest | O0, O0g | 85 | 44/63 / 44/63 |

The same tests fail in the control and in the strict build, with one
exception: glog O0. There, strict's `logging` ran past glog's own 30 s
limit, and the control's `cleanup_immediately` failed. Both are races
in those tests. Run alone under qemu, the control's `logging_unittest`
and the strict one behave the same way: in 4 of 5 runs each they hang,
and in the fifth each crashes in `TestLogSinkWaitTillSent`'s sink
thread. None of these failures is a miscompile.

Fixes made after these rows:
- `emulate-tests` now resolves a relative test command (CLI11's 25
  Catch2 tests, declared as `add_test(name name)`) against its directory.
- `oss-build.sh` links every x86-64 program with the system root's
  loader as interpreter and its libraries on the run path. A program
  the build or a test starts itself now runs: protoc and its plugins,
  death tests, googletest's python harnesses. With this, fmt O0 is
  21/21 in both builds. These are link flags only. Checked on fmt O0
  strict, built once with them and once with `HOD_OSS_X64_INTERP=0`:
  none of the 26 kiln commands that carry them compiles anything, and
  the 50 objects are byte-identical once the tree's own path, which is
  embedded in them, is made the same. Self-started programs run under
  the host's x86-64 translation, while ctest's own test programs run
  under qemu. When a self-started program fails in strict but not in
  the control, it is rerun under qemu before the difference is called
  hod's.
