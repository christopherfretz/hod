# WP-287 — i386, I4: the harness's third target

Design 0008's package I4 (section 4, "Oracle and lane"): 32-bit x86 Linux
as a target of the harness, `hod_testutil::Target::I686` and
`irdiff::Arch::I686`, proven on the oracle's side while hod does not
compile for it. The contract is `spec/harness.md` "Cross runs", "The
third target: i686".

## What landed

- `hod_testutil::target`: `Target::I686` (name `i686`, `i386` accepted
  by `Target::from_name`; triple `i686-unknown-linux-gnu`; GNU prefix and
  system root `i686-linux-gnu`; `qemu-i386`; CPU `pentium2,-mmx`, i.e.
  the Pentium Pro that LLVM's and GCC's default `i686` CPU is; guest
  space `-R 0x20000000`; `ld_emulation` `elf_i386`; Debian packages
  `gcc-i686-linux-gnu`, `binutils-i686-linux-gnu`,
  `libc6-dev-i386-cross`, `libstdc++-14-dev-i386-cross`). `Target::ALL`
  has three targets; **`Target::COMPILED_BY_HOD` is the one place that
  says which targets hod compiles for** (Aarch64 and X86_64), read by
  `Target::compiled_by_hod` and by xtask's `Arch::compiled_by_hod` /
  `Arch::compiled`.
- `hod_testutil::linkers`: the exception `wild` / `elf-i386`
  (`Unsupported`), `links(name, target)`, and `present(Target::I686)`
  without wild.
- Tests that build objects with hod iterate `Target::COMPILED_BY_HOD`
  instead of `Target::ALL` (they did not run i686 before and do not now).
- xtask: `irdiff --target i686|i386` (hod's refusal of the target, by
  any name, is UNSUPPORTED with the name; the reference side is linked
  and run under `qemu-i386`; wild is out of the matrix and `--linker
  wild` is a usage error); `fuzz --target i686` (csmith's program
  through clang and `llc`, the reference's program linked and run under
  `qemu-i386` before the seed is counted as refused); `fuzz` with no
  `--target` runs `Arch::compiled()`; `bench`, `corpus` and `debug`
  refuse `--target i686` with the reason.
- Hosted: `.github/actions/hod-ci/action.yml` installs the i686 cross
  packages on both runners (the same names as the provisioning script:
  both lanes run Debian 13 in the `buildpack-deps:trixie` container) and
  prints `i686-linux-gnu-gcc`, `i686-linux-gnu-ld.bfd` and `qemu-i386`
  versions. The new tests run in the existing `test` job (they are in
  `hod_testutil` and `xtask`) under `HOD_REQUIRE_TOOLS=1`. i686 programs
  run under `qemu-i386` on the x86-64 runner too: one runner for both
  hosts, nothing assumed about the runner kernel's IA-32 support.

## What was measured (AArch64 development host, qemu 10.0.13)

- `crates/hod_testutil/tests/i686_oracle.rs`, four programs: `ints`
  (integer-only, libgcc's 64-bit division; PIE and static), `hello` (a
  `main` calling printf and strlen with a global and an `i64` argument;
  PIE and static), `eh` (a C++ exception, a user type and
  `std::runtime_error`, through libstdc++; PIE), `ret42` (IR: `ret i32
  42` through a call; PIE and static). Each built by clang 19 and 22
  `--target=i686-linux-gnu -O0` (IR as given for `ret42`), `llc -O0
  -global-isel=0 -fast-isel=0`, linked by GNU ld, lld and mold: 14
  configurations x 3 linkers = 42 links, every one ELF32 `EM_386` of the
  model's type, every program's output and status as expected.
- The address-space finding: `qemu-i386` without `-R` cannot start any
  program under the 1 GiB address-space limit the fuzz and irdiff
  runners give programs ("Unable to find a guest_base to satisfy all
  guest address mapping requirements"; `ulimit -v 1048576` reproduces
  it); with `-R 0x20000000` or `-R 0x30000000` a PIE and a static program
  run under that limit.
- csmith seed 1 for i686 (LLVM 22): clang with csmith's headers over the
  i686 system root, `llc`, linked by `i686-linux-gnu-gcc`, run under
  `qemu-i386`: `checksum = F7B2B1F4`, status 0; hod refuses the target
  (`unsupported-target` today), the seed is counted as refused, no error
  (`xtask/tests/fuzz_real.rs`, `an_i686_seed_runs_the_reference_under_qemu_i386`).

## Where to flip

When hod's i686 back end exists (design 0008, I5): add `Self::I686` to
`Target::COMPILED_BY_HOD` (`crates/hod_testutil/src/target.rs`). Then the
tests that iterate it reach their `Target::I686 => unreachable!(...)`
arms (`crates/hod/tests/{alwaysinline_vla,hardening,stack_probe}.rs`),
which need i686 values; `irdiff --target i686` compares hod's programs
with the reference's and needs `unsupported` directives where hod
declines; `fuzz` with no `--target` includes i686; `bench --target
i686` is accepted.

## Not done

- Hosted CI was not run: that the i686 cross packages install on both
  hosted runners (amd64 and arm64 containers) and that `qemu-i386` starts
  under the hosted kernels is unverified until the next hosted run.
- No i686 libc++ (design 0008 section 4.5, package I14), no debug lane
  column (I10), no ABI grid (I6), no corpus (kiln has no 32-bit target).
- `irdiff` over `tests/ir/` for i686 was not run end to end with the real
  hod here; the fakes test (`xtask/tests/irdiff_fakes.rs`,
  `i686_refused_by_hod_is_unsupported_and_the_reference_runs`) covers the
  outcome rule, and the seeds' i686 reference side is for I5 to run.
