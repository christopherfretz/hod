# WP-305 — the unit's code range over a function without a subprogram

The compile unit's `DW_AT_low_pc`/`DW_AT_high_pc` or `DW_AT_ranges` now
name the same runs of functions as the line table's sequences, as `llc`
19 and 22 write them. The rule is `spec/dwarf.md` §6.17 "Runs" (with
§5.6 and §1.3's `.debug_addr` paragraph). Not byte-neutral, on purpose.

## Measured from llc before deciding

C files built with `clang-22 -g -O0 -S -emit-llvm` for each target, then
`llc-19`/`llc-22 -O0 -filetype=obj` (AArch64 with `-global-isel=0
-fast-isel=0`), read with `llvm-dwarfdump --debug-info --debug-rnglists
--debug-aranges --debug-line`. Each range and sequence is named below
by the functions it covers (from the symbol table). `llc` 19 and 22 give
the same answer in every shape, and so do x86-64 and i386 (`i686`; hod
does not write i386 debug information, `x86:debug-info`).

| shape (placement order) | `llc` unit | `llc` sequences |
|---|---|---|
| `f1`, `f2` in `.text.mine`, `f3`, `nd` (nodebug), `f4`, `main` | ranges `f1`; `f3`; `f4,main`; `.text.mine:f2` | the same four |
| the same on AArch64, where `f3` starts at `f1`'s end (0x18) | ranges `[0,0x18)` and `[0x18,0x30)`: two ranges that touch | the same four |
| `nd` first, then `f1`, `main` | `low_pc`/`high_pc` over `f1,main` (x86-64 0x10..0x53) | one |
| `f1`, `main`, `nd` last | `low_pc`/`high_pc` over `f1,main`, ending at `main`'s end | one |
| `f1`, `nd`, `nd2`, `main` | ranges `f1`; `main` | two |
| `f1`, `main`, `nd` in `.text.mine` | `low_pc`/`high_pc` over `f1,main` | one |
| any of these with `-function-sections` | one range per debug function's section; none for `nd` | one per debug function |

- `llc` writes `low_pc`/`high_pc` exactly when the unit's code is one
  run, and `DW_AT_ranges` from two runs on. A nodebug function first or
  last in `.text`, or in another section, leaves one run.
- No `.debug_aranges` from `llc` in any shape (hod writes none, §1.1).
- `DwarfDebug::skippedNonDebugFunction` sets the previous unit to null,
  so the next function's `DwarfCompileUnit::addRange` starts a range;
  a new range is never merged with the one before it, even where they
  touch.

hod before (base `67d656c9`): the unit's range extended over a nodebug
function (`f3,nd,f4,main` as one range on x86-64; `two` written as one
`low_pc`/`high_pc` over `f1,nd,nd2,main`), and on AArch64 the writer
merged touching spans, so `f1` and `f3` (and everything after) were one
range: `f1,f3,nd,f4,main` and `.text.mine:f2`, two ranges against
`llc`'s four.

## The rule

1. `emit/lines.rs` `break_run`: a function without a subprogram of a
   written unit forgets the previous span (`prev_span = None`) and ends
   the line sequence. `unit_span` returns whether the function
   continued the run; `add_function` ends the line sequence whenever it
   did not. The line sequence's other ends (no code, no rows) are inside
   a run. One decision, so the two cannot disagree again.
2. `hod_dwarf` `die.rs` `spans`: spans of one symbol are merged where
   they overlap, not where they only touch. The bridge gives one span
   per run, so touching spans are two runs, and `llc` writes them as two
   ranges. Only the unit's range attributes are affected; no other part
   of `hod_dwarf` changed.

## Evidence

- `crates/hod/tests/debug_unit_ranges.rs`
  `unit_ranges_are_the_runs_llc_writes`: the six shapes above (the
  measured five and `f1`, `f2` in `.text.mine`, `f3`), AArch64 and
  x86-64, with and without `-function-sections`. Each range and each
  sequence is named by the functions it covers. hod's unit
  (`low_pc`/`high_pc` or `DW_AT_ranges`, its runs) equals `llc` 19's and
  22's, hod's ranges equal its sequences, and every object verifies with
  `llvm-dwarfdump` 19 and 22. The test was not run against the base.
  The base's objects of the measured C shapes differ from `llc`'s in
  "between" and "two nodebug" on both targets (checked with a script
  that names the ranges in the same way). "Other section between" is
  not among the measured C shapes. The base's AArch64 "between" object
  already shows its cause: `f1` and `f3` merged into one range.
- `crates/hod_dwarf/tests/dies.rs` `touching_spans_stay_two_ranges`
  checks that spans which touch are two ranges and spans which overlap
  are one. `order_and_chunking_do_not_matter` now cuts each span into
  two overlapping pieces, because pieces that only touch are two runs.
  The test helper gives one span per section run, as the bridge does.
- `cargo xtask compare-binaries`. The base is hod built from `67d656c9`
  and the head from this branch, each in its own target directory. It
  ran over `tests/ir`, the corpus and the x86-64 corpus, plain and PIC,
  with `-j 4`: 6,832 modules and 14,108 comparisons. Results: 13,870
  identical, 8 different, 0 changed-outcome, 230 identical-failure
  (i686 has no debug information, and the rest fail the same way on
  both), 0 harness-error.
  - The 8 differences are 4 modules, each built plain and PIC, all on
    AArch64, and only `.debug_rnglists` differs: kiln's
    `conformance/temp.arg.nontype/class-type-argument-local-debuginfo-run.cpp`
    and `conformance/temp.explicit/definition-in-reopened-namespace-run.cpp`,
    in the LLVM 19 and LLVM 22 builds.
  - None of them has a `nodebug` function. All 4 come from rule 2:
    `.text` functions with COMDAT functions placed between them, so
    the runs of `.text` touch. The unit's ranges go from 9 to 11 and
    from 11 to 12, which is `llc`'s count (`llc-19`/`llc-22` of the same
    IR, AArch64 reference flags).
  - Named by functions, the head's set of ranges and its set of
    sequences equal `llc`'s in all 4 modules; the base's do not. The
    order of the ranges in the list is hod's order (sorted by section
    symbol), unchanged by this package.
  - All 4 head objects verify with dwarfdump 19 and 22.
  - The x86-64 corpus has no difference: its functions are padded to 16
    bytes, so runs seldom touch, and no corpus module has a nodebug
    function between debug functions.
