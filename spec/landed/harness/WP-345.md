## Class A: `DIArgList` on i386 (fixed)

`fits_i386` (`crates/hod_dwarf/src/loclists.rs`) refused every
`ValueLoc::Args` range. It now gives one an entry when each value is a
home of at most 4 bytes or a constant of at most 32 bits, the expression
reads no memory (`DW_OP_deref`, `DW_OP_deref_size`), its constants fit 32
bits, it converts to no type wider than 32 bits, and `arglist_width` is
at most 32: every stack entry is then a 32-bit value, the DWARF stack's
generic type on i386. Measured on `dbg_value_arglist.c` (clang 22):
`llc` writes `q` as `DW_OP_fbreg +24, DW_OP_deref, DW_OP_fbreg +12,
DW_OP_deref, DW_OP_lit4, DW_OP_mul, DW_OP_plus, DW_OP_stack_value` and
`d` as `... DW_OP_minus, DW_OP_stack_value`; hod writes the same with
`DW_OP_deref_size 4` for each `DW_OP_deref` (the same 4 bytes: the
address size). Test: `loclists::tests::i386_arglists_of_32_bit_values`.
The 64-bit targets do not call `fits_i386`: their objects are unchanged
by construction.

Outcome: `d` now has its location (gdb `-5`, as `llc`); `q` still has
none, so the 6 FAILs remain (`print q - p` fails, and gdb's `$1` is
then `d`'s `-5`, a shifted transcript, not a wrong value). The cause
is outside `hod_dwarf`: `hod_cg/src/dbg_value.rs:543` sizes a pointer's
home at 8 bytes on every target (and `:531` a null pointer constant at 64
bits), so on i386 `p`'s value is a `Frame { size: 8 }`, which
`fits_i386` refuses (an 8-byte home does not fit the 32-bit stack). The
fix is the target's pointer size there (4 on i386); not made here
(not this package's file).

## Class B: `stack_protector.c`, lldb (a rule, proposed)

`record`'s line 42 is `snprintf(r.name, sizeof r.name, "rec%d", id);`
with `r` in the guarded block. hod (clang 22, `.text` offsets): rows
`0x33a 42:14 is_stmt` (`mov -0x54(%ebp), %ebx; lea 0x4(%ebx), %ebx`:
the `getelementptr` of `r.name`, through the slot's pointer, which the
i386 guarded block uses for every access, `hod_x86/src/ssp.rs`), `0x343
42:44` (the load of `id`), `0x349 42:3` (the call). `llc`: `0x1b2 42:44
is_stmt` (the load of `id`), `0x1b5 42:3`; its `getelementptr` of the
frame object is folded into the call sequence's `lea` (§5.5: columns
moved by `llc`'s folds). So `thread step-over` from line 41 stops at the
first row of line 42 in both, which is hod's `42:14` and `llc`'s
`42:44`. hod's row is the instruction's own location; no wrong value. On
x86-64 the slot is a frame address, the `getelementptr` folds into its
use in hod too, and the lane passes. Proposed permitted class (lldb
sessions): after a `step over`, a `frame #0:` line that differs only in
the column, hod's being that of a `getelementptr` at that line in the IR
that `llc` folds into a later instruction (caret line with it).

## Class C: rows at the return address (rules, proposed)

- **inlined.cpp** (gdb, `finish` out of `observe` into the inlined
  `scale`): hod's return address is `lea 0x10(%esp), %esp`, the
  release of the call's outgoing argument area, at the call's location
  (`15:3`, not a row start): gdb `0x? in scale ... :15`. `llc` reserves
  the area in the prologue; its second call returns to the row `16:10
  is_stmt`: `scale ... :16`. (Its first inlined copy returns to a reload
  of the PIC base inside the `15:3` row, as hod.) Same as `return-column`
  (§5.7), on i386 the line as well as the column, and gdb's `0x? in`.
- **key_call.c** (clang 22, gdb, 3): hod puts the buoy row `16:11
  is_stmt` at the return address (§5.9 K4, the test's intent): `main ()
  at :16`; `llc` reloads the PIC base (`mov 0xc(%esp), %ebx`) after the
  call inside the non-statement row `16:11`, and its buoy row is after
  it: `0x? in main () :16`. The lldb FAILs (6, both clangs, `16:3` /
  `17:19`) are the step that follows from those two stops (not
  measured row by row).
- **call_sites_direct.c** (clang 22, lldb, 3): three differences in one
  transcript: two `finish` stops at the call's column in hod (`14:11`,
  `15:10`) and the next statement's in `llc` (`14:7`, `15:3`), which is
  `return-column` mirrored; and `breakpoint set --name later` at
  `later + ?` in hod, `later` in `llc`: `llc` builds the leaf `later`
  without a frame (the argument's store elided into its incoming slot),
  so its `prologue_end` row is the function's first byte.
