### Findings

1. **`gcc-torture/llvm{22,19}/builtins/strncmp.c`, x86-64, every
   linker**: hod's program ends with SIGABRT, `llc`'s exits 0. Linking
   the eight combinations of hod's and `llc`'s three objects (test, lib,
   main) aborts exactly when the `lib` module (`builtins/lib/strncmp.c`)
   is hod's. That source declares `unsigned char c1, c2;` without an
   initialiser and returns `c1 - c2` when `n == 0`;
   `builtins/strncmp.c:46` calls `strncmp (++s2, ++s3, 0)` and aborts
   unless the result is 0. The result is the stack's leftover bytes:
   undefined behaviour in the test. The same IR with `c1` and `c2`
   stored 0 at entry, built by hod, exits 0. Not a miscompile; it
   passes on AArch64 by chance. Saved with the reproduction in
   `.build/findings/wp-244/x86_64/strncmp-uninit/`.
2. The declines (each module saved with its stderr under
   `.build/findings/wp-244/<target>/`):

| target | test (LLVM 22 and 19) | refusal |
|---|---|---|
| AArch64 | `kiln/.../dcl.attr.cconv/cc-run.cpp` | `cc:win64cc` |
| AArch64 | `kiln/.../target.acle/exclusive-sysreg-run.cpp` | `intrinsic:llvm.aarch64.ldxr.p0` |
| x86-64 | `kiln/.../dcl.attr.cconv/cc-run.cpp` | `cc:win64cc` |
| x86-64 | `kiln/.../dcl.asm/asm-goto.cpp` | `x64:inline-asm` (`callbr`, `asm goto`) |

## What an L6 gate needs

1. **The expected refusals**, as test and refusal name, both LLVM
   majors, every linker (each is 4 FAIL results per LLVM in strict):
   AArch64 `dcl.attr.cconv/cc-run.cpp` `cc:win64cc`,
   `target.acle/exclusive-sysreg-run.cpp`
   `intrinsic:llvm.aarch64.ldxr.p0`; x86-64 `dcl.attr.cconv/cc-run.cpp`
   `cc:win64cc`, `dcl.asm/asm-goto.cpp` `x64:inline-asm`. A gate over
   the corpus in strict mode has to carry this list itself (the entries
   cannot), and should fail on a refusal not in it and on a listed one
   that has gone.
2. **The strncmp entry** (x86-64, both majors) and the mechanism to
   mark an entry whose program is undefined on one target: there is
   none. Entries are written by `capture`, say "do not edit", and are
   checked against their `sha256` and `bytes` in `MANIFEST.tsv`
   (`spec/harness.md` "corpus", "Manifest"; `verify` step 1), so a
   directive added by hand (an `xfail: x86_64` is in the directive
   format, `spec/harness.md` "Test directives") breaks the manifest.
   `capture` writes only `covers`, `target`, `llvm`, `link`, `llc-args`,
   `args`, `stdin`, `exit` and `stdout` ("Entries"). `SKIPPED.tsv` has
   no reason for undefined behaviour ("Skip reasons"; the reasons are
   `Unfit` names in `xtask/src/corpus/`). Admission (the oracle and the
   `llc -O2` witness, on the capturing target) cannot see behaviour
   that only another code generator's stack layout shows. The only
   acknowledgement is prose on the reasons page ("A FAIL in a test hod
   built is a wrong result unless the entry's program is undefined").
   So today the gate would need its own list for this entry too.

## How to repeat

From the worktree, `source scripts/env.sh`, `CARGO_TARGET_DIR` a build
directory of its own, `HOD_REQUIRE_TOOLS=1`, `HOD_WILD=<wild 0.11.0>`;
`X=$CARGO_TARGET_DIR/release/xtask`, `H=$CARGO_TARGET_DIR/release/hod`:

```
cargo build --release -j 6 -p hod_cli -p xtask
$X corpus verify --strict -j 4 --hod $H .build/corpus
$X corpus verify --target x86_64 --strict -j 4 --hod $H .build/corpus-x64
$X corpus verify --target x86_64 -j 4 --hod $H .build/corpus-x64        # hybrid, for the page
$X corpus reasons --llc -j 4 --hod $H --report docs/status/reasons.md .build/corpus
$X corpus reasons --target x86_64 --llc -j 4 --hod $H --report docs/status/reasons-x64.md .build/corpus-x64
$X debug run -j 4 --hod $H ; $X debug run --target x86_64 -j 4 --hod $H
$X debug verify -j 4 --hod $H ; $X debug verify --target x86_64 -j 4 --hod $H .build/corpus-x64
$X debug trees -j 4 --hod $H .build/corpus ; ... .build/corpus-x64
CARGO_PROFILE_DEV_DEBUG=line-tables-only cargo xtask ci
```

Results: `<build>/corpus/verify-*.tsv`, `<build>/l7/results-*.tsv`.
