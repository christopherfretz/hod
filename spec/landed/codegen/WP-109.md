# WP-109 — pre-opt modules with coroutines (design 0005 §5, §6 C6)

Landed: the pre-opt trigger set is {`alwaysinline`, coroutines}: a front
end may hand hod a module before LLVM's `-O0` pipeline when that pipeline
would only inline `alwaysinline` calls and lower coroutines, on AArch64,
in strict and hybrid mode (`spec/cli.md` "Pre-opt modules", which
replaces "Always-inline" as the section and keeps it as a subsection).
Every coroutine refusal is decided before code generation, so a decline
costs reading and judging, never code generation.

## What it did

| where | change |
|---|---|
| `crates/hod/src/session/coro.rs` | `module_refusal`: at `end_module`, a module with a `presplitcoroutine` attribute set is declined as `attr:presplitcoroutine` when the matrix does not accept the attribute on its target, as `coro:target` when the target's code generator has no coroutine bodies (`Target::CORO_BODIES`), before any body is read. `refusal`: as each body arrives (only in a module that declares a `llvm.coro.*` function or has a `presplitcoroutine` set), the plan's `coro:*` refusals, then the code generator's own, checked by the same rules: `coro:outside-coroutine`, `a64:coro-preserve-cc`, `coro:overaligned-stack-slot`, `coro:begin-shared-block` |
| `crates/hod/src/session.rs` | the two hooks (`judge_module`, `judge_built`) |
| `crates/hod_ir/src/classify/matrix.rs` | the `attr:presplitcoroutine` note; `docs/status/support.md` regenerated. The AArch64 cells of the coroutine attribute and intrinsics were already supported (WP-105 to 107); `intrinsic:llvm.coro.frame` stays unsupported (no front end writes it) |
| `spec/cli.md` | "Pre-opt modules": the pipeline replaced, the trigger set, what hod answers, "Declined early", "Coroutines", kiln's contract with coroutines, the fallback of a pre-opt module (`opt` + `llc`); "Reasons": the module-level row; the test table |

Code generation keeps its checks as the backstop;
`every_coroutine_refusal_is_decided_before_code_generation` holds the
two to the same name for every shape. Before this package, those four
names surfaced only during code generation, after other functions had
been compiled; an x86-64 coroutine module was declined at its first
coroutine body.

## libc++ `support.coroutines`, strict

kiln's runner (`cargo xtask libcxx --tag llvmorg-22.1.8 ...
std/language.support/support.coroutines`, the recipe of
`docs/status/libcxx-hod.md`, `HOD_STRICT=1`, `-j 3`), twice:

- **pre-opt**: kiln's contract emulated without changing kiln: the shim
  of `cargo xtask shim` with its `bin/opt` replaced by a script that runs
  `-passes=verify` in place of kiln's `-O0` pipelines
  (`coro-early,cgscc(coro-split),coro-cleanup,globaldce` and
  `default<O0>`), so `llc` (hod) receives the module as the front end
  wrote it: **25 of 25 pass**; hod built all 25 objects, the 10 coroutine
  modules (17 coroutines, the handle operations and `coro.noop`) from
  their pre-opt bitcode; no OOM kill.
- post-opt (the plain shim, kiln running `opt`): 25 of 25 pass, as
  before.

## Speed and size against `opt` + `llc`

The 44 built modules, release hod on the pre-opt text, against kiln's
route: `opt` with kiln's pipeline (`default<O0>` when the module has an
`alwaysinline` set, else the coroutine passes) writing bitcode, then
`llc -O0 -relocation-model=pic -filetype=obj`. Medians of 7 (hod) and 5
(`opt` + `llc`) process runs per module, summed; load average 22-24 on a
shared machine. Text is `llvm-size`'s.

| dialect | | hod | opt + llc | ratio | hod object / llc object | hod text / llc text |
|---|---|---:|---:|---:|---:|---:|
| LLVM 19 | `-O0` | 530 ms | 1243 ms | 2.3× faster (per module 1.5-4.8×) | 0.92 | 0.69 |
| LLVM 22 | `-O0` | 496 ms | 1080 ms | 2.2× (1.3-4.6×) | 0.92 | 0.69 |
| LLVM 19 | `-g` | 529 ms | 1412 ms | 2.7× (1.6-4.7×) | 0.91 | 0.69 |
| LLVM 22 | `-g` | 445 ms | 1307 ms | 2.9× (1.7-5.4×) | 0.90 | 0.69 |

Most modules are small, so process start dominates both columns. Code is
31% smaller: one body per coroutine where `coro-split` writes the ramp
and two clones (design 0005 expected about half of `llc`'s coroutine
bytes; the 31% is of all code, coroutines and the rest).

## Declines cost little

The largest corpus coroutine module,
`coro.generator/libstdcxx-generator-elements-of-run` (LLVM 22, 429 KB of
text), and the largest refused one,
`basic.contract.eval/run-coroutine-post-enforce` (102 KB). Process wall
time, median of 21 runs, three interleaved rounds (load 22-23):

| | round 1 | round 2 | round 3 |
|---|---:|---:|---:|
| hod builds the largest module (AArch64) | 43.9 ms | 40.8 | 30.7 |
| hod declines it for x86-64 (`attr:presplitcoroutine`, module level; kiln++ `--target=x86_64-unknown-linux-gnu` form) | 18.8 | 24.0 | 17.4 |
| hod declines `post-enforce` (`coro:frame-access-after-suspend`, body level) | 21.1 | 24.3 | 18.8 |
| `opt` + `llc` on the largest module (the fallback's work) | 137.9 | 139.6 | 124.8 |
| `opt` + `llc` on `post-enforce` | 73.3 | 62.1 | 60.8 |

In process (`HOD_TIME_PHASES`), the x86-64 decline of the largest module
is 4.9-6.2 ms (read 1.3-1.8, module-level parse 3.3-4.7, classify under
0.1; no body read, no code generation) against 13.7-23.1 ms for its
build; the `post-enforce` decline is 10.5 ms (bodies read and judged up
to the refused one: 4.5). A declined module adds about 15-30% of the
fallback's own time; what remains is reading the text, which is
`hod_ll`'s.

## Tests

- `crates/hod/tests/coro_preopt.rs` (4): a pre-opt coroutine compiles
  through every phase; each coroutine refusal (`a64:coro-preserve-cc`
  twice, `coro:overaligned-stack-slot`, `coro:begin-shared-block`,
  `coro:outside-coroutine`, `coro:frame-access-after-suspend` in both
  dialects) is the answer without the `bodies` phase and is the name
  `hod::generate` (code generation alone) gives; x86-64 declines by its
  module level (a body that does not parse after it is never read), and
  with the attribute forced on, as `coro:target`; modules without
  coroutines are unaffected.
- `crates/hod_cli/tests/preopt_coro.rs` (3): kiln's command line on
  standard input: `gen-19`/`gen-22` built (status 0), `post-sync` and
  the x86-64 form declined with status 2, the message, no output, the
  coverage log reasons; hybrid: the fallback runs for the declined
  modules only, with the same bytes; a real `opt-22` + `llc-22` wrapper
  as fallback turns the declined module into an object.
- Mutation: `generator_refusal` disabled: the refusal test fails (the
  `bodies` phase ended, i.e. the refusal came from code generation).

## Notes and follow-ups

- x86-64 keeps declining coroutine modules until WP-137 sets the
  matrix cell and `X64::CORO_BODIES`; nothing here needs to change then.
- The plan is computed twice for each coroutine (the session, then code
  generation); it is linear (WP-104: 32 ns per instruction).
- kiln: the contract in `spec/cli.md` "Pre-opt modules", "kiln's
  contract" (kiln's `needs_coro_lowering` and `needs_always_inline`
  match the trigger set). kiln knows the target, so it may skip hod for
  coroutine modules on x86-64 until WP-137.
- `scripts/preopt-corpus.sh` does not set `KILN_LLVM_DIR` for LLVM 19
  entries, so its LLVM 19 coroutine forms use LLVM 22's intrinsics, which
  `opt-19` rejects; this census regenerated them with it set.
