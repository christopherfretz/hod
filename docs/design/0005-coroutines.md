# Design 0005: coroutines without `opt`

Status: proposed 2026-11-12 (WP-100); B accepted in shape by the supervisor, and revised after that review (frame residency rules of 3.4, the invariant of 3.3). A design; no product code. Design
0001 point 6 made coroutines hod's to handle after `alwaysinline`
(WP-021). Today kiln runs `opt` on every module that declares an
`llvm.coro.*` intrinsic and hod refuses an unsplit coroutine by name
(`attr:presplitcoroutine`, `intrinsic:llvm.coro.*`, `type:token`).

Paths are hod's unless marked `kiln:` (kiln at `bd60e1829`). Experiments
ran on the shared host (load 19-27, aarch64); times are proportions.
Inputs and scripts worth keeping are in `docs/design/0005-data/`; every
other input is under `.build/target-wp-100/` and is regenerated by the
commands quoted.

## Question

How does hod compile a module containing unsplit switch-resumed
coroutines (`presplitcoroutine`, `llvm.coro.id/alloc/size/align/begin/
save/suspend/end/free/promise/resume/destroy/done/noop/is_in_ramp`,
`llvm.coro.await.suspend.*`), correctly, at `-O0` speed, without LLVM?

**Answer (section 3.5): approach B.** hod compiles each coroutine body
once. The heap frame holds the values that must survive a suspend, and
they are addressed through a reserved callee-saved register. `resume`
and `destroy` are two small entry stubs that build the same machine
frame and jump into the body just after the suspend point.
`hod_xform` provides the analysis that both approaches need: which
values live in the frame, how suspends are numbered, and what is refused.

## 1. What LLVM does at `-O0`

kiln's lowering (`kiln:crates/kiln_codegen/src/coro.rs`) ports clang's
`CGCoroutine.cpp`. It writes the same IR shapes as clang 19 and 22. The
only differences are dialect: for LLVM 22, kiln writes `void
@llvm.coro.end` plus `@llvm.coro.is_in_ramp()`, where LLVM 19 has `i1
@llvm.coro.end`. With `-fclang-compat=19` kiln writes `bitcast ptr
%promise` before `coro.id`. kiln's driver
(`kiln:crates/kiln_driver/src/codegen_cmd.rs:831`) asks for the lowering
when any `declare ... @llvm.coro.` line appears. That includes a module
whose only coroutine intrinsic is `__builtin_coro_noop` and that has no
coroutine. The pipeline is `coro-early,cgscc(coro-split),coro-cleanup,
globaldce`, the coroutine part of `default<O0>`.

The reference input is `0005-data/gen.cpp`: a generator with an
initial, a yield and a final suspend; a local whose address is taken;
a loop. It was built with clang 22 to `gen.c22.pre.ll`, and run through
`opt` at each stage:

```sh
clang++ -std=c++20 -O0 -S -emit-llvm -Xclang -disable-llvm-passes gen.cpp -o pre.ll
opt -passes='coro-early' -S pre.ll                                       # early.ll
opt -passes='coro-early,cgscc(coro-split)' -S pre.ll                     # split.ll
opt -passes='coro-early,cgscc(coro-split),coro-cleanup,globaldce' -S pre.ll  # post.ll
```

The front end's shape is the input. `coro.id(align, promise, null,
null)` is followed by `coro.alloc`, and on its true edge by `operator
new(coro.size)`. A `phi` (null | mem) feeds `coro.begin(id, mem)`. The
body follows. Each await is `coro.save` → `coro.await.suspend.{void,
bool,handle}(awaiter, frame, wrapper)` → `coro.suspend(save, final)`.
The suspend's result goes to a `switch i8 %s, label %suspended [0:
%resume, 1: %destroy]`. Cleanups lead to `coro.free(id, frame)` and
`operator delete(mem, coro.size)`. The suspended edge leads to
`coro.end(null, false, none)` and then to the ramp's `ret`. The unwind
path does `coro.end(null, true, none)`, then `is_in_ramp` (or the `i1`
result on LLVM 19) chooses between freeing the frame and only
rethrowing.

### 1.1 `coro-early`

The rewrites run in every function, whether or not it is a coroutine
(`gen.c22.early.ll`, `main` and the `coroutine_handle` members):

| intrinsic | becomes |
|---|---|
| `coro.resume(p)` | `call fastcc void (coro.subfn.addr(p, 0))(p)` |
| `coro.destroy(p)` | the same with index 1 |
| `coro.done(p)` | `icmp eq (load ptr, p), null`: the resume pointer is null |
| `coro.promise(p, align, from)` | `gep i8, p, ±alignTo(16, align)`; minus when `from` is true |
| `coro.noop()` | `@NoopCoro.Frame.Const`, a **private** constant `{ptr, ptr}`. Both pointers are `@__NoopCoro_ResumeDestroy`, an internal `fastcc void(ptr)` that returns |
| `coro.free(none, …)` | its token operand is set to the function's `coro.id` |

`coro.id` is marked cannot-duplicate and gets the function itself as its
third operand. In a function that calls `coro.suspend`, `noalias` is
removed from the arguments (observed: the `sret` argument loses
`noalias`). The two removals matter only to an optimizer.

### 1.2 `coro-split`, switch ABI

**Suspend points.** Each `coro.suspend` is a suspend point. They are
numbered in instruction order, with the final suspend (`i1 true`) moved
last. In `gen`: initial 0, yield 1, final 2. The index field has type
`iN`, where N = max(1, ⌈log₂ #suspends⌉): `i2` in `gen`, `i1` in a
two-suspend `task`. The index is stored at `coro.save`, before the
`await_suspend` wrapper runs (the wrapper may resume the coroutine on
another thread). A final suspend instead stores `null` to the resume
pointer. If the coroutine has an unwinding `coro.end`, it also stores
the final index (`0005-data/exceptions.cpp`: `store i1 true` next to the
`null`). Before splitting, edges into the suspend's successors are split
so that no `phi` takes an operand from across a suspend (the `.from.N`
blocks of `post.ll`).

**Which values go into the frame.** The rule is decided per value. A
value goes into the frame when its content or address must survive a
**resumption edge**: the 0 or 1 successor of a suspend switch. Paths
that pass `coro.end` are cut. The suspended (default) edge stays in the
same activation. The categories:

- The promise alloca is a header field.
- An alloca with `!coro.outside.frame` stays on the stack. clang 22 puts
  this on parameter allocas; kiln and clang put it on the
  `get_return_object` result (GRO); kiln marks nothing else.
- Uses are collected through *aliases*: pointers derived by GEP or cast
  are followed, and their uses count as uses of the alloca. An alloca is
  *escaped* when some use, through an alias or not, is anything other
  than a load from it, a store to it, a `memcpy`/`memmove`/`memset` on
  it, a lifetime marker, or a debug record. Examples of escapes: a store
  *of* its address, a call argument not marked `captures(none)`, a
  `phi`, a `select`, `ptrtoint`. In kiln's output, `captures(none)`
  appears only on intrinsic declarations, so every call argument
  escapes.
- An alloca with lifetime markers (on the whole alloca, not on a part of
  it) goes into the frame if some use, including a `lifetime.end`, is
  reachable from a `lifetime.start` across a suspend. If it is escaped,
  it also goes in when a suspend lies on a path between two of its
  `lifetime.start`s, or on a loop through one.
- An escaped alloca without lifetime markers **always** goes into the
  frame. Once the address has escaped, whether the alloca is "used after"
  a suspend cannot be decided from its direct uses.
- An unescaped alloca without lifetime markers goes into the frame if
  one use reaches another across a suspend.
- An SSA value used across a suspend is spilled to the frame at its
  definition and reloaded in the clones.
- If a frame-resident alloca may be written before `coro.begin` (a
  store, or an escape, that `coro.begin` does not dominate), the
  original stack alloca stays for those uses. Its contents are copied
  into the frame field just after `coro.begin`, and the uses that
  `coro.begin` dominates are redirected to the field.

The rule was checked with hand-edited IR (`.build/target-wp-100/exp/
esc*.pre.ll`):

- An alloca passed to a call only before the first suspend is in the
  frame, even as an `sret` argument.
- An alloca that is stored before the first suspend and loaded after it
  is in the frame.
- An alloca passed as `captures(none)` before the first suspend and
  loaded after it is in the frame.
- kiln's unescaped return-value slot stays on the stack. It is stored
  before the initial suspend and loaded after `coro.end`.

SSA spills happen at `-O0`, though rarely. One corpus module
(`expr.await/reference-result-bound-to-reference.cpp`) spills two
values. Both are the `ptr` that `await_transform` returns when it
yields a reference: it is used by `await_ready` before the suspend and
by `await_resume` after it.

**Frame type and layout.** The frame type is `%F.Frame = { ptr resume,
ptr destroy, promise, ... }`. The resume pointer is at 0, the destroy
pointer at 8, and the promise at `alignTo(16, align(promise))`. All
other fields, the index included, are packed by
`performOptimizedStructLayout`, even at `-O0`: largest alignment first,
with gaps filled. In `gen`:

| offset | field |
|---|---|
| 0 | resume |
| 8 | destroy |
| 16 | promise (4) |
| 20 | parameter copy `n` |
| 24 | `p` |
| 32 | `local` |
| 36 | `i` |
| 40 | index `i2` |
| 41-43 | three awaiters |

The size is 48 (`operator new(48)`). Three awaiter allocas that never
cross a suspend stay on the stack in every clone. `coro.size` becomes
the constant size. `coro.align` becomes the frame's alignment: the
largest field alignment.

**Over-alignment** (`0005-data/overaligned.cpp`: an `alignas(64)`
promise and an `alignas(128)` local that lives across a suspend):

- LLVM lays the frame out as if its start were aligned to 128. Index and
  awaiters are at 16-20, then 43 padding bytes, the promise at 64, the
  local at 128, and the size is 256.
- Without `-fcoro-aligned-allocation` the frame comes from
  `operator new(256)`. At run time `&promise % 64 == 48` and
  `&local % 128 == 48`: LLVM quietly misaligns both.
- With `-fcoro-aligned-allocation` the frame comes from
  `operator new(256, align_val_t(128))`. Both objects are aligned, and
  the layout is the same.

`from_promise` relies only on the promise offset.

**Clones.** Three clones are made, each `internal fastcc void(ptr
frame)`: `F.resume`, `F.destroy` and `F.cleanup`. Each is a full copy of
the body. In the ramp `F` and in each clone, the suspend's switch
becomes a constant: `switch i8 -1` in the ramp, `0` in `.resume`, `1` in
`.destroy` and `.cleanup`. At `-O0` nothing deletes the dead arms, so
every clone carries the whole body:

| | instructions (IR lines) |
|---|---|
| the 67 coroutines of the kiln corpus, before splitting | 11,821 |
| ramp plus three clones, after splitting | 38,848 (**3.29×**) |
| `gen`, before / after | 164 / 634 (3.87×) |

Each clone starts with a load of the index and a `switch` to the
`resume.N` blocks. The differences between the clones:

- `.resume`: the final suspend's case is removed, since resuming at the
  final suspend is undefined.
- `.destroy`: if there is no unwinding `coro.end`, `.destroy` first
  tests whether the resume pointer is null and, if so, enters the final
  suspend's destroy arm. Otherwise it dispatches on the index alone.
- `.cleanup`: differs from `.destroy` only in that `coro.free` returns
  null, so nothing is deallocated. It is used when allocation was
  elided.

**The ramp at coroutine start.** At `coro.begin` the ramp stores
`@F.resume` and `select coro.alloc, @F.destroy, @F.cleanup` into the
header. Arguments and allocas written before `coro.begin` are copied
into the frame after it.

**Allocation elision is off at `-O0`.** `CoroElide` is not in the
pipeline. `coro.alloc` becomes `true` (`br i1 true` in `post.ll`), and
`F.cleanup` is reachable only through `select i1 true`, which is dead.

**`coro.end`.**

- In the ramp: a no-op. The code after it is the ramp's return path.
  The LLVM 19 `i1` result is false there, and `is_in_ramp` is true.
- Non-unwinding, in a clone: becomes `ret void`.
- Unwinding, in a clone: marks the coroutine done (null resume pointer,
  final index) and falls through to the `resume` of the landing pad.
  `is_in_ramp` is false, so the clone does not free the frame.

**Symmetric transfer.** `coro.await.suspend.handle(awaiter, frame,
wrapper)` is lowered differently in the ramp and in the clones.

In the clones, it becomes a call of the wrapper, then a tail call of the
returned handle's resume function, then `ret void`:

```
%h = invoke ptr @F.__await_suspend_wrapper__final(ptr %awaiter, ptr %frame) to ... unwind ...
%fn = load ptr, ptr %h
musttail call fastcc void %fn(ptr %h)
ret void
```

In the ramp, the resume function is called normally and control goes on
to the suspended edge. `.void` and `.bool` become plain calls (or
invokes) of the wrapper. The tail call is load-bearing at `-O0`. In
`0005-data/deep-symmetric-transfer.cpp`, a loop awaits 3,000,000 tasks,
with two transfers each, on an 8 MB stack. Built with `opt` + `llc`, it
prints `3000000 1`. With `musttail` replaced by `call` in `post.ll`, it
dies with SIGSEGV.

**Exceptions.** Landing pads are cloned with the body, so every clone
has the whole LSDA. The C++ `unhandled_exception` try/catch is ordinary
IR. An exception that `unhandled_exception` rethrows leaves `.resume`
through the unwinding `coro.end`, which has marked the coroutine done.
In `0005-data/exceptions.cpp` the exception reaches `main` through
symmetric transfers, and destructors run in the expected order.

**Debug information** (`clang++ -g`, then the same pipeline, then
`llc -O0`, `.build/target-wp-100/exp/gen.g.dwarf`):

- Each clone gets its own `distinct DISubprogram` with the same `name`
  and `linkageName: "F.resume"`, `.destroy` or `.cleanup`.
- A clone receives the frame in `%.debug = alloca ptr`. Every frame
  variable is `#dbg_declare(ptr %.debug, …, DIExpression(DW_OP_deref,
  DW_OP_plus_uconst, off))`, which becomes `DW_OP_fbreg -8, DW_OP_deref,
  DW_OP_plus_uconst 0x18` in DWARF.
- An artificial `__coro_frame` of type `F.coro_frame_ty` has members
  `__resume_fn`, `__destroy_fn`, `__promise`, the variables by name,
  `__coro_index`, and unnamed fields such as
  `struct_std____n4861__suspend_always_0`.
- `__promise` is a variable.
- `DW_TAG_label`s `__coro_resume_N` mark the resume points.
- In the ramp, the frame variables are `#dbg_declare`s on the
  `coro.begin` **SSA value** with `DW_OP_plus_uconst`. SelectionDAG at
  `-O0` drops them: the ramp's DIE has `n` (the parameter alloca, which
  is not in the frame) and a location-less `__coro_frame`, and **no**
  `p`, `local` or `i`.

### 1.3 `coro-cleanup` and `globaldce`

`coro-cleanup` lowers what is left:

- `coro.subfn.addr(p, i)` becomes `load ptr, gep {ptr, ptr}, p, 0, i`.
- In a function that was not split, `coro.alloc` becomes true,
  `coro.begin` becomes its memory operand, and `coro.free` becomes its
  frame.
- `coro.id` and `coro.save` are deleted.

After it, no `llvm.coro.*` intrinsic remains (counted per stage on
`gen`: 13 kinds before, 11 after early, 5 after split, 0 after
cleanup). `globaldce` changes no definition in any experiment: the set
of `define`s is the same with and without it. At `-O0`, it only deletes
declarations.

### 1.4 What LLVM gets wrong: two uses after free

**The exception slots.** The leaf coroutine of `0005-data/exceptions.cpp`
keeps the exception-pointer and selector slots in the frame. These
slots are unescaped and have no lifetime markers. LLVM's test for them
pairs every use with every use: some store in a landing pad reaches,
across a suspend, some load on another path, and that counts as a
crossing. No load ever sees a value stored before a suspend.

The ramp's unwind path then frees the frame and *afterwards* loads
those slots to rethrow. `0005-data/gro-throws-uaf.cpp` makes
`get_return_object` throw to reach that path. Built with `opt` + `llc`
from LLVM 19 and from LLVM 22:

- Plain, it prints `caught gro`.
- With `GLIBC_TUNABLES=glibc.malloc.tcache_count=0 MALLOC_PERTURB_=165`
  (freed memory filled with 0x5a), it **crashes with SIGSEGV** (exit
  139).

The simpler `ramp-throw.cpp`, where the body throws in the ramp, is
fine. There the slots do not cross a suspend and stay on the stack.

**The return object under a postcondition** (kiln only: clang 22 has no
P2900 contracts). A coroutine's postcondition is evaluated by the ramp
after `coro.end` on the return object. In kiln's output that return
object is an alloca without lifetime markers. The postcondition takes
its address (`r.ok()`), so the alloca is escaped and LLVM puts it in
the frame. If the coroutine runs to completion inside the ramp, the
ramp frees the frame before the postcondition reads the return object.

`0005-data/post-sync.cpp` has `initial_suspend` and `final_suspend`
both `suspend_never`, and `post(r: r.ok())`. Built with kiln++
`-fcontract-evaluation-semantic=enforce` and LLVM 22 `opt` + `llc`:

- Plain, it prints `42`.
- Under the same poisoning, the postcondition fails on the freed bytes
  and the program terminates (exit 134).

Three corpus modules have the same shape:
`basic.contract.eval/run-coroutine-post-{enforce,observe,quick-enforce}`,
in `ea()` and `bad()`. They work only because those coroutines suspend
before the ramp returns. In that case the ramp still reads the frame
while the coroutine is suspended, which is a data race once another
thread may resume it.

Two consequences follow:

- The oracle is not perfect. Validation compares behaviour and knows
  the oracle's own failures (section 5).
- An implementation must not copy LLVM's rule blindly. hod narrows the
  rule for unescaped slots, where precision is provable (3.4, rule 3).
  For escaped slots hod keeps LLVM's rule and refuses the unsafe shape
  by name (3.4, the safety conditions).

## 2. The observable ABI, and what is private

**Must match exactly.** Another object compiled by `llc` resumes,
destroys and inspects hod's coroutines, and the reverse, because
`coro-early` inlines these operations into every caller:

- **Frame header:** the resume pointer at offset 0 and the destroy
  pointer at offset 8. Each points to a `void(ptr frame)` function that
  follows the C calling convention: `fastcc` equals C for one pointer
  argument on AArch64 and on x86-64.
- **`coro.subfn.addr` indices:** 0 is resume, 1 is destroy.
- **`done()`:** the resume pointer is null exactly from the final
  suspend onward. That includes a coroutine finished by an exception
  through an unwinding `coro.end`. Before the final suspend it is
  non-null. Null must be stored *before* the final `await_suspend`
  wrapper runs, because the wrapper may hand the handle to another
  thread.
- **Promise offset:** `alignTo(16, alignof(promise))` from the frame
  start. `from_promise`/`promise()` (`coro.promise` with `±offset`)
  depend on it. The alignment is the one passed to `coro.promise` by
  the code that uses the handle; it is the promise type's alignment.
- **Allocation:** through the front end's `operator new(coro.size)` (and
  aligned variants with `coro.align`), freed through its
  `operator delete(…, coro.size)`. The size need only be the same at
  both calls. kiln's `promise-new-delete-const-size-run` checks exactly
  that, not a value.
- **The noop frame:** a frame whose two pointers lead to a function
  that returns. Each object has its own private copy, so equality
  across objects is not required.
- **Symmetric transfer runs in constant stack** (1.2).

**Private to one coroutine**, so hod may differ:

- the layout after the header and the promise;
- the frame size;
- the index's encoding and location, and whether one exists at all;
- the number of clones, their names, and whether they are separate
  functions;
- which values live in the frame;
- the cleanup clone.

Two of these are seen by tools rather than by programs. Debuggers and
pretty printers look up `__coro_frame`, `__promise` and `__coro_index`
by name. Symbolizers name the resume pointer's target. Section 5 keeps
those names.

## 3. Approaches

All three approaches share one question: which values must survive a
resumption edge (1.2, made precise in 3.4). They differ in where the
cloning happens, if anywhere.

### 3.1 A: `hod_xform` splits as LLVM does

This reproduces section 1 as IR to IR on `hod_ir`. It produces the ramp
and the three clones (or two, without `.cleanup`) as `hod_ir` bodies
that the existing code generator compiles unchanged.

- **What changes:**
  - `hod_ir` has no in-place rewriting. A body is built once through
    `FunctionBuilder` (`spec/ir.md` §5.1), so A rebuilds four bodies per
    coroutine with value maps: allocas become offsets from the frame
    argument, SSA spills get reloads, `phi`s are split at suspend
    edges, and switch arms are folded.
  - New module symbols are needed (`F.resume`, `F.destroy`, and the
    frame type if kept), plus new debug nodes: a subprogram per clone,
    rewritten `#dbg_declare`s, the frame type.
  - The module tables are read-only while bodies compile on workers
    (`spec/ir.md` §5.1). Growing them is a planned extension (§10)
    that design 0004's streaming session would also have to adopt.
    Adding the symbols when the reader meets `presplitcoroutine` avoids
    that, but ties the reader to the transformation.
  - `hod_cg`/`hod_a64` change only for `musttail` through a loaded
    pointer, which already exists (§5.4 tail exits). `hod_eh` needs
    nothing.
- **Correctness risks:**
  - cloning (value maps over `phi`s, landing pads, debug records);
  - the spill analysis;
  - reproducing LLVM's frame rule, including its use after free (1.4),
    unless it is improved;
  - the debug-info rewrite.

  A's strength is that its output is IR. `hod_xform`'s output can be
  run through `llc` and through hod, so the transformation is tested
  apart from the code generator.
- **Compile time and size:** 3.29× the instructions for coroutine bodies
  (1.2), plus building them. In the 25 kiln corpus modules, `llc`'s
  coroutine code is 66,708 bytes of ramps plus 161,508 bytes of clones,
  out of 312,052 function bytes: **73% of the code, 52% in clones**.
  A would emit the same proportions.
- **Debug info:** same as LLVM, unless hod fixes the ramp's variables
  (1.2).
- **Unwind:** four FDEs and four LSDAs per coroutine.
- **Escaped allocas:** in the frame, as LLVM does.
- **Dynamic allocas:** the same as LLVM. Each activation allocates its
  own; if one is used after a resumption, the reference dangles,
  undefined in LLVM too.
- **Refused:** whatever the cloner does not handle, by name.

### 3.2 B: one body, the frame in the heap, entry stubs

hod at `-O0` already keeps every value that outlives a call in a frame
slot (`spec/codegen.md` §4.4: the save set is empty, so a call spills
every live value to its home). A suspend point can therefore be lowered
as **a call that returns −1 now and returns 0 or 1 later, in another
activation**. At the point just after that call, no register holds a
live value. Every value that crosses is in its home, and the homes of
crossing values are in the heap frame. A second activation can enter
there.

```
F:          ramp prologue (machine frame FRAME_S, saves x29, x30, x19); mode := ramp
            ... code before coro.begin: stack slots only
            coro.alloc → 1;   coro.size → movz/movk patched at end_function
            coro.begin(id, m) → x19 := m; [x19,#0] := adr F.resume; [x19,#8] := adr F.destroy
            ... body: heap-resident slots are [x19, #o], all others [x29, #o]
            coro.save k → [x19,#idx] := k  (final: also [x19,#0] := 0)
            coro.await.suspend.* → call of the wrapper (handle form: 3.3)
            coro.suspend k:   mov w0, #-1
   .Lk:                       ; re-entry point: w0 = 0 (resume) or 1 (destroy)
            ... the switch on w0 as usual; the suspended edge leads to coro.end
            coro.end(false): mode == ramp ? fall through : branch to epilogue (ret void)
            ... the ramp's return path; one epilogue restores x19, x29, x30
F.resume:   the same prologue (same FRAME_S); x19 := x0; mode := clone;
            w16 := [x19,#idx]; dispatch → .Lk with w0 = 0
F.destroy:  the same, with w0 = 1
```

- **What changes:**
  - **`hod_xform`:** the plan (3.4).
  - **`hod_cg`:**
    - a second area in `Frame`, `FrameRef::Coro(o)`, a bump allocator
      that starts after the header and the promise;
    - homes and body slots placed in it according to the plan;
    - `coro.size`/`coro.align` patch sites;
    - the `Target` hooks for the entry stubs and the re-entry label;
    - `coro.suspend` treated as a call by the location policy.
  - **`hod_a64`:**
    - `Cursor::frame` and the slot addressing of `mem.rs` (the only two
      places that name `FP` as a slot base, `common.rs:235`,
      `mem.rs:231`) take x19 for `Coro`;
    - the prologue saves x19 in coroutine functions: a new 8-byte
      register-save slot at `Local(16)`, CFI `offset x19`, restored in
      the epilogue and in tail exits;
    - the stubs;
    - the intrinsics;
    - the mode slot (one machine-stack word).

    x19..x28 are not in hod's pool (§5.5: pool x9-x14), so reserving
    x19 costs no register pressure.
- **Correctness risks:**
  - Entering a function in the middle. The re-entry point is exactly a
    call's return point, the one state the code generator already
    reasons about. The stub has built the same machine frame (FRAME_S
    is final when `end_function` patches all three prologues).
  - The plan's crossing analysis: a value that crosses but is homed on
    the stack is wrong code. It is shared with A.
  - The x19 save, restore and CFI.
  - Mode-dependent `coro.end`, `is_in_ramp`, and the handle form.
- **Compile time and size:**
  - The body is compiled **once**. A coroutine costs its ramp-sized code
    plus two stubs of about 10 instructions and a dispatch of about 2
    instructions per suspend.
  - On the corpus proportions above, that is about 67 KB in place of
    228 KB. Module code is about **half** of A's (~157 of ~312 KB in
    `llc`'s bytes; hod's own bytes scale the same).
  - Compile time follows instruction count, about 0.3× A's work on
    coroutine bodies.
  - The analysis is linear in blocks × suspend points (max 6 suspends
    per coroutine in the corpus).
- **Debug info:**
  - One subprogram, valid in every activation. Heap variables are
    `DW_OP_breg19 +off`. Unwinders and debuggers recover x19 in outer
    frames from the callees' CFI, the standard rule for callee-saved
    registers.
  - Unlike `llc`'s, hod's ramp shows the frame variables after
    `coro.begin`.
  - The stubs are local `STT_FUNC` symbols named `F.resume` and
    `F.destroy`, so a resume pointer symbolizes as with LLVM. Each has
    an artificial subprogram with `__promise` and `__coro_frame`.
  - In a resumed activation the PC is inside `F`, so backtraces name
    the coroutine itself (LLVM's clones carry the same `DW_AT_name`).
- **Unwind:** one FDE and one LSDA for `F`. Its CFI rows
  (CFA = x29 + FRAME_S; x29, x30 and x19 saved under it) hold for every
  activation, because every entry builds the same frame. The stubs get
  FDEs of their own, or rows that restate the entry state; landing pads
  are shared.
- **Escaped allocas:** in the heap by LLVM's rule (3.4, rules 4 and 5),
  so an address taken in one activation stays valid in the next.
- **Dynamic allocas:** on the machine stack (§5.2), dangling after a
  resumption as in LLVM. The first version refuses them, together with
  `stacksave`/`stackrestore`, in coroutine bodies
  (`coro:dynamic-alloca`): a `stackrestore` of a value saved by another
  activation would move `sp` into a dead stack. The corpus count is 0.
- **Refused:** see 3.4 and section 4.

**Variant B0, rejected:** the frame pointer *is* the heap frame.
CFI defines the CFA from x29, and the unwinder restores the caller's
`sp` from the CFA, which would be a heap address. Supporting that needs
`DW_CFA_def_cfa_expression` with a stored `sp`. Outgoing arguments,
dynamic allocations and the ramp before `coro.begin` still need a real
stack. And every slot, including ones that must not outlive a free
(3.4), would sit in the heap.

### 3.3 Details of B that the packages must get right

- **Invariant: no frame access once the coroutine may run elsewhere.**
  The suspending activation makes *no access through x19* (no load,
  store, spill to a heap home, or reload) after an `await_suspend`
  wrapper (`coro.await.suspend.void/bool/handle`) has returned. This
  covers every path from the return of the wrapper to the `coro.suspend`
  and the whole −1 path after it, up to the activation's return or tail
  exit. Once the wrapper returns, the coroutine may already be running
  or destroyed on another thread, or (`0005-data/resume-inside-await-
  suspend.cpp`) inside the wrapper itself. `.bool`'s *false* edge is
  exempt: the coroutine did not suspend.

  How B keeps it:
  - Under hod's location policy (`spec/codegen.md` §4.1, §4.4), a home
    value is stored to its home when it is defined, and a call only
    displaces *register* values. Every value live across the suspend is
    therefore already in its heap home before the wrapper is called.
    The wrapper call itself may displace register values; that happens
    *before* the call.
  - The `coro.suspend` "call" displaces nothing and stores nothing. At
    that point no register value is live: the only values defined after
    the wrapper's return are the `.bool` result and the suspend's own
    result, and both have stack homes, since neither is live on a
    resumption edge. C3 asserts this.
  - `phi` incoming slots are always on the machine stack.
    - The switch on a `coro.suspend` result writes its successors'
      incoming slots **per edge, after the dispatch** on w0, unlike
      `spec/codegen.md` §4.5's "all successors before the terminator".
      The 0 and 1 edges are therefore written in the resumed activation.
      The corpus has `phi`s on 14 resume, 9 destroy and 5 suspended
      successors, out of 233 suspend switches (kiln and libc++).
    - Every other edge is written and read in one activation.
  - These are not x19 accesses, and are allowed:
    - the mode test (`[x29, #mode]`);
    - the handle form's `x16 := [x0]`, which reads the *other*
      coroutine's frame;
    - the epilogue's restore of the saved x19 from the machine stack.
  - A heap slot or heap value used on a −1 path cannot be placed
    anywhere that keeps the invariant. The plan refuses it
    (`coro:frame-access-after-suspend`, 3.4).

  **Older dialect.** In LLVM before the wrapper intrinsics,
  `await_suspend` was an ordinary call between `coro.save` and
  `coro.suspend`. The corpus has none of it: all 182 kiln and 51 libc++
  suspends use a wrapper intrinsic, as clang ≥ 19 does. If it appears,
  the same invariant holds from `coro.save` on, because every call after
  the save may publish the handle. Inlined `await_suspend` code that
  reads its awaiter from the heap is therefore refused, also as
  `coro:frame-access-after-suspend`.

  C3 checks this structurally:
  - The plan exports the *suspended region*: the instructions from each
    wrapper's return (or from `coro.save` in the older dialect) to its
    `coro.suspend`, and every block reachable from a −1 edge. A block
    shared with other paths counts whole, because its code is shared.
  - When the emitter forms a `FrameRef::Coro` address inside that
    region, it reports `CgError::Internal`. This check is on in every
    build: it costs one bit test per frame access.
  - A test disassembles every coroutine of the seeds and of the corpus
    and finds no `[x19…]` operand in the region's address ranges.

  The behavioural check is `resume-inside-await-suspend.cpp` (5.3).
- **The handle form** (`coro.await.suspend.handle`, possibly invoked):
  call the wrapper with (awaiter, x19), then load `x16 := [x0]`.
  - ramp mode: `blr x16` with `x0 = h`, outside the invoke's call-site
    range, then go to the suspend's −1 path;
  - clone mode: a tail exit, the epilogue (x19 restored) then `br x16`
    with `x0 = h`.

  Both paths are emitted, and a test on the mode chooses between them.
  The `.void` and `.bool` forms are calls (or invokes) of the wrapper.
- **`coro.end(unwind=true)`:**
  - clone mode: store 0 to the resume pointer and the final index;
  - ramp mode: nothing.

  The value of `is_in_ramp`, or of LLVM 19's `i1 coro.end` (which is
  true when **not** in the ramp: `kiln:coro.rs:759-763`), is computed
  from the mode slot.
- **The index is always stored**, the final suspend's included. The
  destroy stub then dispatches on the index alone and needs no null
  test.
- **`coro.free`** is x19 (allocation is never elided). **`coro.alloc`**
  is true. **`coro.frame`** is x19. **`coro.id`** and the tokens produce
  nothing; `type:token` is accepted as the type of these intrinsics'
  results and operands only. **`coro.promise`/`resume`/`destroy`/`done`/
  `noop`** in any function are the rewrites of 1.1 (package C2).
- **Heap layout:**
  - `[0,16)` is the header.
  - The promise is at `alignTo(16, A_p)`.
  - The index is a 4-byte field, then the heap body slots, then the
    crossing homes, in order of need.
  - The frame alignment is the maximum of 16 and every heap slot's
    alignment. `coro.align` returns it.
  - A heap slot aligned above 16 in a coroutine that does not call
    `coro.align` is refused (`coro:overaligned-frame`): only aligned
    allocation makes that alignment true. LLVM silently misaligns in
    this case (1.2).

### 3.4 The plan (shared by A and B)

`hod_xform::coro::plan(&Module, &Body) -> Result<Option<CoroPlan>,
Refusal>` runs before code generation. It gives `None` for a body
without `presplitcoroutine`. The interface is fixed here so that packages C1 and
C3 can be written against it (as C1 landed it; `spec/xform.md` §3.1 is
normative):

```rust
pub struct CoroPlan {
    pub begin: InstId,                  // the coro.begin
    pub promise: Option<SlotId>,        // header field at promise_offset
    pub promise_offset: u32,            // alignTo(16, align)
    pub frame_align: u32,               // ≥ 16
    pub heap_slots: BitSet<SlotId>,     // Body::slots that live in the frame
    pub heap_values: BitSet<InstId>,    // results whose home is in the frame
    pub begin_copies: Vec<SlotId>,      // heap slots with a stack shadow before coro.begin
    pub begin_value_copies: Vec<InstId>, // heap values defined before coro.begin
    pub suspends: Vec<Suspend>,         // in index order
    pub suspended_region: BitSet<BlockId>, // with Suspend::wrapper..suspend (3.3)
    pub has_unwind_end: bool,
    pub final_index: Option<u32>,
}
pub struct Suspend {
    pub save: InstId, pub wrapper: Option<InstId>, pub suspend: InstId,
    pub index: u32, pub is_final: bool,
}
```

**Definitions.**

- A *resumption edge* is a 0- or 1-arm of a switch on a `coro.suspend`
  result.
- Reachability *after* a resumption follows the blocks of a resumed
  activation. It stops at `coro.end(false)`, and takes only the false
  side of `is_in_ramp` (the true side of LLVM 19's `coro.end` result).
- The *uses* of an alloca include the uses of its *aliases*: pointers
  derived from it by `getelementptr` (any indices), `bitcast` or
  `addrspacecast`, followed transitively.
- An alloca is **unescaped** iff every use is one of:
  - a `load` from it;
  - a `store` *to* it (the address operand);
  - `llvm.memcpy`/`memmove`/`memset` with it as an address operand,
    which counts as a store, or as a load for a source;
  - a lifetime marker.

  `#dbg_*` records are not uses. Anything else is an escape: a store
  *of* the address or of an alias, a call or invoke argument (whatever
  its attributes), `phi`, `select`, `icmp`, `ptrtoint`, `ret`. An alias
  that is itself live across a resumption edge is also an escape (C1
  test: none at `-O0` in the corpus).

  Following aliases is necessary, not an optimisation. kiln returns a
  small aggregate return object coerced (`ret i64`). Its return-value
  slot is reached only through GEPs, and the ramp loads it on its
  return path, which runs after the frame is freed when the coroutine
  completes in the ramp. Treating the GEP as an escape would put the
  slot in the heap (rule 5), and every such coroutine would then be
  refused under the safety conditions below.
- A slot *has lifetime markers* iff some `llvm.lifetime.start` names the
  alloca itself, not an alias at a nonzero offset.

**An SSA value is in `heap_values`** iff it is live-in on a resumption
edge. C1 computes it with the same forward dataflow as rule 3 (a
definition kills; a use after an edge since the definition is a hit;
`coro.end(false)` and the ramp-only side of `is_in_ramp` reset), which
is equivalent on SSA form; at `-O0` most values are block-local and are
skipped by their use facts. `heap_values` holds instructions only: an
argument used after a resumption edge is refused (below), so no
argument needs a home in the frame. (C1 changed the field from
`BitSet<ValueId>`, a type `hod_ir` does not have.)

**An alloca slot is in `heap_slots`** by the first rule that applies:

1. **The promise:** in the header, not in `heap_slots`.
2. **`!coro.outside.frame`:** stack. The plan refuses
   (`coro:outside-frame-across-suspend`) a marked slot that has a use
   after a resumption edge. This checks the front end's promise cheaply;
   LLVM trusts it.
3. **Unescaped:** heap iff some load can see a store made before a
   resumption edge.
   - This is a forward dataflow over two bits per alloca: "stored on
     some path" and "a resumption edge passed since the last store".
     The bits are joined by union. A store sets the first and clears
     the second; a resumption edge sets the second. A load (or memcpy
     source) with both bits set means heap.
   - Lifetime markers play no part here.
   - Sound because an unescaped slot's contents are observable only
     through its loads.
   - It differs from LLVM, which pairs every use with every use (1.4).
     It keeps the exception and selector slots on the stack, removing
     the first use after free of 1.4.
4. **Escaped, with lifetime markers:** heap iff either
   - (a) some use, including a `lifetime.end`, is reachable from a
     `lifetime.start` through a resumption edge, or
   - (b) a resumption edge lies on a path from one `lifetime.start` to
     another, or on a cycle through one.

   This is LLVM's rule, with both clauses. Clause (b) covers a loop
   whose body restarts the lifetime: the address published in one
   iteration must stay the same in the next.
5. **Escaped, without lifetime markers:** heap, always. This is LLVM's
   rule. Once the address has escaped, no rule based on direct uses can
   tell whether the slot is read after a suspend. In `int x = 0; int *p
   = &x; co_await s; *p = 1;` only `p` is loaded after the edge. In
   `T t; reg.add(&t); co_await s; reg.poke();` nothing names `t` after
   it. Both are seeds (5.3).

**Before `coro.begin`.** A heap slot with a use on a path from entry
that has not reached `coro.begin` is handled as LLVM does (1.2):
- Such uses address a machine-stack *shadow*.
- Just after `coro.begin`, the shadow's bytes are copied into the heap
  slot, on every path through `coro.begin`. The slot is listed in
  `begin_copies`.
- Later uses address the heap.

Corpus count, kiln: **5 slots in 2 modules**. All are parameter allocas
whose address is passed to the promise's `operator new`
(`promise_alloc_template`, and the `elements_of` overload of
libstdc++'s `generator`). libc++: 0. So the copy is specified, not
refused. One shape is still refused: an *alias* (an SSA pointer)
computed before `coro.begin` and used after it, because it would still
point at the shadow (`coro:frame-before-begin`; corpus count 0).

**Values before `coro.begin`** (C1, from kiln's maintainers). `this`, a
lambda's closure pointer and VLA bounds are SSA values loaded before
`coro.id` and used after suspends. They are heap values like any other,
listed in `begin_value_copies`: stored to a machine-stack home where
they are defined and copied to their heap home just after `coro.begin`.
This is not `coro:frame-before-begin`. kiln's order before `coro.begin`
is: static allocas; argument stores into parameter allocas (with a GEP
for a coerced argument); the debug spill; the `this` alloca and its
load; VLA bounds; `pre` contract checks; `coro.id`, then `coro.alloc`,
`coro.size`, the allocation (and the GRO-on-allocation-failure branch),
a `phi`, `coro.begin`.

**Parameters** (C1, from kiln's maintainers). Every parameter gets a
frame copy right after `coro.begin`. The original parameter alloca is
read only (a) by the allocation call's arguments, (b) once for the copy,
and (c) by a callee-destroyed (`trivial_abi`) parameter's destructor in
the ramp after `coro.end`. (a) makes it rule 5 with a `begin_copies`
entry; (b) alone keeps it on the stack (rule 3). kiln does not yet mark
parameter allocas `!coro.outside.frame` (its WP-1374 will); until then
(c) is a rule-5 heap slot used in the suspended region, refused as
`coro:frame-access-after-suspend` (count: 0 in the corpus and in
libc++). Arguments themselves are used after a suspend only in the ramp
after `coro.end`: the `sret` pointer and an indirect callee-destroyed
parameter's destructor. Those uses are not after a resumption and are
not refused.

A pointer to the shadow that escaped into memory before `coro.begin` and
is dereferenced after it sees stale data. LLVM has the same hazard. In
the 5 corpus slots the escape is the argument of `operator new`, which
returns before `coro.begin`.

**Safety conditions.** No slot or value that code reaches after the
frame is freed, or inside the suspended region of 3.3, may be in the
heap. Rules 1-3 never produce such a heap slot:
- A rule-3 slot is heap only if a load after a resumption edge needs
  it.
- The ramp's tail after `coro.end(false)` and the unwind path after
  `is_in_ramp` are not reachable after a resumption.
- The cleanup-destination slot is stored again before every read in
  the activation that frees.

The plan's tests assert this on the corpus. Rules 4 and 5 can produce
such a slot. The corpus has exactly one shape, and kiln's markings are
listed with it:

| shape (corpus, per LLVM version) | kiln marks it | clang marks it | hod |
|---|---|---|---|
| return object read by a contract postcondition on the ramp tail (`r.ok()` takes its address): 6 slots in 3 modules, `ea()`/`bad()` of `basic.contract.eval/run-coroutine-post-{enforce,observe,quick-enforce}` | no | n/a (no P2900) | refused |
| GRO kept in a separate object (5 slots) | `!coro.outside.frame` | yes | stack (rule 2) |
| `sret` return object | n/a: an argument, not an alloca | n/a | never a slot |
| cleanup objects (temporaries with destructors) on the ramp's unwind path | lifetime markers; never alive across a resumption in the corpus (rule 4 puts 0 of them in the heap with a use after free) | same | rule 4 |

hod follows **LLVM's rule with no exception**, and refuses the unsafe
shape by name: `coro:frame-access-after-suspend`, for a heap slot or
heap value with a use in the suspended region or after the frame is
freed.

A narrower exception was considered and rejected. The return object
under a postcondition is created on a path from which no resumption
edge is reachable. But that path is also the suspending activation's −1
path. A pointer published there can be used by a resumed activation
after the ramp has returned, and nothing in the IR rules that out.

The refused modules fall back to `opt` + `llc`, which carries the
hazard (1.4, `post-sync.cpp`). The fix belongs to the front end: kiln
can mark the return-object slot `!coro.outside.frame`, as it does for
the GRO. The C++ object belongs to the ramp, not to the coroutine
(section 7). With the mark, hod keeps the slot on the stack, and so
does LLVM, which removes the bug.

**C1's gate** follows: on the 100 pre-opt corpus modules, hod's
`heap_slots` ∪ `begin_copies` must be a superset of `opt`'s `%F.Frame`
allocas minus the rule-3 slots, with **no other exemption**. Every
heap slot must also satisfy the safety conditions, or be refused by
name. Only the 6 slots above are expected to be refused.

**The plan also refuses:**

- an argument or `Incoming` area used after a resumption edge
  (`coro:argument-across-suspend`);
- a dynamic `alloca`, `llvm.stacksave` or `llvm.stackrestore`
  (`coro:dynamic-alloca`), which can reach the plan from kiln;
- the shapes `spec/xform.md` §3.8 lists (`coro:begin-shape`,
  `coro:suspend-shape`, `coro:frame-intrinsic`, `coro:variadic`,
  `coro:unwind-end-without-final`, `coro:overaligned-frame`).

kiln always calls `await_suspend` through
`llvm.coro.await.suspend.{void,bool,handle}` (call or invoke), so every
suspended region starts at a wrapper.

A `phi` on a resumption successor needs no rule. Its incoming value is
read after the re-entry (3.3), so a value defined before the suspend is
live-in on the edge and lands in `heap_values`.

### 3.5 Recommendation: B

B because:

1. It compiles each coroutine body **once**, where A compiles it about
   3.3 times. That is about half of a coroutine module's code and work,
   and hod exists for compile speed.
2. It needs **no new IR infrastructure**. Cloning, symbols and debug
   nodes added after reading, and growing module tables are all
   absent, so the streaming and parallel model of `spec/ir.md` §5.1 and
   design 0004 stays as it is.
3. Its debug info is **simpler and better**: one subprogram, one
   location per variable valid in every activation, and variables in
   the ramp.
4. It needs one FDE and one LSDA per coroutine.
5. The hard part, the plan, is shared with A. Choosing B wastes nothing
   if B is later overturned.

What would overturn it:

- **x86-64 code generation** arriving before or with coroutine demand.
  B needs a second target implementation: the stubs, rbx as base, the
  prologue. A is target-independent. Mitigation: the target-specific
  part of B is small (3.2), and `hod_cg` owns the logic.
- C3's diff showing that the `Coro` base reaches far beyond `Cursor` and
  `mem.rs`. If more than about 15 sites name `FP` as a slot base, A's
  isolation becomes worth its cost.
- A requirement that the transformation be checked by `llc` apart from
  the code generator. Only A, or approach C-actor below, allows that.
- kiln's maintainers choosing approach C-front.

### 3.6 Other approaches

- **C-actor: a GCC-style actor function, made by `hod_xform`.** The ramp
  allocates the frame and calls `F.actor(frame, mode)`. The single body
  dispatches on the index, and `resume`/`destroy` are thunks. This keeps
  B's compile-once property and A's target independence.

  It still needs A's IR infrastructure: new functions, symbols, debug
  nodes. The ramp's code after `coro.end` (GRO conversion, `sret`) has
  to be cut out of the body and given a context pointer. Its tail call
  `F.actor(frame, mode)` → `resume(h)` has mismatched prototypes, which
  is invalid `musttail` in LLVM IR, so `llc` could not check C-actor's output
  either. Its debug info is worse than B's: the variables are in
  another function, behind an argument. **Not chosen.**
- **C-front: kiln lowers coroutines itself**, as GCC's front end does: no
  `llvm.coro.*` at `-O0`, the frame as a struct, an actor with a state
  switch, and `musttail` for transfers. hod would then need nothing new
  except `musttail` through a loaded pointer, which exists. kiln's `-O0`
  route through LLVM would also lose its `opt`.

  The costs fall on kiln: a second lowering, kept separate from the
  `-O1+` route (which keeps `presplitcoroutine` for `CoroElide`), plus
  its own frame debug info. It is kiln's decision, so it is asked
  (section 7).

So, under 3.4, the plan refuses 3 modules per LLVM version
(`coro:frame-access-after-suspend`, the contract postconditions of
1.4). It specifies the copy at `coro.begin` for 2 modules and refuses
nothing else in the corpus or in libc++.

**Not seen, so refused by name at first:** `coro.frame` (trivial; could
be accepted), dynamic allocas and `stacksave` in coroutine bodies, the
retcon and async ABIs (`llvm.coro.id.retcon*`, `.async`, already
unknown intrinsics), an unwinding `coro.end` without a final suspend,
over-aligned heap slots without `coro.align`, arguments used after a
resumption, an alias computed before `coro.begin` and used after it,
an `!coro.outside.frame` slot used after a resumption, variadic
coroutines, and a `coro.suspend` whose result is not used by one
`switch` (a front-end shape kiln does not write).

Elsewhere in kiln's tests, about 45 sources use coroutines. Most are
diagnostics, `constexpr` or compile-only tests. `tests/codegen/coro_*.cpp`
(5) check IR text, and `bench/runtime/generator-iterate.cpp` is a bench.

**Cost of LLVM's route today:**

- The coroutine pipeline over the 25 modules takes 0.29 s in all, about
  12 ms each and mostly start-up, at 64 MB peak.
- On the largest module (8649 lines), `opt` takes 0.02-0.05 s and `llc`
  on its output takes 0.07 s at 69 MB.
- What hod removes is the `opt` process, the 3.3× body growth that `llc`
  then compiles, and kiln's bitcode hop (`llvm-dis` in the shim; 392
  libc++ modules arrived as bitcode in WP-077).

## 5. Validation

The comparison is by **behaviour**, never bytes. Every program is built
twice from the same pre-opt module: hod; and `opt -passes='default<O0>'`
+ `llc -O0 -global-isel=0 -fast-isel=0`, the WP-021 wrapper. Both
programs are run, and their stdout and exit status must match.

1. **Corpus:** `scripts/preopt-corpus.sh` plus `cargo xtask irdiff
   --hybrid` over the 50 coroutine modules, LLVM 19 and 22, with the
   pre-opt oracle (WP-021's method). The tests carry `//@ stdout`.
2. **libc++:** kiln's runner with the shim in strict mode on
   `support.coroutines` (25 tests, 10 modules through hod), then the
   full hybrid run: 0 differences from the baseline.
3. **Seeds** under `tests/ir/coro/`, pre-opt with expected output:
   - `gen`;
   - deep symmetric transfer (3,000,000 transfers on 8 MB: a missing
     tail call dies);
   - `ramp-throw`, `gro-throws-uaf` and `exceptions`;
   - destroy at the initial, a middle and the final suspend, with
     destructor counts;
   - `done()` before and after the final suspend, and after an escaped
     exception;
   - `from_promise(p) == h` and `h.promise()` with an `alignas(32)`
     promise under aligned allocation;
   - `coro.noop` and the handle operations;
   - allocation failure;
   - an SSA value live across a suspend (the
     `reference-result-bound-to-reference` shape);
   - **`escaped-local.cpp`**, rule 5 (3.4). It has `int x; int *p = &x;
     co_await s; *p = 1; use(x)` and `T t; reg.add(&t); co_await s;
     reg.poke();`. Expected stdout `1 7` / `poked 5`, in both dialects,
     as kiln writes it (lifetime markers, rule 4) and with the markers
     deleted from the IR (rule 5). Checked with `opt` + `llc` 19 and 22,
     plain and poisoned. With `x` and `t` forced onto the stack (marked
     `!coro.outside.frame` by hand), LLVM's own build prints `65535 7` /
     `poked 65535`.
   - **`resume-inside-await-suspend.cpp`**, the invariant of 3.3, for
     `.void`, `.bool` and `.handle`. Each `await_suspend` resumes the
     coroutine to completion and then takes the freed frame's block back
     as a canary. Expected stdout `void: body 3` / `canary ok`, then the
     same for `bool` and `handle`, in both dialects, plain and poisoned.
     A store through the frame pointer inserted after the wrapper's
     return in LLVM's split IR prints `canary BROKEN`.
   - **`params-before-begin.cpp`**, the copy at `coro.begin`. The
     promise's `operator new` takes the parameters by reference and
     changes one. Expected stdout `new 3 4 x` / `body 3 5 x`, in both
     dialects, plain and poisoned.
   - `post-sync.cpp`: *not* a seed for hod's output. It is refused
     (`coro:frame-access-after-suspend`), and its census line asserts
     the refusal.
   - each in the LLVM 19 (`i1 coro.end`) and the LLVM 22 dialect.

   The harness parts are built in **C2** with their own tests (supervisor
   decision):
   - **A pre-opt oracle per seed**, which WP-021 saw as ERRORs.
   - **A dialect tag.** An LLVM 22 seed is not valid for LLVM 19's
     `opt`, so the "both LLVMs" rule applies per dialect.
   - **An oracle-skip mark:** `oracle-skip(<reason>, llvm=<versions>)`
     on a seed whose oracle is wrong. Such a seed carries its own
     expected output, and it is compared with that output only, never
     with "either". The marks are listed in `spec/harness.md`.

     `gro-throws-uaf` (LLVM 19, 22) carries one: the oracle crashes
     under poisoning.
4. **Mixed objects:**
   - a coroutine compiled by hod, resumed, destroyed, `done()`-tested
     and `from_promise`d from an `llc` object, and the reverse;
   - symmetric transfer between a hod and an `llc` coroutine, in both
     directions;
   - all under bfd, lld and mold.
5. **Poisoned frees, as a differential sanitizer.** Every coroutine run
   above is repeated with `GLIBC_TUNABLES=glibc.malloc.tcache_count=0
   MALLOC_PERTURB_=165` and `MALLOC_CHECK_=3`; hod's build must
   survive. clang's ASan runtime is not installed on this host
   (`libclang_rt.asan_cxx.a` missing), and valgrind is not either. This
   poisoning caught LLVM's bug in 1.4. To catch a stale callee-saved
   register, a test has an `llc` caller that keeps a value in x19
   across `h.resume()` and checks it.
6. **Debugger** (`tests/debug/coroutine.cpp`, gdb, plus lldb where
   present):
   - Stop in a *resumed* activation after a `co_yield`: `bt`, `info
     locals`, `p i`, `p n`, `finish`. The transcripts equal `llc`'s.
   - Stop in the ramp after `coro.begin`: hod shows `p`, `local` and `i`
     where `llc` shows none. This is an expected, documented difference
     (an `xfail` with that reason on the `llc` side).
   - A *suspended* coroutine, from `main`: `info symbol` on the
     handle's resume pointer prints `_Z5counti.resume`; `p
     *('_Z5counti.coro_frame_ty' *) h.address()` (once C5 lands) shows
     `__promise` and the variables; `p h.promise().cur`.
   - `llvm-dwarfdump --verify` is clean on every `-g` coroutine object.
7. **Mutations**, each of which a test above must catch:
   1. a crossing value homed on the stack;
   2. an exception slot moved to the heap (caught by `ramp-throw` under
      poisoning);
   3. no null store at the final suspend (caught by `done()`);
   4. the promise at 16 regardless of alignment (caught by aligned
      `from_promise` and the mixed objects);
   5. symmetric transfer as a call (caught by deep transfer);
   6. x19 not restored in the epilogue or a tail exit (caught by the x19
      caller);
   7. an unwinding `coro.end` that does not mark done;
   8. the destroy stub entering with w0 = 0 (caught by destructor
      counts);
   9. `is_in_ramp` inverted on LLVM 19 (caught by the frame freed twice
      or never);
   10. the x19 CFI row dropped (caught by an exception through a hod
       coroutine called from `llc` code that uses x19);
   11. an escaped slot left on the stack: rule 5 or rule 4 disabled
       (caught by `escaped-local`, as demonstrated with LLVM above);
   12. a heap home written after the wrapper returned, e.g. the
       `coro.suspend` "call" re-storing live values, or the suspend
       switch writing `phi` incoming slots before dispatch. This is
       caught by the structural check of 3.3 (`CgError::Internal` and the
       disassembly test), and by `resume-inside-await-suspend` (broken
       canary, or a crash under poisoning);
   13. an alias computed before `coro.begin` used after it, or the
       `coro.begin` copy omitted (caught by `params-before-begin`: the
       parameter copies made after `coro.begin` would read an
       uninitialised heap slot. The corpus's `promise_alloc_template`
       never reads its parameters, so it would not catch this).

## 7. Decisions taken, and questions for kiln

**Decided by the supervisor (review of this design):**

1. x19 is reserved and saved in coroutine functions.
2. The pre-opt oracle and the dialect-tagged seeds are built in C2, as a
   harness part with its own tests. C3 uses them.
3. A seed whose oracle is wrong carries its expected output and an
   explicit `oracle-skip` mark, with the reason and the LLVM versions;
   never "accept either". The marks are listed in `spec/harness.md`.
4. The noop frame is generic in `hod_cg`: a per-object private
   constant and a private function that returns, emitted on first use,
   with one small `Target` hook for the function's body.

**For kiln's maintainers:**

1. Would you rather lower coroutines in kiln at `-O0` (approach C-front,
   section 3.6)? If yes, C1 and C3-C5 are not needed.
2. **Information: two latent uses of freed memory on kiln's LLVM route
   today** (1.4). Both reproduce with `opt` + `llc` 19 and 22 under
   `GLIBC_TUNABLES=glibc.malloc.tcache_count=0 MALLOC_PERTURB_=165`.
   - `0005-data/gro-throws-uaf.cpp`: `get_return_object` throws. The
     ramp frees the frame, then reads the exception slots LLVM put in
     it. SIGSEGV. clang has the same bug.
   - `0005-data/post-sync.cpp`: a P2900 postcondition on a coroutine
     that completes in its ramp. The escaped return object is in the
     frame and is read after the ramp freed it. The postcondition fails
     (exit 134). With a coroutine that suspends instead, the ramp reads
     the frame of a suspended coroutine, which is a race if another
     thread resumes it.

   Proposed fix for the second: mark the return-object alloca
   `!coro.outside.frame`, as kiln already does for a separate GRO. hod
   refuses the shape until then (3 corpus modules).
3. Will you mark parameter allocas `!coro.outside.frame` as clang 22
   does? Today the five parameters passed by reference to a promise
   `operator new` live in the frame with a copy at `coro.begin`. That is
   correct, but marking them is simpler and keeps them on the stack.
   Are kiln's parameter allocas guaranteed to be read only for the
   parameter copies, before the first suspend?
4. Does kiln ever emit, in a coroutine body, a dynamic `alloca`,
   `stacksave`, a use of an argument after a suspend, an alias computed
   before `coro.begin` and used after it, or an `await_suspend` call
   without a wrapper intrinsic? hod refuses all of them by name.
5. When hod accepts coroutines (C6), kiln's driver stops running `opt`
   for modules whose triggers are only `alwaysinline` and coroutines
   (`needs_coro_lowering`), on the same contract as WP-021, and falls
   back for a refused module. Agreed?
