## What it did

The readers (`hod_ll` reads text, `hod_bc` reads bitcode) both did the
same lowering. That shared logic is now in `hod_ir::kit`, and both readers call it:

| step | kit | removed from the readers |
|---|---|---|
| GEP to `PtrAdd` | `Gep`, `GepError`, `gep_index_value`, `Lowered`, `stand_in` | the folding, scaling, vector and refusal code of each reader's `getelementptr`; `index_value` (both), `sext64` (bc) |
| static alloca to slot | `AllocaDesc`, `lower_alloca`, `AllocaError` | the slot/dynamic split and the refusal order of each reader's `alloca` |
| attributes | `string_attr`, `fn_keyword`, `value_keyword`, `add_typed`, `merge_fn_attrs`, `AttrUse`, `attr_construct`, `CALL_SITE_FLAGS`, `set_call_site_flags` | `lossy`, `mem_keyword`, `clear_mem` (ll); the group merge and `CALL_SITE_FLAGS` (bc) |
| special globals, attachments | `SpecialGlobal`, `SpecialError`, `deliver_special`, `annotations_construct`, `GlobalAttachment`, `global_attachment_construct` | the `Special` enums, `array_elements`/`special()` (ll), `special_of`/`special()` (bc) |
| named metadata, module flags | `NamedMetadataKind`, `named_metadata_construct`, `module_flag`, `BranchUpgrade` | each reader's flag decoding and its `Upgrade` struct with its `apply` |
| debug fields (after WP-149) | `di_node`, `define_di_node`, `define_di_tuple`, `invalid_di_ref`, `unsupported_field`, `unsupported_field_construct`, `di_atom`, `add_location`, `compile_unit`, `function_subprogram`, `variable_expression`, `finish_debug`, `DEBUG_INVALID`, `WIDE_ENUMERATOR`, `ASSIGN_ARG_LIST`, `DebugRecordKind`, `DebugRecord`, `emit_debug_record`, `debug_intrinsic_construct`, `unsupported_record_construct` | each reader's `RecordKind`, `OldRecord`, record emission, intrinsic and record name maps, `finish_debug`'s used-and-invalid rule, the `!dbg`/`!llvm.dbg.cu` kind checks, node building over LLVM's defaults, the distinct-or-uniqued define, the empty-tuple stand-in, the unsupported-field rule, the atom-rank check, the duplicated in-place location adds (ll) |

## Where the readers disagree (kept as they were)

None of these differences changes bytes or a refusal name.

- `special-global:<name>` for other `llvm.*` variables depends on how the name is spelled. ll matches
  `@llvm.` in the unquoted token. bc matches names made only of
  `[A-Za-z0-9-._$]`.
- The messages and error kinds for malformed attributes differ. ll gives Syntax errors ("this attribute
  does not apply to functions"). bc gives Invalid errors ("attribute 'x' does not apply to
  functions").
- The AArch64 branch-protection upgrade happens at different points. ll gates it while reading the flags. bc gates it
  when it applies the upgrade. The effect is the same.
- Constant GEP indices are read differently. ll keeps a fast path for decimal literals. bc always passes a value and
  uses `gep_index_value`.
- An alloca without a count is `i32 1` in text. Bitcode always carries a count. Each reader
  still checks that the count is an integer.
- Some refusals exist only in bitcode: `typeless-type-attribute`, `attribute-range-list-wide`,
  `attribute-encoding` and `attribute-kind`.
- Debug: a `DILocation` column over 16 bits is a syntax error in text and
  none (0, LLVM's `adjustColumn`) in bitcode; an atom rank over 8 bits is
  Syntax ("value for 'atomRank' too large") in text, Invalid in bitcode.
- Debug: `debug:invalid` against what. In a body, ll notes it against the
  function. bc notes it against the function too for records, but against
  the module for a node a function's METADATA block defines.
- Debug: an unknown `#dbg_*` record is a syntax error in text. In bitcode
  the one LLVM knows, `#dbg_declare_value`, is recorded by its
  `di_record` construct. Versions and layouts (`debug-layout`) exist only
  in bitcode, and `DW_*` keywords and the required fields only in text.
