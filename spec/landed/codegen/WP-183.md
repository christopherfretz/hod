# WP-183: stack protectors (`ssp`, `sspstrong`, `sspreq`)

## What is implemented

`ssp`, `sspstrong` and `sspreq` (clang's and kiln's `-fstack-protector`,
`-strong`, `-all`) are built on both targets, matrix rows `attr:ssp`,
`attr:sspstrong`, `attr:sspreq` `ON` (were refused). The rule is
`spec/codegen.md` §5.6.24; the plan is target-neutral
(`hod_cg::guard::GuardPlan`, made in `FnCx::plan_guard` before
`begin_function`), the code per target (`hod_x64::guard`,
`hod_a64::guard`).

- **Which functions**: any of the three attributes and (`sspreq`, a body
  slot, or an `alloca` instruction): a superset of LLVM's choice for each
  attribute, since hod keeps no slot types. `"stack-protector-buffer-size"`
  changes nothing.
- **Layout**: the escaping slots (address used other than as an in-bounds
  `load`/`store` pointer) form one block at the top of the local area,
  allocated last in `end_function`; the 8-byte guard follows the last slot
  at once, unaligned, so a 1-byte overflow reaches it. Each slot of the
  block is reached through a pointer slot (`SlotPlace::Indirect`), as an
  over-aligned slot is. A function with a dynamic area has a second, low
  guard: x86-64 `Local(0)`, AArch64 `[x29-16]` (`sub sp, sp, #16`; hod's
  frame record is at the frame's bottom there).
- **Value**: x86-64 `fs:[0x28]`; AArch64 `__stack_chk_guard` through the
  GOT under every model. `llc` reads it directly (`ADR_PREL_PG_HI21`) in a
  module without `PIC Level`, which no PIE link with bfd accepts; the
  seeds carry clang's `PIC Level`/`PIE Level` flags.
- **Check**: first in `teardown`, so every return and every `musttail`
  exit; x86-64 with `r10`, AArch64 with `x16`/`x17` around a push of `x16`
  (an indirect tail callee). The failure stub (`__stack_chk_fail`, PLT32 /
  CALL26) follows the last exit with the body's CFA rules restated.

## What stays refused, by name

- `ssp:coroutine`: a protected presplit coroutine (its resume stubs enter
  the body past the entry code that stores the guard). Note that kiln's
  `-fstack-protector-strong` puts `sspstrong` on coroutines too.
- `ssp:target`: a target without `Target::enter_guard` (backstop).
- `module-flag:stack-protector-guard`, `-guard-reg`, `-guard-offset`,
  `-guard-symbol` (`-mstack-protector-guard*`): unchanged; building them
  takes a module property in `hod_ir` (props), then the value source per
  target.
- `intrinsic:llvm.stackprotector`, `intrinsic:llvm.stackguard`: unchanged
  (front ends at `-O0` do not write them).

## Evidence

- `tests/ir/stack_protector.ll` (intact frames: char array, int array, a
  struct with an array, an escaping scalar, a dynamic alloca, plain
  locals, `sspreq` without locals, `musttail`, an untaken `noreturn`
  path, a loop of 100 calls) and `tests/ir/stack_protector_smash.ll` (a
  64-byte overflow: SIGABRT after `intact 65`). `cargo xtask irdiff
  --witness`: x86-64 and AArch64, LLVM 19 and 22, bfd/lld/mold: 24 of 24
  PASS. `cargo test -p xtask --test irdiff_real`: 12 passed.
- `crates/hod/tests/stack_protector.rs`: text and `llvm-as` 19/22
  bitcode give the same object for both seeds on both targets; each
  attribute brings `__stack_chk_fail` (and `__stack_chk_guard` on
  AArch64), none without; `ssp:coroutine` is named with its function.
- C probes (clang 22 → IR → `llc` 22 and hod, PIE, run natively on
  AArch64 and under qemu on x86-64): the first overflow length in 0..64
  that aborts with "stack smashing detected", `-fstack-protector-strong`:

  | case | x86-64 llc | x86-64 hod | AArch64 llc | AArch64 hod |
  |---|---|---|---|---|
  | `char[16]` | 9 | 1 | 1 | 1 |
  | `int[5]` | 5 | 1 | 1 | 1 |
  | struct with `char[12]` | 1 | 1 | 1 | 1 |
  | escaping `long` | 1 | 1 | 1 | 1 |
  | `alloca(40)` | SIGSEGV at 20 | 9 | SIGSEGV at 20 | 9 |

  Length 0 returns normally everywhere. Under `-fstack-protector` `llc`
  leaves the `int` array and the scalar unprotected (SIGSEGV at 12 to 17)
  and hod aborts at 1; `-fstack-protector-all` matches the table. A C++
  probe that throws through protected frames: hod aborts wherever `llc`
  does, and the exceptions are caught.
- A real unit (`std::vector`, `std::map`, `std::string`, `std::sort`,
  exceptions, a `char[32]` and a struct with `char[12]`) through
  `kiln++ -fstack-protector-strong` with `KILN_BACKEND=hod
  KILN_HOD_STRICT=1`, both targets: 203 (x86-64) and 1015 (AArch64)
  guard relocations, runs correctly, and an overflow of 1 byte aborts.
- Debug info: `cargo xtask debug verify` on `-g -fstack-protector-strong`
  modules (C and C++, both targets): clean. `cargo xtask debug trees`:
  the only difference from `llc` is a guarded variable's location,
  `DW_OP_fbreg N, DW_OP_deref` (through its pointer slot, as an
  over-aligned slot) against `DW_OP_fbreg N`; without the attributes the
  same modules are same/permitted. gdb prints a guarded `int[5]` after
  it is filled, and backtraces through the frame.
- Mutations, each caught by `irdiff` on `stack_protector_smash.ll`
  (bfd, lld, mold) and reverted: x86-64 with the check removed
  (`hod_x64::guard::check` returns at once): hod's program ends with
  SIGSEGV, `llc`'s with SIGABRT; AArch64 with the guard below the slots
  (`GuardPlan::plan`, guard at 0, slots from 8): SIGBUS against SIGABRT.

## Second landing: protected coroutines, guarded variables' class

- **Coroutines** (`spec/codegen.md` §5.6.24 rules 1, 2 and 6, §7.6): a
  protected presplit coroutine is built. Each resume and destroy stub
  stores the guard and the pointer slots again, with final offsets
  (`hod_x64::guard::stub_enter`, `hod_a64::guard::stub_enter`, one call
  each in `coro_body.rs` `stubs`). The heap frame's slots (the promise
  and `heap_slots`) are not on the machine stack and stay out of the
  block, and an over-aligned promise no longer counts toward the low
  guard. `ssp:coroutine` is kept only for a coroutine that would need
  the low guard (the coroutine plan refuses each such shape first). The
  block's order changed from body order to decreasing size, largest at
  the top next to the guard. With body order, a 1-byte overflow of a
  buffer hit a pointer-holding slot above it (SIGSEGV instead of
  SIGABRT).
- **Overflow inside a coroutine body** (`clang++-22 -O1 -Xclang
  -disable-llvm-passes -fstack-protector-strong`; three segments
  around `co_yield`s, each with a `char[16]` written `n` bytes past its
  end; `llc` through `opt-22 default<O0>` with CoroSplit). The first `n`
  that aborts with `stack smashing detected`, the same on x86-64 and
  AArch64: the ramp, `llc` 1 and hod 1; the first resumed activation
  (entered through a stub), 17 and 17; the second, `llc` 1 and hod 33
  (`llc`'s split clone holds only that segment's buffer; hod's one body
  holds all three, and the overflow reaches the guard after the buffers
  above it). `n = 0` runs normally everywhere. Three arrays in one
  function (`two.c`): on AArch64, `llc` and hod both abort at 1, 17 and
  33; on x86-64, `llc` at 9, 25 and 41, hod at 1, 17 and 33.
- `irdiff` on protected copies of the `tests/ir/coro` seeds and the two
  `stack_protector` seeds, both targets, LLVM 22 and 19: 63 PASS, 0
  FAIL, 17 SKIP on each target. libc++'s coroutine tests through
  `kiln++ -fstack-protector-strong` with `KILN_BACKEND=hod
  KILN_HOD_STRICT=1`: 25 of 25 pass on each target.
  `crates/hod/tests/stack_protector.rs`
  `a_protected_presplit_coroutine_is_built` replaces the refusal test.
- Mutation, caught by the overflow probe and reverted: with
  `hod_x64::coro_body::stubs` not calling `guard::stub_enter`, hod's
  program dies with SIGSEGV at `n = 0` in every segment (the stale
  pointer slots), where `llc`'s runs normally.
- **Debug info** (`spec/dwarf.md` §6.7): the trees class `stack
  protector` (`xtask/src/debug/trees.rs` `location_class`, only in a
  module naming `ssp`, `sspstrong` or `sspreq`) permits `DW_OP_fbreg N,
  DW_OP_deref` against `DW_OP_fbreg N`. `cargo xtask debug trees --llc
  22` on `tests/debug/stack_protector.c` and `coroutine.cpp`, both under
  `-fstack-protector-strong`: x86-64 `stack protector` (C); AArch64
  `realigned frame` (C) and `realigned frame, byval, stack protector`
  (C++). The x86-64 C++ module differs only in a `DW_AT_frame_base` of
  `__await_suspend_wrapper__init`, the same without the attributes,
  so the protector does not cause it. The debugger harness: the new
  `tests/debug/stack_protector.c` and `tests/debug/coroutine_ssp.cpp`
  pass, 12 of 12 results on each target (gdb, lldb, every linker,
  clang 19 and 22).
