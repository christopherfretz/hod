# WP-278 — five real projects on AArch64 at the release candidate, and zlib on x86-64

Measured: magic_enum, tl_expected, zlib, zstd and mold, both flavours
(`O0` = `-O0`, `O0g` = `-O0 -g`), natively on an AArch64 host, each with
a fresh control (`--mode llc`) and a strict build (`--mode strict`, every
object by hod) at the release candidate hod `cd6ef6bc` with kiln
`8f93304ee` (kiln 1.2.0). Their earlier rows were from older hod commits
and an older kiln. Then zlib on x86-64 (cross-built, tests under qemu),
both flavours, control and strict at the same commits. No change under
`crates/` or `scripts/`.

## Commands

From this worktree (`scripts/oss/` as on the release branch at
`d61efae8`), after `source scripts/env.sh`, with
`MAKEFLAGS=--jobserver-auth=fifo:/run/hod/lanes.fifo`,
`HOD_OSS_HOD=<frozen copy of the candidate>` (`install -m 555`, sha256
`80138ec1411506d5b4048f1eac49e8b377f9eeedb21e70ae43e3c81ab094929c`
checked on both, `--version` run), `KILN_OSS_CXX=<kiln 1.2.0 kiln++>`,
`HOD_OSS_KILN=8f93304ee`:

    scripts/oss/oss-run.sh <project> --modes "llc strict" --strict
    scripts/oss/oss-run.sh zlib --target x86_64 --flavours "O0g O0" --modes "llc strict" --strict --keep

Sources are the pinned tags of `scripts/oss/projects.toml`. Each row's
own caps from `projects.toml` (mold: `test_vmem_kb` 96000000) applied to
control and strict alike. Judged by kiln's stats log (the `backend` of
every object) and the reports' test status, test by test against the
control.

- zlib: the 37th TU is compiled with `--coverage`, which kiln never
  offers to any back end (stats: "not offered: coverage"); it is built
  by LLVM in strict as in the control. The failing link in both modes is
  `infcover`: this host has no `libclang_rt.profile.a`, so
  `zlib_coverage` is Not Run in both. Because ctest then exits non-zero,
  the row's minigzip round trip (after `&&`) runs in neither mode.
- zstd: `zstreamtest` fails in control and strict alike ("Allocation
  error : not enough memory", seed 3173672436, line 1693) under the
  row's address-space cap.
- mold: `x86_64-arch-x86_64-empty-mergeable-section` fails in control
  and strict alike; 23 tests are skipped in both.

## zlib on x86-64: the earlier difference

The previous strict run (hod `e98267c0`) had 4/6 tests against the
control's 5/6: `zlib_static_example` failed with "gzread err:". Its log
shows ctest starting tests 1 to 3 at once; `example.c` writes and reads
back the fixed file `foo.gz` in the working directory, which
`zlib_example` and `zlib_static_example` share. The row's ctest now runs
`-j1`, and both modes are 5/6, equal. Probes on the kept trees,
`zlib_example` and `zlib_static_example` together: with `ctest -j2`,
control O0g 32 of 40 runs fail, strict O0g 27/40, control O0 36/40,
strict O0 28/40; serially (`-j1`) 0 of 20 fail in either mode; each
mode passes 2 of 2 runs of the pair alone. A race between the two
tests, independent of the back end.
