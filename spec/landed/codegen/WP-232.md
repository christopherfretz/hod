# WP-232: under-aligned atomics, the rest of the class

Spec: `spec/codegen.md` §5.5.1 (AArch64 atomics, "Below its size's
alignment") and §5.6.10 (x86-64, the same heading).

WP-231 sent an x86-64 load, store, `xchg` and `cmpxchg` whose alignment
is below their size to libatomic's generic routines. This package does
the same on AArch64, and on both targets the other `atomicrmw`
operations and the accesses whose value operand is the pointer itself.

## What `llc` emits

- AArch64 (`llc` 22 and 19, `aarch64-unknown-linux-gnu`): the default
  features, `+lse`, `+outline-atomics` and `+lse,+outline-atomics` all
  give the same undefined symbols for an under-aligned load, store,
  `xchg`, `cmpxchg`, `atomicrmw add` of `i32`, `fadd` of `float` and
  `add` of `i128`: `__atomic_load`, `__atomic_store`,
  `__atomic_exchange`, `__atomic_compare_exchange`; no exclusive pair,
  no LSE instruction, no `__aarch64_*` helper.
- The other `atomicrmw` operations, on both targets: a plain load of the
  cell (`ldr`/`movl`, `ldr q0` or two `movq` for `i128`), then a loop
  that computes the new value, stores the old and the new value to two
  stack slots and calls `__atomic_compare_exchange(size, ptr, &old,
  &new, order, failure)` until it returns true (AArch64 tests bit 0 with
  `tbz`), the result being the old value's slot. `failure` is
  `getStrongestFailureOrdering(order)`: `acq_rel` gives 4 and 2,
  `release` 3 and 0, `seq_cst` 5 and 5.

## What was built

- `crates/hod_a64/src/atomic.rs`: `under_aligned`, `load_generic`,
  `store_generic`, `xchg_generic`, `cmpxchg_generic` (the expected value
  in the result's slot, the returned `bool` stored as the flag), and
  `rmw_generic`, the loop. The aligned loops' computations are now
  functions the loop shares: `int_new` (with `extend_operand`),
  `float_new`, `wide_new`. Every value of the loop is in a frame slot,
  the pointer too, and every register is displaced before it, so the
  call inside the loop displaces nothing.
- `crates/hod_x64/src/atomic.rs`: `rmw_generic`, the same loop, sharing
  `int_new`, `float_op` and `wide_new` with the aligned loops and the
  `i128` libatomic loop (`wide_new` gained `add`, `sub`, `and`, `nand`,
  `or`, `xor`, which that loop calls single routines for). `half` is
  computed in `float` with the inline conversions of the aligned loop,
  where `llc` calls `__extendhfsf2` and `__truncsfhf2`.
- Both targets: a value operand that is the pointer itself (a store of
  `ptr %p` to `%p`, `xchg` of it, `cmpxchg` with it as the expected or
  the new value) is stored to its slot and to a slot of its own, and
  the call's pointer argument is loaded from that slot (`CallArg::Mem`):
  the pointer's register is asked for once (`ptr_copy`, `ptr_arg`).
- The type and `bfloat` checks come before the alignment one: an
  under-aligned `fp128` is `atomic-type`, an under-aligned `bfloat`
  `fadd` `atomic-bfloat-op`, as when aligned.

## Evidence

- `crates/hod_x64/tests/common/generic_atomics.rs`: the suite both
  targets run, 177 functions: WP-231's 52, every integer `atomicrmw`
  operation other than `xchg` for `i16`, `i32`, `i64`, `i128` at each
  alignment listed, the six floating-point ones for `half`, `float`,
  `double`, and the three accesses whose value is the pointer. Its C
  driver computes each operation's result itself (integers on
  `unsigned __int128`, the signed compares on sign-extended values;
  floating point in its own type on finite, nonzero, non-NaN inputs so
  that `maxnum` and `maximum` agree and every result is exact), forces
  the `udec_wrap` zero case and an operand equal to the cell, and checks
  the bytes around the cell.
- `crates/hod_a64/tests/atomic.rs`
  `under_aligned_atomics_run_against_libatomic`: under the default
  features, `+lse` and `+outline-atomics`, hod plain and under every
  stress option, `llc` 22 and `llc` 19 (`usub_cond`, `usub_sat`,
  `fmaximum`, `fminimum` from `llc` 22 in that leg), each linked with
  `-latomic` by every linker and run natively: 708 calls a leg, none
  wrong. `under_aligned_atomics_call_libatomic_generic`: 25 forms under
  each feature set, plain and stressed, name the routine and no
  `__aarch64_*` helper.
- `crates/hod_x64/tests/leftovers.rs`
  `under_aligned_atomics_run_against_libatomic`: the whole shared suite
  (177 functions), hod plain and under every stress option, `llc` 22
  and `llc` 19 (the four newer operations from `llc` 22), each linked
  with `-latomic -lm` (`llc` calls `fmaxf`, `fminf`, `fmax`, `fmin` on
  x86-64) by every linker and run under qemu here: 708 calls a leg,
  none wrong.
  `crates/hod_x64/tests/atomic.rs`
  `under_aligned_atomics_call_libatomic_generic`: 26 forms (9
  `atomicrmw` loops, 4 accesses whose value is the pointer), plain and
  stressed.
- `refused_atomics_by_name`: neither target has an `atomic-unaligned`
  case left; the type and `bfloat` refusals hold under-aligned on both.

## What stays refused or open

- `a64:atomic-unaligned` and `x64:atomic-unaligned` are no longer
  returned; the names stay in the support table.
