# WP-170: back-end costs

Four cuts in what the back ends pay per query, none of which changes an
object. Callgrind instruction counts, `HOD_THREADS=1`, the release
profile, `hod --strict --filetype=obj -O0 -mtriple=<triple>`; the
inputs are the bench's stl-heavy, templates, huge-function and
tiny-functions, and stl-heavy and templates built with `-g`. Run-to-run
noise on one binary is about ±1.3M (malloc), so a change under that is
reported as none.

## Proof of no change

An identity table, built for the base (ff5688c) and after each item:
both corpora (aarch64 6,250 inputs, x86_64 6,244) and the seeds
(`tests/ir`, `tests/roundtrip`, `tests/debug`, for both targets), each
as text and as bitcode (`llvm-as-22`): 25,360 rows, each the object's
hash or the error's text. Base: text 12,032 objects and 648 errors,
bitcode 11,998 objects, 36 errors, 646 without bitcode. The table after
each of the four items is identical to the base's; the table after the
last, built twice, is identical to itself.

In all: −1.4% to −2.8% on every input and both targets (stl-heavy
−11.9M / −11.7M, templates −12.3M / −11.6M, huge-function −10.9M /
−11.2M, tiny-functions −3.4M / −3.1M, stl-heavy -g −18.0M / −17.8M,
templates -g −17.0M / −15.6M, x86_64 / aarch64).

1. `TypeTable::kind` (`crates/hod_ir/src/types.rs`): always inlined for
   the kinds without parts, so the caller's match on the kind becomes a
   match on the type's tag; struct, function and target-extension types,
   which borrow from the table's pools, take `kind_with_parts`, out of
   line. A plain `#[inline]` changed nothing (LLVM declined it). Both
   back ends' `class_of` are inlined too (`hod_x64` and `hod_a64`
   `target.rs`); `hod_a64` had the same pattern and gains as much.
2. `hod_cg`'s maps keyed by compiler-assigned ids hash with `IdMap`
   (`crates/hod_cg/src/idhash.rs`, FxHash's multiply and a final mix; no
   random state). Changed: `emit` `local_aliases` (`SymId`), `copies`
   (`SymId`), `signatures` (`SymbolId`). Nothing reads them in order but
   `local_aliases`, whose loop writes one distinct symbol an entry, so
   the order cannot reach the object. Kept on SipHash:
   `emit/section.rs` `by_name` (keyed by section names, which are input
   bytes); `emit` `sections` of the structors (keyed by an input
   priority, a handful of entries); `key_rows` `candidates` (keyed by
   input atom groups, not hot).
3. `DebugInfo::loc_in_atom` (`crates/hod_ir/src/debug/mod.rs`) takes
   `loc_without_atom`, the pre-WP-149 `loc`, first when the atom is
   `DiAtom::NONE`; `loc` calls it directly. The back end's part:
   `key_rows::is_key` asked for the whole subprogram node to read one
   flag; it now asks `DebugInfo::has_key_instructions`, which tests the
   flag's bit in the node's mask. Inputs without `-g` do not reach
   either.
4. `DebugInfo::node`: about 470k calls on stl-heavy -g (x86-64), from
   `hod_dwarf`'s type and DIE writers, the reader's `finish_debug`,
   `emit::finish` and `verify`. `Dec` read each word as an index into
   the table's cells (`get(at).map_or(0, ..)`) and now takes the words
   after the mask off the front of a slice; past the end a word is
   still 0 and a list still empty. `node`'s own cost there: 75.8M →
   69.5M. Tried and dropped (stl-heavy -g x86-64): a per-kind decode
   out of line (+6.0M), `node` always inlined with that decode out of
   line (+5.4M), a `node` without strings for `verify` (+1.8M: it
   duplicated `DiNode::decode`), the mask taken with `split_first` too
   (+1.9M). Of what is left in `node`, string lookups are about 17%
   and the prologue and epilogue about 11%.

## Follow-ups

- `crates/hod_ir/src/strings.rs:95` `span`: three bounds checks a
  string, about 17% of `node`.
- `crates/hod_dwarf/src/types.rs:207` `drain`, `:916` `method_attrs`,
  `:1021` `type_die`: decode a whole node to read one or two fields; a
  field reader as `has_key_instructions` would avoid most of `node`.
- `crates/hod_cg/src/emit/section.rs:270` `entry`: hashes the name up to
  three times a call (`contains_key`, `insert`, `get_mut`); `by_name`
  is the 9.4M of SipHash left on stl-heavy x86-64.
- `crates/hod_x64/src/features.rs:221`: the target-features split, about
  6M on every x86-64 input.
