# WP-357 — the speed figures of the 1.1.0 candidate

A measurement package: no change under `crates/` or `xtask/`. It repeats
WP-288's two tables (hod against `llc -O0`, and kiln end to end) for the
1.1.0 release candidate, adds a third (hod 1.0.0 against the candidate on
the same inputs), and regenerates `docs/status/perf.md` from the first
table's run. Nothing here gates the tag (`docs/status/perf.md` is not a
condition of `docs/RELEASE.md`).

## Method and its limits

- **One loaded host.** The shared development machine (aarch64, 24
  cores), with other release lanes and agents running. The load average
  (`uptime`) is beside every wall-time number: 21 to 30 throughout,
  against 13 to 26 for WP-288. Wall times and their ratios move with the
  load (below: the same table at load 16 to 24 and at 25 to 30); the
  **instruction counts are the firm numbers** (WP-292 measured their
  repeatability at 0.018% at worst; here the candidate's sums from the
  bench and from table 3's script agree to 0.01%).
- **x86-64 objects are a cross run** on this host (`--target x86_64`):
  hod and `llc` produce x86-64 objects on an aarch64 machine. Nothing was
  measured on a native x86-64 host.
- **Not measured against `clang -O0` in process.** `llc` is a separate
  process reading text IR, as hod is; clang's own back end run inside
  the compiler, without printing and reading the IR, was not measured.
- **hod on one thread.** In table 1's first pass hod inherited the shared
  jobserver (`MAKEFLAGS` exported by `scripts/env.sh`), which `cargo xtask
  bench` does not remove from hod's timed runs (only from the counted
  ones), so hod could take idle tokens on large modules. That pass is
  kept as a side record; table 1 below is the second pass, run with
  `MAKEFLAGS` unset and `HOD_THREADS=1`. WP-288's run sourced the same
  `env.sh`, so its wall times may have had that jobserver too; its
  instruction counts did not (counted runs are `HOD_THREADS=1` without
  `MAKEFLAGS`).
- **hod started from the workspace volume** (found after this run; see
  "Rerun with hod on the container's disk" at the end). Every hod wall
  time in tables 1 to 3 below includes about 10 to 25 ms of program start
  of a binary on the bind-mounted workspace that `llc` (installed on the
  container's own disk) never paid. Harness follow-up: `xtask bench`
  executes the hod it is given in place (from wherever `--hod` points)
  and strips `MAKEFLAGS` only from the counted runs, not from the timed
  ones; it should copy hod next to `llc`'s kind of disk (or say where
  hod lives) and run every hod process without the jobserver.
- End to end: aarch64 only, as in WP-288 (kiln cross-compiling to
  x86-64 needs a target sysroot the host does not have set up).
- Raw logs, results files and scripts are in the run directory
  `.build/release-1.1.0/perf/` (`run-bench.sh` with `bench-*.log` and
  `build/bench/results-*.tsv`; `pass1-jobserver/`; `e2e.sh`, `e2e/`,
  `e2e-sum.py`; `old-new.sh`, `old-new.tsv`, `old-new.log`,
  `old-new-summary.tsv`; `instr-llvm22.tsv`).

up to 0.6 MiB on some small ones.

## Rerun with hod on the container's disk

**The bias.** The development host runs every agent in a container whose
workspace (`/Volumes/AgentWork/...`, where `.build/` and both hod binaries
live) is a bind mount; `llc` lives on the container's own disk
(`/usr/lib/llvm-22`). Starting a program from the bind mount is slow:
measured by the supervisor (load 32, fastest of 9, four corpus modules of
50 to 70 KB), the same hod binary took 14 to 30 ms per run from the
volume and 1.5 to 3.7 ms from a copy on the container's disk, against 14
to 17 ms for `llc`; `hod --version` 6.2 ms against 0.8 ms. So every hod
wall time in tables 1 to 3 above carries 10 to 25 ms of program start
that `llc` never paid. Instruction counts are not affected (callgrind
counts user-mode instructions, not the time to page the binary in).

Confirmed here before the rerun (2026-11-17 17:26 UTC, load 26.97),
fastest of 9, twice: `hod-a68a0d5d --version` 4.33 / 5.72 ms from the
volume, 1.24 / 1.68 ms from the local copy (`perf-local/bias.log`). The
input's location matters too: strict hod (local) on the LLVM 22 aarch64
`templates.ll`, object written locally, fastest of 9, twice: 40.62 /
41.51 ms reading the input from the volume, 35.87 / 36.37 ms from a local
copy (load 26.50). That is more than 1 ms, so the 80 bench inputs (LLVM
22 and 19, both targets; copied with their stamps from
`perf/build/bench/inputs`, not produced again) and every object hod or
`llc` writes were moved to the container's disk too: in table 1 this also
takes the volume out of `llc`'s reads and writes, not only hod's.

**Method.** Both hod binaries copied to a `mktemp -d /tmp/hod-perf-*`
directory on the container's disk (sha256 checked equal to the table at
the top), the scripts of `.build/release-1.1.0/perf/` copied to the run
directory `.build/release-1.1.0/perf-local/` and changed only in the hod
they execute and where they write: `run-bench.sh` (the bench's build
directory, hence its inputs and objects, on the local disk; results files
copied back to `perf-local/build/bench/`), `e2e.sh` and `e2e-sum.py`,
`old-new.sh` (no callgrind count), with `best.sh` and `bias.log` for the
two checks above. Everything else as in sections 1 to 3: hod on one
thread (`MAKEFLAGS` unset, `HOD_THREADS=1`), 5 runs, one run at a time.
Measured 2026-11-17 17:26 to 17:32 UTC at load 23.65 to 34.05 (higher
than the first run's 21 to 30). Every input built by hod in every run, no
decline, no fallback, no error; all 100 end-to-end jobs exited 0, no
`hod_reason`, no `hod_skip`; every table 3 run exited 0.
