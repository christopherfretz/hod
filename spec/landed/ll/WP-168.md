# WP-168 — keyword codes in the lexer, the label scan replayed (`hod_ll`)

Landed: the two structural cuts WP-159 left for the text reader
(`spec/landed/ll/WP-159.md`, "What is left", items 1 and 2), in six
commits on `crates/hod_ll/src` (`kw.rs` new; `lexer.rs`, `parser.rs`,
`lib.rs`, `index.rs`, `body.rs`, `inst.rs`, `types.rs`, `consts.rs`, `attrs.rs`,
`call.rs`, `globals.rs`, `meta.rs`, `debug.rs`), each with its counts in
its message, and `spec/ll.md` §2, §2.2, §2.8, §10, §11.3. No change to
emitted bytes, refusals, error messages or error positions (below). No
edit outside `hod_ll` and the spec. Safe Rust (`#![forbid(unsafe_code)]`
stays), no new dependency.

## Method

As WP-159: Callgrind instruction counts, `HOD_THREADS=1`, the release
profile with `debug = 1` (fat LTO, one code unit), attributed by each
instruction's own function (`callgrind_annotate --inclusive=no`);
`hod --strict --filetype=obj -O0 -mtriple=T -o out.o in.ll`. The host
is AArch64 Linux, so the instructions counted are AArch64's for both
targets. `hod_ll`'s own count is the sum over the functions whose name
is in `hod_ll::`. Hot spots inside a function were read from
`--dump-instr=yes` profiles against `objdump`. With fat LTO, code moves
between functions from one build to the next by up to about 2M on
these inputs (a function's count can change by 1 to 2M with no change
to it); totals are what is compared.

- **a** (3b0d0be): `Kw`, a one-byte code for each of the 238 words the
  parser compares against and `i1` to `i128`, assigned in the lexer to
  every `Word` and `IntType` token by a perfect hash (§2.2), unused.
  It is not free: +21 to +23M on the large inputs, about 35
  instructions a word for the key, the multiply, two table loads and
  the compare, on about 490,000 words (stl-heavy, with the scans).
  An earlier version with `u128` keys cost +28.8M.
- **b** (193fa52): `at_word`, `eat_word`, `expect_word` and the index
  scan's word test compare the code.
- **c** (692676a): `parse_type`'s word types and integer types by code.
- **d** (09084c1): the instruction dispatch, flags, predicates, word
  constants and constant expressions by code; `scan_labels`' terminator
  test by code.
- **e** (92e601d): one dispatch on the first byte in `next_token`
  (punctuation, words, `%`/`@` names and numbers straight to their
  rule, the rest to `compound`); a fast path for a word or integer type
  of at most 15 bytes with sixteen bytes of source from its start, not
  `u0…`/`s0…`/`cc`-digit and followed by a byte that neither goes on a
  label nor ends one: found and keyed from those sixteen bytes, with no
  frame, everything else through the old rules (`word_rule`); the same
  for digits before `number_rule`; class runs tested eight bytes at a
  time without an end test per byte; the code tables padded to 256 so
  a slot's byte needs no bounds test.
- **replay** (item 2): `scan_labels` records the tokens it lexes
  (outside parentheses) with the offset each was looked for at, and the
  body's lexer takes a recorded token when asked at that offset instead
  of lexing it (§2.8). On stl-heavy 224,000 tokens are replayed, about
  33 instructions each against about 70 to lex one. At most 65,536
  tokens (1 MiB) are kept per scan; huge-function's one scan is longer
  than that, so it gains little and pays the recording; tiny-functions
  has few scans. Peak memory on the bench inputs moves within the
  run-to-run noise (stl-heavy 21 to 24 MB either way, with threads).

## Exactness

A keyword code is only a name for a word's bytes: every test that
compared the text now compares the code of the same word, and a word
that is not a keyword has `Kw::Other`, which no keyword test matches.
The tables are built at compile time and the build fails on a shared
slot; `kw.rs` tests every keyword in its own slot, a word of the same
length placed in a keyword's slot rejected by the compare, and the
code tests against the text tests. The lexer's fast paths take only
tokens whose rules come to the plain word, type or integer; every
other token, and every error, goes through the rules as they were
(`the_word_fast_path_is_the_rules`: some 11,500 generated words around
the 16-byte bound before every kind of byte, and every keyword). A
replayed token is the token the lexer gives at that offset, as a token
depends on the source and the offset alone; no `Eof` or `Error` token
is recorded, so error text and positions are the lexer's
(`replayed_tokens_are_the_lexed_ones`).

## Byte identity

WP-092's table over 12,680 inputs (the AArch64 and x86-64 corpora and
the seeds `tests/{ir,roundtrip,debug}` for both targets, each as text
and as `llvm-as` bitcode, `--strict --filetype=obj -O0`; a row is the
object's hash or the first 200 bytes of the error). Before (ff5688c):
11,997 rows with text equal to bitcode, 36 declined by both, 646 with
no bitcode, and one where text and bitcode differ, as before this work
(`kiln/llvm19/conformance/target.neon/bfdot-target-attribute-run.cpp.ll`,
AArch64). The tables after b, d, e and replay are identical to the one
before, byte for byte.

## What is left

The 20% goal on the text reader is not met: `hod_ll`'s own count falls
9.4% on stl-heavy (259.9M → 235.5M; 20% is 207.9M, 27.6M further). On
stl-heavy x64, after:

- the lexer, 108M: `next_token` 41.7M (37 a token: the blank skip,
  most of it the indentation after a line feed, the dispatch, the
  punctuation tokens), `word` 33.3M (about 70 a word, half of it the
  key and the hash), names 14.2M (`global` 8.1M: mangled names, 3
  instructions a byte), replay 7.5M, numbers 5.6M, `compound` 4.0M;
- `skip_group` 16.7M, the index scan over the bodies, 2.8 instructions
  a byte;
- locals (`Fx::set`, `local_value`, `key`, `take_number`, `get`) 19M;
- `parse_type` 13.3M, `expect` 10.9M, `call` 10.4M;
- attributes: `AttrMemo::keyword` 9.7M (about 65 a word) and the byte
  match of `value_keyword` after it. Codes for the attribute words
  would take them to one load, but only 18 codes are left in a byte:
  the most common ten or so would fit.

Of the per-token costs, what a token costs the parser beyond the lexer
(the 12-byte token returned through memory and copied into `Parser`,
then read back) is spread over every parse function and is not
measured here.
