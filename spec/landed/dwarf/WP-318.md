# WP-318 — the string pool keyed by the debug store's string id (`hod_ir`, `hod_dwarf`)

Item 1 of WP-313's list (`spec/landed/dwarf/WP-313.md`, "What remains")
and item 3 of WP-311's: `DebugStrings::index` hashed the bytes of every
string a DIE names, although every such string but a handful is a string
of `hod_ir`'s debug store, interned there with an id. Four commits on
`crates/hod_ir/src/debug/` (`node.rs`, `mod.rs`), the re-export list of
`crates/hod_ir/src/lib.rs`, `crates/hod_dwarf/src/` (`strings.rs`,
`die.rs`, `types.rs`, `template.rs`, `func.rs`, `inline.rs`,
`global.rs`, `label.rs`, `spec.rs`, `reduced.rs`, `split.rs`),
`spec/ir.md` §6.2 and `spec/dwarf.md` §6.3. No change to emitted bytes,
refusals or error messages. Safe Rust, no new dependency. Base 99e91e06.

## Method

As WP-308 and WP-311: Callgrind instruction counts, `HOD_THREADS=1`, the
release profile, `hod --strict -O0 -filetype=obj -relocation-model=pic
[-mtriple=x86_64-unknown-linux-gnu]` on the bench inputs (`cargo xtask
bench --generate`, clang 22), both targets; the base built from its own
commit into its own target directory. Self cost per function, summed
over the source files a function's inlined code comes from. The pool's
requests were counted by a temporary counter per call site (`#[track_caller]`
on `Writer::strx`, never committed), each request classed by whether
the store holds its bytes.

## Who asks the pool, and for what

On `stl-heavy-g` (x86-64) the walk asks the pool 34,106 times; every one
of them is a string the store holds. On `tiny-functions-g` 10,011
requests, one made up by the writer (`__ARRAY_SIZE_TYPE__`). The made-up
strings are that one, the conversion base types' names of §6.31, and the
unit's producer, name and compilation directory (three per unit, held by
the store but read as bytes from the plan). The calls by site, at the
base, `stl-heavy-g` / `templates-g` / `tiny-functions-g`:

| site | requests |
|---|---:|
| member function linkage name and name (`types.rs`, `Kind::Method`) | 15,583 / 6,502 / 0 |
| local variable and parameter names (`func.rs`, `inline.rs`) | 7,518 / 5,550 / 5,002 |
| template parameter names (`template.rs`) | 4,653 / 3,459 / 0 |
| typedefs, pointers, template aliases (`types.rs`, derived types) | 1,829 / 65 / 1 |
| subprogram definitions' linkage name and name (`func.rs`) | 2,207 / 533 / 5,001 |
| composite types, members, enumerators, static members | 2,122 / 452 / 0 |
| globals, namespaces, labels, base types, the unit | under 150 each |

So a design that pays for the byte path (a hash in the store, then one in
the pool) is free in practice: under ten requests per unit take it.

## The design, and the invariant

`hod_ir` (spec/ir.md §6.2): `DiView::ids()` gives a `DiIds<R>`, the same
node with one method per field, where a string field reads as a `DiStr`
(its bytes and its id) and any other field as through the view
(`DiFieldId::Id`, a sealed trait implemented by the field types). Store
strings are interned, so equal bytes are one id, and ids are dense:
`DebugInfo::string_count()`. `DebugInfo::find_string(bytes)` is the
store's string with those bytes and its id, `None` for the empty string
or bytes no node holds.

`hod_dwarf` (spec/dwarf.md §6.3): `DebugStrings` keeps two tables. The
store's strings: a `Vec` of entries (`.debug_str` offset, last unit,
index there; 12 bytes) indexed by the store's id, of `string_count()`
entries, made at the first id asked for. Every other string: the
byte-keyed hash table as before. `index_str(DiStr)` reads the first;
`index(bytes)` asks the store first (`find_string`) and, if the store
holds the bytes, uses the store's entry, else the hash table.

The invariant: a string has an entry in exactly one of the two tables.
The store is borrowed, unchanged, for the whole write and is content-
interned, so the bytes of a store string always find the same id, and a
string the store does not hold can never come in by id. Whichever way a
string is first asked for (id or bytes), and whichever later, it is the
same entry; an entry is created at first use in the walk's order, and
`.debug_str` grows and `.debug_str_offsets` is numbered at that moment,
exactly as the byte-keyed table did. The made-up strings are hashed
twice (the store, then the pool), but there are a handful per unit.

The pool's store is the first one `use_store` names; each unit names its
plan's (`Writer::unit`, the split unit's writer). A unit whose plan reads
another store is served by the bytes of its strings (`index_str` falls
back to `index`), so ids of two stores are never mixed. The skeleton of
split DWARF pools its four strings in a pool of its own, by bytes, as
before; DWARF 4 converts the same indices to `DW_FORM_strp` offsets.
`unit_offsets`, `data`, the error cases (`NulInName` and `TooLarge` at a
string's first use) are unchanged.

A writer that holds the node decoded (most of them: WP-311 kept full
decodes where a writer reads most fields) has bytes, not ids; it reads
the one field again through a view (`Writer::strx_of` /
`opt_name_of`): two array reads and, for a name (the first field of its
kind) no step over other fields, against a hash of the whole name and a
compare of the bytes. In debug builds `strx_of` asserts that the field
read again is the decoded one.

Tests: `strings::tests::by_id_and_by_bytes_agree` (each order of id and
bytes, a made-up string, the empty string, a second unit, a NUL, and a
unit of another store, against a pool by bytes alone);
`debug::node::tests::views_read_fields_as_nodes_do` now also checks every
field of every kind read through `ids()` (bytes and id of strings, the
value of every other field).

## What remains, ranked

1. The decodes WP-311 left (26.2 M of `DebugInfo::node` on
   `stl-heavy-g`), now the largest cost of the walk; `Writer::die` 9.1 M
   and `type_die` 4.5 M self.

   decode that also hands out string ids (a `DiNode` variant of
