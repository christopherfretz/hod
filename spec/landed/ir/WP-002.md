# WP-002 — hod_ir foundations: target and data layout, type table with layout, constant pool with address normal forms

Landed: `spec/ir.md` §1 (ids and errors), §2.1 (target), §3 (types), §4.1
and §4.2 (constants), the folding functions §4.2 asks for, and initializer
flattening, which the spec does not have yet (proposed text below as §4.3).
Not here: symbols (§2.2), functions (§5), debug information (§6),
`classify` (§8), the printer (§9). `Module` is a shell holding the target,
the type table and the constant pool; `SymId` and `BlockId` are bare ids.

## What it did

`crates/hod_ir`, one module per concern, `lib.rs` only re-exporting:

| module | contents |
|---|---|
| `ids` | `TypeId`, `ConstId`, `SymId`, `BlockId`: `u32` newtypes; fixed `TypeId`s for `void`, `label`, `metadata`, `token`, the six float kinds, `ptr`, `i1`..`i128` |
| `error` | `IrError { kind, message }`, `IrErrorKind` (11 kinds), `IrResult` |
| `intern` | the hasher and open-addressing table the two pools share |
| `target` | `DataLayout` (parser, alignment queries, `Display`, `layout_difference`), `TargetSpec`, `Arch`, `Os`, kiln's layout strings |
| `types` | `TypeTable`: interning, layout at interning, queries |
| `constant` | `ConstPool`: constructors, canonical forms, the `Const` view, `ConstOp` |
| `fold` | `fold_gep`, `fold_cast`, `fold_binary` |
| `flatten` | `flatten`: a constant as bytes and `Fixup`s |
| `wide` | arithmetic on integers wider than 64 bits (crate-private) |
| `module` | `Module::new(TargetSpec)` |

Sizes, asserted in unit tests: a type entry is 24 bytes, a `TypeKind` view
24, a constant entry 16, a `Const` view 32, `ConstOp` 1, `Fixup` 32; every
id 4.

## Decisions where the spec was silent

Types (§3):

- **Sizes and offsets are `u64` bytes.** A type whose size in bits does not
  fit `u64` (more than `MAX_TYPE_SIZE` = 2^61 - 1 bytes) is refused with
  `TypeTooLarge` at interning; nothing wraps afterwards.
- **Store size is stored, alloc size is derived** (store size rounded up to
  the ABI alignment), so a type entry stays 24 bytes.
- **Preferred alignment is computed, not stored** (`pref_align_of`). Its
  one use is `global_align(ty, explicit, has_section)`, the alignment `llc`
  gives a variable (`DataLayout::getPreferredAlign`: a variable larger than
  16 bytes with no alignment of its own gets 16).
- **Opaque structs never get a body.** `opaque_struct()` returns a new
  unsized type on each call. A producer reading `%T = type opaque` followed
  later by a body interns the body when it sees it; with opaque pointers no
  type needs the forward reference.
- **Target extension types are unsized** and interned by name. LLVM gives
  some of them layouts through a per-target table; none is in scope.
- **"Scalable" is a flag on every type that contains a scalable vector**,
  not only on the vector. Sizes of such types are the minimum (`vscale` 1).
- **The stride of `getelementptr` over a vector is the element's width in
  bytes** (`<4 x i24>` steps by 3, `<2 x x86_fp80>` by 10), not its alloc
  size, and a vector whose elements are not whole bytes has no stride
  (`element_stride` is `None`). This is what LLVM's constant folder does.
- `MAX_INT_BITS` is 2^23, `MAX_ADDR_SPACE` 2^24 - 1, alignments at most
  2^32: LLVM's limits.

Target (§2.1):

- **The data-layout grammar is LLVM 22's**, which is stricter than
  LLVM 19's (`datalayout_diff.rs` checks 34 accepted and 59 rejected
  strings against `opt` 22).
- **`layout_difference` compares what changes hod's output**: endianness,
  the address-space-0 pointer, the *effective* ABI and preferred alignment
  of every integer width, the five float widths and every vector width
  either string names, aggregate and stack alignment, and the program,
  alloca and globals address spaces. It ignores pointers in other address
  spaces, mangling, native widths, non-integral address spaces and
  function-pointer alignment. So clang 19's AArch64 string (no `p270`
  entries) matches the target; a string that merely spells a default out
  matches too.
- A module with no data-layout line is not an error: like `llc`, hod uses
  the target's.

Constants (§4):

- **Constructors are methods of `ConstPool` taking `&TypeTable`** (two
  need `&mut`: `bytes` and `fold_gep`, which may intern an array or vector
  type). `Module` exposes both tables as public fields so they can be
  borrowed separately.
- **`SymDiff` is `{ ty, a, b, addend, plt }`**, not `{ a, b, addend,
  width }`: it carries its integer type (constants are typed), and `plt`
  says `a` came through `dso_local_equivalent`, which the relative-vtable
  form needs (`R_*_PLT32`). `a - a` without `plt` is canonicalized to the
  integer `addend`.
- **`IntOfAddr { ty, addr }` wraps the id of an address constant**
  (`Addr`, `DsoLocalEquivalent`, `NoCfi`, `BlockAddr`); **`AddrOfInt`
  holds a `u64`** and is the pointer with that absolute value
  (`addr_of_int(0)` is `null`).
- **Canonical forms**, so that equal values are one `ConstId`: integers
  are reduced modulo 2^N (inline up to 64 bits; wider ones are exactly
  `ceil(N / 64)` words, the top one masked); an aggregate, splat or byte
  string of zeros is `Zero`; one of only `poison` is `Poison`, of only
  `undef` is `Undef`; an `[N x i8]` of integers is `Bytes`; a fixed vector
  of one repeated element is `Splat`. A scalar zero is the integer or float
  zero, not `Zero`.
- **A relocation addend is reduced to the width of its field.**
  `int_of_addr` at 8, 16 or 32 bits, and truncating a `SymDiff`,
  sign-reduce the addend to that width, so `trunc(x + 2^40)` and
  `trunc(x)` are one constant. `llc` does not (see "Differences from
  `llc`").
- **What the folds reduce** (everything else becomes `Expr`, which has no
  image):
  - `fold_gep`: any constant index path over sized, non-scalable types;
    on `Addr` it adds to the addend, on `null` or `AddrOfInt` it gives
    `AddrOfInt`, on `poison`/`undef` it propagates. Index values are
    sign-extended; arithmetic wraps at 64 bits.
  - `fold_cast`: `trunc`/`zext`/`sext` of integers; `trunc` of `IntOfAddr`
    and `SymDiff`; `ptrtoint`/`ptrtoaddr` and `inttoptr` between addresses
    and integers (address space 0); `bitcast` between integers and floats
    of one width and of a type to itself.
  - `fold_binary`: `add`, `sub`, `mul`, `xor`, `and`, `or`, `shl` of
    integers at any width (`shl` by the width or more is `poison`); `add`
    and `sub` at up to 64 bits over the linear forms *number*, *symbol +
    number* and *symbol - symbol + number*, as long as the result is again
    one of the three.
  - `undef` operands are not folded by `fold_binary` (LLVM's answers
    depend on the operator); `poison` propagates.
- `undef` and `poison` in an initializer are zero bytes, per §4.1.
- **`is_zero_or_undef`** is LLVM's test for `.bss` (`isNullOrUndef`): zero,
  `undef`, `poison`, or an aggregate or vector of only those. `{ i32 undef,
  i32 0 }` goes to `.bss`.

Tests:

- `#[allow(clippy::many_single_char_names)]` on four unit-test modules

## What LLVM does that was not expected

- **LLVM 20 and later have no default `i1` alignment entry**; LLVM 19 has
  `i1:8:8`. `i1` then takes the entry of the next wider integer, so with
  `i8:8:32` (AArch64) the preferred alignment of `i1` is 4 in LLVM 22 and
  1 in LLVM 19, and a global `i1` (or array of them) is aligned
  differently by the two. hod follows LLVM 22. The tests model LLVM 19 by
  parsing `i1:8-` in front of the string.
- **`llc` ignores the module's data-layout string** and uses the target
  machine's; only `opt` honours a custom string. The custom-layout tests
  therefore read alignments off `opt -S` (which prints the preferred
  alignment on an `alloca` and the ABI alignment on a `load`) and sizes
  off `opt -passes=instsimplify`.
- **A vector of plain data whose bytes are all the same byte is emitted as
  one fill of its alloc size**, tail padding included: `<3 x i8> <i8 7,
  i8 7, i8 7>` is `07 07 07 07`. "Plain data" is LLVM's
  `ConstantDataVector`: elements of `i8`, `i16`, `i32`, `i64`, `half`,
  `bfloat`, `float` or `double`, none of them `undef`. `flatten` does the
  same so that images are byte-identical; the padding is not part of the
  value either way.
- **Vectors whose elements are not whole bytes are bit-packed**, element 0
  in the lowest bits, `undef` elements as zero bits (`<5 x i1> <1, undef,
  0, 1, 1>` is the byte 25).
- **An `x86_fp80` bit pattern with the wrong explicit integer bit is
  rewritten by LLVM** into a NaN (exponent all ones) when it reads the
  literal. `float()` stores the bits it is given; a producer passing
  LLVM's own bits never sees the difference.
- **Constant-expression operators in LLVM text**: `add`, `sub`, `xor` in
  both versions; `mul` up to LLVM 19 only; `and`, `or`, `shl`, `zext`,
  `sext` in neither; `ptrtoaddr` from LLVM 22. `fold_binary` and
  `fold_cast` implement all of them; those the text format lacks have unit
  tests only.
- **An integer literal in an address expression is zero-extended by
  `llc`**: `add (i32 ptrtoint (ptr @x to i32), i32 -8)` is assembled as
  `x + 4294967288`, a relocation no linker will apply without an overflow
  error, while `sub (..., i32 8)` is `x - 8`.
- **A zero-sized variable is placed in `.bss` with size 0**; a zero-sized
  *common* symbol is given size 1.
- **What `llc` refuses in an initializer**: `add` of two addresses,
  `xor`/`mul` with an address, and `ptrtoint` to an integer wider than the
  pointer. hod's folds leave each as `Expr`, and `flatten` fails with
  `UnsupportedInitializer` (`fold_diff.rs`, `what_llc_rejects_has_no_image`).

## Differences from `llc`

- **Narrow relocation addends.** For a field narrower than 64 bits hod's
  addend is the sum reduced to the field's signed range; `llc` writes the
  unreduced 64-bit sum. They are equal modulo the field's width, so the
  linked value is the same whenever both link, and hod's is the one more
  likely to pass a linker's overflow check. They differ as written only
  when `llc`'s addend does not fit the field. `flatten_diff.rs` has two
  such cases (70000 in an `i16`; the zero-extended `-8` above) and compares
  those two modulo the width, asserting that they do differ as written;
  every other relocation is compared exactly.
- **A number minus an address** (`sub (i64 4, i64 ptrtoint (ptr @a to
  i64))`): `llc` emits a PC-relative relocation with no symbol. It is not
  one of the normal forms, so hod keeps the `sub` as `Expr`.
- **An address in an integer that is not 8, 16, 32 or 64 bits wide**
  (`i24 ptrtoint (ptr @a to i24)`): `llc` emits a 32-bit relocation over
  the four bytes the `i24` is allocated; `flatten` refuses.
  Both are pinned by `what_llc_accepts_and_hod_does_not`, which fails when
  either side changes.
- **`sub (ptrtoint @g, ptrtoint @g)` is the integer 0 for hod**, so a
  variable initialized with it satisfies `is_zero_or_undef` and belongs in
  `.bss`. LLVM keeps the expression (`.quad g-g`), so `llc` puts the same
  eight zero bytes in `.data`.

## Tests

Unit tests in each module (63): interning identity, structural identity of
named structs, every `IrErrorKind`, the size assertions, wide-integer and
zero canonicalization, each fold, each image rule.

Differential tests, `crates/hod_ir/tests/`. Each needs LLVM's tools in
`/usr/lib/llvm-22/bin` and `/usr/lib/llvm-19/bin`; without them a test
prints a note and passes, and with `HOD_REQUIRE_TOOLS=1` it fails. Four
configurations: AArch64 and x86-64, each with LLVM 22 and LLVM 19 and
kiln's layout string for that pair.

| file | oracle | per configuration |
|---|---|---|
| `layout_diff.rs` | one `llc` object | 400 types: 1407 sizes, ABI alignments and offsets; 1460 global alignments and sizes |
| `datalayout_diff.rs` | `opt` | LLVM 22: 34 layout strings, 9894 sizes and alignments; LLVM 19: 5 strings, 1455; grammar: 34 accepted and 59 rejected strings (LLVM 22) |
| `flatten_diff.rs` | one `llc` object, `llvm-objdump -s -j .data`, `llvm-readelf -S -r -s` | 652 variables (600 random over 300 types, 52 by hand): size, `.bss` placement (158), 68160 bytes of `.data` (68408 with LLVM 19's AArch64 string), 189 relocations |
| `fold_diff.rs` | one `llc` assembly file | 1539 expressions (1500 random, 39 by hand); 4 (LLVM 22) or 5 (LLVM 19) initializers `llc` rejects; 2 it accepts and hod does not |

The generators are deterministic (fixed seeds), so the counts are stable.

Not covered against LLVM, and why:

- A `dso_local_equivalent` on its own and one-byte fixups are compared as
  assembly only: x86-64 has no relocation for `.quad f@PLT`, AArch64 none
  of one byte.
- `blockaddress` fixups: the labels of blocks are private to `llc`.
  Unit-tested only.
- Scalable vectors: LLVM rejects them in constant `getelementptr`s and in
  initializers. Unit-tested only.
- Which fixups an assembler can encode. A `Diff { a, b }` is encodable
  when `a` and `b` are defined in one section (a number), or when `b` is
  defined in the section of the field (PC-relative against `a`).
  Otherwise `llc` reports "Cannot represent a difference across sections"
  or "symbol ... can not be undefined in a subtraction expression".
  `flatten` cannot know sections; the object writer must check and report.

## Proposed text for `spec/ir.md`

WP-002 may not add sections to the spec. The code and tests cite §4.3 for
the following, which is offered for the supervisor to merge.

> ### 4.3 Initializer images
>
> `ConstPool::flatten(types, c, bytes, fixups)` appends the image of
> constant `c` to `bytes` and a `Fixup { offset, size, target, addend }`
> to `fixups` for each address in it. Exactly `alloc_size_of(type of c)`
> bytes are appended; fixup offsets are positions in `bytes`, in
> increasing order; on error both buffers are left as they were.
>
> - Little-endian targets only (`UnsupportedTarget` otherwise).
> - An integer or float occupies its store size, low byte first; bits
>   above an integer's width are zero. `x86_fp80` is ten bytes.
> - Padding, `undef` and `poison` are zero, with one exception for
>   identity with LLVM: the tail padding of a vector of `i8`, `i16`,
>   `i32`, `i64`, `half`, `bfloat`, `float` or `double` numbers whose
>   bytes are all one byte repeats that byte.
> - A struct field is at its field offset; array element `i` at `i` times
>   the element's alloc size; element `i` of a vector whose elements are
>   whole bytes at `i` times the element's width in bytes. A vector whose
>   elements are not whole bytes is one little-endian integer with
>   element 0 in its lowest bits.
> - An address leaves zero bytes and a fixup: `Sym(s)` for `Addr` and
>   `no_cfi`; `Plt(s)` for `dso_local_equivalent`; `Block { func, block }`;
>   `Diff { a, b }` and `PltDiff { a, b }` for `SymDiff`. The field's value
>   is target + addend, truncated to `size` bytes (8 for a pointer; 1, 2, 4
>   or 8 for an integer).
> - No image (`UnsupportedInitializer`): `Expr`, the `none` token, an
>   address in an integer whose width is not 8, 16, 32 or 64 bits, an
>   address in a vector whose elements are not whole bytes. `UnsizedType`
>   and `InvalidType` (scalable) for types without a fixed size.
> - A writable variable belongs in `.bss` exactly when
>   `ConstPool::is_zero_or_undef` holds for its initializer.
> - Tested by: `tests/flatten_diff.rs` against `llc`'s `.data` and
>   relocations, both targets, LLVM 19 and 22.

Statements in the spec that the implementation contradicts:

- §3 and §11 name `clang`'s `sizeof`/`offsetof` as the layout oracle. Most
  LLVM types have no C declaration; the tests use `llc` (target layouts)
  and `opt` (custom layouts).
- §11 names `opt` as the constant-folding oracle. LLVM IR has no folded
  form for `symbol + addend` that `opt` could print; the tests use `llc`'s
  assembly, which is that form.
- §4.2 gives `SymDiff { a, b, addend, width }`; it is `{ ty, a, b, addend,
  plt }` (above).
- §4.2 says a producer "must reduce to the first forms whenever the
  expression is reducible". Two expressions `llc` can emit are not reduced
  (above, "Differences from `llc`").

## For the next work packages

- WP-003 (symbols): `SymId` is a bare index; nothing checks that a `SymId`
  in a constant exists. `Module` needs the symbol table and should make
  `ConstPool` constructors reachable without exposing unchecked ids, or
  `verify` must check them. `global_align` wants the variable's explicit
  alignment and whether it has a section.
- WP-004 (functions): `BlockId` is in `ids.rs`; `BlockAddr { func, block }`
  is unchecked in the same way. `PtrAdd` (§5.4) can reuse
  `TypeTable::field_offset`, `element_stride` and the index sign-extension
  rule of `fold_gep`.
- Producers (`hod_ll`, `hod_bc`, the bridge): call `fold_gep`, `fold_cast`
  and `fold_binary` for every constant expression and pass the result on;
  an `Expr` in an initializer is for `classify` to reject.
- LLVM 19 input: `check_data_layout` reads both strings by LLVM 22's
  rules, so it cannot see the `i1` difference. Its whole effect is that a
  global of type `i1` (or an array of them) with no explicit alignment is
  aligned to 4 by hod on AArch64 where `llc` 19 aligns it to 1:
  over-aligned, and correct.
- The data emitter (`hod_obj` users): `Fixup` to relocation is the mapping
  `flatten_diff.rs` implements in `resolve`; it is the reference.
