# WP-169 — bitcode reader, the structural cuts (`hod_bc`)

Landed: three cuts in `crates/hod_bc/src` (`bitstream.rs`, `body.rs`),
one commit each with its counts, and two differential tests in
`bitstream/tests.rs`. No change to emitted bytes, refusals, error
messages or error positions (below). No edit outside the crate and
`spec/bc.md` §2.3, §9.1. Safe Rust, no new dependency. This is item 4
of `spec/landed/ll/WP-159.md` "What is left".

## Method

As WP-159: callgrind instruction counts (`HOD_THREADS=1`, the release
profile with `debug = 1`), attributed by each instruction's own
function (`callgrind_annotate --inclusive=no`); command `hod --strict
--filetype=obj -mtriple=<target> -o out.o in.bc`. The host is AArch64
Linux; x86-64 runs are cross. Inputs: the bench sources stl-heavy,
templates, huge-function and tiny-functions compiled by clang 22 for
each target (`-O0 -S -emit-llvm`, the manifest's flags) and the corpus
module `kiln/llvm22/stress/cleanup-scopes-30k.cpp.ll` (AArch64), each
as `llvm-as-22` bitcode. `hod_bc` is the functions named `hod_bc::`;
the bitstream is `hod_bc::bitstream::`. The base is ff5688c (WP-159
and WP-092 merged); its counts reproduce WP-159's final ones
(stl-heavy x64 393.48M against 393.47M).

## No check removed

The compiled ops are the definition operand for operand, so
`MAX_ABBREV_OPS` counts what it counted. The fast Fixed read is taken
only where at least 64 bits are left and the field lies in the word at
the current byte; any other field is `BitReader::read`, which makes the
truncation error at the same position. "A record without a code" can
no longer be reached: `define_abbrev` lets only a scalar be first, so
the code is read from the first op. A block with no BLOCKINFO entry
when it is entered still searches BLOCKINFO per record, since a
BLOCKINFO read inside it can add one; an entry, once made, never moves.
`Fx::get`'s fast path takes only an id below the instructions defined
whose type is the one expected (or none is), which is exactly where the
old path returns that instruction without error; any other id, every
forward reference and every type mismatch goes the old way.

Tests added: `compiled_abbreviations_read_as_the_definition_says`
(every scalar and array encoding, Fixed widths 1 to 64, behind a field
of every offset 0 to 63, over pseudo-random bits with tails of 0 to 130
bits: `Cursor::record` against a field-by-field reference reader in the
test, value, end position and error alike) and
`unabbreviated_records_read_as_one_number_at_a_time` (VBR6 operands
mixing one-chunk and long numbers, every start offset, cut short by
the block's end, with a number over 64 bits). Widening the fast Fixed
read's bounds (60 bits, 60 left) fails the first; the batch decoders
tried (below) were checked the same way while they were measured.

## Tried and dropped

Each measured on stl-heavy x64 and cleanup a64, against the commit
before it:

- **The record API handing out a slice of a buffer the cursor owns**
  (step b): the callers already read a buffer reused from record to
  record, through a slice (`Ops`), so moving the `Vec` into the cursor
  removes no work. What a batch can remove is the capacity test of each
  push: one `extend` of known length for UNABBREV_RECORD's operands and
  an array's elements gave −0.90M (−0.24%) / −3.60M (−0.23%); doing the
  scalars of an abbreviated record the same way as well gave less
  (−0.36M / −2.76M). Filling a buffer sized up front instead
  (`resize`) costs more in `memset` than it saves (+0.97M / +1.65M).
  Under half a percent: not kept.
- **Decoding several VBR numbers from one word** (each chunk of the
  word in one pass, a number cut by the word's end read again):
  +2.2M / +25M; only the one-chunk numbers of a word, the others by
  `vbr` (measured together with the array runs below): +1.4M / +9.0M. Records have few operands and many take two or
  more chunks, which the one-number fast path already decodes from one
  word.
- **Array runs of Fixed and Char6 elements read without checks** (the
  count was checked against the bits left): +0.02M / +0.20M.
- **A two-chunk VBR case before the chunk loop:** +0.64M / +2.73M.
- **The abbreviation id of `Cursor::next` read with `fixed`:** +4.3M on
  cleanup (with `fixed` inlined).
- **`#[inline]` on `Cursor::next` and `Cursor::record`:** +0.88M /
  +0.91M (LTO then leaves `abbrev` out of line).
- **Steps c and e not made, by their bound:** `Ops::next` (the
  per-operand read the hottest records would skip by reading the slice
  directly) is 0.75M (0.20%) on stl-heavy and 7.9M (0.50%) on cleanup
  in all; the instruction dispatch (`Fx::record`'s match and
  `Fx::instruction`'s match on the code) is about 40 instructions an
  instruction record, of which merging the two matches could save
  about 10 (≈3.6M, 0.23%, on cleanup's 360,000 instructions). Neither
  can reach half a percent.

## What is left

After these cuts the bitstream is 10.2% of stl-heavy x64 and 10.0% of
cleanup. Of it, VBR decoding is most (on cleanup about 45M of 158M),
the abbreviation id read and the call overhead of `Cursor::next` and
`Cursor::record` (each out of line, about 16 instructions of prologue
and epilogue per call, ≈12M on cleanup's 390,000 records) next. A
cheaper VBR needs a different decode (the chunks' payloads compacted
with masks and shifts, not a loop), which pays only for numbers of
three chunks or more. In the body reader, `get_any` (module values and
constants, 13.7M on cleanup) and `call_attrs` (≈14M) are the largest
left.
