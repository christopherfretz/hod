# WP-184: `-fcf-protection` on x86-64

## What is implemented

- **`module:cf-protection-branch`** `ON` on x86-64 (was `todo(T-X64)`,
  the first refusal of `-fcf-protection=full` modules); AArch64 keeps
  refusing both CET flags (`never(X64_ONLY)`; `llc` 19 and 22 ignore them
  there: no note, no code). `endbr64` placement (`crates/hod_x64/src/cet.rs`,
  `spec/codegen.md` §5.6.25): every function entry but a `nocf_check`
  one (`cet::entry`, one call from `frame::begin`, first instruction);
  address-taken blocks and landing pads (`hod_cg` `Target::branch_target`,
  from `emit_block` after the label, before the `phi` loads), an
  `invoke`'s landing stub; the `llvm.eh.sjlj.setjmp` resume point; the
  coroutine stubs `F.resume`/`F.destroy` and `__NoopCoro_ResumeDestroy`
  (`Target::NOOP_CORO_FN_MARKED`, `endbr64; ret`, as `llc` 22 writes it);
  after a direct call of a function declared `returns_twice`.
- **`nocf_check`** kept: function flag `FnAttrs::NO_CF_CHECK` (bit 21)
  and call-site flag (`CallDesc::nocf_check`); row `attr:nocf_check` `ON`
  on both targets. An indirect `nocf_check` call under
  `cf-protection-branch` is refused, `x64:nocf-check-indirect-call`
  (needs `notrack`, `3e`, not in `hod_mc_x64`; `llc` aborts on the
  `musttail` form).
- **The note**: `hod_cg`'s `gnu_property` writes IBT (1) and SHSTK (2)
  through the new generic `hod_obj::elf::add_gnu_properties` (a list of
  `(pr_type, pr_data)`, sorted, padded to 8; `spec/object.md`).

## What `llc` does (19 and 22 identical, `-O0`, x86_64, from probes)

| place | `llc` | hod |
|---|---|---|
| entry, external / `linkonce_odr` / weak / hidden | `endbr64` | same |
| entry, local, address in data or `llvm.used` | `endbr64` | same |
| entry, local, only called directly | none | `endbr64` (harmless superset: a `nop`) |
| entry, `nocf_check` | none | none |
| after direct call of `returns_twice` declaration | `endbr64` | same |
| after call with `returns_twice` on the call site only, or indirect | none | none |
| `blockaddress` block (with or without `indirectbr`) | `endbr64` | same |
| landing pad | `endbr64` after the EH label | same; plus one in a landing stub |
| `llvm.eh.sjlj.setjmp` resume | `endbr64` | same |
| `callbr` indirect target | none | none |
| switch | jump table `notrack jmpq` | no jump table |
| indirect `nocf_check` call | `notrack call` | refused |

## Evidence

- `tests/ir/cf_protection.ll` (x86-64; `;@ unsupported(aarch64): *`):
  `cargo xtask irdiff --witness --target x86_64`, LLVM 22 and 19, bfd,
  lld, mold: 3 PASS each; AArch64 3 UNSUPPORTED
  (`module:cf-protection-branch`).
- `crates/hod_x64/tests/cf_protection.rs`: per function, entry mark,
  marks after calls (by callee) and other marks against `llc` 22 and 19
  on the seed with full / branch / return / no flags and an sjlj module
  (the only differences the two in the table); consumers in hod's object:
  every `.gcc_except_table` landing, every code address held in data and
  every function symbol but `nocf_check` ones start with `endbr64`, also
  over every `tests/ir/coro/*.ll` seed with the flag; the note byte for
  byte and header for header `llc`'s for each flag set; freestanding
  programs (own `_start`, since the cross system root's start files carry
  no property) of hod's, `llc`'s and mixed objects, linked `-nostdlib
  -static` by bfd (`-z cet-report=error` for full), lld (`-z force-ibt`,
  `-z shstk`) and mold: exit 42 under `qemu-x86_64`, `readelf -n` IBT and
  SHSTK (IBT only for the branch-only variant with sjlj). `qemu-x86_64`
  does not enforce IBT or shadow stacks: the runs prove the marks do not
  change behaviour; the shape and consumer checks prove they are where an
  enforcing processor needs them. Refusals: indirect and `musttail`
  `nocf_check` calls under the branch flag; accepted without it.
- `crates/hod/tests/cf_protection.rs`: seed text and `llvm-as` 19 / 22
  bitcode give the same object on x86-64 for each flag set; AArch64
  refuses the flags and accepts `nocf_check` from both.
- Mutation: `emit_block` without the `BranchTarget::Block` mark fails
  `endbr64_where_llc_puts_it` (`ba_only`) and
  `every_indirect_branch_target_is_marked`; reverted.
- Real unit: REAL_UNIT

## Neighbouring hardening (not in this package)

| option | what reaches the backend | what building it takes |
|---|---|---|
| `-fcf-protection=return` alone | `cf-protection-return` | already `ON` (WP-143): SHSTK note only; `llvm.eh.sjlj.setjmp`/`longjmp` stay refused under it |
| `-mfunction-return=thunk-extern` | function attribute `fn_ret_thunk_extern` (rejected) | every `ret` becomes `jmp __x86_return_thunk` |
| `-mindirect-branch-cs-prefix` | module flag `indirect_branch_cs_prefix` | a `cs` prefix (`2e`) on calls/jumps to the retpoline thunks |
| `-mretpoline` | `"target-features"` `+retpoline-indirect-calls`, `+retpoline-indirect-branches` | indirect calls/jumps through `__llvm_retpoline_r11` (or external thunks with `+retpoline-external-thunk`), the thunk bodies in comdats |
| `-fsanitize=cfi` | type tests resolved in LTO; the backend sees `.cfi` jump tables (`jumptable` attribute) | requires LTO; the jump table entries (`jmp` + `int3` padding) |
| `-fsanitize=kcfi` | module flag `kcfi`, operand bundle `kcfi` on indirect calls, `!kcfi_type` | the `__cfi_` prefix hash before each function, the check sequence before each indirect call, `.kcfi_traps` |
| `-mbranch-protection=bti` (AArch64) | `branch-target-enforcement` | WP-185: implement `Target::branch_target` (`bti j`/`bti c`), `NOOP_CORO_FN_MARKED`, the note through `add_gnu_properties` |
