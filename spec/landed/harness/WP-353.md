# WP-353: the coroutine corpus in the gate, and `llvm.gcov`

Two independent parts, base `fc4690dd`.

## 1. The coroutine corpus as gate steps

Landed (`xtask/src/ci.rs`, `xtask/src/corpus.rs`,
`xtask/src/corpus/expected.rs`):

- Two full-gate-only steps, last in `STEPS` and `FULL_ONLY`:
  `corpus-coro-aarch64` and `corpus-coro-x86_64`. Two steps, not one
  `corpus-coro`, so they follow the per-target pattern of every other
  full-only step (`step_target` names the target, a failure names it, and
  either can be run alone). `step_target` now reads the part after the
  LAST `-` (`corpus-coro-x86_64`: `x86_64`); the step's family is the part
  before it.
- Each runs `corpus verify --strict` (`-j` of irdiff's default, 4) of
  `corpus::coro_dir_for`: `<build root>/corpus-coro/` and in it the name
  of the target's default corpus (`corpus`, `corpus-x64`, `corpus-a64`),
  with its own list, `docs/status/corpus-coro-expected.tsv`
  (`expected::coro_path`). `ci::corpus_gate_inputs` picks corpus and
  list for both kinds of L6 step. An absent corpus skips the step, or
  fails it under `HOD_REQUIRE_TOOLS=1`, as for the main corpus; the line
  names the recipe (`corpus capture --route hod`, WP-350).
- The coroutine corpus's list has no row (header only): hod builds every
  entry on both targets. The main list keeps its two x86-64 rows. A row
  naming a test absent from the corpus verified stays a list problem
  (unchanged code); proven below.
- No hosted workflow change: the hosted lanes run named quick steps only,
  and the full-only steps are in none of them (`--quick --step
  workflows` and `--step scripts` pass, no mirrored edit asked for).
- Docs: `spec/harness.md` "ci" (step list, `--step` list, test names),
  `docs/VALIDATION.md` "Full gate" (the steps, where the corpus lives,
  how it is captured) and the full compare-binaries recipe with the two
  coroutine corpora as two more `--corpus` arguments. Usage in
  `xtask/src/main.rs`.

Tests: `ci::tests::the_full_gates_steps` (nine full-only steps, the
coroutine ones last), `the_coroutine_corpus_steps_have_their_own_corpus_and_list`,
`corpus::expected::tests::the_workspaces_list_reads` (the coroutine list
reads and is another file).

## 2. `!llvm.gcov`

Measured first: `llc` (`-O0 -global-isel=0 -fast-isel=0`, module on
standard input so the file name is not in the object) with and without
the `!llvm.gcov = !{...}` line, LLVM 19 and 22, plain and
`-relocation-model=pic`: a hand module for x86-64, AArch64 and i686,
each with and without full debug information (12 per LLVM and mode),
the reduced module `gcov-reduced.ll` (i686), and zlib's
`infcover-coverage.ll` (i686; LLVM 22 only: llc 19 cannot read its
`captures(none)`). 30 pairs, 30 byte-identical, 0 different. Code
generation ignores it.

Landed: `hod_ir::kit::NamedMetadataKind::of` drops `llvm.gcov` (beside
`llvm.ident`, `llvm.errno.tbaa`); both readers go through it.
`spec/ir.md` "Named metadata and module flags" and §7 say so. Test:
`crates/hod_ir/tests/kit.rs`. Seed `tests/ir/gcov_named_metadata.ll`
(`-g`, a call, `printf`): irdiff PASS on aarch64 and x86_64 (5 results
each) and i686 (3), LLVM 22 and 19; `cargo test -p xtask --test
irdiff_real` 12 passed. `docs/status/support.md` unchanged (the support
document lists no dropped named metadata; regenerated with `HOD_BLESS=1`,
no diff).

The rest of the `-coverage` module: hod `--strict -O0 -filetype=obj`
builds `infcover-coverage.ll` on i686, x86-64 and AArch64 (the latter two
with the triple changed and the data layout and CPU attributes removed),
plain and PIC, exit 0, no refusal. That module holds no instrumentation
(no `__llvm_gcov_*` global or function, no `llvm_gcov_*` call): clang
wrote the named metadata without the profiler's output, so a module
with the instrumentation itself is not yet measured.
