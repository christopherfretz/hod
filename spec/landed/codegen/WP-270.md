# WP-270: the rewrites of `markAliveBlocks`

Spec: `spec/codegen.md` §5.6.8 "Folded constants and the blocks they
remove" (step 4 and the paragraph after it); `spec/ir.md` §5.7 (two
attributes kept).

## Found

WP-269 kept four rewrites of `markAliveBlocks` as written: an access
through `null`, an `invoke` of a `nounwind` callee, an `invoke` of a
`noreturn` callee, an `indirectbr` on a constant `blockaddress`. hod's
object then held a landing pad (with the personality, an LSDA and
`_Unwind_Resume`), a normal destination, the code after a `null` access
or an `indirectbr` target that `llc`'s does not, and the undefined
symbols only those reference.

## Measured

`llc` 19 and 22, x86-64 `-O0` and AArch64 `-O0 -global-isel=0
-fast-isel=0`, and `opt -passes=lower-constant-intrinsics` (the same
pass; its IR shows the rewrite). Every row is the same for both majors
and both targets. Each function folds a `br` on `llvm.is.constant`
whose dead arm deletes a block (so `removeUnreachableBlocks` runs).

| shape | `llc` |
|---|---|
| `invoke` of a `nounwind` callee, result used | `call` + `br` to the normal destination; the pad loses the edge; with no pad left, no personality, no LSDA, no `_Unwind_Resume` |
| same, the pad shared with an `invoke` that may throw | the pad stays; its `phi` loses the entry, and one left with one value is that value (`phi [1, %a], [2, %b]` became 2) |
| unused `invoke` of a `nounwind willreturn memory(none)` callee | `br` alone, the call gone (`use_empty && !mayHaveSideEffects`) |
| `invoke` of a `noreturn` callee that may throw | stays an `invoke`; its normal destination is a new block holding only `unreachable` (`%cont.unreachable`, placed before the old one); the old one loses the edge (`phi` entry) and dies without another predecessor; the pad stays |
| `invoke` of a `noreturn nounwind` callee | both: `call` + `br` to the new `unreachable` block; the pad and the old normal destination lose their edges (the real-code shape of WP-269) |
| non-volatile store to `null` (address space 0), atomic or not | the block ends there with `unreachable`; the rest and the successor edges go |
| volatile store to `null` | kept |
| store to `null` in a `null_pointer_is_valid` function | kept |
| store to `ptr addrspace(1) null` | kept (`llc`); hod refuses the address space anyway (`addrspace:pointer`) |
| `call void null()` | the block ends there |
| `indirectbr blockaddress(@f, %t), [%t, %u]` | `br label %t`; `%u` loses the edge |
| `indirectbr` whose `blockaddress` block is not listed | `unreachable` |
| no block deleted (the folded `br` has both edges to one block) | nothing of the above: `removeUnreachableBlocks` does not run |
| the pad's `phi` collapses to 3 and the pad branches on `icmp eq %p, 3` | not refolded: the `icmp` is an instruction, `ConstantFoldTerminator` does not see a constant; both arms stay |
| `invoke` with an unknown operand bundle | `llc` fails (`cannot lower calls with arbitrary operand bundles`) |
| `invoke` of `asm unwind` with `nounwind` | `call` + `br` in `llc`; hod refuses `x64:inline-asm-unwind` on x86-64 |

With `-g` (clang-22, a `try` around a call of a function defined after
the caller, so clang `invoke`s it and then marks it `nounwind`): `llc`'s
line table has no row of the handler; it has a row for the `br` that
leaves the `try`, which it emits as a jump to the next block (a block
whose only instruction is a `br` always gets one at `-O0`) and hod falls
through (P1 of `spec/dwarf.md` §5.7); AArch64 also keeps the rewritten
`if`'s `br` (P1). The call keeps its location (`changeToCall` copies it).

`markAliveBlocks` runs once: the rewrites happen in its depth-first
order, each `removePredecessor` may collapse a `phi` (as for a folded
`br`), and a terminator folds only on a constant operand.

## Rule

hod does in step 4 what was measured, with these exact conditions (the
code: `crates/hod_cg/src/const_fold.rs`, `Lci::mark_alive`,
`Lci::alive_invoke`, `Lci::alive_terminator`):
- a call through, or a non-volatile store to, `undef`/`poison`, or
  `null` in address space 0 of a function without
  `null_pointer_is_valid`: the block ends there (`Action::Unreachable`);
- an `invoke` through `null` (without `null_pointer_is_valid`) or
  `undef`: the block ends at it;
- an `invoke` of a `noreturn` callee (on the call or the declaration)
  whose normal destination does not start with `unreachable`: the normal
  edge goes (`remove_pred`); the `invoke` is lowered with its unwind
  edge and nothing after the call (`Action::NoNormal`);
- an `invoke` of a `nounwind` callee (on the call or the declaration),
  under a personality that is not an SEH one: the unwind edge goes, and
  the `invoke` is lowered as a call (no landing pad in its call-site
  row) followed by a `br` to the normal destination, or by nothing when
  the previous rule took that edge (`Action::Call`);
- `indirectbr` on `blockaddress` of the function itself: a `br` to the
  block (`Action::Jump`), or `unreachable` when it is not listed;
- when, after the walk, no emitted block is a landing pad and the
  personality is one LLVM knows, the function has no pads
  (`FnCx::has_pads`): no personality, no LSDA. This also covers a pad
  that died with a deleted `invoke` (WP-261), which kept both until now.

`willreturn` and `null_pointer_is_valid` are kept attributes now
(`FnAttrs::WILL_RETURN`, bit 22, also on call sites;
`FnAttrs::NULL_POINTER_IS_VALID`, bit 23; support rows
`attr:willreturn` and `attr:null_pointer_is_valid`, both `ON`).

## Kept as written

Where hod cannot decide as `llc` does, the instruction stays as it was
written, with all its edges (WP-269's behaviour: correct code, a
superset of `llc`'s blocks):
- an `invoke` of a `nounwind` callee that may be a `br` alone: the call
  or the declaration is `willreturn` and no user of the result is left
  unreplaced. `llc` drops the call when it also does not write memory;
  hod keeps no memory effects, so it cannot tell. With a user (or
  without `willreturn`) the rewrite is exact;
- an `invoke` of an intrinsic or of inline assembly;
- an `indirectbr` in a module with `cf-protection-branch` or BTI: LLVM
  destroys the `blockaddress` when nothing else uses it, and its block
  then loses the landing instruction; hod does not count a constant's
  uses;
- an `indirectbr` on anything but a plain `blockaddress` constant of the
  function (a cast, a folded `select`);
- `llvm.assume(i1 false/undef)` and `llvm.experimental.guard(i1 false)`,
  which `markAliveBlocks` also ends a block at: not modelled.

The module flag `eh-asynch` (which also stops the `nounwind` rewrite)
is refused by `classify` as an unknown flag, so it never reaches here.
No new refusal: the four names WP-269 retired stay retired.

## Tests

- `rewrites`, both targets (x86-64 under `qemu-x86_64` here): twelve
  programs: `null-access`, `null-valid`, `null-volatile` (and an atomic
  store), `nounwind-invoke`, `noreturn-invoke`,
  `noreturn-nounwind-invoke`, `throw-caught` (a real `__cxa_throw` caught
  by a pad that a rewritten `invoke` also named; its `phi` prints 2),
  `indirectbr`, `indirectbr-unlisted`, `combined` (a `nounwind` invoke,
  a `null` store and an `indirectbr` in one function); kept:
  `willreturn-invoke`, `indirectbr-cet`. Undefined symbols equal to
  `llc` 19's and 22's (a kept shape: plus the listed ones), the program
  prints what `llc` 22's prints, and the same module without the folded
  branch gives `llc`'s symbols too.
- `nounwind_invoke_unit`: WP-269's reduced unit, undefined symbols now
  equal to `llc`'s (no `__gxx_personality_v0`).
- `debug_info`, the `invoke` source: hod's object verifies, has no row
  of the handler or the dead arm, and the rows `llc` has but the P1 ones.
- Corpus pre-check: `cargo xtask irdiff --linker lld` over every corpus
  entry that calls `llvm.is.constant` or `llvm.objectsize`: AArch64 6
  and 6, x86-64 20 and 20 (LLVM 19 and 22), all 52 PASS, hod built every
  object.
- The WP-269 tests, the hod_bc convergent row (the call site now also
  prints `willreturn`), the attribute table (40 kept, 47 dropped) and
  the support page all pass; `classify_random`'s token pair moved to
  seed 2633.

## Real code

The two evidence units of WP-269 (`main` of a kiln-built unit of the
fifth set of real projects, reduced and full; x86-64, PIC, `--strict`):
- reduced: undefined symbols now equal to `llc` 22's (WP-269: plus
  `__gxx_personality_v0`); neither object has an LSDA or an
  `.eh_frame` personality now (hod had both);
- full: hod has no undefined symbol `llc`'s lacks; `llc`'s has the five
  `std::allocator<char>` members of WP-269's record more (local copies in
  hod, older than this change). Both have `main`'s LSDA (other pads stay).
Byte equality with `llc` was not expected and not seen (hod's code
differs everywhere).
