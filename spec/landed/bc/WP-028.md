# WP-028 — hod_bc stage 1: the bitstream and the module level

Landed: `spec/bc.md` §1 to §10. This covers:

- the bitstream container (wrapper, magic, abbreviations, BLOCKINFO,
  blocks), with skipping;
- the identification block;
- the whole module level, read into a `hod_ir::Module` with the
  decisions `hod_ll` makes for the same module as text.

Function blocks are stepped over and handed on as spans (§7). Debug-info
nodes take their id and are not read (§6).

Not here:

- function bodies (the next stage);
- debug information;
- a definition's own metadata attachments (§10).

## What it did

`crates/hod_bc` uses `std` and `hod_ir`. For tests it also uses `hod_ll`
and `hod_testutil`.

| module | contents |
|---|---|
| `bitstream` | `Cursor`, `BlockInfo`, `BlockSpan`, `Entry`: fields, VBR, blocks, abbreviations, BLOCKINFO, skipping (§2) |
| `codes` | block ids and record codes (§4) |
| `raw` | the first pass: records kept in one `u64` pool, function spans, metadata strings and slots (§3) |
| `types` | the TYPE block, resolved without recursion (§5.2) |
| `attrs` | attribute group decoding, the kind table, function, return and parameter attributes as `hod_ll` builds them (§5.3) |
| `consts` | values and lazily built module-level constants, without recursion (§5.6) |
| `module` | the build in `hod_ll`'s order, `read_module`, `ReadOptions`, `BcModule`, `ModuleBits`, `FunctionBits` (§5, §7) |
| `error` | `BcError`, `BcErrorKind` (§8) |

There are 19 tests in five binaries:

- 13 bitstream unit tests (§9.1);
- `differential` (§9.2);
- `oracle` (§9.3);
- `robustness`, 4 tests (§9.4);
- `examples/bcread` for timing (§9.5).

## Evidence

**The differential** (§9.2) ran over the full corpus (5,760 modules).
Bitcode came from each major's `llvm-as`. The module `hod_bc` reads was
compared with the module `hod_ll` reads from `llvm-dis` of the same
bitcode, by the structural dump of §9.2.

| LLVM | modules | agree | both refuse | differ | tool failures |
|---|---|---|---|---|---|
| 19 | 2864 | 2864 | 0 | 0 | 0 |
| 22 | 2896 | 2896 | 0 | 0 | 0 |

The classes of difference found and fixed on the way:

- attribute kind 105 (`nocreateundeforpoison`, new in 22) was missing,
  and 7 LLVM 22 modules were refused for it.

**The handwritten module** (§9.3) agrees on LLVM 19 and 22, and its dump
holds all 42 constructs it asserts.

**Robustness** (§9.4):

| check | reads | slowest read | peak memory growth |
|---|---|---|---|
| every truncation of a 3,360-byte file | 3,360 | 0.4 ms | 1.3 MB |
| every single-byte corruption, all 255 values per position (release) | 856,800 | 1.9 ms | 0.5 MB |
| random inputs | 2,000 | 0.3 ms | 1.3 MB |

No read panicked, and every truncation was an error.

bodies are skipped by length. That is against 5 ms for `hod_ll` on its
text and 300 ms for `llvm-dis`.

## For later stages

- **The body stage** reads `ModuleBits::functions()` spans with
  `Cursor::enter_at` and `block_info()`. Value ids start at
  `value_count()`. Module-level constants come from `constant()`, which
  needs `&mut Module`. To read bodies in parallel, build the constants
  they use first, or give each body its own constant table (§7).
- **Metadata ids.** `ModuleBits` does not expose the module metadata
  slot table. Function blocks refer to module metadata by id, for
  attachments and `!dbg`, so the body or debug stage must add an
  accessor over `raw::MdSlot`.
- **Definition attachments.** A definition's `global-metadata:` notes
  come from its function block's METADATA_ATTACHMENT (§10). The body
  stage must give them, so that a `define … !kind !N` agrees with
  `hod_ll`.

## Gaps in hod_ir and hod_ll

- `hod_ir::Types::target_ext` takes a `&str`. A non-UTF-8 target type
  name is read lossily (`types.rs:315`). The same holds for attribute
  string keys in notes (`attrs.rs:279`, `attrs.rs:345`).
- `hod_ir` keeps no type or integer parameters of target extension
  types. Neither reader can deliver them.
