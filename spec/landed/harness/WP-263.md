# WP-263 — expected results for the real-project lanes

Landed: the real-project lanes judge a test that passes under `llc` and
not under hod against a list of expected results,
`docs/status/oss-expected.tsv` (`spec/harness.md` "Real projects",
"Expected results"), and `spec/cli.md` "Always-inline" states what a
body that observes its own code address sees out of line ("Code
addresses"). No code under `crates/` changed: hod's output is the 1.0
candidate's (02fe2d02).

## The finding

The hosted real-project workflow ran for the first time on the
candidate, on native x86-64 runners. Its summary failed on one test in
four builds: abseil 20260107.1, `absl_symbolize_test`, flavours `O0`
and `O0g`, modes `hod` and `strict`. The control (`llc`) passes it in
both flavours. The program's output under hod strict (`O0`; `O0g` alike):

```
absl/debugging/symbolize_test.cc:482: Failure
Expected equality of these values:
  symbol
    Which is: "inline_func"
  __FUNCTION__
    Which is: "TestWithPCInsideInlineFunction"
TestWithPCInsideInlineFunction failed
...
[  PASSED  ] 9 tests.
```

`TestWithPCInsideInlineFunction` calls `inline_func`, an
`ABSL_ATTRIBUTE_ALWAYS_INLINE` function whose body is `leaq 0(%rip),
%reg` (x86-64; `call 1f; 1: pop` on i386; nothing on any other
architecture, so AArch64 is not affected), and asks the symbolizer which
function that pc is in, expecting the caller. hod compiles the call out
of line (WP-021, WP-188): in the strict binary `TestWithPCInsideInlineFunction`
has `callq inline_func`, and `inline_func` (a weak definition, `W` in
`nm`) is the frame, the `leaq (%rip), %rax` and the return, as
`non_inline_func` is. The symbolizer names `inline_func`, correctly for
that address. Everything else the program checks passes under hod: the
same pc read in the `noinline` `non_inline_func`
(`TestWithPCInsideNonInlineFunction`), the return address naming `main`
(`TestWithReturnAddress`), and the nine gtest cases (`Symbolize.Cached`,
`Truncation`, `SymbolizeWithDemangling`, `SymbolizeSplitTextSections`,
`SymbolizeStackConsumption`, `SymbolizeWithDemanglingStackConsumption`,
`SymbolizeWithMultipleMaps`, `InstallAndRemoveSymbolDecorators`,
`ForEachSection`), the gtest lines equal to the control's but for the
milliseconds. The project's other failing test, `absl_raw_hash_set_test`,
fails in the control too.

On the AArch64 development machine the x86-64 lane runs the tests under
qemu-x86_64, where the control fails this test as well, so the local
lane never showed a difference.

**Reproduction.** Twenty lines: an `always_inline` function returning
`leaq 0(%rip)`, a `noinline` caller asking `dladdr` (the program linked
with `-rdynamic`) for the symbol of that pc. Built by kiln for
x86_64-linux-gnu at `-O0`, run under qemu-x86_64: with `llc` it prints
`caller (caller)` and exits 0 (the `leaq (%rip)` is inside `caller`);
with hod strict it prints `callee (inline_func)` and exits 1 (`caller`
has `callq inline_func`). Same source, flags and run otherwise.

**Decision.** By design: a call to an `alwaysinline` function out of
line is hod's documented behaviour, and the value of a code address is
not one the language promises; a body that observes it is accepted, not
declined (`spec/cli.md` "Code addresses"). The test is listed as an
expected result rather than changing the code generator before 1.0.

## The list

`docs/status/oss-expected.tsv`, beside `corpus-expected.tsv`, nine
tab-separated columns: project, target (`aarch64`, `x86_64`, `*`; the
architecture built for, the host for a native build), flavour, mode,
test, the outcome (`fails`), a text the test's output must contain (or
`-`), the reason, the spec section. Its entry at landing:

| project | target | flavour | mode | test | text | spec |
|---|---|---|---|---|---|---|
| abseil | x86_64 | `*` | `*` | `absl_symbolize_test` | `Which is: "inline_func"` | `spec/cli.md` "Always-inline" |

The stale rule, per entry and per build it matches where the control
and the build both have test results: stale when the test passes in the
build, or when neither has the test. A worse test an entry names is
expected only when the build has it and its output contains the text;
otherwise it stays a regression. The control failing the test too
(qemu-x86_64) is no difference: the entry is moot there, not stale.

## The harness

- `scripts/oss/oss-report.py`: `check` (rewrites
  `TEST-REGRESSIONS.txt`, unexpected only, `TEST-EXPECTED.txt` and
  `TEST-STALE.txt` from every report; exit 1 on a regression or a stale
  entry, 2 on a malformed list), `unexpected <project> <flavour>
  <mode>` (for oss-run.sh's choice to keep a tree), `--expected <file>`;
  `status` and `census` show expected differences with their reason in a
  note, and the census has a section "Expected results" (expected, moot,
  stale).
- `scripts/oss/oss-run.sh`: copies the list into its snapshot, keeps a
  tree only for an unexpected difference, runs `check` after each
  flavour (it no longer appends to the regressions file).
- `.github/workflows/oss.yml`, the summary step only: `check` over the
  merged artifacts (each project's artifact carries its own
  `TEST-REGRESSIONS.txt`, and merging kept only one of them), then the
  census as before, the expected differences printed, and exit 1 when
  `TEST-REGRESSIONS.txt` or `TEST-STALE.txt` is not empty.
- `scripts/oss/oss-report-selftest.py`: synthetic reports for each
  rule (expected, unexpected, another failure, no entry, stale by a
  pass, stale by a missing test, control fails too, another target, a
  malformed list); 43 checks. CI could run it in the summary job before
  `check`, or in the quick gate's script checks; no workflow runs it yet.

**Against the hosted run.** The summary step's commands over a copy of
the abseil x86-64 artifact's reports, logs and findings: exit 0, four
`EXPECTED` lines, the status rows `hod: 1 expected
(absl_symbolize_test (note n))`; with the entry removed, exit 1 and the
four regressions as the run printed them.

## Follow-ups

1. Run `scripts/oss/oss-report-selftest.py` in CI (the summary job or
   the quick gate).
2. An always-inline that is really inlined (a later optimizing mode)
   would remove the entry; the stale rule then asks for its deletion.
