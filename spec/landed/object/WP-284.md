# WP-284 — i386, I1: ELF32 and `SHT_REL` in `hod_obj`

The contract is `spec/object.md` "ELF32 and `SHT_REL`". The design is
`docs/design/0008-i386.md` sections 1.2, 3.2 and 3.5 (row I1 of 6.1).

## What landed

- `Machine { AArch64, X86_64, I386 }`, `Object::for_machine`,
  `Object::machine`; `I386Reloc` (the 12 kinds of design 3.2 plus `None`
  and `Other`) with `field_size`; `RelocKind::I386`, `RelocKind::machine`,
  `RelocKind::for_machine`; `CHDR32_SIZE`; the errors
  `AddendNotRepresentable { section, offset, addend }`,
  `NotInElf32 { what }` and `Limit::Elf32Field`.
- The writer (`src/elf.rs`): one code path for both classes, the record
  sizes and alignments in a `Form` (52/40/16/8 bytes, alignment 4,
  `.rel` prefix, `SHT_REL`); the addends added into a copy of each
  relocated section's bytes as they are streamed; the ELF32 range checks
  before anything is emitted.
- `compress_section` for i386: `Elf32_Chdr`, alignment 4, the addends put
  into the bytes before compression.
- `add_init_array`/`add_fini_array` align to the address size; GNU
  property notes are `NotInElf32`.
- Tests: `tests/i386.rs` (12 tests) and unit tests in `src/reloc.rs`.

## Measured from LLVM (llvm-mc 22, `-triple=i686-linux-gnu`)

- `.rel<name>`: `SHT_REL`, `SHF_INFO_LINK`, entry size 8, alignment 4;
  `.symtab` alignment 4, entry size 16; section header table at a
  4-aligned offset; `e_flags` 0; ELFOSABI_NONE.
- The addend in the bytes: `calll helper` holds `fc ff ff ff` (-4) with
  `R_386_PC32` against the section symbol `.text.helper`; `.long answer+4`
  holds 4; `.long _start-8` holds `f8 ff ff ff`.
- Every relocation number of design 3.2 (`R_386_32` 1, `PC32` 2, `PLT32`
  4, `GOTOFF` 9, `GOTPC` 10, `TLS_IE` 15, `TLS_GOTIE` 16, `TLS_LE` 17,
  `TLS_GD` 18, `TLS_LDM` 19, `TLS_LDO_32` 32, `GOT32X` 43) from
  `llvm-readelf -r` of one assembled instruction each: all as the design
  says.
- Overflow: `.long ext+0x100000000` assembles to `00000000` and
  `.long ext-0x80000001` to `ffffff7f`, without a diagnostic (LLVM keeps
  the low 32 bits); `.long ext+0xffffffff` and `-0x80000000` are stored.
  hod accepts `-2^31 ..= 2^32 - 1` and refuses the rest by name.
- `.quad ext+5` in an i386 object: "unsupported relocation type" (no
  64-bit data relocation exists).
- `--compress-debug-sections=zlib`: `Elf32_Chdr` `01000000 cc000000
  01000000`, the section aligned to 4, the addend inside the stream.

## Corrections to the design

- The design names `Arch::I386`. `hod_obj::Arch` is matched exhaustively
  in `hod_eh`, `hod_dwarf` and `hod_cg` (`hod_eh/src/target.rs:134`,
  `hod_eh/src/lib.rs:842`, `hod_dwarf/src/target.rs:40`,
  `hod_dwarf/src/x86_64.rs:76`, `hod_cg/src/emit/mod.rs:277,286,445`),
  which this package does not own, so a third variant would not compile.
  The machine is `hod_obj::Machine`; `Arch` keeps two variants until the
  back ends handle i386, when folding `Machine` into `Arch` is a
  mechanical change.
- Design 1.2 says "the set of 3.3" for `I386Reloc`: it is the set of 3.2.
- Design 1.2 calls an addend that does not fit "an internal error": it is
  the stable `AddendNotRepresentable`.
- The contract file is `spec/object.md` (not `spec/obj.md`), the record
  directory `spec/landed/object/`.

## Proof that the 64-bit objects did not change

`cargo xtask compare-binaries` of release `hod` built from the base
(48676d07) and from this branch, each in its own target directory, over
`tests/ir` and the two corpora (`.build/corpus`, `.build/corpus-x64`), in
both modes: see "Results" below. The 64-bit paths keep their record
encoders; the shared code takes its sizes from the `Form`, whose ELF64
values are the former constants.

## Results

- `compare-binaries`: 14 036 modules, 28 072 comparisons: identical
  27 848, different 0, changed-outcome 0, identical-failure 224 (110 per
  mode whose triple is neither target, 2 per mode on x86-64),
  harness-error 0: PASS. (The head binary was built before two clippy
  rewrites of the ELF32-only range checks, `value <= u32::MAX` into
  `u32::try_from(value).is_ok()`, which no 64-bit object reaches.)
- `HOD_REQUIRE_TOOLS=1 cargo test -p hod_obj`: every test passes, among
  them the 12 of `tests/i386.rs`: `llvm-readelf` 19 and 22 read the
  program with the expected header, sections, symbols and relocations;
  header, symbols, relocations and the bytes of `.text`, `.text.helper`,
  `.data` and `.debug_info` equal `llvm-mc`'s object's; GNU ld
  (`i686-linux-gnu-ld.bfd`), ld.lld 22 (`-m elf_i386`) and mold
  (`-m elf_i386`) link it statically, and each program exits with 42
  under `qemu-i386`.
- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --
  -D warnings`, `cargo check --workspace --all-targets`: clean, with no
  file outside `crates/hod_obj` changed.

## Not done

- The existing test files (`structure.rs`, `tools.rs`, the link tests)
  are not parametrized over the third machine: their reader in
  `tests/common/mod.rs` is ELF64 only. `tests/i386.rs` covers the same
  ground for i386 with its own ELF32 field reads and the readelfs.
- No ELF32 reader: `hod_obj` has none in `src/` (the reader is test
  support).
- The hand-built program is compared with `llvm-mc`'s object of the same
  assembly, not `llc`'s of an `.ll` (the program needs `int $0x80`; both
  go through LLVM's MC object writer).
- GNU property notes for i386 (`NotInElf32`); `SHT_X86_64_UNWIND` given to
  an i386 object is not refused.
