# WP-003 — hod_ir module level: symbols, COMDATs, inline assembly, function attributes, module properties and flags

Landed: `spec/ir.md` §2 (the module's tables other than types, constants
and debug), §2.1 (module properties and the module-flag mapping), §2.2
(symbols, the declare-then-define rules, constructors and destructors),
and the function half of §5.7 (the attribute table and interned function
attribute sets). Not here: function bodies and call-site attributes
(WP-004), debug nodes (WP-005; a function symbol stores a `DiId` and
nothing reads it), `classify` (§8), the printer (§9), any parser.

## What it did

`crates/hod_ir`, new or rewritten modules:

| module | contents |
|---|---|
| `symbol` | `SymbolTable` (crate-private) and the public vocabulary: `Linkage`, `Visibility`, `UnnamedAddr`, `TlsModel`, `Retained`, the description structs `VariableDesc`, `FunctionDesc`, `AliasDesc`, `IFuncDesc`, the views `Symbol` and `SymbolKind` |
| `comdat` | `ComdatKind`, `Comdat`, the COMDAT table |
| `asm` | `InlineAsm`, the inline-assembly table |
| `attrs` | added to WP-004's shared types: `UwTable`, `FnStr`, `FnAttrs`, `FnAttrsId`, `FnAttrsView`, the interned sets, the interned parameter-attribute lists, and the class table `ATTRIBUTES` with `attr_class` and `attr_info` |
| `props` | `ModuleProps` and its enums, `BranchProtection`, the module-flag mapping (`FlagBehavior`, `FlagValue`, `FlagClass`, `ModuleFlag`, `KNOWN_MODULE_FLAGS`, `IGNORABLE_MODULE_FLAGS`, `module_flag_class`) |
| `strings` | a byte-string interner the tables share (crate-private) |
| `module` | `Module`: the producer-facing API over all of the above, plus `Structor`, module-level assembly, `StringLists` (linker options, dependent libraries) and `Unsupported` records |

`error.rs` gained four kinds at the end of `IrErrorKind`: `InvalidSymbol`,
`SymbolRedefined`, `UndefinedSymbol`, `InvalidModuleFlag`. `lib.rs` gained
the `mod` lines and re-exports. `CallConv`, `ParamAttrs` and `ParamMem`
are as they were on `main`; `encode_align` and `decode_align` in `attrs`
became `pub(crate)`.

Sizes, asserted in unit tests: a symbol entry is 48 bytes, `ModuleProps`
40, a `Structor` 16, an inline-assembly entry 16, a COMDAT entry 12, the
fixed part of a function attribute set 12, one string of a set 8,
`FnAttrsId` 4.

Measured, not gated (`tests/symbol_perf.rs`, optimized build, three runs
on the shared development host): for 100,000 symbols whose names average
115 bytes, creating a symbol by name takes 150 to 210 ns, describing it
32 ns, finding it by name 59 to 73 ns, finding that a name is absent 55
to 76 ns, reading it back through `Symbol` 2 ns. Unoptimized: 971, 142,
710, 717 and 25 ns.

## Decisions where the spec was silent

All of these are now in `spec/ir.md`; this is the list of what was open.

Symbols (§2.2):

- **Three states: unresolved, declaration, definition.** `symbol_named`
  creates an unresolved symbol, so a producer has an id for a name before
  it knows what the name is. A symbol that is still unresolved at
  `verify_symbols` is `UndefinedSymbol`.
- **Declare-then-define.** Describing a declaration or an unresolved
  symbol again replaces the description wholesale, including its kind
  (a declared function may become an alias). Describing a definition is
  `SymbolRedefined`, even with an equal description.
  `set_initializer` and `set_has_body` are the two shortcuts from
  declaration to definition; `discard_definition` is the way back
  (LLVM's `convertToDeclaration`), meant for `available_externally`
  bodies that will not be compiled. Retained marks survive everything.
- **No merging and no agreement check** between an earlier and a later
  description. With opaque pointers nothing that refers to a symbol
  depends on its type.
- **Anonymous symbols are local.** LLVM accepts `@0 = global ...` and
  `llc` names it `__unnamed_1`; hod refuses an anonymous symbol with a
  non-local linkage instead of taking over that naming scheme.
- **`dso_local` is normalized** to LLVM's implied value when a symbol is
  described, so `Symbol::dso_local()` is the answer and no consumer
  re-derives it.
- **Immediate checks and end checks are separate.** Everything that
  depends only on the description is checked by `set_*`; what depends on
  other symbols (alias targets, resolvers, declarations' linkage once it
  is known that no definition follows, dangling `SymId`s in constants)
  by `verify_symbols`, once.
- **A declaration's personality is not refused** (LLVM refuses it). It
  is never read, and `discard_definition` clears it.
- **Address spaces are kept**, a `u32` per symbol up to
  `MAX_ADDR_SPACE`, so `classify` can name a non-zero one; the spec said
  "0 only".
- **An alias target is a constant** that is `Addr`, `AddrOfInt` or `Expr`.
  The end checks follow `Addr` targets; the other two are for `classify`.
  **An IFUNC resolver and a personality are `SymId`s**; a personality
  that is some other constant is recorded as unsupported.
- **Parameter attributes of functions are interned as lists**, so a
  symbol entry holds one `u32` for all of them and functions with the
  same attribute shape share storage. A list may be shorter than the
  parameter list.
- **Constructor priorities are `u16`**, clamped as `llc` clamps them.
- **Names**: not empty, no zero byte (`llvm-as` refuses both too).

Module (§2, §2.1):

- **`record_unsupported`**: `hod_ir` has no field for a number of rare
  LLVM constructs (DLL storage, prefix and prologue data, `gc`,
  `partition`, a variable's `code_model`, memory tagging of a variable)
  and none for a rejected attribute. Instead of a field each, the
  producer records the construct by name and `classify` reports the
  first record. The construct names in §2.2 are proposals for §8.
- **`ModuleProps` is a public field** of plain data. The bridge assigns
  it; an LLVM-IR producer feeds module flags to `set_module_flag`.
- **Known flags are checked harder than LLVM checks them**: integer, in
  the range hod has a meaning for. LLVM's verifier range-checks none of
  them and type-checks about half.
- **`Require` flags are kept and not evaluated.** A module whose
  requirement is not met is refused by LLVM; hod keeps the entry (it is
  never ignorable, so `classify` will refuse any module that has one
  until someone gives requirements a meaning).
- **Behaviors are validated (1 to 8) and otherwise ignored** for known
  flags.
- **`!llvm.dependent-libraries` is kept**, like `!llvm.linker.options`
  (an addition; §7 now says so).
- **Module-level assembly is one byte string**, each appended piece
  ending in a newline.
- **Infallible methods do not return `IrResult`**: `add_ctor`,
  `add_dtor`, `append_module_asm`, `record_unsupported`,
  `set_comdat_kind`, `discard_definition`. They have no input to refuse.

Attributes (§5.7):

- **Keyword and string attributes are separate name spaces** in the
  table (`AttrSyntax`): LLVM would accept `"nounwind"` in quotes as an
  unrelated string attribute.
- **Function attribute sets are interned** (`FnAttrsId`, four bytes per
  function). Flags are a `u32`, `uwtable` and `alignstack` a byte each,
  strings `(FnStr, interned value)` pairs ordered by key.
- **`FnAttrsId` is defined in `attrs.rs`**, not `ids.rs`, to leave the
  shared file alone.
- **Additions to the spec's lists**, each justified in §5.7:
  - dropped: `builtin`, `norecurse`, `inlinehint`, `noext`,
    `allocalign`, `allocptr`, `null_pointer_is_valid`,
    `nocreateundeforpoison`, `vscale_range`,
    `disable_sanitizer_instrumentation`, `nosanitize_bounds`,
    `nosanitize_coverage`, `noprofile`, `skipprofile`, and the string
    `no-trapping-math`. Without `builtin`, `norecurse`,
    `nocreateundeforpoison`, `disable_sanitizer_instrumentation` and
    `no-trapping-math`, no C++ translation unit from clang 22 would pass.
  - kept strings: `branch-protection-pauth-lr`, `guarded-control-stack`,
    `stack-protector-buffer-size`, `min-legal-vector-width`,
    `no-jump-tables`.
  - made explicit: `align` (parameters), `readnone` and `writeonly`
    (the spec's "`readonly` and the `memory(...)` family"),
    `dereferenceable_or_null`, the ten `sanitize_*` names, the three
    stack-protector keywords, the six fast-math strings.
- **Left rejected** although an argument for "dropped" exists:
  `nodivergencesource`, `noduplicate`, `optdebug`, `optforfuzzing`,
  `coro_elide_safe`, `coro_only_destroy_when_complete`, and the strings
  `profile-sample-accurate`, `use-sample-profile`,
  `no-inline-line-tables`, `denormal-fp-math*`. None appears in clang's
  output for an ordinary build.

Tests:

- `#[allow(clippy::many_single_char_names)]` on the `symbol` unit tests
  (as in WP-002's modules), `too_many_lines` on the table of cases in
  `tests/symbols_as.rs`, `struct_excessive_bools` on that file's `Spec`,
  which mirrors a line of LLVM text.

## What LLVM does that was not expected

- **`Attributes.td` is not in the Debian LLVM packages.** The two name
  lists in `tests/data/` were extracted from the file at the upstream
  tags of the installed versions (`llvmorg-19.1.7`, `llvmorg-22.1.8`,
  fetched from GitHub; URL, SHA-256 and the extraction pipeline are in
  each file's header), and then checked against the installed `llvm-as`
  19 and 22: each accepts every keyword of its own list, 19 refuses all
  ten keywords that only 22 has, and 22 still reads `nocapture`, which
  LLVM 21 replaced by `captures(none)`.
- **`builtin` is listed as a function attribute and `llvm-as` refuses it
  on a declaration** ("'builtin' attribute not valid on function"); it
  parses at call sites only.
- **Module flags of clang 19 and 22 differ in value.** The AArch64
  protection flags are 1 from clang 19 and 2 from clang 22, and LLVM's
  reader *upgrades* a module with value 1 by copying the flags onto
  every function as string attributes and rewriting them to 2. hod reads
  function protection from the function, so a producer that does not go
  through LLVM's reader has to do the same. `frame-pointer` on AArch64 is
  1 (non-leaf) from clang 19 and 4 (non-leaf-no-reserve) from clang 22;
  LLVM 19 refuses the string attribute `"frame-pointer"=
  "non-leaf-no-reserve"` and accepts the module flag value 4 unread.
- **`-funwind-tables` does not lower the `uwtable` flag**: asynchronous
  tables are the default on both targets and stay; only
  `-fno-asynchronous-unwind-tables -funwind-tables` gives 1. With
  `-ffreestanding` clang writes no `uwtable` module flag (19 and 22,
  both targets), while clang 22 for x86-64 was seen to keep `uwtable` on
  every function.
- **Debian's clang defaults to PIE**: `PIC Level` 2 and `PIE Level` 2
  with no option; `-fPIC` removes `PIE Level`.
- **LLVM's verifier checks module-flag values unevenly.** It demands an
  integer for `PIC Level`, `PIE Level`, the three `sign-return-address*`
  flags, `branch-target-enforcement` and `wchar_size`, and accepts a
  string for `Code Model`, `uwtable`, `frame-pointer`, `Dwarf Version`
  and the rest. It range-checks none of them (`PIC Level` 9 verifies).
  It does evaluate `Require` entries.
- **Constructor priorities are unsigned and clamped**: -1, 65536 and
  `i32::MAX` all land in the plain `.init_array`, the same section as
  65535, while 0 is `.init_array.0`.
- **AArch64 reaches every `extern_weak` symbol through the GOT**, also
  one stated to be `dso_local`. Otherwise GOT use in PIC code follows
  LLVM's implied-`dso_local` rule exactly, on both targets and versions.
- **LLVM 19 accepts a definition of an opaque type**
  (`@x = global %opaque zeroinitializer` verifies); LLVM 22 refuses it.
  Every other symbol case has the same verdict in both versions.
- **`externally_initialized` changes nothing in the object**: `llc` 22
  puts a zero variable in `.bss` and a constant in `.rodata` with it as
  without it. It is dropped.

## Differences from LLVM

Pinned by `tests/symbols_as.rs`, which fails when either side changes.

Symbols, where hod accepts and `llvm-as` refuses:

- a name described twice as a declaration, a declaration followed by a
  definition, and a declared function that becomes an alias or an IFUNC
  (LLVM's text has no second mention of a name; these are the
  declare-then-define rules);
- a personality on a declaration.

Symbols, where `llvm-as` accepts and hod refuses:

- an anonymous symbol with non-local linkage;
- with LLVM 19 only, a definition of an opaque type.

Module flags: LLVM refuses a `Require` that is not met or names no flag
(hod keeps it); LLVM accepts `PIC Level` 9, `PIE Level` 3, `Code Model`
9, `uwtable` 3, `frame-pointer` 9, and a string for `Code Model` or
`uwtable` (hod refuses each); LLVM refuses a string `wchar_size` (hod
does not look at a flag it ignores).

transition and each `SymbolRedefined` / `InvalidSymbol` /
`UndefinedSymbol` / `InvalidModuleFlag` case, the end checks including
alias cycles and chains, interning identity of attribute sets whatever
the order they were filled in, the size assertions, the flag mapping
field by field. One doctest (`FnAttrs`).

Integration tests, `crates/hod_ir/tests/`. As in WP-002 each needs the
LLVM 19 and 22 tools, passes with a note without them and fails without
them under `HOD_REQUIRE_TOOLS=1`.

Not covered against LLVM, and why:

- `Code Model`, `Large Data Threshold`, `branch-protection-pauth-lr` and
  the stack-probe flags are in the known and ignorable lists from a wider
  one-off survey (`-mcmodel=`, `-mbranch-protection=pac-ret+pc`,
  `-fstack-clash-protection`); `clang_survey.rs` covers the option list
  of §2.1 only. The flag mapping for them is unit-tested.
- The C++ in `clang_survey.rs` includes no header: the x86-64 C++
  standard library headers are not installed for cross compilation. A
  libc++-heavy unit may show attributes the survey has not seen; they
  would be rejected by name, not mishandled.
- COMDAT kinds, inline-assembly flags, linker options and module-level
  assembly have no validity rules beyond their types; unit-tested only.
- Call-site attributes belong to WP-004.

## For the next work packages

- **`classify` (§8)** has four inputs from here: `Module::unsupported()`
  (report the first record), `Module::other_flags()` (refuse one that is
  not `ignorable`, as `module-flag:<name>`), non-zero `addr_space` on a
  symbol, and alias targets that are not `Addr`. It should also settle
  the construct names §2.2 proposes.
- **Producers (`hod_ll`, `hod_bc`, the bridge)**: call
  `attr_class` for every attribute and `record_unsupported("attr:...")`
  for a rejected one; apply LLVM's module-flag upgrade for protection
  flags of value 1 if not reading through LLVM; call `verify_symbols`
  once at the end; skip `null` constructor entries; use `add_*` only
  when a failed description may leave an unresolved name behind.
- **WP-004**: `FunctionBuilder` can take `&Module` and read
  `module.symbol(id)` for the callee's type, calling convention and
  attributes; `Module::inline_asm` gives the `AsmId` an inline-assembly
  call needs. Call-site `noreturn` / `nounwind` / `returns_twice` are
  not in `FnAttrs`' interned sets unless WP-004 chooses to reuse them
  (`intern_fn_attrs` works for any set).
- **WP-005**: `FunctionDesc::subprogram` is stored and returned
  unchecked; the variable's global-variable expressions (§6) have no
  field yet.
- **Object writer**: `Symbol::dso_local()` is already LLVM's implied
  value; on AArch64 `extern_weak` goes through the GOT regardless.
  `Structor::priority` 65535 means the unsuffixed section.
- **Open**: metadata attachments on global variables other than `!dbg`
  (`!type`, `!absolute_symbol`, `!associated`, ...) are not addressed by
  §7 or by this work package; `!associated` and `!absolute_symbol`
  change the object and need a field or an "unsupported" name.
