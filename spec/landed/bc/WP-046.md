# WP-046 — hod_bc stage 2: function bodies

Landed: `spec/bc.md` §11, with §1, §7 and §10 brought up to date. The
FUNCTION blocks are read into `hod_ir` bodies with the decisions
`hod_ll`'s body parser makes for the same module as text. The module
metadata slot table is exposed (§7).

Not here:

- debug information: `!dbg` locations, debug records and the debug
  intrinsics are skipped, as for a module without `-g` (§6, §11.6);
  `hod_ll`'s `ParsedBody::debug` has no counterpart yet;
- bitcode older than LLVM 19's format (§11.8).

## What it did

| module | contents |
|---|---|
| `body` | `BodyReader`, `ReadBody`, `read_bodies`; the walk of a FUNCTION block, value numbering, forward references, blocks, operand bundles, definition attachments, call-site attribute groups (§11.1, §11.2, §11.6, §11.7) |
| `inst` | every instruction record, ported from `hod_ll`'s checks and decisions, and calls with their attributes, intrinsic checks and inline asm (§11.3 to §11.5) |
| `consts` | the function CONSTANTS layer over the module constants; `Values` is `Clone`, one copy per reader |
| `types` | the notes a function type's parameters carry (`param_notes`) |
| `module` | `FunctionBits::type_id`, `ModuleBits::metadata_count`/`metadata` and `Metadata` |
| `codes` | `func`: the FUNCTION block's record codes |

Tests: `tests/bodies.rs` (5 tests), `tests/data/bodies.ll`, a second
robustness file `tests/data/bodies-llvm19.bc`, and the `bc-bodies` /
`ll-bodies` modes of `examples/bcread.rs`.

## Evidence

**The differential** (§11.9) over the full corpus (5,760 modules):
bitcode from each major's `llvm-as`, `hod_bc`'s bodies compared with
`hod_ll`'s bodies of `llvm-dis` of the same bitcode, each instruction
written out, then the module dump of §9.2. 2 min 49 s, 8 workers.

| LLVM | modules | agree | both refuse | differ | tool failures | bodies delivered | functions unsupported |
|---|---|---|---|---|---|---|---|
| 19 | 2864 | 2864 | 0 | 0 | 0 | 24005 | 4 |
| 22 | 2896 | 2896 | 0 | 0 | 0 | 24226 | 4 |

The classes of difference found and fixed on the way, all on the
handwritten module:

- the test dump printed `switch` case constants as raw `ConstId`s, which
  depend on the order constants are built; the dump now writes them
  out (`tests/common/mod.rs`; see the `hod_ir` gap below).

**The handwritten bodies** (`tests/data/bodies.ll`) agree on LLVM 19 and
22. It holds every record of §11.3 except CALLBR, and the unsupported
names it expects: `alloca:inalloca`, `alloca:swifterror`, the five
funclet instructions, `syncscope:agent`, `call:forwarded-varargs`, and a
definition's `global-metadata:custom` (with `!prof` dropped).

**Robustness** (§9.4, release), over `module-llvm19.bc` (3,360 bytes)
and `bodies-llvm19.bc` (5,436 bytes), each read as the module and then
every body:

| check | reads | slowest read | peak memory growth |
|---|---|---|---|
| every truncation (all errors) | 8,796 | 0.10 ms | 1.2 MB |
| every single-byte corruption, eight values per position | 68,721 | 1.6 ms | 1.4 MB |
| random inputs | 2,000 | 0.04 ms | 1.1 MB |

No read panicked.

**Cost** (§11.10). Release build, best of 20 reads (5 for the large
module) of the module and every body. Peak memory is `/usr/bin/time %M`
of one process, input included. `llvm-dis` is the best of 5 wall times
to `/dev/null`.

| module | instructions | `hod_bc` on bitcode | `hod_ll` on `llvm-dis` text | `llvm-dis` |
|---|---|---|---|---|
| cleanup-scopes-30k, LLVM 19 (3.6 MiB bc, 24 MiB text) | 330,079 | 72.2 ms, 219 ns/inst, 49.6 MiB | 147.5 ms, 447 ns/inst, 66.7 MiB | 402 ms, 130 MiB |
| cleanup-scopes-30k, LLVM 22 | 330,079 | 72.6 ms, 220 ns/inst, 45.3 MiB | 146.7 ms, 445 ns/inst, 66.6 MiB | 344 ms, 134 MiB |
| p19-placement-arg (kiln conformance), LLVM 19 | 151 | 0.068 ms, 451 ns/inst, 2.1 MiB | 0.075 ms, 498 ns/inst | 11.9 ms, 51 MiB |
| `bodies.ll`, LLVM 19 | 135 | 0.070 ms, 521 ns/inst | 0.070 ms, 516 ns/inst | |

Time per instruction on the 330k-instruction module is half that of a
small module (where the module level dominates): no worse than linear.
Against the `llvm-dis` round trip the large module goes from 550 ms
(`llvm-dis` + `hod_ll`) to 72 ms.

## Unverified

Records and fields neither the corpus nor a handwritten test exercises:

- CALLBR is in 6 corpus modules (they agree) but not in the handwritten
  module;
- debug records other than `#dbg_declare` (62–66): skipped by code
  range, exercised only through `#dbg_declare` in the corpus;
- the CMP2 flags operand (`samesign`, LLVM 20+), the optional alignment
  of CMPXCHG and ATOMICRMW, and ALLOCA's explicit address-space field;
- scalable vector allocas (`alloca:scalable`) and GEPs over scalable
  types;
- metadata-typed operand-bundle inputs (`bundle:metadata-input`): LLVM
  writes them with metadata ids, without a type, so they are detected
  only when forward; such an input read as a value is an approximation;
- the refused old-format records of §11.8 (no LLVM 19 or 22 writes
  them).

## For WP-048 (hod_cli without llvm-dis)

- `hod::compile` (`crates/hod/src/lib.rs:321`) declines bitcode as
  `bitcode-input`; it would call `hod_bc::read_module` and
  `hod_bc::read_bodies` instead of `hod_ll::parse_module` and
  `parse_bodies`. `ReadBody` is shaped as `ParsedBody`, without `debug`.
- `hod::effective_triple` reads the triple from text; for bitcode it
  needs the module's target from `read_module`.
- A module with debug information still needs `llvm-dis` (or a debug
  stage in `hod_bc`) until bodies carry `BodyDebug`.
- `BcError` maps to the driver's failure reasons as `LlError` does:
  `Unsupported(name)` is a construct, the rest malformed input.

## Gaps in hod_ir and hod_ll

- `hod_ir::Switch`'s `Debug` prints case values as raw constant ids
  (`crates/hod_ir/src/body.rs:1479`), so a dump of a body is not
  comparable across readers without writing them out.
- `hod_ll::ParsedBody::debug` (`crates/hod_ll/src/body.rs:313`) has no
  reader-neutral type a bitcode debug stage could fill.
