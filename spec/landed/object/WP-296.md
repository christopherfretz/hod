# WP-296 — smaller objects

Three ways hod's `-g` objects were larger than `llc`'s, each now written
as `llc` writes it. The rules are in `spec/object.md` "String table" and
`spec/dwarf.md` (`.debug_addr`; §1.3, §3, §4.5, §5.6 for the line
table). None of the three is byte-neutral: they change object bytes on
purpose, and only in the sections they name.

## What landed

1. **One string table** (`e0c1f4d1`, `hod_obj`). Section names and symbol
   names share `.strtab`, at section index 1, which is also
   `e_shstrndx`, as `llc` 19 and 22 write it on aarch64, x86_64 and i386.
   There is no `.shstrtab` any more. The table is written in one pass,
   without sorting or tail merging, and string IDs are ordinals. Size on
   stl-heavy `-g` (aarch64): 502,061 bytes, against 502,050 for LLVM's
   tail-merged table. The byte order differs from `llc`'s.
2. **Shared `.debug_addr` entries** (`6872175e`, `hod_dwarf`). There is one
   entry per distinct (symbol, addend, TLS) key, in DIE order, with the
   unit's spans pooled last, as `llc`'s `AddressPool` does. stl-heavy `-g`
   x86_64 has 4,109 entries, down from 7,398; `llc` 22 writes 4,111.
   - A non-split unit with one span writes its `DW_AT_low_pc` ULEB before
     its index is known. The ULEB is reserved at the widest index the
     unit can have and patched afterwards, padded with `0x80` bytes when
     the index is shorter. `llc` writes the minimal length.
   - Writing the spans first was rejected: it moves the split TLS indices
     away from `llc`'s
     (`hod/tests/debug_real_projects.rs`
     `split_thread_local_variables_are_written_as_llc_writes_them`).
3. **One line sequence per run of functions** (`hod_dwarf` `LineProgram`
   `push_open`/`close`; `hod_cg` `emit/lines.rs`). A function's rows
   continue the sequence of the function placed just before it when that
   function is of the same unit and the same section and the new
   function starts at or after its end. The last row covers the padding
   between them. A sequence ends, at the end of its last function's
   code, when the next function placed:
   - is in another section;
   - is of another unit;
   - has no subprogram of a written unit or no code;
   - has no rows;
   - or when the module ends.

   The first three are `llc`'s rules (`DwarfCompileUnit::addRange` and
   `DwarfDebug::skippedNonDebugFunction` terminate the line table). The
   fourth is hod's own: such code is not covered by a row.

## Measured from llc before deciding (step 3)

- A C file with `.text` functions `f1`, `f3`, `f4` and `main`, a function
  `f2` with `section ".text.mine"` between `f1` and `f3`, and a
  `nodebug` function between `f3` and `f4`, built with clang-22 `-g`. Its
  `llvm-dwarfdump --debug-line` from `llc` 22 (x86_64 and aarch64, the
  latter with `-global-isel=0 -fast-isel=0`) and `llc` 19 (x86_64) shows
  four sequences: `f1` (ending at `f1`'s end, 0xf, not at the padded
  0x10); `f2`; `f3` (ending at its end, where the nodebug function
  starts); and `f4`+`main`. In the last one, `f4`'s last row at 0x7c
  covers the padding to `main` at 0x80. The unit's `DW_AT_ranges` are
  the same four runs.
- hod's object after the change has the same four sequences, with the
  same ends, and verifies clean with dwarfdump 19 and 22.
- The number of sequences in hod's object now equals `llc` 22's on all
  16 bench `-g` inputs (table below). Before, tiny-functions had 5,001
  against 1, and stl-heavy 3,307 against 3,276.

85 KB of `.debug_line` and 5,000 address relocations. On the inputs whose
functions are almost all COMDAT members (templates), it changes nothing.

Instructions (callgrind, whole process): step 3 against step 2 is within
±0.25% on every input (−1.05M on tiny-functions aarch64, +2.07M on
templates x86_64). Peak RSS is within ±1.7 MB, in both directions.
