# WP-237 — a variable-length array in an `alwaysinline` body

Landed: the `alwaysinline:stacksave-escapes` rule accepts the `-O0`
variable-length array (`stacksave_escapes` and `keeps_saves_only` in
`crates/hod/src/session/inlining.rs`; `spec/cli.md` "Always-inline", the
list of constructs that are not inlining-sensitive and the refusal
table's row). Tests: `crates/hod/tests/alwaysinline_vla.rs` (executed,
both targets, data `crates/hod/tests/data/alwaysinline_vla/`) and
`a_saved_stack_slot_is_not_an_escape`,
`a_saved_stack_that_escapes_is_declined` in
`crates/hod/tests/inlining.rs`.

## What was wrong

Building DuckDB at `-O0` with kiln and strict hod declined one object of
1,901: jemalloc's `src/tcache.c`, `alwaysinline:stacksave-escapes` in
`tcache_bin_flush_impl_small`. A C front end writes a variable-length
array at `-O0` as

    %s = call ptr @llvm.stacksave.p0()
    store ptr %s, ptr %saved_stack     ; an alloca of the entry block
    %a = alloca %T, i64 %n
    ...
    %r = load ptr, ptr %saved_stack
    call void @llvm.stackrestore.p0(ptr %r)

and the rule read the store as an escape.

## The rule

A `llvm.stacksave` result does not escape when every use is
`llvm.stackrestore`, or a store into a slot (`ValueKind::Slot`, an
`alloca` of the entry block) that keeps saves only: every instruction
that names the slot is a store into it of a `llvm.stacksave` result, a
load from it whose result only `llvm.stackrestore` uses, or
`llvm.lifetime.start`/`.end`. Still declined: the saved pointer, or a
pointer loaded from the slot, returned, passed to a call or stored
anywhere else; the slot's address returned, passed or stored; another
value stored into the slot; a slot that is a dynamic `alloca`.

Why it is safe: the saved pointer never leaves one activation of the
body. hod compiles the body out of line, where the pair restores the
body's own stack pointer before it returns; the caller's stack pointer
is as it was and the array lives until the restore.

## What LLVM does (`opt -passes=always-inline`, 19 and 22 alike)

The body's own pair is kept: inlined, it saves and restores the
caller's stack pointer around the array. Around every inlined body that
has a dynamic `alloca` the inliner puts a pair of its own
(`%savedstack = call ptr @llvm.stacksave.p0()` before, the restore at
the inlined return), so nested bodies nest the pairs, and a body
inlined in a loop does not grow the stack. Either way the stack pointer
after the body is the one before it.

## Evidence

- `alwaysinline_vla.rs`: clang 22's pre-opt modules for each target
  (`-O0 -Xclang -disable-llvm-passes`; the C is not kept, the `.ll` is
  the test data): arrays of 1-, 4-, 8- and 24-byte elements and of a
  64-byte-aligned element, two arrays in one body, a body inlined twice
  into one caller, one in a loop of 100,000 iterations (its address must
  not move: 8,000 bytes a turn would be 800 MB), an early return out of
  the array's scope (clang writes it through its cleanup block, which
  restores), an array in a loop's scope, nested bodies each with an
  array, a caller with its own array, and the shape of
  `tcache_bin_flush_impl_small` called from another always-inline body.
  The driver passes 0, 1, 2, 17, 1,000 and 100,000 elements. hod plain,
  hod with every function under `Stress::ALL`, and `opt
  -passes=always-inline` + `llc -O0` 19 and 22, each linked by bfd, lld
  and mold: 12 runs a target, every output the same; the loop's array
  never moves, the aligned array is aligned, a probe frame's address
  after the calls is the one before.
- The saved module (`tcache.c`, 7,000 lines) builds with `hod --strict
  -O0 -relocation-model=pic`. Against `opt -passes=always-inline` +
  `llc-22 -O0`: the same 44 global definitions and 64 undefined
  symbols; hod has 108 more local function symbols, the out-of-line
  bodies the inliner deletes (WP-021). The functions are about 5,000
  lines between them, so the regression is the hand-written module of
  the same shape in `inlining.rs` and the C-derived shape above.
