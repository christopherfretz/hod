# WP-327 — i386: coroutines (handle operations, bodies, symmetric transfer)

Landed: `crates/hod_x86/src/coro.rs` (handle operations, stage A).
Bodies (stages B to D) are **parked**: the `esi` design below does not
work with the i386 pool as it is (see "Stage B"). Behaviour:
`spec/codegen.md` §7.6 (target-independent) and `spec/codegen-x86.md`
§18 (this target; §15 before the merge onto debug information, SSE and vectors). Base: `f492182b` (branch `wave/44`).

## The six design questions (answered before the code)

Measured with clang++ 22 `--target=i686-linux-gnu -O0 -Xclang
-disable-llvm-passes`, then `opt -passes='default<O0>'` and `llc -O0
-mtriple=i686-unknown-linux-gnu` (19 and 22 alike).

1. **The frame base register is `esi`.** `ebx` is the GOT pointer of
   every PLT call under PIC (`pic::emit_call`, `pic::got_pointer`), of
   `cmpxchg8b` (`atomic.rs`) and of `___tls_get_addr` (`tls.rs`): it
   cannot be the base. `edi` is borrowed by `memset` and the aggregate
   zeroing (`bytes::set`, `agg.rs` `rep stos`). `esi` is written in this
   back end only by `memcpy`/`memmove` (`bytes::copy`), which pushes it
   first and pops it last; between the push and the first `pop esi` the
   only frame access is the length (`Len::Slot`, `esi` still intact),
   and between the two pops none. Every call preserves it (callee-saved
   in cdecl, fastcc and every hod function, whose prologue saves `ebx`,
   `esi`, `edi`); an unwinder restores it from the CFI rows at a landing
   pad (the stubs state the prologue's rows). `int.rs`, `mem.rs`,
   `atomic.rs`, `dynstack.rs`, `va.rs`, `eh.rs`, `x87.rs`, `tls.rs` and
   `pic.rs` never name it. A coroutine takes `esi` out of the pool and
   the holdable set (`X86::coro`, `REG_INFO_CORO`). **This is not all
   that reserving it costs, as the code showed (stage B):** the pool is
   then `ebx`, `edi`, and i386 lowerings pin three. The
   one construct that could write it is inline assembly (an `S` operand,
   an `esi` clobber): in a function with the coroutine frame such an
   `asm` is refused, `x86:coro:asm-base` (no reload: a memory operand of
   the `asm` may itself be formed on `esi`).
2. **Where values live.** `hod_xform::coro::plan` decides residency (the
   promise, `heap_slots`, `heap_values`: what lives across a suspend);
   `hod_cg::coro_body::setup` lays out the heap frame and presets every
   heap value's home to `FrameRef::Coro(offset)`; a 64-bit integer is a
   `Mem` value of 8 bytes there (its two halves at `o` and `o + 4`), a
   `float`/`double` a `Mem` value of its size. `hod_x86` forms every frame
   operand in ONE place, `common::frame_mem` (all loads, stores, copies
   and addresses go through `frame_inst`), so `FrameRef::Coro(o)` is
   `[esi + o]` there and `frame_inst` reports the access
   (`coro_body::access`). Every suspend point is an x87 barrier: the
   80-bit copy of a value is in a machine-stack slot, which a resumed
   activation does not have, and `llc` lowers each of
   `coro.suspend`, the `await.suspend` wrappers, `coro.resume` and
   `coro.destroy` with a call or a function boundary (the split clones
   enter at the block after the suspend).
3. **Conventions.** `F.resume`/`F.destroy` are `fastcc void(ptr)`
   (LLVM's split clones; measured: the clone reads its frame from `ecx`
   and a tail transfer is `movl (%ecx), %eax` · teardown · `jmpl
   *%eax`): on i386 `fastcc` puts the frame pointer in **`ecx`**, not on
   the stack, the caller pops nothing, and the stub returns with `ret`.
   The ramp keeps the coroutine's own signature: `sret` (the usual
   C++ return object on i386: `ret $4`), `byval`, fastcc, regparm all
   come from `abi::assign` as for any function. A resumed activation
   shares the ramp's epilogue but was entered by a stub: where the ramp
   pops (`abi::callee_pop` > 0) the epilogue tests the mode word and
   returns with a plain `ret` in a resumed activation. Symmetric
   transfer: after the wrapper returns `h` in `eax`: `mov edx, [eax]` ·
   `mov ecx, eax` · `cmp dword [ebp + mode], 0` · `jne exit` · `call
   edx` (the ramp); `exit` (a `FnCx::coro_tail_exit`, `frame::end`'s
   tail-exit loop) tears the frame down and `jmp edx` with `h` in `ecx`.
   No stack argument is rewritten: the brief's guess of a cdecl stack
   argument does not hold.
4. **Allocation.** `llvm.coro.size.i32` is the layout's size;
   `coro.align` the layout's alignment (`max(frame_align, 16)`);
   `coro.alloc` 1 (no elision); `coro.free` is `esi`; `coro.id`'s
   alignment operand is not read. clang (19, 22) allocates the frame with
   `operator new(size)` unless `-fcoro-aligned-allocation`
   (`__STDCPP_DEFAULT_NEW_ALIGNMENT__` is 8 on i686, glibc's `malloc`
   returns 16-aligned blocks); a frame aligned above 16 without
   `coro.align` is the plan's `coro:overaligned-frame` on every target.
   The header is two pointers: resume at 0, destroy at **4**, and the
   promise at `alignTo(8, align)` (LLVM's `{ptr, ptr, i8}` field 2;
   measured: `coroutine_handle::promise()` is `frame + 8` for a promise
   aligned to 4). The plan's header size follows the pointer size of the
   data layout (`hod_xform`; 16 on the 64-bit targets: byte-neutral).
5. **Exceptions.** An `invoke` in a body is `hod_cg`'s call sequence
   (WP-314's tables): its landing pad runs in the activation that made
   the call, `esi` restored by the unwinder from the stub's or the
   prologue's rows (both state `esi` at CFA − 16). `coro.end` in an
   unwind path marks a resumed activation done (resume word 0, the final
   index) exactly as on x86-64. The landing pad's `eax`/`edx` are not the
   base.
6. **Models and CPUs.** No relocation names a stub: `coro.begin` takes
   the stubs' addresses with `call .+0` · `pop ecx` and a label fixup
   (position independent in every model, no text relocation); the noop
   frame is `R_386_32` (static) or `@GOTOFF` from the GOT pointer (PIC,
   PIE), as `llc` writes it; every call goes through `pic::emit_call`.
   Nothing here depends on `cmov` or SSE. GNU ld, lld and mold link it.

## Stages

### A. Handle operations: done

`coro.resume`, `destroy`, `done`, `promise` and `noop` are lowered in any
function (`coro.rs`, `spec/codegen-x86.md` §18). The noop frame is two
words of the target's address size (`hod_cg/src/emit/noop.rs`: 8 bytes on
i386, still 16 on the 64-bit targets). `coro.resume` and `coro.destroy`
are x87 barriers (`x87.rs` `barrier`).

- `crates/hod/tests/i386_coro.rs`, `handle_operations_run_as_llc_s`:
  `coro/handles.ll` gives 72 runs equal to the `opt` + `llc` oracle.
  That is LLVM 19 and 22; the default CPU (no SSE) and `-mcpu=i686`;
  static and PIE; GNU ld, lld and mold; and the facade, `Stress::ALL`
  and llc objects.
- `what_is_refused`: `x86:coro-promise` for a variable alignment, a
  handle-only module compiles, and a body is `coro:target`.
- **The barrier, measured.** llc 19 and 22 spill a `double` live across
  `coro.resume` or `coro.destroy` as 8 bytes. With the barrier arm off,
  the run test fails. `handles-22-default-exe` (bfd) prints
  `double 0x0p+0` where llc prints `double -0x1p-54`.
- **irdiff i686, full tier, stage A alone.**

  | LLVM | PASS | FAIL | UNSUPPORTED | ERROR | SKIP |
  |---|---|---|---|---|---|
  | 22 | 126 | 0 | 78 | 0 | 44 |
  | 19 | 126 | 0 | 75 | 0 | 45 |

  The base was 123 PASS, 81 UNSUPPORTED (22) and 78 UNSUPPORTED (19).
  The `coro/noop` seed now passes.
- **Declines (LLVM 22).** `x86:intrinsic` went from 4 to 3, and
  `coro:target` stays at 5. The others are unchanged:
  - `attr:alignstack` 1;
  - `x86:abi:wide-arg` 2;
  - `x86:atomic:op` 1;
  - `x86:cf-protection` 3;
  - `x86:constant` 1;
  - `x86:float:cast` 2;
  - `x86:float:fp128` 1;
  - `x86:indirect-branch` 1;
  - `x86:inline-asm:goto` 1;
  - `x86:stack-protector` 2;
  - `x86:vector` 3.

- **compare-binaries** (the base release against stage A's head, over
  `tests/ir` and the two kiln corpora). AArch64: 3487 × 2 compared, 0
  different, 0 changed outcome. x86-64: 3456 × 2 compared, 0 different,
  0 changed outcome. i686: 111 × 2 compared, 0 different, 4 changed
  outcomes. Each of the 4 goes from an error to compiling:
  `coro/handles.ll` and `coro/noop.ll`, plain and PIC. The base refused
  them as `x86:intrinsic`.

### B. Bodies: parked

The code was written: `coro_body.rs`, with stubs, dispatch, `coro.begin`
without relocations, suspend, end, symmetric transfer, `esi` as the base
and the frame operand formed in `common::frame_mem`. irdiff i686 then
gave 141 PASS, 0 FAIL, 0 ERROR on both LLVM 22 and 19 (base: 123 PASS).
The seeds `noop`, `alloc-fail`, `promise-aligned`,
`resume-inside-await-suspend`, `resume-inside-handle` and `ssa-across`
passed; `coro:target` had gone and `x86:intrinsic` had dropped from 4
to 3.

**Why it is not landed (measured).** Reserving `esi` leaves a
coroutine's pool with two general registers. Several i386 lowerings pin
three:

- `alu::icmp` pins `def_reg` plus both operands of `compare`.
- Some lowerings of `atomicrmw`, `cmpxchg` and `call` do too.

So `RegInfo::check` rejects the coroutine's pool against
`MIN_POOL_GPR_32` = 3. Lowering the minimum to 2 makes real bodies fail.
clang 22's `gen.cpp` (an `int` generator) fails in `_Z4intsi`: "no
register is free: more are pinned than the pool has (at %39 = icmp)".

With `MIN_POOL_GPR_32` = 2, the i386 test suite under the `min_pool`
stress mode fails 16 test binaries (5 pass). The failing
instructions are: icmp 21, atomicrmw 4, call 3, cmpxchg 1. The irdiff
seeds passed only because their bodies are small.

**The decision needed.** One of these:

1. Make every i386 lowering pin at most two general registers, then
   lower `MIN_POOL_GPR_32` to 2. The failure list above is where to
   start. The work is outside this package's modules and touches files
   other implementers own.
2. Base the heap frame on another register:
   - `ebp`, with the coroutine's machine locals addressed from `esp`.
     A coroutine has no dynamic stack (`coro:dynamic-alloca`), but
     every `esp` adjustment inside a lowering would need its offsets
     corrected.
   - Or no reserved register: reload the frame word into a register
     the access may use. The scratch registers carry data through
     `frame_inst` in many lowerings, so this needs a register the
     allocator gives.

The stage B code is kept outside the repository, under
`.build/target-wp-327/stage-b/` (`coro_body.rs`, `tracked.patch` with
every hook).
