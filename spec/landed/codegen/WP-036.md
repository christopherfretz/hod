# WP-036 — the AArch64 memory group

Landed: `crates/hod_a64/src/mem.rs`, `spec/codegen.md` §5.5.1 "Memory
(WP-036)", the support-matrix rows of what is implemented and tested.

## What it does

- `load` and `store` of every `Gpr`-class value: `i1` to `i64` of every
  width, and `ptr`; plain and volatile (the same code, never dropped or
  repeated). Exactly the store size is read or written, odd sizes (3, 5,
  6, 7 bytes) in two or three accesses; a stored width that is not a
  multiple of 8 is masked first, so padding bits are zero; a load
  zero-extends.
- Addresses through a pointer register, a stack slot (direct, far, or
  over-aligned through its indirect place), a symbol with an offset
  (folded into the addend below 2^20, honouring the relocation model and
  the GOT; other code models are `a64:code-model`), or a constant
  address.
- `ptradd`: constant offsets and constant indices folded, variable
  indices of any width up to 64 sign-extended (`sxtw` kept in the
  addressing mode for an `i32`), scaled by shift or multiply; deferred
  and fused into the next access's addressing mode when it is the only
  use (§4.6), computed into a register otherwise.
- `alloca` with a constant or variable count of any width, zero-sized,
  over-aligned (up to 2^32); `llvm.stacksave` and `llvm.stackrestore`.
  Both `alloca` and `stackrestore` mark the frame dynamic.

## Refused

- `a64:load-fpr`, `a64:store-fpr`: a `load` or `store` of an `Fpr`
  value (WP-039).
- `a64:ptradd-vector`: a `ptradd` producing a vector of pointers.
- `a64:atomic` (`target::ATOMIC`): an atomic `load` or `store`.
- `limit:frame-size`: an `alloca` alignment that is not a power of two or
  is above 2^32; fixed slots beyond `MAX_A64_FRAME` (as before).
- `Mem`-class values (wide integers, aggregates) are `aggr`'s (WP-040).

## Evidence (`crates/hod_a64/tests/mem.rs`)

- A local generator (`tests/common/mem_gen.rs`) of straight-line
  functions over a 256-byte buffer, stack slots (sizes 0 to 70000,
  alignment up to 64), globals and dynamic allocas: stores and loads of
  every width of {1, 7, 8, 9, 15, 16, 17, 24, 31, 32, 33, 40, 47, 48, 55,
  56, 63, 64} and `ptr`, through every address form (plain, constant
  global GEPs, one or two variable indices of widths {1, 7, 8, 16, 17,
  32, 33, 63, 64}, chains), with barriers that force the unfused path;
  every load is observed. 1200 functions (about 5300 loads, 13600
  stores, 18300 `ptradd`s, 2700 volatile accesses) are compared with
  `hod_interp` in four modes: hod plain, hod under `Stress::ALL`, hod
  PIC, and `llc -O0 -global-isel=0 -fast-isel=0`. The C driver places
  the buffer at the end of a page followed by a `PROT_NONE` page and
  passes garbage above every argument's width. `HOD_MEM_SEEDS` runs more
  (`many_generated_functions_agree`, ignored).
- `the_stack_forms_hold_natively`: `stacksave`/`stackrestore`, dynamic
  allocas with an `i17` count and alignments 64 and 4096, zero-sized,
  constant-count and 17 MB allocas, slots aligned to 128, a `[0 x i8]`
  slot and a 70000-byte slot; hod plain and stressed and `llc`, linked by
  every linker.
- Exact words for the fused forms and their unfused counterpart, an
  `i17` store's exact sequence, one emission of a dead volatile load,
  and the refusal names.

## Mutations (each caught by the tests above, then reverted)

1. No mask on an odd-width store.
2. `uxtw` instead of `sxtw` for an `i32` index.
3. A 3-byte access done as one `w` access.
4. A variable `alloca` count not zero-extended.
5. The constant offset dropped when an index register is present.
6. A narrow index not sign-extended.

## Stack usage

hod gives each value that lives across an instruction an 8-byte home,
slots their size, plus the 16-byte frame record, rounded to 16: a
function with a 16-byte slot and two loaded values takes 48 bytes where
`llc -O0` takes 16, a leaf with two loaded values 32 where `llc` takes
none.
