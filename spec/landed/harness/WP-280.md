# WP-280 — the dlopen TLS driver keeps its five threads alive together

A defect of a test's C driver, found by the hosted `ci.yml` run of the
version-bump commit `658a0130` and fixed before the tag. No change to
hod's code: one file, `crates/hod_x64/tests/data/tls/dl_driver.c`.

## The finding

Run 43816507280 of `658a0130` (2026-11-16): the job `arm / test x64`
failed in both attempts, each time in `descriptors_through_dlopen`
(`crates/hod_x64/tests/tls.rs`, WP-213), each time at the driver's last
check, "every thread's copies at addresses of their own", for all five
variables of one pair of threads, with every per-thread check passing
(the addresses hod's code forms equal `dlsym`'s in every thread, and
every thread sees fresh values). Attempt 1: case
`1048576-hod-llc19desc-lld`; attempt 2: case `1048576-hod-hoddesc-mold`.
The other 17 jobs were green. The test had passed in every hosted run
since it was added (2026-11-14), the run of the candidate `cd6ef6bc`
among them, and passes on the development host (the full gate of
`658a0130`; then 4 runs alone on one core, and 8 runs of the whole `tls`
test binary on four cores with the reporting driver below: no failure). Same runner image
(`ubuntu-24.04-arm` 20261111.182.1), same container image digest, same
qemu (10.0.13), same core count in the passing and the failing runs.

## The cause

The check holds only while the five threads are alive at once, and the
driver did not make them be. It created four threads, ran the same
function on the main thread, and joined the four in order. With a
1 MiB thread-local block the loader allocates each thread's copy at the
thread's first access and frees it when the thread is joined. A thread
that first touches its copy after an earlier thread has been joined is
given the freed block at the same address.

A probe on the hosted runner (workflow run 43823642911 of a branch that
is not merged; `Linux 7.0.0-1017-azure`, Neoverse-N2, 4 cores, qemu
10.0.13) measured:

- With no hod: a library of three thread-locals (one of 1 MiB) compiled
  by `x86_64-linux-gnu-gcc`, loaded by `dlopen`, a driver of the same
  shape, run under `qemu-x86_64`. 300 runs alone and 8 loops of 150 at
  once, per dialect: two threads recorded the same addresses in 13 of
  1500 runs with `-mtls-dialect=gnu` and in 24 of 1500 with
  `-mtls-dialect=gnu2`. In every failing run printed (the first 5 of each; 4
  of each with their events) the pair is the first thread created and
  the last, and the last thread's work ends after the first has been
  joined.
- The test with a driver that reports the pair and the order of events
  (each thread's first access and end, each join): of 5 runs of the
  whole `tls` test binary, 1 failed, threads 1 and 4, with thread 1
  joined (event 9) before thread 4's first access (event 11). 10 runs
  of the test alone: no failure.
- The test with the fix below: 8 runs of the whole test binary, no
  failure (and 3 runs alone on the development host).

On the development host the no-hod reproduction of the same shape does
not reuse an address (60 runs per dialect, and with the last thread
delayed by 300 ms); a reproduction that joins each thread before it
creates the next reuses the address every time, natively and under
`qemu-x86_64`.

## The fix

The five threads meet at a `pthread_barrier` of five after they have
recorded their addresses, so all five are alive when the addresses are
taken; a `pthread_create` that fails ends the driver instead of leaving
the others at the barrier. The other threaded TLS drivers
(`crates/hod_x64/tests/data/tls/driver.c`, `crates/hod_a64/tests/data/
tls/driver.c`, `tests/ir/tls.ll`, `tests/ir/tls_desc.ll`,
`tests/debug/tls.c`, `crates/hod/tests/tls_cxx.rs`,
`crates/hod_obj/tests/link_tls.rs`) compare a thread's addresses with
the main thread's, which is alive throughout, and are unchanged.
