# WP-354: i386, the outgoing argument area reserved in the prologue

Spec: `spec/codegen-x86.md` §3 ("The outgoing argument area"). Module:
`crates/hod_x86/src/frame.rs` (`reserves_calls`, `prologue_size`,
`call_area`), `target.rs` (`Target::adjust_sp` goes through
`call_area`), `coro_body.rs` (the resume / destroy stubs' prologue uses
`prologue_size`). Tests: `crates/hod/tests/i386_outgoing.rs`, program
`crates/hod/tests/data/i386/outgoing/calls.c`. Why:
`spec/landed/harness/WP-352.md` (key_call.c under lldb: hod's return
address was the release of the call's area, `lea 0x10(%esp), %esp`).

## Stage 1: what `llc` does, what hod did

`llc-22 -O0 -global-isel=0 -fast-isel=0 -mtriple=i686-unknown-linux-gnu`
(and `-relocation-model=pic` with `"frame-pointer"="all"`); hod = base
`422cfcb3`'s CLI on the same module.

| case | `llc` | hod at base |
|---|---|---|
| plain calls, 8 and 20 bytes of arguments | `sub $28, %esp` once; `mov` to `N(%eax)` with `eax = esp`; nothing after the `call`; `add $28` in the epilogue | `lea -0x10(%esp)` / `lea -0x20(%esp)` before each call, `lea +area` after |
| `sret` call (the callee pops 4) | `subl $4, %esp` right after the call (re-reservation), no release | `lea -4(%esp)` then `lea +0x10(%esp)` |
| variadic call (`printf`) | reserved, as a plain call | around the call |
| `byval` (20 bytes) | reserved (`sub $44`), copied with `mov`s to the area | around the call (`lea -0x20`) |
| dynamic `alloca` | NOT reserved (`hasVarSizedObjects`): `sub $16` before the first call, merged with the next | around each call |
| over-aligned local (`align 64`) | reserved; the frame realigned (`and $-64, %esp`) | `hod_cg`'s `dynamic_slot` area in the entry code, then around each call |
| `stdcall` / `fastcall` / `thiscall` | reserved; `subl $N` after each call | refused (`cc:x86_stdcallcc`, ...): not reached |
| `musttail` | `jmp f2@PLT`, no area | staged in the local area, no area (unchanged) |
| stack protector (`sspreq`) | reserved; the guard above the area (`24(%esp)`) | around each call |
| `llvm.stacksave` / `stackrestore` alone | reserved (no variable-sized object) | around the call |
| `invoke` under PIC | reserved; the pad is entered directly; `ebx` reloaded from a spill slot after each call | around the call; the pad entered through a stub `lea +area` · `jmp pad` |
| `inalloca` / `preallocated` | not measured | refused before WP-354 (`abi.rs`); not reached |

Where hod made it: `hod_cg`'s call sequence (`crates/hod_cg/src/call.rs`
`run_call`: `t.adjust_sp(-area)` before the stores to
`FrameRef::Outgoing(n)`, `t.adjust_sp(+area)` after the call and in an
`invoke`'s pad stub); `Target::adjust_sp` was `frame::adjust_sp` (`lea
esp, [esp + delta]`); the callee pop's `lea -p` in `target.rs`
`emit_call`; the prologue's `sub esp, imm32` patched in `frame::end`;
the stores `[esp + n]` in `common.rs` (`FrameRef::Outgoing`). CFI: the
CFA is `ebp`-based from the prologue on, so no row follows `esp`; no
`DW_CFA_GNU_args_size` is written by hod or by `llc` here.

## Design

- `frame::begin` decides `reserves_calls` from the body before the
  prologue: no `alloca` instruction is left in the body (static entry
  allocas are slots) and no slot is aligned above 16. Those two are what
  move `esp` below the prologue's in hod (`dynstack`); they keep the old
  path exactly.
- `Target::adjust_sp` is called by `hod_cg`'s call sequence only. In a
  reserving function `frame::call_area` records the largest area
  (rounded to 16) and emits nothing; the release and the pad stub's
  adjustment are no-ops.
- `frame::end` patches `FRAME + OUT` into the prologue's immediate.
  `OUT ≡ 0 (mod 16)` and lies below the local area, so `Local(o)`'s bias
  (`-(12 + FRAME)`), the frame description, the ssp guard's slots, the
  coroutine words (`esi` is unrelated: the heap frame) and the CFI are
  unchanged. The coroutine stubs' copy of the prologue uses the same
  `prologue_size`.
- A callee that pops (an `sret` hidden pointer) is followed by
  `lea -p(%esp), %esp`, as before, which is `llc`'s re-reservation.
- Kept on the old path besides: the hand-written runtime calls of `x87`,
  `sse`, `fpclass`, `tls` (their own `lea` around the call: correct, a
  follow-up for `llc`'s shape); `invoke`'s pad stub is now `jmp pad`
  alone (`hod_cg` decides the stub from the area; harmless, a `hod_cg`
  follow-up).

## Evidence

- `i386_outgoing.rs`: `programs_with_calls_run_as_llc_s`, 72 runs
  (`calls.c` and the `.ll` program, static and PIE, GNU ld / lld / mold,
  `llc` 19 and 22, plain and stressed objects) print and exit as `llc`'s;
  `calls.c` checks at run time that `esp` is 16-aligned in callees (deep
  recursion of 20000, calls in a loop of 1000 with `esp` compared to the
  first iteration's, after `alloca` / VLA, under an over-aligned local).
  `the_area_is_reserved_in_the_prologue`: the prologue's `sub $0x2c`
  (12 + 32), the instruction after each call (not an `esp` move; `lea
  -4(%esp)` after an `sret` callee; `lea 0x10(%esp)` with a dynamic
  `alloca`).
- Every `i386*` test binary of `-p hod` (35) and `-p hod_x86`: pass.
- `cargo xtask irdiff --target i686 --llvm 22` / `--llvm 19`: 171 PASS,
  0 FAIL, 0 ERROR each.
- `scripts/oss/i686/i686-oss.sh <p> strict`: zlib 37 units by hod, 11 / 11
  tests; bzip2 9 units, 32 / 32; zstd 118 units, 3 / 3.
- compare-binaries, head against a release build of base `422cfcb3`
  (own target dir), `tests/ir` + the corpus's `kiln` + `corpus-x64/kiln`,
  `-j 4`: 14168 comparisons; aarch64 and x86-64 0 different; i686 97
  different per mode (plain, pic) of 121, as expected; 0 changed outcome
  on every target; 47 identical failures.
- The i686 debug lane (`cargo xtask debug --target i686 -j 4`): 488
  results, 423 PASS / 6 FAIL / 59 SKIP (WP-352 at its base: 475, 411 /
  6 / 58; this base has 13 more results). key_call.c lldb: PASS (the 6
  lldb FAILs are gone), inlined.cpp gdb passes without a rule. Rules
  used: `return-row` 0 (was 9), `entry-row` 3, `local-label` 3,
  `return-column` 12, `value-range` 15, `pre-opt checks` 36.
  **New: key_call.c gdb, 6 FAIL** (clang 19 and 22, bfd / lld / mold).
  Cause (`llvm-dwarfdump --debug-line`, PIC objects of the clang-22
  module): `llc`'s return address of every call is its PIC-base reload
  `mov 0xc(%esp), %ebx` in a LINE-0 row; gdb's `finish` stops there and
  prints `0x? in main () at key_call.c:16`. hod has no reload: its
  return address is now the next instruction, which starts a row (the
  clang-22 key-instruction buoy `16:11 is_stmt` at 0xa2; with clang 19
  the first row of line 17), so gdb prints `main () at key_call.c:16`
  (clang 22, the same line, no address) or `:17` (clang 19). Before
  WP-354 the return address was the `lea` release inside the call's row,
  which `return-row` permitted. Not fixed here (see PARKED.md): the
  choices are `llc`'s shape (the GOT pointer reloaded after each call
  under PIC, in a line-0 row) or a session rule; both need a decision.
