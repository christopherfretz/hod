# WP-016 — `xtask irdiff` and the `tests/ir/` directive format

Landed: `spec/harness.md` "irdiff" and "Test directives" (layer L4 of
`docs/VALIDATION.md`), the seed corpus in `tests/ir/`, and the L4 step of
`cargo xtask ci`.

## What it did

- `xtask/src/irdiff.rs`: the command (`parse_args`, `run(&Config) ->
  Result<Report, String>`), test collection, tool discovery glue.
- `xtask/src/irdiff/directives.rs`: the `;@` format: `parse`,
  `Expectations`, `Expectations::to_directives` (the canonical form).
- `xtask/src/irdiff/process.rs`: the bounded child process every tool and
  every program goes through.
- `xtask/src/irdiff/tools.rs`: finding the oracle, the linker driver and
  the linkers; the check of which linker made a program.
- `xtask/src/irdiff/engine.rs`: `Session`, the core that takes "an IR file
  and its expectations" and returns records; nothing in it knows of
  `tests/ir/`.
- `xtask/src/irdiff/report.rs`: records, the results file, the summary,
  the exit status.
- `xtask/src/main.rs`: `cargo xtask irdiff`, and the `irdiff` step of
  `cargo xtask ci` (quick tier with the default oracle for `--quick`,
  every test with LLVM 22 and with LLVM 19 for the full gate).
- `tests/ir/`: 29 hand-written programs, 11 of them in the quick tier.
  All are UNSUPPORTED today (`codegen-not-implemented`), and PASS in
  hybrid mode.
- `xtask/tests/irdiff_fakes.rs` (fake tools, every outcome),
  `xtask/tests/irdiff_real.rs` (real tools, gated), and
  `xtask/tests/common/mod.rs` (a scratch directory under the build
  directory).

No new dependency, no `unsafe`, nothing changed in `hod`, `hod_cli`,
`hod_testutil` or `spec/cli.md`.

## Decisions, and why

- **Limits without `unsafe` and without a dependency.** The address-space
  and CPU limits are set by a `/bin/sh -c 'ulimit ...; exec "$@"'` wrapper;
  the wall-clock limit is enforced by the harness, which kills the child's
  process group. The kernel limits hold even if the harness dies. Core
  files are switched off in the same wrapper: a test may be expected to
  die by a signal, and must not leave a `core` in the work directory.
- **Linking goes through `gcc -B<dir>`**, where `<dir>` holds the chosen
  linker under the name `ld`. `-fuse-ld=` knows only the names the
  driver's version was built with and resolves them by its own search;
  `-B` works for any linker and lets the harness pin the exact binary it
  found (which lld of two installed, for one). Because that trusts the
  driver to honour `-B`,
  the harness verifies the result: the `.comment` signature of the program
  must be the asked linker's. A wrong linker is an ERROR, not a silent
  hole in the matrix.
- **lld and mold run with one thread.** The harness is what
  parallelises, and a thread pool per core counts against the
  address-space limit: on this 24-core host, linking one small object,
  lld 22 with its default pool fails under a 1 GiB limit and still prints
  a `std::system_error` under 2 GiB, and mold 2.37 fails under 512 MiB;
  with one thread both link under 256 MiB. The margin below the 4 GiB
  tool limit would shrink with the number of cores.
- **The oracle's side is an ERROR, hod's side is a FAIL**, with no
  exception. That includes "the oracle's program does not behave as the
  directives say": the test is wrong, and nothing is said about hod.
- **`unsupported` is exact and `xfail` does not cover it.** A decline
  without the directive, a decline with another reason, and hod compiling
  a test that still carries the directive are FAILs that `xfail` cannot
  turn into XFAIL. Otherwise coverage numbers would drift from the tests:
  the commit that teaches hod a construct has to remove the directive.
- **Exit status 3** separates "the run cannot be trusted" (ERROR, missing
  required tool) from "hod is wrong" (1), so a caller such as `bisect`
  can tell them apart; 2 stays usage, as for `shim`.
- **Cross targets build both objects and stop.** The decline, a failure
  of hod, and a broken oracle are all visible without running anything,
  so they are reported; only "hod built it and nothing can run it" is
  SKIP. Emulated runs are left to the work package that provisions them.
- **A test file has no `target triple`.** The harness passes `-mtriple`,
  so one file serves both targets; a test that is valid for one says so
  with `target:`.
- **The relocation model follows the link**: PIC objects for a PIE, static
  objects for `link: no-pie`. A PIC object in a non-PIE program is not
  expressible yet.
- **`stdout:` lines, each ending in a newline.** Output without a final
  newline and non-UTF-8 output cannot be written; no test needed them.
  Standard error is not compared: `llc` and hod are not required to make
  programs that print the same diagnostics, and the tests print through
  stdout.
- **Directive errors are collected, not first-wins**, so a file is fixed
  in one pass; the test is an ERROR and never run.
- **Defaults: `-j` is the smaller of 4 and the cores, capped at 16; tools
  60 s and 4 GiB, programs 10 s and 1 GiB.** The host is shared.
- **The default hod is the development-profile build** of the workspace,
  the binary the rest of the gate has just built. Timing hod is the
  benchmark's business (`bench`), not this harness's.
- **The work directory is removed even when a test fails**, unless
  `--keep` is given: an unattended gate must not fill the disk. The detail
  of a record says what differed.
- **The results file's name carries the target, the oracle and the mode**,
  so the runs of the full gate do not overwrite each other.
- **`va_arg` is not in the corpus.** For AArch64 Linux `llc` 19 and 22
  compile it as if `va_list` were a pointer and the program reads garbage
  (checked with a three-argument sum). There is no oracle for it.

## Evidence

On the development container (aarch64 Linux, 24 cores, shared and loaded;
LLVM 22.1.8 and 19, gcc 14.2, GNU ld 2.44, lld 22, mold 2.37.1; no wild):

- `HOD_REQUIRE_TOOLS=1 cargo xtask ci --quick`: green, 86 s in all with a
  warm build. Its `irdiff` step: 11 tests, 33 results, 33 UNSUPPORTED, in
  1.5 s.
- `cargo xtask irdiff`: 29 tests, 87 results, 87 UNSUPPORTED, 2.9 s
  (`-j 1`: 7.6 s). `--llvm 19`: the same, 2.8 s.
- `cargo xtask irdiff --tier quick`: 33 UNSUPPORTED in 1.5 to 2.1 s
  (`-j 1`: 3.0 s).
- `cargo xtask irdiff --hybrid`: 87 PASS in 4.5 s; `--llvm 19`: 87 PASS in
  4.3 s. This is the run that proves the corpus: every program, linked by
  bfd, lld and mold, prints what its directives say.
- `cargo xtask irdiff --target x86_64`: 29 UNSUPPORTED (objects built by
  the oracle, nothing run) in 0.6 s, with both oracles.
- `cargo test -p xtask`: 44 unit tests (3 s), `irdiff_fakes` 21 tests
  (15 s), `irdiff_real` 5 tests (14 s).

Timings vary with the load of the host; the same commands were measured
between 2.7 s and 4.4 s for the full corpus.

## Not verified

- **wild.** It is not installed. Its discovery (`wild`, `ld.wild`) and
  its place in the matrix are tested with fakes only; its `.comment`
  signature is not checked and whether it needs a thread option under the
  address-space limit is unknown.
- **x86_64 programs, through the harness.** `irdiff --target x86_64`
  builds the objects and runs nothing. Out of band, once: every test was
  compiled for x86_64 with `llc` 22 and 19, linked with
  `x86_64-linux-gnu-gcc` (GNU ld) and run under `qemu-x86_64`; all 29
  programs printed and ended as their directives say. So the corpus's
  expectations hold on x86_64, but no run of the harness shows it, and
  lld and mold were not part of that check.
- **The gate without tools.** The skip paths are tested with fakes; the
  whole of `cargo xtask ci` was only run on this machine, where the tools
  exist. A CI runner without LLVM 22 or 19 will note and skip L4.

## Left open

- Running cross-target programs in the harness. The container now has
  `qemu-x86_64` and an x86_64 cross `gcc` with its sysroot, so the step is
  a cross driver per target, `-L <sysroot>` for the emulator, and the
  three linkers in cross mode; it was out of this package's scope.
- wild's signature and thread option, once it is provisioned; then it
  moves into the required linkers.
- Families the seed corpus does not have yet: bit-manipulation and
  floating-point intrinsics (`ctpop`, `ctlz`, `bswap`, `fabs`, `sqrt`,
  `fma`), vectors, `indirectbr`, `byval` and `sret` arguments, 16-bit
  and 128-bit floating point.
- A way to write expected output without a final newline, or binary.
- A PIC object linked into a non-PIE program.
- The `va_arg` instruction: hod will have to decline it or define it;
  there is nothing to compare against on AArch64.
- `irdiff_fakes` and `irdiff_real` add about half a minute to the test
  step of the quick gate, most of it tests that wait for a time limit to
  fire.
