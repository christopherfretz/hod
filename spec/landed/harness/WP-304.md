# WP-304 — `tiny-functions` and threads

Item 9 of the ranked list of `spec/landed/harness/WP-288.md`: "`tiny-functions`
does not scale with threads" (64.7 ms at 1 thread, 85.7 ms at 8). Landed:
`crates/hod/src/back.rs` (the calling thread of a parallel compile lays
the chunks out while the workers make them), a test in
`crates/hod/tests/back.rs`, and `spec/cli.md` "Threads" and "The back
half" step 5. Byte-neutral at every thread count; one thread runs the
code it ran before.

## Method

The base is `eb7ae0d2` (built in its own target directory from `git
archive`), the head this package. Inputs: the bench inputs `tiny-functions`,
`stl-heavy`, `templates`, `containers`, with and without `-g`, as clang 22
writes them for aarch64 and x86-64 (16 modules). Each run: `hod
-filetype=obj -O0 --threads=<n>`, hod's own phase report
(`HOD_TIME_PHASES`), 15 repetitions per configuration, base and head
interleaved per run (A B A B), load average 14 to 18 of 24 cores.
Diagnosis: temporary timers in `hod::back` (per chunk, per thread, first
functions), `/proc/thread-self/stat` fault counters, callgrind
(`--separate-threads=yes`, `--toggle-collect`), `/usr/bin/time`. `perf` is
not in the container.

## The claim does not reproduce on `eb7ae0d2`

At the base, more threads are not slower on any of the four tiny-functions
inputs (minimum / median ms, total): aarch64 `-g` 44.0 / 49.4 at 1 thread,
39.2 / 51.1 at 8; aarch64 plain 23.0 / 28.9 and 20.7 / 27.1; x86-64 `-g`
40.9 / 48.1 and 39.9 / 47.6. Emission gets faster with threads (aarch64 `-g`
9.5 → 7.2 minimum), the rest does not move.

WP-288's 85.7 ms at 8 threads came with `read` 6.4 → 16.0 ms. `read` ends
when the input has been read (process start, the command line, reading the
file: `spec/cli.md` "Phase report"), before anything looks at the thread
count, so it cannot depend on it: those 8-thread runs were taken under
other load. That base was also older (WP-290 and WP-291 landed since).

## Why `tiny-functions` scales so little (measured)

`tiny-functions-g` (aarch64) is 5,001 bodies of 4 IR instructions, 20,027
in all: `wanted_threads` gives 4 threads (one per 4,096), the plan 16
chunks of 313 functions. Of the about 9 ms of `emission` at one thread:

- compiling the bodies, 3.5 ms; the only part that threads divide;
- laying the chunks out (`ModuleEmitter::add_chunk`), 2.9 ms, serial;
- the rest (`ModuleEmitter::new`, `check_functions`, the attribute
  groups), about 2.7 ms, serial.

At 4 threads (base): the workers ended after 2.0 to 2.3 ms, then the
calling thread laid out all 16 chunks after the join: 2.7 to 2.9 ms.

Of the 3.5 ms of compiling, 1 to 2 ms is the FIRST function: 0.7 to
2.3 ms for a function of 4 instructions whose next ones take 1 to 8 µs.
Callgrind counts 19,327 instructions in that first call, so it is not
work: the call takes 6 major page faults (`/proc/thread-self/stat`), the
first execution of code generation's text pages. hod's binary lives on the
workspace's host-shared mount (`fakeowner`, FUSE-like), where every run
takes 39 major faults; on a disk file system they are minor faults from
the page cache. Every worker needs the same pages, so this start is not
divided among threads: with 4 workers each one's first chunk takes 1.2 to
3.0 ms, every later chunk of the same size 0.2 to 0.3 ms. When the calling
thread compiled chunk 0 alone before the workers started (an experiment),
the workers' first chunks took 0.25 to 0.47 ms: the cost is once per
process, not per thread.

Ruled out, with the measurement:

- Thread start: the workers began 60 to 280 µs after the plan.
- Page faults on heap memory and malloc arenas: with
  `glibc.malloc.top_pad=64 MiB` the faults of the workers fall from about
  180 to under 15 each and the join time does not move (2.0 to 2.3 ms);
  with `arena_max=1` it gets worse (3.0 to 3.4 ms).
- More work on more threads: callgrind counts 360.5 M instructions at 1
  thread and 361.9 M at 4 (+0.4%).
- A shared table, a lock or false sharing in code generation: none is
  written while bodies compile (the module, bodies and attribute groups
  are read-only; the two atomics are touched once per chunk and on a
  failure).
- Uneven chunks: the 16 chunks went 4 to each thread.
- Reading the bodies in parallel (`bodies`, 9.6 to 10.2 ms, the largest
  phase): `tiny-functions` averages fewer than `READ_MIN_BODY_BYTES` (512)
  per body, and WP-063 measured parallel reading of such bodies slower
  (0.66x to 0.93x). Not `hod_ll`'s module reader either: `read` and `parse`
  do not depend on the thread count.

## The fix

The serial lay-out after the join is the part of the parallel compile that
threads could hide, and on modules with debug information it is as long
as the parallel compile itself (base, aarch64, 8 threads: `stl-heavy-g`
workers 4.7 ms then lay-out 8.6 ms; `templates-g` 3.5 then 5.3). Now the
calling thread lays the chunks out in module order as they are made and,
while the next one is not made yet, takes and compiles a chunk itself
(`Work::lay_out`); the workers post their chunks to a board under a mutex
and signal a condition variable. Chunks are added in the same order, so
the object is the same; a chunk is freed as soon as it is added (fewer
chunks held at once than before); a refusal is still the first in module
order (the chunk laid out next is the first that can hold it), and the
emitter's refusal still comes after a function's. A worker that panics
marks the board broken so that the calling thread stops waiting; the panic
is raised when the worker is joined, as before. How the work is split
(`wanted_threads`, `plan`, `CHUNKS_PER_WORKER`) is unchanged, so is the
one-thread path.

"Use fewer threads when the work is small" was considered: the measurement
does not support it, since at the base already no thread count is slower
than one beyond the noise on these inputs.

## What remains

- The first function's start on this host (1 to 2 ms of major faults of
  hod's text on the shared mount) is the floor of a parallel compile; on
  a disk file system it is a few minor faults. Not hod's.
- `tiny-functions`' largest phases are `parse` (with `-g`) and `bodies`
  (read serially, by the WP-063 thresholds); the lay-out (2.9 ms) and the
  emitter's start (about 2.7 ms) stay serial.
- The lay-out itself (`add_chunk`, with `-g` the line table and DIEs of
  each function) is now the critical path of a parallel emission on the
  `-g` inputs: 8.6 ms of `stl-heavy-g`. Making it cheaper is a codegen
  package.
