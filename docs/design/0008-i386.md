# Design 0008: 32-bit x86 Linux (`i686-*-linux-gnu`)

Status: proposed with WP-240. A design only: no code generation lands
with it. 32-bit x86 Linux is a planned third target; today hod refuses
every 32-bit module as `unsupported-target` (`hod_ir::TargetSpec::from_triple`,
`crates/hod_ir/src/target.rs:630`). This document says what each crate
assumes about a 64-bit target and what changes, states the i386 System V
ABI as LLVM implements it (the skeleton of `spec/abi-x86.md`), and orders
the work.

Measurements ran on the shared AArch64 host with `llc`, `llvm-mc`,
`llvm-readelf`, `llvm-objdump` and `llvm-dwarfdump` 19 and 22, clang 19
and 22, `qemu-i386` 10.0.13, ld.lld 22.1.8, mold 2.37.1, GNU ld 2.44 (as
`x86_64-linux-gnu-ld.bfd`) and wild 0.11.0. No i686 C library is
installed, so nothing that needs libc links here (section 4.1). Every
probe is under `docs/design/0008-data/`:

- `abi/NN-*.ll` with `run.sh` (llc 19 and 22, SelectionDAG and FastISel,
  `-O0`, static or PIC by file name), `norm.sh` (strips directives) and
  `cmp.sh` (counts differing lines 19 against 22 and SelectionDAG
  against FastISel). The `.dag22.s` outputs are kept, and the `.dag19.s`
  ones where they differ from 22 after `norm.sh` (02, 03, 08, 09-pic).
  `a.c`, `b.c`, `eh.cpp`, `dbg.c` are the C and C++ probes for clang.
- `mc/compare.sh` with `compare.out`: `llvm-mc` encodings in both modes.
- `run/run.sh` with `run.out`: objects linked by each linker and run
  under `qemu-i386` without a C library.

## Question

What does hod need to write correct `-O0` objects with production debug
information for `i686-unknown-linux-gnu`, how is each piece checked on
this host, and in which order does the work go?

**Answer.**

1. **A new back-end crate, `hod_x86`**, beside `hod_x64`, built on
   `hod_cg` unchanged in shape and on `hod_mc_x64` with a 32-bit mode.
   `hod_x64` names its 64-bit registers in about 1350 places (`r10`/`r11`
   488, `Size::Q` 661, `xmm14`/`xmm15` 198), and its scratch and pool
   sets do not fit in eight registers; a mode flag would touch every one
   of them. Section 1.5 argues it with numbers.
2. **`i64` is a memory value.** `Target::class_of` is already per target:
   `hod_x86` classes `i64` (and `double` without SSE2) as `Mem`, a frame
   slot of two 4-byte words, and lowers each operation on the halves.
   `hod_cg` gains no notion of register pairs.
3. **The ABI is mostly the stack**, but less uniform than its reputation
   (section 2, `spec/abi-x86.md`): every aggregate return through `sret`
   with the callee popping the pointer (`retl $4`), `i64` in `edx:eax`,
   `float`/`double`/`x86_fp80` in `st0`, IR struct returns in up to
   `eax`/`edx`/`ecx` or `st0`/`st1`, `inreg` in `eax`/`edx`/`ecx`, and
   **vectors and `half` whose passing depends on the CPU** (SSE: `xmm0`
   to `xmm2`; without SSE: split on the stack, returned through a hidden
   pointer).
4. **clang's default `i686` CPU has no SSE** (`"target-cpu"="i686"`,
   `"+cmov,+cx8,+x87"`, both clang 19 and 22): `float` and `double` are
   computed in x87 for a default build. hod therefore needs an x87 scalar
   path from the first floating-point package; SSE2 scalar code is a
   second path, chosen by the function's CPU. `fptosi`/`sitofp` with
   `i64` use x87 even with SSE2 (measured).
5. **PIC without `rip`**: a per-function `calll .L$pb; popl` (llc does not
   use `__x86.get_pc_thunk` at `-O0`), `@GOT`/`@GOTOFF` from that base,
   `ebx` loaded with the GOT pointer before every `@PLT` call, `.rel`
   sections with implicit addends written into the section bytes. TLS
   uses `%gs` and the exact GD/LD sequences the three linkers relax.
6. **The lane is cheap to provision** (`gcc-i686-linux-gnu`,
   `libc6-dev-i386-cross`, `libstdc++-14-dev-i386-cross`; `qemu-i386` is
   installed) and links with bfd, lld and mold; **wild does not link
   i386** (`Emulation 'elf_i386' is not yet supported`). kiln has no
   32-bit target, so all evidence until it does comes from clang's i686
   IR and from `llc` as the oracle.

### 1.2 `hod_obj`: ELF32 and `Elf32_Rel`

LLVM writes i386 objects as ELFCLASS32, `EM_386`, flags 0, with **`.rel`
sections** (`SHT_REL`, entry size 8) for code, data, `.eh_frame`,
`.gcc_except_table` and the debug sections; the addend is in the section
bytes (`readelf -S` of `09-globals-pic.o`; a jump table's `R_386_GOTOFF
.text` entries hold the block offsets `0x102`, `0x10c`, ...; a `@PLT`
call's field holds `-4`, `fc ff ff ff`). `.eh_frame` is `SHT_PROGBITS`,
not x86-64's `SHT_X86_64_UNWIND`.

The writer keeps its model: a `Reloc` with an `addend: i64`. For an i386
object the writer:

- writes 52-byte file headers, 40-byte section headers, 16-byte symbols
  (`st_name`, `st_value`, `st_size`, `st_info`, `st_other`, `st_shndx`:
  a different field order from `Elf64_Sym`) and 8-byte `Elf32_Rel`
  (`r_offset`, `r_info = sym << 8 | type`);
- names each relocation section `.rel<name>`, type `SHT_REL`;
- **adds each addend into the section bytes at the field** while it
  streams the section (a 4-byte little-endian add; every i386 field hod
  writes is 4 bytes, `R_386_16`/`R_386_8` are not needed), and rejects an
  addend that does not fit the field as an internal error. The field is
  zero before (the encoders leave relocated fields zero), so the add is a
  store; the writer must not assume it, a `.long sym+4` in data already
  holds 4 if a producer put it there, so the rule is "field := field +
  addend" with exactly one writer of the addend.
- refuses a 64-bit relocation kind in a 32-bit object and the reverse
  (a type check at `add_relocation`, as the arch check is today).

`RelocKind` gains `I386(I386Reloc)` with the set of 3.3. `.symtab` symbol
values and sizes fit 32 bits by construction (an object over 4 GiB is
refused). Compression (`Elf32_Chdr`, 12 bytes) for `.debug_*` follows the
class. Cost: about 400 lines in `elf.rs`/`reloc.rs`, tested as today with
`llvm-readelf` and the three linkers.

### 1.3 `hod_mc_x64`: one encoder, two modes

Measured with `llvm-mc` 22 (`mc/compare.out`): an instruction whose
operands are 8-, 16- or 32-bit registers and memory with 32-bit base and
index registers has **the same bytes in 32-bit mode as the x86-64 form
with the 64-bit address registers** (`movl %eax, (%ecx)` = `movl %eax,
(%rcx)` = `89 01`; SIB, displacements, `0x66`, the x87 and SSE forms,
`cmpxchg8b`, `shld`, `push`/`pop`/`call *r`/`ret $n`, `B8+r imm32`). What
differs:

| construct | 64-bit mode | 32-bit mode | encoder change |
|---|---|---|---|
| REX (`r8`-`r15`, `xmm8`-`xmm15`, `spl`/`bpl`/`sil`/`dil`, `REX.W`) | prefix `0x40`-`0x4f` | those bytes are `inc`/`dec`; none of these registers exist | refuse at construction (a debug assertion in the mode, an error in `hod_asm`) |
| ModRM `mod=00 rm=101` | `rip`-relative | absolute `disp32`, no SIB | absolute addressing without SIB: `movl 0x1234, %eax` is `a1 34 12 00 00` (moffs) or `8b 05 ...`, not `8b 04 25 ...` |
| `movl moffs, %eax` (`a1`) | 64-bit offset | 32-bit offset; llvm-mc chooses it for `eax` | optional; `8b 05 disp32` is equally valid |
| `inc`/`dec r32` | `ff c0` | `40+r` (llvm-mc chooses the short form) | none required: `ff c0` is valid; the L1 oracle must accept it (below) |
| `push`/`pop`/`call`/`jmp` indirect, `ret` | 64-bit operand | 32-bit operand | none (same bytes) |
| `movsxd` (`63`), `syscall`, `cmpxchg16b`, `movabs`, `cdqe`/`cqo` | valid | `arpl`, invalid, or absent | refuse in the mode |
| `%gs`/`%fs` | `%fs` for TLS | `%gs` for TLS | none (prefix `65`) |

So one encoder serves both modes with a `Mode` carried by the code
buffer (or by a type parameter on the operand constructors): the
`Mem::absolute` form, the refusal of REX-only operands and of 64-bit-only
mnemonics. The bulk (725 public functions, the x87, SSE, AVX and EVEX
tables) is shared unchanged; AVX and AVX-512 in 32-bit mode encode the
same with the high register bits forced (only `xmm0`-`xmm7`, `zmm0`-`zmm7`,
`k0`-`k7`), and stay out of scope until a module needs them.

**Oracle cost.** The L1 harness assembles AT&T text with
`--triple=x86_64-unknown-linux-gnu` (`tests/l1/harness.rs:178`). A
32-bit L1 needs the same sweeps printed with `%e..` address registers
and run with `--triple=i686-unknown-linux-gnu`, plus an equivalence for
the two forms where `llvm-mc` picks a shorter encoding (`inc`/`dec`
`40+r`, `a1` moffs): either the 32-bit mode emits those forms too (byte
identity, simplest to test) or the comparison decodes both. Recommended:
emit the `llvm-mc` forms in 32-bit mode, so the L1 comparison stays
byte-for-byte. Size: one session (the mode, the absolute form, the short
forms, the 32-bit L1 driver over the existing sweeps restricted to
registers 0-7).

### 1.4 `hod_cg`: no register pairs

`hod_cg` decides a value's class through `Target::class_of`
(`crates/hod_cg/src/target.rs:132`) and sizes `Gpr` slots by
`RegInfo.gpr_bytes`; nothing in it assumes that a 64-bit integer fits a
register. The x86-64 back end classes `iN` (N ≤ 64) and pointers `Gpr`
(`crates/hod_x64/src/target.rs:330`); i128 is already `Mem` and is
lowered word by word from its slot. `hod_x86` does the same one size
down:

| type | class on i386 | slot |
|---|---|---|
| `i1`-`i32`, `ptr` | `Gpr` | 4 bytes |
| `i64`, `i128`, wider | `Mem` | alloc size (8, 16, ...), alignment from the layout (4) |
| `float` | `Fpr` with SSE; `Mem` without | 4 |
| `double` | `Fpr` with SSE2; `Mem` without | 8, alignment 4 |
| `x86_fp80` | `Mem` (as on x86-64) | 12, alignment 4 |
| `<N x T>` of 8 or 16 bytes | `Fpr` with SSE2; `Mem` without | 8 or 16 |

An operation on a `Mem` value loads the halves it needs into
temporaries (`add`/`adc`, `sub`/`sbb`, three `imul`/`mul` for a product),
which is how llc writes them (`01-int.dag22.s` `r64`; `11-libcalls`
`mul`, `shl` with `shld` and `testb $32`). What `hod_cg` gains is small:
an `Arch::I386` arm in the runtime tables (the libgcc routines of 5.2, the
`@PLT` suffix rule of 3.1), and the frame's `STACK_ALIGN` of 16 with a
4-byte return address and an `ebp` frame (13-frame: `pushl %ebp; movl
%esp, %ebp; subl $8, %esp` leaves `esp` 16-aligned at the call).

The **register budget** is the binding constraint. The x86-64 back end's
pool has five general registers (`rbx`, `r12`-`r15`), two scratch
(`r10`, `r11`), and takes `rax`, `rcx`, `rdx` as fixed registers
(division, shifts by `cl`, `cmpxchg`, returns); "a lowering pins at most
four general pool registers" (`spec/codegen.md`, x86-64 register sets).
i386 has six usable general registers with `ebp` as the frame pointer:
`eax`, `ecx`, `edx` (caller-saved) and `ebx`, `esi`, `edi`
(callee-saved). The proposal:

- **pool**: `ebx`, `esi`, `edi` (three; `ebx` is also the PLT GOT
  register in PIC, reloaded from a slot before each `@PLT` call, as llc
  does: `09-globals-pic.dag22.s` `calls`);
- **scratch and fixed**: `eax`, `ecx`, `edx`, taken per instruction
  (`edx:eax` for products, quotients and `i64` returns, `cl` for shifts,
  `ecx` for `inreg`/`thiscall`/`nest`);
- **no lowering pins more than two pool registers plus the three fixed
  ones**. The worst case is `cmpxchg8b`: `edx:eax` expected, `ecx:ebx`
  new, an address register (llc uses `esi`), so five of the six and
  `ebx` saved around it in PIC (`12-atomic.dag22.s`). The `min_pool`
  stress mode (`crates/hod_cg/src/driver.rs:213`) runs every lowering at
  this size from the first package.

Since a value that does not fit lives in its slot, three pool registers
cost loads and stores, not correctness; the x86-64 lowerings that pin
four pool registers (vector lane loops, the wide multiply) are written
again for i386 with the halves in memory.

### 1.5 `hod_x64` and a third back end: separate crate

Three options:

| option | what | cost measured |
|---|---|---|
| A. a mode in `hod_x64` | `X64 { bits: 32 }`; every lowering branches | 488 references to `r10`/`r11`, 661 `Size::Q`, 198 `xmm14`/`xmm15`, 17 `r8`/`r9`/`r12`-`r15`, 12 `rip` sites; the pool and scratch sets of 1.4 differ; every x86-64 test would need to keep passing through the branches |
| B. shared `x86` layer | move register-agnostic modules to a crate both use | the agnostic part is small: the x87 lowering (`x87.rs`, 1026 lines) uses `r11` and `rip` constants; the SSE intrinsics (`x86.rs`, `x86/ext.rs`, `x86/sys.rs`, 3148 lines) use `xmm14`/`xmm15` and `r11` scratch; both would need parameterising by a register set first |
| C. **separate crate `hod_x86`** | i386 only; depends on `hod_cg`, `hod_mc_x64` (32-bit mode), `hod_obj`; copies `hod_x64`'s patterns | about 10-14k lines over the packages of section 6 (the x86-64 crate is 28k with AVX/AVX-512, coroutines, CET and the large code model, none of which the first i386 milestones need) |

**Recommended: C.** The same argument design 0006 §1.3 made for x86-64
against AArch64 holds: what is target-specific is the register file, and
on i386 it is the register file that changes. Sharing comes later and by
extraction, not by branching: once both crates exist, the SSE intrinsic
tables (the `llvm.x86.sse*` names clang emits for `<emmintrin.h>` in an
SSE2 function) can move to a module generic over two scratch `xmm`
registers (`xmm6`/`xmm7` on i386), measured then. The x86-64 crate is not
touched by the i386 packages except where a shared table moves to
`hod_cg` (as design 0006's R1 did).

### 1.6 `hod_eh` and `hod_dwarf`

Both are table-driven by `Arch`. The i386 table (measured on `eh.cpp`
and `dbg.c`, clang 22 `-O0 -g -gdwarf-5`, static and `-fPIC` alike):

| field | i386 | x86-64 |
|---|---|---|
| code / data alignment factor | 1 / -4 | 1 / -8 |
| return address column | 8 (`eip`) | 16 |
| CIE initial instructions | `DW_CFA_def_cfa: esp(4) +4`, `DW_CFA_offset: eip(8) -4` | `rsp+8`, `rip -8` |
| FDE encoding | `pcrel sdata4` (0x1b), `R_386_PC32` | same encoding, `R_X86_64_PC32` |
| personality | `indirect pcrel sdata4` (0x9b) **also when static** | 0x9b PIC, 0x03 static |
| LSDA | `pcrel sdata4` (0x1b) static and PIC | 0x1b PIC, 0x03 static |
| LSDA type-table | 0x9b, through a local `.L_ZTIi.DW.stub` in `.data` holding `R_386_32 _ZTIi` | 0x9b PIC with `DW.ref`, 0x03 static |
| personality reference | `DW.ref.__gxx_personality_v0` (hidden, weak, COMDAT `.data.DW.ref...`, `R_386_32`) | same shape, `R_X86_64_64` |
| `.eh_frame` type | `SHT_PROGBITS` | `SHT_X86_64_UNWIND` |
| frame base | `DW_OP_reg5` (`ebp`), parameters `DW_OP_fbreg +8` | `DW_OP_reg6` (`rbp`), `fbreg -N` |

DWARF register numbers on i386 Linux: `eax` 0, `ecx` 1, `edx` 2, `ebx`
3, `esp` 4, `ebp` 5, `esi` 6, `edi` 7, `eip` 8, `st0`-`st7` 11-18,
`xmm0`-`xmm7` 21-28 (the first nine measured in the CFI above; `st0` 11,
`st7` 18, `xmm0` 21, `xmm7` 28 measured from the `.eh_frame` bytes
`8b 03`, `92 05`, `95 02`, `9c 04` that `llvm-mc -triple=i686` writes for
`abi/cfi.s`).
x86-64 numbers `rdx` 1 and `rcx` 2, the other way round.

The unit header's `address_size` is 4; `DW_AT_low_pc`, `.debug_addr`
entries, range and location lists, `DW_OP_addr` and the line program's
`DW_LNE_set_address` carry 4-byte addresses with `R_386_32`; section
offsets stay DWARF32 (`R_386_32` to the section). A TLS variable's
location is `DW_OP_const4u` with `R_386_TLS_LDO_32`, then
`DW_OP_GNU_push_tls_address` (`dbg.c`; llvm-dwarfdump 22 itself warns
"failed to compute relocation: R_386_TLS_LDO_32", so a debug test must
allow that warning). `hod_dwarf` writes 8-byte addresses literally at 18
sites (`[0; 8]` or `Abs64`); each becomes `target.address_size` with the
target's address relocation. Size: one session for both crates.

### 1.7 `hod_ir`, `hod_xform`, constant folding

clang 19 and 22 write the same layout for i686 Linux (`a.c`):
`e-m:e-p:32:32-p270:32:32-p271:32:32-p272:64:64-i128:128-f64:32:64-f80:32-n8:16:32-S128`.
What it means, measured with `sizeof`/`_Alignof` in `a.c`:

- pointers 4 bytes; `i64` has no entry, so its ABI alignment is LLVM's
  default 4 (hod's default table already says so, `target.rs:152`);
- `double` ABI alignment 4, preferred 8 (`struct { long long; double;
  char; }` is 20 bytes, alignment 4);
- `x86_fp80` alignment 4, so `long double` is 12 bytes;
- `i128` alignment 16 (clang refuses `__int128` on i686, but
  `_BitInt(65..128)` and generic IR reach it).

`DataLayout::parse` handles all of it; `TargetSpec` gains the arm, the
built-in string and `i686`/`i586`/`i486`/`i386` in `from_triple` (clang
writes `i686-unknown-linux-gnu`; `i386-linux-gnu` is Debian's multiarch
name). Constant folding takes the pointer width from the layout already
(`crates/hod_ir/src/fold.rs:239`), and GEP offsets wrap at the index
width (32 bits here): a probe-backed test belongs to the first IR package
(a GEP whose 64-bit offset differs from its 32-bit one). `hod_xform`
has no target dependence. `hod_interp` (the constant evaluator) is not
involved in code generation.

### 1.8 `hod_asm`

Inline assembly in an i386 module uses the 32-bit register names, `%gs`,
no `rip`, and constraints with i386 meanings: `A` is `edx:eax` (a 64-bit
operand in a pair), `q` is `eax`-`edx` (the byte-addressable ones),
`R` is the legacy eight, `t`/`u` are `st0`/`st1`. `hod_asm/src/x64/` (2771
lines) parses operands for the 64-bit mode; a 32-bit operand set and the
`A` pair are one package after the encoder mode, with the existing asm
tests' oracle (`llvm-mc`) run at `-triple=i686`.

### 1.9 The facade, the CLI and the harness

`hod` maps a triple to a back end; `-march=`/`-mcpu=` names of 32-bit
CPUs (`i686`, `pentium4`, `prescott`, `core2`, ...) must be known to the
feature reader, because **on i386 the CPU alone decides the features**:
clang writes `"target-cpu"="pentium4"` with `"target-features"=
"+cmov,+cx8,+fxsr,+mmx,+sse,+x87"` and llc then uses SSE2 (`movsd`,
`mulsd`) from the CPU, not from the list. The x86-64 reader accepts any
`target-cpu` because its baseline already has SSE2
(`crates/hod_x64/src/features.rs:11`); the i386 reader needs a CPU table
(LLVM's 32-bit CPU names to {x87, cmov, cx8, mmx, sse, sse2, sse3, ...})
and must refuse a CPU it does not know.

`hod_testutil::Target` gains `I686`: GNU prefix `i686-linux-gnu`, sysroot
`/usr/i686-linux-gnu`, Debian architecture `i386` in the cross package
names (`gcc-i686-linux-gnu`, `libc6-dev-i386-cross`,
`libstdc++-14-dev-i386-cross`), emulator `qemu-i386`, and a new notion
"runs natively on an x86-64 host" (an x86-64 Linux kernel runs i386
programs when built with IA-32 emulation, which the hosted runner's
should be; checked by the lane's first run, not assumed).

## 2. The i386 System V ABI as LLVM implements it

The rules, each with its probe, are the skeleton `spec/abi-x86.md`; this
section gives the ones that decide the design. All are identical in llc 19
and 22, SelectionDAG and FastISel, except where the table says (`cmp.sh`:
0 differing lines for `01`, `04`-`07`, `10`-`13`).

| rule | probe |
|---|---|
| every argument on the stack, at `4(%esp)` on entry, in order, each in a 4-byte-aligned slot of its size rounded to 4 (`i8` takes 4, `double` 8 at alignment 4, `x86_fp80` 12) | `01-int` `call64`, `02-fp` `calld` |
| `i64` returned in `edx:eax`, `i32`/`ptr` in `eax`, narrower in `al`/`ax` without extension (as x86-64, `spec/abi-x64.md` §7) | `01-int` `r64`, `r8`, `r16s` |
| `float`, `double`, `x86_fp80` returned in `st0`; a caller that drops the value pops it (`fstp %st(0)`) | `02-fp` `rd`, `calldrop` |
| `fp128` returned through a hidden pointer, callee pops it (`retl $4`) | `02-fp` `rq` |
| `half`: on the stack; returned in `ax` without SSE2, in `xmm0` with it | `02-fp` `rh`, `06-vec-*` `fh` |
| `sret`: the pointer is the first stack argument; the **callee pops it** (`retl $4`) and returns it in `eax`; the caller re-adjusts (`subl $4, %esp` after the call) | `04-aggr` `rs`, `crs` |
| `inreg sret`: in `eax`, no pop | `05-cc` `inrp` |
| clang returns **every** C struct through `sret`, even `struct { char; }` (Linux i386; not the Darwin/Windows small-struct rule) | `b.c` |
| IR first-class aggregate returns: up to three 32-bit parts in `eax`, `edx`, `ecx`; floating parts in `st0`, `st1`; larger ones demoted to a hidden `sret` (`retl $4`) | `04-aggr` `rpair`, `rtriple`, `rquint`, `rdd`, `rfi` |
| `byval(T)`: the bytes are copied into the argument area at the argument's offset; `align 16` does not move the offset (the area's base is 16-aligned) | `04-aggr` `cbv`, `cbv16` |
| clang passes small structs expanded into their fields (`{int,int}` as `i32, i32`), others `byval`; `_Complex float` returns as `i64` in `edx:eax`, `_Complex double` through `sret` | `b.c` |
| `inreg` (`regparm(3)`): `eax`, `edx`, `ecx` in order; an `i64 inreg` takes `eax:edx` | `05-cc` `inr`, `inr64` |
| `i128` and `fp128` arguments: **LLVM 22 aligns them to 16 on the stack, LLVM 19 to 4** (the one ABI difference between the two; kiln writes 22, so 22 is the rule, and the 19 grid row is marked) | `03-i128`, `02-fp` `rq` |
| `i128` returned through a hidden pointer; `i128` division inline (no `__divti3` call: libgcc for i386 has none) | `03-i128` |
| vectors with SSE: the first three 128-bit vectors in `xmm0`-`xmm2`, the rest on the stack at alignment 16; return in `xmm0` (`<8 x float>` in `xmm0`, `xmm1`); `<2 x i32>` in `xmm0` | `06-vec-sse2` |
| vectors **without** SSE: elements on the stack, returned through a hidden pointer (`retl $4`) | `06-vec-nosse` |
| callee-saved: `ebx`, `esi`, `edi`, `ebp`; `esp` 16-aligned at every call (Linux `S128`) | `05-cc` `clobber`, `13-frame` |
| `va_list` is one pointer; `va_arg` rounds up to 4 and steps by the slot size (`double` at alignment 4) | `07-varargs` |
| `musttail` and `tail` lower to `jmp` with the arguments rewritten in the caller's incoming area | `08-tail` |
| `nest` in `ecx` | `08-tail` `cn` |
| `fastcc` (IR): `ecx`, `edx`, caller pops; `tailcc`: `ecx`, `edx`, callee pops a 16-aligned area (`retl $12` for one stack word) | `05-cc` `fcc`, `tcc` |
| Windows-style conventions on Linux, only by attribute: `x86_stdcallcc` (callee pops, `retl $8`), `x86_fastcallcc` (`ecx`, `edx`, callee pops), `x86_thiscallcc` (`this` in `ecx`, callee pops), `x86_regcallcc`, `x86_vectorcallcc` | `05-cc`, `b.c` |
| `preserve_mostcc`, `preserve_allcc`, `coldcc`: on i386 the C convention's argument passing (their save sets are not measured: refused) | `05-cc` |

**In scope for the first ABI package:** C, `inreg`, `sret` (both forms),
`byval`, IR aggregate returns, the x87 returns, `i64` pairs, varargs,
`musttail`, `nest`, `fastcc` (llc writes it for internal functions only
when optimising, but kiln may write it: `kiln_llvm/src/inst.rs:452`
maps calling convention 8). **Refused by name** until a package needs
them: the vector conventions of SSE functions (one package after the
SSE2 path), `x86_stdcallcc`/`x86_fastcallcc`/`x86_thiscallcc`/
`x86_regcallcc`/`x86_vectorcallcc` (clang emits them on Linux only for an
explicit attribute; the corpus question is open, section 8),
`preserve_*cc`, `tailcc`, `i128`/`fp128` arguments (until the 19/22 rule
is a grid row).

## 3. Position independence, TLS, exceptions, DWARF

### 3.1 PIC and PIE

Measured on `09-globals-pic` (llc 22, `-relocation-model=pic`):

- **The GOT pointer** is computed per function that needs it, by `calll
  .L1$pb; .L1$pb: popl %reg; addl $_GLOBAL_OFFSET_TABLE_+(.Ltmp0-.L1$pb),
  %reg`. The call has no relocation (`e8 00 00 00 00`); the `addl`
  immediate is `R_386_GOTPC` with addend 3 in place (the distance from
  the label to the field: `81 c3 03 00 00 00`). llc 19 and 22 do **not**
  use `__x86.get_pc_thunk.*` at `-O0` (GCC does); hod uses the call/pop
  form, which needs no COMDAT thunk.
- Data: an external or preemptible global through the GOT,
  `movl g@GOT(%ecx), %eax` (**`R_386_GOT32X`**, never plain `GOT32` in
  llc 22 for `mov`), then the load; a local or hidden one at
  `x@GOTOFF(%ecx)` (`R_386_GOTOFF`); constants in `.rodata.cst*` the same
  way; jump tables as `.long .LBB@GOTOFF` entries added to the base.
- Calls: to a preemptible function `calll f@PLT` (`R_386_PLT32`, addend
  -4) **with `ebx` holding the GOT pointer** (reloaded from its slot
  before every such call); to a hidden or local function `calll f`
  (`R_386_PC32`, no `ebx`). In a static (non-PIC) object llc writes
  `calll ext@PLT` too, and `R_386_32` for data addresses.
- Address of a preemptible function: `movl f@GOT(%reg)`; of a local one:
  `leal f@GOTOFF(%reg)`.

What the linkers do with these (`run/run.out`): GNU ld and mold relax
`GOT32X` loads of a non-preemptible symbol to `leal x@GOTOFF(%ebx)`;
**ld.lld 22 does not**, it keeps the GOT slot with an `R_386_RELATIVE`
(correct with a dynamic loader; the probe's loader-less PIE crashes on
it). hod writes `GOT32X` as llc does and relies on no relaxation.

### 3.2 Relocations hod writes

| relocation | number | where |
|---|---|---|
| `R_386_32` | 1 | data pointers, static absolute addresses, debug sections, the `DW.ref` and type-info stubs |
| `R_386_PC32` | 2 | direct calls to local/hidden functions, `.eh_frame` |
| `R_386_GOT32X` | 43 | `movl x@GOT(%reg)` |
| `R_386_PLT32` | 4 | `calll f@PLT`, `___tls_get_addr@PLT` |
| `R_386_GOTOFF` | 9 | `x@GOTOFF`, jump tables |
| `R_386_GOTPC` | 10 | the GOT pointer's `addl` |
| `R_386_TLS_GD` | 18 | `leal x@TLSGD(,%ebx,1), %eax` |
| `R_386_TLS_LDM` | 19 | `leal x@TLSLDM(%ebx), %eax` |
| `R_386_TLS_LDO_32` | 32 | `x@DTPOFF(%reg)`, and the DWARF TLS location |
| `R_386_TLS_IE` | 15 | static: `movl x@INDNTPOFF, %reg` (absolute GOT entry address) |
| `R_386_TLS_GOTIE` | 16 | PIC: `movl x@GOTNTPOFF(%ebx), %reg` |
| `R_386_TLS_LE` | 17 | `movl %gs:x@NTPOFF, %reg` |

`R_386_GOT32` (3), `R_386_TLS_LE_32`, `R_386_TLS_GOTDESC`/`TLS_DESC_CALL`
(TLS descriptors, `-mtls-dialect=gnu2`) are not written by llc's default
and are refused when an input would need them.

### 3.3 TLS

`10-tls` and `10-tls-pic` (llc 19 = 22):

| model | sequence | relocations |
|---|---|---|
| general dynamic | `leal x@TLSGD(,%ebx,1), %eax` (7 bytes, SIB with no base) then `calll ___tls_get_addr@PLT` (three underscores: the `regparm` variant, argument in `eax`) | `TLS_GD`, `PLT32` |
| local dynamic | `leal x@TLSLDM(%ebx), %eax`, `calll ___tls_get_addr@PLT`, then `x@DTPOFF(%eax)` | `TLS_LDM`, `PLT32`, `TLS_LDO_32` |
| initial exec | PIC: `movl x@GOTNTPOFF(%ebx), %reg; movl %gs:(%reg), ...`; static: `movl x@INDNTPOFF, %reg` | `TLS_GOTIE` / `TLS_IE` |
| local exec | `movl %gs:x@NTPOFF, %reg` | `TLS_LE` |

A static executable model for a GD variable is IE (llc picks the model
from the relocation model, as on x86-64). The linkers relax only these
exact byte sequences: bfd, lld and mold all turned GD into `movl %gs:0,
%eax; subl $off, %eax` (mold: `addl`) and LD into `movl %gs:0, %eax`
plus a nop in a static link (`run/run.out`). So the GD pair is emitted
as one unit, with `ebx` the GOT pointer and nothing between the `leal`
and the `calll`.

### 3.4 Exceptions

Section 1.6 has the encodings. What differs from x86-64 beyond the
table: the landing pad receives the exception pointer in `eax` and the
selector in `edx` (`llc -O0 abi/14-eh.ll`: the landing pad begins
`movl %eax, -12(%ebp); movl %edx, -16(%ebp)`), `_Unwind_Resume` is
called `@PLT`, and the type-info
stubs are local data the back end must write (one per type-info in a
function's LSDA, `.L_ZTIi.DW.stub`).

### 3.5 Notes and properties

`.note.GNU-stack` as on the other targets. CET (`-fcf-protection`) on
i386 is `endbr32` and the `GNU_PROPERTY_X86_FEATURE_1_AND` note with
4-byte alignment: refused until asked for (no i386 distribution enables
it by default that this design knows of).

### 3.6 DWARF and debuggers

Section 1.6 has the numbers. gdb debugs an i386 program under
`qemu-i386 -g <port>` with `gdb-multiarch` (`set architecture i386`), the
setup the debug lane uses for x86-64 under emulation; the first debug
package confirms it on a `ret` program. lldb 19 reads the same objects.

## 5. The baseline instruction set

### 5.1 What a default build has

| build | `target-cpu` | features | scalar `float`/`double` |
|---|---|---|---|
| clang 19 and 22 `--target=i686-linux-gnu` (also `i386-`, `i586-`) | `i686` | `+cmov,+cx8,+x87` | x87 |
| `-march=pentium4` | `pentium4` | `+cmov,+cx8,+fxsr,+mmx,+sse,+x87` (SSE2 implied by the CPU) | SSE2, results returned through `st0` (`movsd`, `mulsd`, then `fldl` of a stack copy) |

So **hod cannot require SSE2** without refusing every default-built
module that touches floating point. Recommendation: **i686 (`cmov`,
`cx8`, x87) is the baseline hod requires; SSE2 is used when the
function's CPU has it.** Two scalar floating-point paths, both of which
`hod_x64` already has in some form (SSE2 everywhere, x87 for
`x86_fp80`, `x87.rs`):

- **x87 path (first).** Every `float`/`double` operation loads its
  operands from their slots onto the x87 stack, computes, and stores the
  result (`fstps`/`fstpl`), rounding to the type at every store. Returns
  are `st0` anyway. Conversions to integers set the control word for
  truncation around `fistp` (llc: `fnstcw`/`fldcw`, 9 in `11-libcalls`).
- **SSE2 path (second).** As x86-64, with `xmm0`-`xmm7` and returns
  moved to `st0` through a stack slot.

Requiring SSE2 instead would make the first milestones smaller (no x87
arithmetic path) and refuse the default build's floating point by name;
the x87 path costs about one session (arithmetic, comparisons through
`fucomip`, conversions with the control word) on top of the x87 code that
exists for `x86_fp80`. Vectors without SSE are `Mem` values handled by
the lane loops `hod_cg` already has (`lanes.rs`), with the
element-on-the-stack ABI of section 2.

### 5.2 Integers and atomics

| operation | llc (`11-libcalls`, `12-atomic`) | hod |
|---|---|---|
| `i64` add, sub, and, or, xor, compare | pairs with `adc`/`sbb` | same, halves from the slot |
| `i64` mul | three multiplies inline | same |
| `i64` shifts | `shld`/`shrd` plus `testb $32` and a select | same |
| `i64` `sdiv`/`udiv`/`srem`/`urem` | `__divdi3`, `__udivdi3`, `__moddi3`, `__umoddi3` (libgcc; `@PLT` in PIC) | same calls |
| `smul.with.overflow.i64` | inline (no `__mulodi4`) | inline |
| `fptosi`/`fptoui` to `i64`, `sitofp`/`uitofp` from `i64` | x87 `fistpll`/`fildll`, **also with SSE2** | x87 |
| atomic `i64` load/store | x87 `fildll`/`fistpll` without SSE2; `movq`/`movsd` with it | same |
| atomic `i64` RMW, `cmpxchg` | `lock cmpxchg8b` loop (`edx:eax`, `ecx:ebx`, address in `esi`) | same |
| atomic `i128` | `__atomic_load` and friends (libatomic) | calls |
| `fence seq_cst` | `lock orl $0, (%esp)` without SSE2; `mfence` with | same |
| `i128` division | inline expansion (no libgcc routine) | refused (`x86:i128-div`) until needed |

`cx8` is in the i686 baseline, so `cmpxchg8b` needs no feature check.

### 5.3 The default relocation model

clang 22 `--target=i686-linux-gnu -###` passes `-mrelocation-model pic
-pic-level 2 -pic-is-pie -mframe-pointer=all`, as for x86-64: **a default
i686 build is PIE**. So every program csmith or the debug lane builds
with clang's defaults needs the GOT pointer of 3.1 for its globals and
`ebx` at its `@PLT` calls; PIC is on the critical path to the second
milestone, not an option after it. Static code (`-fno-pic`) is the
smaller first step and stays supported.

  against llc 22, both executed under `qemu-i386`, checksums equal, over
  the seed count the x86-64 csmith lane uses.
- **C: libc++ tests with clang's IR** (I14): the suite as on x86-64,
  hybrid (llc fallback per module) then strict.

## 7. Risks

- **x87 rounding.** hod rounds every x87 result to its type at the store;
  llc at `-O0` may keep an intermediate on the x87 stack. Results then
  differ in the last bit for some inputs (double rounding), legitimately
  under `FLT_EVAL_METHOD` 2. Floating-point comparisons against llc need
  inputs that avoid it or a tolerance stated per test; csmith (no floats)
  is unaffected.
- **Register pressure.** Three pool registers against x86-64's five: a
  lowering that needs more must work from memory. Mitigated by
  `min_pool` stress from I5 on.
- **Feature-dependent ABI.** Vectors and `half` pass differently with and
  without SSE; a module mixing CPUs per function (one `target-cpu` per
  function) can call across the two rules. LLVM uses the callee's
  definition's features at a direct call; hod must do the same or refuse
  the mix by name.
- **LLVM 19 and 22 differ** on `i128`/`fp128` argument alignment. hod
  follows 22 (kiln's version); a test of linking hod code to code from an
  LLVM-19-based compiler must exclude those types.
- **kiln has no 32-bit target.** All evidence until I15 is clang's IR;
  kiln's own choices (its aggregate layouts, intrinsics, `fastcc`) may
  raise refusals late.
- **No wild.** The i386 linker matrix is bfd, lld, mold.
- **Emulation time.** libc++ under `qemu-i386` costs about three hours a
  run here (4.5); the hosted x86-64 lane may run i386 natively if its
  kernel has IA-32 emulation.

## 8. Open questions for the owner

1. Baseline: accept clang's default `i686` (x87 floating point, the
   recommendation), or require SSE2 (`pentium4`) and refuse the rest?
2. Relocation model: PIE from the first milestone onwards (clang's
   default, 5.3), or static first and PIC as a later step?
3. Windows-style conventions on Linux (`stdcall`, `fastcall`, `thiscall`,
   `regcall`, `vectorcall` by attribute): refuse by name, or support?
4. Sysroots: Debian's `i686-linux-gnu` cross packages only, or also
   another distribution's i386 libraries (which baseline do they assume)?
5. libc++ for i686: enable the `i386` foreign architecture to download
   Debian's archives, or build libc++ from the fetched sources?
6. kiln: request an `i686` target now, or after milestone C with clang's
   IR?
7. `-mregparm=N`, `-mrtd`, `-malign-double`, `-mstackrealign` builds:
   in scope (they change the ABI or the frame), or refused?
