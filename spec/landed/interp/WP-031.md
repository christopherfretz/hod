# WP-031 — `hod_interp`: the reference interpreter and the program generator

Landed: `spec/interp.md` (all of it), the crate `crates/hod_interp`, its row
in `spec/README.md`, and the `hod_interp` line of `docs/ARCHITECTURE.md`.

## What it did

- `crates/hod_interp/src/value.rs`: `Val`, `Agg` (§3).
- `src/memory.rs`: `Memory`: allocations, written flags, the access check,
  the stack discipline (§4).
- `src/ops.rs`: the arithmetic kernels: integer and float binary
  operations, compares, float-to-integer, the integer intrinsics (§5.1,
  §5.2, §5.3, §5.6).
- `src/error.rs`: `Trap`, `Stop` (§5, §7, §8).
- `src/interp.rs`: `Program`, `Interp`, `Config`, `Outcome`, `Event`,
  `HostCx`; the run loop over an explicit frame stack; module loading;
  every instruction; calls; intrinsics (§2, §5, §6, §7, §8).
- `src/host.rs`: `sink` and `source` (§6.1).
- `src/generate.rs`: `Options`, `Generated`, `Coverage`, `generate` (§9).
- `tests/instructions.rs`, `memory.rs`, `calls.rs`, `unsupported.rs`:
  hand-computed expectations for every instruction, trap and unsupported
  reason. `tests/robustness.rs`: random unguarded programs.
  `tests/generate.rs`: the generator's properties. `tests/llvm_oracle.rs`
  with `tests/llvm_text/`: the LLVM oracle (§10). `tests/common/`: the
  one-function fixture.

No `unsafe`, no dependency besides `hod_ir` (and `hod_testutil` for tests).
Nothing changed in `hod_ir`: the public builder and read API were enough.
Outside the crate and its spec: `Cargo.toml` (the workspace dependency
entry), `Cargo.lock`, `spec/README.md`, `docs/ARCHITECTURE.md`.

## Decisions, and why

- **Traps instead of choices.** Wherever LLVM's semantics leave room
  (poison, `undef` from memory, the bits of a NaN, a misaligned access that
  happens to work), the interpreter stops with a named trap. An oracle that
  picked one of the allowed behaviors would report correct compiled code as
  wrong.
- **`undef` and `poison` constants are zero** because `spec/ir.md` §4.1
  makes that hod's definition; so `freeze` is a copy.
- **Alignment is the allocation's, not the address's.** An access states
  an alignment; whether an under-aligned allocation happens to sit at an
  aligned address is layout. The check is "the allocation guarantees it".
- **Addresses are never reused,** so a dangling pointer cannot alias a
  newer allocation and `use-after-free` is exact for stack memory.
- **Padding is unwritten,** in stored aggregates and in initializers. The
  second is stricter than any compilation (they all emit zeros): chosen so
  that the rule for padding is one rule. Recorded in §12.
- **Computed NaNs trap by default.** Simple and safe; `NanPolicy::Host` for
  callers that know their NaNs are not observed.
- **Unsupported is lazy.** A reason is reported when execution reaches the
  construct, so a module that merely contains an `invoke` in a function
  never called is still usable.
- **A step is an instruction or a `phi` on an edge,** so that the
  generator's fuel bound is a count of instructions, exact for
  straight-line code.
- **The generator makes trap-freedom a matter of construction, not of
  retry.** It never runs the interpreter. Each value carries what must be
  known about it (type; for floats a magnitude bound, "not negative", "at
  least 1"; for pointers the region), and each operation that could trap
  gets operands that cannot make it. A generator that filtered by running
  the oracle could not find an oracle that is wrong about what traps.
- **Address-dependence is excluded syntactically:** `ptrtoint` results
  never join the value pool; three idioms use them (§9.2).
- **The mix of operations is biased toward keeping information.** With
  uniform choices values collapse to 0 and -1 within a few dozen
  instructions (`and`, shifts, quotients by large divisors) and wrong
  results are masked. Divisors and shift amounts are mostly small,
  multipliers odd, half of the constants random, and each function folds
  its values into its result with `acc * odd + value`. A mutation check
  (below) was the measure.
- **The LLVM printer is a test file,** covering only what the generator
  emits, to be replaced by `hod_ir`'s printer (WP-006).

## Evidence

On the development host (AArch64 Linux, LLVM 22.1, one test thread).

- `cargo test -p hod_interp`: 18 unit tests, 13 + 13 + 11 + 7 + 1 + 8 + 2
  integration tests, 1 doc-test; about 3 seconds of test time in a debug
  build.
- Generator properties (`tests/generate.rs`): 300 seeds verify, run to an
  `i64` within the bound, and cover every counter; 19 switches each
  checked off over 60 seeds; sizes from 1 instruction to 3 × 3000.
- LLVM oracle, quick: 54 programs agree at `-O0` and at `-O2`, under a
  second.
- LLVM oracle, slow (`-- --ignored`): 4240 programs (2000 default,
  2000 tiny, 200 of 6 × 400, 40 of 3 × 3000) agree at `-O0` and at `-O2`;
  54 seconds. No disagreement was ever attributed to LLVM.
- Disagreements found while writing it: none in the interpreter. The
  oracle's power was checked by breaking the interpreter on purpose:
  `ashr` as `lshr`, `srem` with the divisor's sign, `usub.sat` wrapping,
  `frem` rounding to nearest were each caught by the quick batch. Two
  mutations were not caught by 54 programs (`fshr` by a multiple of the
  width returning the wrong operand; `uitofp` to `float` rounding twice):
  both need a rare operand, and both have direct tests.
- Robustness: 1000 random unguarded programs end in 20 different ways
  (result, 15 traps, the three limits, unsupported); none panics, none is
  `Invalid`.
- Throughput, release build: the generator emits an instruction in about
  0.3 µs (3 to 4 million a second); the interpreter takes about 53 ns a
  step (19 million a second); a program of 4 functions × 2000 instructions
  (8400 instructions, 8200 steps) runs in 0.43 ms, a default one (430
  instructions, 1000 steps) in 54 µs, set-up included. Debug build: about
  2.5 µs an instruction and 0.35 µs a step.
