## What `llc` does, checked

- **`cf-protection-branch`, `cf-protection-return`.** `llc` 19 and 22
  with the flag `i32 0` write the same as with `i32 1` (`endbr64` and
  the IBT bit; the shadow-stack bit); without the flag, neither.
  `hod_ir` now reads both by presence; `module:cf-protection-branch`
  stays `todo(T-X64)`. `emit_llc.rs` has a `cf-protection-return` 0
  case.
- **`//` in x86-64 assembly.** `llvm-mc` 19 and 22 assemble `nop // x`
  and `movl $1, %eax // x y z` as the instruction alone, and `llc`
  accepts an inline template and module assembly with it: `//` is a
  comment on x86-64 as on AArch64. `hod_ir` treated it as text; it now
  reads it as a comment, and `emit_asm.rs`'s comments case runs on
  x86-64.
- **The constraint letter `A`.** `llc` 19 and 22 refuse `a`, `b`, `c`,
  `d`, `S`, `D` ("couldn't allocate input reg") but read `A`: `=A` of
  `i64` after `rdtsc` is `rax` alone, of `i128` `rdx:rax`; an input `A`
  is moved to `rax` (`rdx:rax`); a tied `=A,0` is a copy. hod's
  inline-assembly path lowers only empty templates, so `A` stays
  `x64:inline-asm-constraint` (empty template) and `rdtsc` stays
  `x64:inline-asm`; `the_constraint_letter_a_stays_refused` pins both.
  WP-128's record listed `A` among the letters `llc` refuses.
- **`ubsantrap`.** `67 0F B9 00` for kind 0, `67 0F B9 40 kk` up to
  127, `67 0F B9 80 kk 00 00 00` above, in `llc` 19 and 22 alike.
- **16 bytes without `cx16`.** `llc`'s calls and order numbers as
  above; its `atomicrmw max` loop reads the cell with two plain `mov`s
  first and passes the failure ordering `acquire` for `acq_rel`.

## Differences from `llc`, deliberate

- `half` `atomicrmw fmax`/`fmin`: when both operands are NaN, or zeros
  of different signs, hod and `llc` return different operands; the
  language reference allows either. The tests leave those cases out.
- The `half` conversion inside the loop quiets a signaling NaN, as
  libgcc's `__extendhfsf2` does, so the result is the one `llc`'s
  library calls give.
