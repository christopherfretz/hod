# WP-007 — hod_ll: the lexer and the module-level parser

Landed: `spec/ll.md` §1 to §10 as far as the module level goes: the lexer,
the index scan and the skipper, every top-level entity of LLVM 19 to 22
text built into a `hod_ir::Module`, the tables a body parser needs
(`ModuleText`), errors and limits. Not here: the instructions of function
bodies (WP-008; bodies are found and stepped over), debug nodes (metadata
is indexed and `debug-info` recorded), a printer (WP-006), the command
line (WP-043).

## What it did

`crates/hod_ll`, all new; `std`, `hod_ir` and, for tests, `hod_testutil`:

| module | contents |
|---|---|
| `lexer` | `Lexer`, `Tok`, `Token`, `unescape` (§2) |
| `skip` | stepping over a bracketed group eight bytes at a time (§4.2) |
| `index` | the index scan: every top-level entity's kind, name and extent (§4.1) |
| `parser` | the phases (§4.3), the token cursor, the nesting counter, the notes of unsupported constructs, the end checks |
| `types` | types, named types and the order they are resolved in (§5.1, §5.2) |
| `consts`, `float` | constants, floating-point literals, constant expressions, `blockaddress` (§5.3 to §5.5) |
| `attrs` | parameter, return and function attributes, attribute groups, calling conventions, the branch-protection upgrade (§5.6, §7.3) |
| `globals` | variables, numbered globals, functions, aliases, IFUNCs, COMDATs, the special arrays (§5.7 to §5.9) |
| `meta` | the metadata index, named metadata, module flags, linker options, dependent libraries (§7) |
| `names` | an open-addressed map from name spans to numbers, without copies |
| `error` | `LlError`, `LlErrorKind` (§8) |
| `lib` | `parse_module`, `scan_only`, `ParseOptions`, `ParsedModule`, `ModuleText`, `FunctionText`, `AttrGroup`, `Span`, `limits` |

Tests, 39 in six binaries, about 35 s of wall time unoptimized:
17 unit tests; `tests/differential` (9: acceptance, objects against
`llc`, canonical text against `llvm-as | llvm-dis`, module flags against
clang options, the body parser interface); `tests/syntax` (6: a table of
493 snippets with verdict, error kind, line and column, each run through
`llvm-as` 19 and 22); `tests/robustness` (4); `tests/perf` (3, printed).
`spec/ll.md` §10 maps them to sections.

Evidence from the last run (clang and LLVM 19 and 22, both targets):

- The corpus is 62 modules, 28.5 MiB, with 20,032 function bodies
  (25.6 MiB of body text). Everything `llvm-as` accepts in it parses, as
  written and as `llvm-dis` of the same and of the newest LLVM prints it.
- Against `llc`'s objects, 58 modules: 3,562 variables whose 87,760 bytes
  and 2,744 relocations equal `ConstPool::flatten` of what was parsed;
  10,146 functions, 176 aliases; every symbol's binding, visibility,
  section, COMDAT, alignment and size. 32 variables are replaced by GOT
  entries in `llc`'s object and one initializer has no image
  (`labels.relative`); both are named in the test.
- Against canonical text: 11,040 function headers, field by field.
- The syntax table: 493 rows; 43 are named differences from `llvm-as`;
  of the 385 diagnostics both give, 381 are on the same line.
- Robustness: every prefix of seven hand-written files, 1,500 seeded
  mutations of each, 192 variants of each of four clang modules, and 55
  inputs built to be deep, long or repetitive; none panics and each
  returns well inside a second.

Measured (`spec/ll.md` §9; optimized, shared host): the module-level
parse of clang 22's 3.65 MiB `-O0` text of `tests/data/stl.cpp` takes
4.4 ms (827 MiB/s), of the 9.68 MiB `-g` text 10.9 ms (892 MiB/s);
bodies are stepped over at 4.9 to 6.1 GiB/s; the lexer alone runs at 555
to 652 MiB/s; peak memory beyond the text is 1.3 and 3.3 MiB. `llvm-as`
takes 103 and 298 ms on the same texts, with the bodies parsed, the
module verified and bitcode written.

## Decisions where the brief and `spec/ir.md` were silent

All are in `spec/ll.md`; this is the list of what was open.

- **Two steps, index then phases** (§4), instead of one pass with
  forward-reference patching. Measured: lexing every token of the file
  once costs more than the whole two-step parse (5.6 ms against 4.4 ms
  on the 3.65 MiB text), because three quarters of clang's text is
  bodies and the scan does not lex them.
- **The skipper counts one bracket pair** and knows three regions where
  brackets do not count (strings and quoted names, `;` comments,
  `/* */` comments). It is exact, not a heuristic: the differential test
  compares every body span with a line scan of canonical text, and the
  unit test compares every alignment with a byte loop.
- **One dialect, the union of LLVM 19 to 22**, no version switch (§3.2).
  The syntax table runs every row through both `llvm-as` versions, so a
  row accepted by one of them is visible as such.
- **`ParsedModule { module, text }`** with the text side read-only and
  `Sync` (§6): a body parser can share both, or keep `&mut Module` while
  readers hold `&ModuleText`. A test reads bodies from four threads
  while the main thread adds to the module.
- **Parameter names are not kept** at the module level; a body parser
  reads them from `FunctionText::params`. Keeping them would cost an
  allocation per parameter for every function, including declarations
  that are never called.
- **`BlockId` of a `blockaddress` is the block's position in the text**
  (§5.5), found by counting terminator words before the label. It needs
  no body parse, and it fixes the numbering a body parser must use.
- **Numbered globals that are not local are named `__unnamed_K`** in
  file order and recorded (§5.7): LLVM numbers them in emission order,
  which the parser cannot know.
- **Named types are resolved in dependency order by an iterative walk**
  (§5.2). The first version recursed into a forward-referenced type and
  hit the nesting limit at about 100 nested named structs, while clang
  and `llvm-dis` print the outer type first as a rule.
- **The later of two definitions of an attribute group is the group**,
  as in LLVM (checked with `llvm-as | llvm-dis` 19 and 22); the first
  version merged them.
- **Floating-point literals follow LLVM's rules exactly** (§5.4),
  including the refusal of `float 0.1` and the normalization of
  `x86_fp80` patterns that are not values.
- **`ppc_fp128` is read as `fp128`** and recorded, so that a module
  naming the type in a declaration still parses; the price is that
  `fp128` accepts a `0xM` literal.
- **The AArch64 branch-protection upgrade is always applied** (§7.3):
  one text means one thing whichever LLVM wrote it, and the canonical
  text of the newest LLVM is then the oracle.
- **Limits** (§8): nesting 200, far above anything in the corpus and far
  below what a thread's stack holds; decimal integer literals of at most
  65,536 digits.
- **Errors carry kind, offset, line and column**; line and column are
  computed once, when an error leaves the crate.

## Surprises from LLVM

Lexer and parser:

- `%1x` is `%1` and `x`; `i1x` is `i1` and `x`; `cc10` is `cc` and `10`;
  `1e40` is not a floating-point literal; a zero byte in the file is
  white space.
- A string cannot contain a `"` in any form; the first one ends it.
- An unknown word where a function attribute may stand ends the header,
  and the error is "expected top-level entity" at that word.
- Numbered globals must ascend through the file; numbered types and
  metadata nodes may come in any order.
- `%U = type %T` with `%T` a struct leaves `%U` undefined. `@"" = …` is
  a global without a name.
- LLVM 19 and 22 still read `i32*` and `T addrspace(N)*`, including
  `%T = type { %T* }` and `{ [2 x %T]* }`; LLVM 22 refuses
  `{ void (%T)* }`.
- LLVM 19 accepts `%T = type { %T }` and an initializer of an opaque
  type; LLVM 22 refuses both.
- `mul` is a constant expression in LLVM 19 only; `shl` in neither.
  `x86_mmx` is a type in LLVM 19 only.
- `/* */` comments, `ptrtoaddr`, `captures`, `dead_on_return`,
  `nodivergencesource`, `sanitize_realtime`,
  `sanitize_realtime_blocking`, `sanitize_alloc_token` and
  `sanitize_type` are LLVM 22 only.
- An empty attribute group is refused; `attributes #4294967296` is
  accepted; a second `attributes #N` replaces the first.
- `, align N` and `, section "…"` may be repeated on a variable.
- `dllimport` without `external` requires an initializer. A bare
  `comdat` still needs `$name = comdat …`.
- `cc 1024` and a PIC level of 7 are accepted.
- `dereferenceable(0)`, `allockind("bogus")` and `memory(bogus)` are
  refused by the parser, not the verifier.
- `!named = !{i32 1}` is refused: a named node holds nodes only.
- A `blockaddress` of a numbered block is read only before the
  function's definition.
- A struct index of `getelementptr` must be `i32`.
- A wrong signature on `@llvm.memcpy.p0.p0.i64` is a verifier error in
  LLVM 19 and accepted by LLVM 22.

Tools and code generation, met while building the oracles:

- `llc` crashes on a `zeroinitializer` element in `@llvm.global_dtors`,
  and on an `!llvm.linker.options` entry without exactly two operands; `llvm-as` 19
  crashes in the bitcode writer on a malformed `^N = gv:` summary.
- LLVM 22's verifier refuses the old form of TBAA in
  `!llvm.errno.tbaa`.
- A constructor priority above 65535 is clamped. `coldcc` definitions
  are not supported by `llc` on AArch64.
- A common symbol of size 0 is emitted with size 1. An undefined
  thread-local symbol has type `STT_TLS`.
- LLVM 19 aligns an `i1` global to 1 on AArch64; LLVM 20 and later to 4.
- A discardable `unnamed_addr` constant that holds only a symbol's
  address is replaced with a GOT entry (the relative-vtable
  `.rtti_proxy` variables).
- clang 22's `frame-pointer` module flag on AArch64 is 4 where clang
  19's was 1; `-mbranch-protection=standard` includes the guarded
  control stack; `-mcmodel=large` on x86-64 writes a large data
  threshold of 0.
- The branch-protection upgrade exists in LLVM 22's reader only, and
  for AArch64 only.
- clang and `llvm-dis` print a struct type before the types it holds.

## Gaps in `hod_ir` that were worked around

Nothing in `hod_ir` was changed. Where it had no place for something,
`hod_ll` does the following; each is a candidate for a later work
package.

- No `ppc_fp128`, `x86_amx` or `x86_mmx` type: read as `fp128`, a target
  extension type and `<1 x i64>`, each recorded.
- No `ptrauth` constant: the pointer operand stands in, recorded.
- No image for a difference of block addresses
  (`ConstPool::flatten` gives `UnsupportedInitializer`).
- No debug nodes yet, so `FunctionDesc::subprogram` is `None`; the
  `!dbg` attachments are kept on the text side (`FunctionText::dbg`,
  `ModuleText::symbol_dbg`).
- An anonymous symbol must be local: other numbered globals are named
  `__unnamed_K`.
- A symbol's name may not be empty: `@"" = …` is an error.
- No place for attributes on a variable: recorded as
  `global-attributes`.
- The attribute table has no positions (function, parameter, return),
  so a dropped or rejected attribute in the wrong place is not refused.
- `CallConv` holds at most 1023 and has no keyword table for the x86
  conventions: `hod_ll::call_conv_keyword` has the whole list.
- The PIC level is 0 to 2.
- `fold_gep` takes a struct index of any integer type; no check that a
  `dso_local_equivalent` names a function.
- Types are immutable once interned, so a named type that reaches
  itself through an old-style pointer other than `%T*` cannot be
  defined (§3.2).
- Struct names and the parameters of target extension types are not
  kept.
- Variables in the `llvm.metadata` section are delivered as ordinary
  variables; no consumer yet knows not to emit them.
- The data layout is LLVM 22's: an `i1` global on AArch64 has `i8`'s
  alignment, 4, where LLVM 19 gave 1.

## What is left

- WP-008: function bodies, on `ModuleText` (§6). It must number blocks
  in text order, read parameter names from `FunctionText::params`, and
  record a group's `rejected` names when it applies the group to a call.
- Debug nodes: `MetadataIndex` gives every node's kind and span; nothing
  reads the fields of a specialized node, and `debug-info` is recorded
  for every module compiled with `-g`.
- `blockaddress` of a block without a label in the text
  (`blockaddress:unlabelled-block`): needs the body parser's numbering
  of unnamed values, so it can be closed in WP-008.
- The 43 named differences from `llvm-as` in `tests/syntax/rows.rs`;
  most are the verifier's rules (§3.5) and `hod_ir`'s limits above.
- `MAX_NESTING` of 200 applies to aggregate constants: a constant
  nested deeper than that (LLVM has no limit of its own) is refused
  with `Limit`. Nothing in the corpus comes near it.
- The driver that parses bodies in parallel and the command line are
  WP-043; `hod_ll` is not yet called by anything but its tests.
