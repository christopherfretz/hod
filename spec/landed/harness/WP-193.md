## Coroutines through kiln with hod

Every coroutine module kiln offers, built with `KILN_BACKEND=hod
KILN_HOD=<this hod> KILN_HOD_STRICT=1` and run against kiln with `llc`
(the control, the same command without the variables), on both targets
(x86-64 under `qemu-x86_64`). Which back end built each module is read
from `KILN_STATS_LOG` (`backend`, `hod_reason`, `triggers`): a decline
(hod's status 2) falls back to `opt` + `llc` even under
`KILN_HOD_STRICT=1`, so a passing program alone does not show that hod
built it.

- **The corpora.** The kiln entries whose test uses coroutines (the
  source names `co_await`, `co_yield`, `co_return`, `coroutine_handle`,
  `<coroutine>` or `<generator>`, or the captured module has a
  `.resume` clone): 54 entries per target, 50 of them modules with the
  `coro` trigger (25 tests, LLVM 22 and 19; the other 4 only name a
  keyword). Each rebuilt from its manifest row's producer arguments in
  a mirror of kiln's tree: all 50 built by hod, none declined or
  failed, and every program, hod's and the control's, behaves as the
  entry says, on both targets.
- **kiln's own harness** (`cargo xtask test --no-oracle`, AArch64) on
  the 28 coroutine run tests, which adds the two `env:` tests the
  corpus skips: 25 pass with hod and with `llc`, 3 skipped (ASan, no
  sanitizer runtime on this machine); its 23 coroutine modules all
  built by hod.
- **libc++** (`llvmorg-22.1.8`, kiln's `cargo xtask libcxx`):
  `std/language.support/support.coroutines` (25 tests; the only libc++
  tests with a coroutine body or `<coroutine>`, with the
  `coroutine.version` test and a `.verify` test), natively and for
  x86-64 under qemu (`scripts/libcxx-x64-kiln.sh`): 25 of 25 pass with
  hod and with `llc` on both; 10 coroutine modules and 15 that use only
  handles, all built by hod.
- **A stack-protected coroutine** (`-fstack-protector`, `-strong`,
  `-all`, both targets): declined by name, `ssp:coroutine` (WP-183),
  and built by the fallback; the program is right. Before WP-183 the
  name was `attr:ssp*`. The reproducer is kept with the findings.

No refusal otherwise, and no program that passes with `llc` and fails
with hod.

## What the procedure missed

1. **A `-g` entry names the preparing branch's directory.** kiln++
   writes the absolute path of its own resource directory
   (`<P>/kiln-src/resource/include/...`) into the `!DIFile` of a
   resource header, which `-fdebug-prefix-map` of the capture's mirror
   does not cover: the corpus is not location-independent for its `-g`
   entries (the current corpus names WP-165's build directory, the new
   one this package's). Behaviour is unaffected; every move reports the
   two entries as changed. A capture that runs kiln++ from the mirror's
   `resource` (or maps the kiln checkout) would fix it.
2. **Coroutine entries are post-`opt`.** A capture runs kiln with its
   default back end, so its coroutine entries are bitcode after
   CoroSplit, never the pre-`opt` module kiln now gives hod. The census
   above rebuilds them through kiln++; the corpus alone cannot show
   what hod does with kiln's coroutines.
3. **kiln's `xtask libcxx` from a clone** finds the libc++ checkout and
   tree only under the clone's own `.toolchain/`; links to the
   workspace kiln's `.toolchain/libcxx-22-root` and
   `libcxx-llvmorg-22.1.8` make it work.
