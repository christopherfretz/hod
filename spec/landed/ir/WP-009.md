Landed: `spec/ir.md` §8 (rewritten from a stub into §8.1 to §8.11) and
`docs/status/support.md`, generated from the matrix. Not here: flipping
any row to supported beyond the handful the matrix already marks (each

## Decisions where the spec was silent (conservative: reject)

- `debug:*` rows are not-implemented until the debug-information track.
  A frontend that always emits the `Dwarf Version` / `Debug Info Version`
  module flags is therefore refused wholesale at `debug:module-flags`.
- Under `Support::shipped` every body is refused first at `cc:ccc`, every
  module with a definition at `global:function-definition` /
  `global:variable-definition`. A module of external declarations only
  is accepted.
- `const-expr:*` (19 rows) are rejected by design on both targets.
- `Const::Addr` of a thread-local symbol is `tls:address-in-constant`
  everywhere, even as the argument of `llvm.threadlocal.address`.
- `returns_twice` is checked on the body's function, the call and the
  direct callee.
- A declaration's attributes and a callee declaration's parameter
  attributes are not consulted: the call site's own type and attributes
  govern. A direct call through another function type than the callee's
  is not an error.
- Function-level checks are made in the body pass, so a driver must
  classify every body it compiles.
- Vectors are one class; element kinds, aggregate member types, global
  value types and pointee types are not examined. Results of `cmpxchg`,
  `landingpad` and `*.with.overflow` are `aggregate`.
- `Intrinsic::Other(name)` is always refused, as `intrinsic:<name>`.
- `ssp*`, `target-cpu`, `target-features`: not-implemented. Sanitizers
  and branch protection: unplanned or rejected.
- `invalid:initializer` and the personality case of `invalid:symbol` are
  defensive; current builders cannot produce them.
- The constant walk has no memo and a depth limit of 64
  (`limit:constant-nesting`).
- Malformed input goes to the fallback or not by `spec/cli.md`'s rule,
  not by this crate's.

## Cost: target not met

`cargo run --release -p hod_ir --example classify_throughput`, aarch64,
host under heavy load (load average about 20 on 24 cores), so only the
ratio to "build" in the same run means anything:

| | before the short way | final |
|---|---|---|
| build one instruction | 15.2 ns | 15.1 ns |
| classify, accepted, one 1M-instruction body | 9.2 ns/inst | 8.1 ns/inst |
| classify, accepted, 5000 bodies of 197 | 9.9 ns/inst | 8.7 ns/inst |
| refuse a body at its first reason | 41 ns/body | 18.7 ns/body |
| module pass, accepted | 6.9 ns/symbol | 7.4 ns/symbol |
| census, body | 150 ns/inst | 154 ns/inst |
| census, module | 68 ns/symbol | 69 ns/symbol |

Classifying an accepted body costs about half of building it, not the
small fraction the brief asked for. Per instruction kind (accepted):
load about 4 ns, store 5-6, add/icmp/ptradd 6-7, a plain direct call
about 23, br 4. For scale, `body_throughput` in the same conditions
reports verify at 26.5 and a plain read through the public API at 4.7
ns/instruction, so the walk is within about 2x of merely reading every
operand once. Not investigated: whether `Body::inst` + `Inst::operands`
and `class_code` inline into `Walker::body` in release, and whether the
call path (`Inst::call`, `CallSite::intrinsic`, `Symbol::kind` in
`returns_twice`) can be made cheaper. That the accept path does not
allocate is by construction, not asserted by a test (it would need an
allocator shim, and `unsafe` is forbidden).

## Open questions

- Is half the build cost acceptable for now, or should a follow-up
  package chase the cost target (the call path first)?
- Should `debug:module-flags` stay a module-wide refusal until the debug
  track lands, given every frontend that emits debug information carries those flags?
