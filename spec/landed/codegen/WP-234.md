# WP-234: `getelementptr` on vectors of pointers

Spec: `spec/codegen.md` §5.5 "Memory (WP-036)" (AArch64) and §5.6.4
"Memory (WP-123)" (x86-64), "Vector `getelementptr`"; `hod_ir`'s
`ConstPool::fold_gep`.

kiln `-O2` modules of libc++ tests (the `flat_multimap` tests) hold a
`getelementptr` whose base is `<2 x ptr> zeroinitializer` and whose
index is a constant `<2 x i64>`; strict hod refused them as
`x64:ptradd-vector` / `a64:ptradd-vector`. `llc` builds them.

## What was built

- `crates/hod_x64/src/mem.rs` `ptr_add_vector` and
  `crates/hod_a64/src/mem.rs` `ptr_add_vector`: a `ptradd` whose result
  is `<N x ptr>` is lowered one lane at a time, with scalar arithmetic.
  Every vector operand's image is found first (a `Mem` vector's slot,
  or an `Fpr` vector's register stored into a fresh 16-byte frame slot
  and given back at once); a scalar operand is splatted (put again for
  each lane); a scalar constant index, and a zero-like vector one, is
  folded into the constant offset. For each lane: the base's lane plus
  the offset, then each index's lane sign-extended from its width (the
  low 64 bits of an `i128` lane or scalar: truncation) and scaled as a
  scalar `ptradd`'s index and added; the sum stored as the result's
  lane. x86-64 computes in `rcx`/`rdx`, which hold no values; AArch64
  takes two pool temporaries per lane and gives them back after it, so
  nothing is pinned across lanes under `Stress::ALL`. The result's image
  is its slot (`Mem`), or a frame slot loaded into its register at the
  end (`Fpr`). `N` is any lane count whose lanes are addressable (1 to
  256); `inbounds`, `nuw` and `nusw` change nothing.
- `crates/hod_ir/src/fold.rs` `fold_gep_lanes`: a constant
  `getelementptr` with a fixed vector operand folds lane by lane into a
  vector of the lanes' addresses (`Addr`, `AddrOfInt`, `null`), in an
  initializer or as an operand; before, it stayed an `Expr` and both
  targets refused it as `const-expr:getelementptr`.
- `crates/hod_a64/src/vector.rs` `spill_at`: an `Fpr` vector stored at
  a given frame place (what `spill` does into a scratch image).
- The names `x64:ptradd-vector` and `a64:ptradd-vector` are gone from
  the code (nothing is refused under them).

## Evidence

- `crates/hod_x64/tests/vector_gep.rs` and
  `crates/hod_a64/tests/vector_gep.rs` `vector_geps_run_as_c_computes_them`
  (one module and one C driver, `crates/hod_x64/tests/data/vector_gep/`):
  17 functions (16 called from C, one internal callee) and two
  initializers, compiled by hod plain and under `Stress::ALL` and by
  `llc` 22 and 19 (four objects per target), linked by bfd, lld and
  mold, dynamic and static (24 programs per target, 48 in all), and
  run; the driver computes every expected address itself. Covered: a
  vector base with a scalar index, a scalar base with a vector index, a
  vector base with vector indices, five indices at once (array stride
  120, struct stride 24, a struct field, an element stride), a splat
  struct field index, element sizes 1, 2, 3, 4, 8, 24, 120 and 3e9,
  indices of 8, 16, 32, 33, 64 and 128 bits (negative values, and high
  bits that truncation drops), 1, 2, 3, 4 and 8 lanes, a constant
  offset beyond 32 bits, the result stored, returned, passed by value to
  and returned from an internal function, and read by `extractelement`;
  constant operands (a global as the scalar base, a constant vector
  index with a variable base, a constant vector base of a global and
  `null` with a variable or constant index); the two reduced census
  functions; a constant vector `getelementptr` with a vector base as an
  operand and two with a scalar base in initializers.
- What `llc` cannot build: the two initializers as constant vector
  `getelementptr`s (`initializers.ll`). `llc` 22 at `-O0` does not
  finish on `@cv` on x86-64 (more than 60 s) and fails on both with
  "Unknown ELF relocation type" on AArch64; a vector base in an
  initializer it refuses outright ("unsupported expression in static
  initializer"; that form is in `hod_ir`'s unit test only). hod builds
  `initializers.ll`; the `llc` objects are built from
  `initializers_by_lane.ll`, the same addresses written one lane at a
  time, so the driver checks the same values against every object.
  Every function builds under `llc` 22 and 19 on both targets.
- The first execution of the lowering found no defect: hod plain and
  stressed agree with the driver on both targets as `llc` does.
- The same files' `the_reduced_census_modules_compile`: both reduced
  modules (`.build/findings/dbg-O2/ptradd-vector/{x64,a64}`) compile,
  plain and stressed; `what_stays_refused_is_refused_by_name`.
- `crates/hod_ir/src/fold.rs` `vector_gep_folds_lane_by_lane`, and
  `gep_without_normal_form_is_an_expr` (a lane that does not fold keeps
  the `Expr`).

## What stays refused

- An index vector whose lanes are not 8, 16, 32, 64 or 128 bits
  (`<N x i33>`): `x64:vector-odd-element`, `a64:vector-odd-element`.
- `<N x i1>` indices: `x64:vector-mask` / `a64:vector-mask` (`mask-wide`
  beyond 64).
- More than 256 lanes: `x64:vector-length`, `a64:vector-length`.
- Scalable vectors stay `hod_ir`'s `getelementptr:scalable`.
- A constant vector `getelementptr` some lane of which does not fold
  (an unknown lane, a base that is not a symbol plus an offset) stays
  `const-expr:getelementptr`.

## Notes

- `hod_interp` still refuses a vector `getelementptr` as
  `inst:ptradd-vector` (the interpreter is not part of this package).
  No generator emits a vector `getelementptr`, so no differential test
  feeds it one; `hod_interp`'s tests pass unchanged.
- The executed tests are portable to the hosted CI: the module carries
  no attributes and no target features, the lowering is integer-only,
  and the driver is plain C (GNU `vector_size` and `__int128`).
