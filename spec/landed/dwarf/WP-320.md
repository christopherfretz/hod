# WP-320 — the debug-node decodes that remained (`hod_dwarf`, `hod_ir`, `hod_cg`)

Item 1 of WP-318's ranked list (`spec/landed/dwarf/WP-318.md`, "What
remains"; WP-311's "What remains" 1 and 2): the full decodes of
`DebugInfo::node` left after WP-311, and a question left by WP-312
(`spec/landed/object/WP-312.md`, Evidence): why the bench gate reads the
small inputs' peak memory higher after it. Three commits:
`crates/hod_dwarf/src/` (`die.rs`, `types.rs`, `func.rs`, `spec.rs`),
`crates/hod_ir/src/verify.rs`, `crates/hod_cg/src/emit/lines.rs`. No
change to emitted bytes, refusals or error messages; no rule of
`spec/ir.md` or `spec/dwarf.md` changes (views and ids are used as
WP-311 and WP-318 defined them). Safe Rust, no new dependency.

## Method

As WP-311 and WP-318: Callgrind instruction counts, `HOD_THREADS=1`, the
release profile, `hod --strict -O0 -filetype=obj -relocation-model=pic
[-mtriple=x86_64-unknown-linux-gnu] -o out.o in.ll` on the bench inputs
(`cargo xtask bench --generate`, and `--target x86_64`), both targets, as
the counts gate runs hod. Base 9a365e99. Self cost per function summed
over the files its inlined code comes from; calls of `DebugInfo::node`
summed by the source file and line of the calling instruction (callgrind
`--dump-instr=yes`, the `fi=` file of the call's cost line).

## Part A: the small inputs' peak memory after WP-312

The gate's memory is the peak resident set (`/usr/bin/time` `%M`,
`xtask/src/bench/measure.rs`), not the heap. On aarch64, nine runs per
input, 8e441c4b (before WP-312) against 9a365e99, the upper medians in
KiB: small-c 5352 -> 5432, interp 5732 -> 5840, interp-g 6116 -> 6196,
small-cxx-g 5728 -> 5864; the spread of one binary over nine runs is
200 to 600 KiB, which is the rest of what the gate saw.

- The heap is not it: `valgrind --tool=dhat` on interp-g, peak 1,908,720
  bytes in 244 blocks for both binaries (at the end 8.7 KB before, 323 KB
  after: the written object and module that are not freed, after the
  peak).
- Read at the moment hod opens its output (a FIFO nobody reads yet, so
  hod blocks there with the object prepared; `/proc/<pid>/smaps`), per
  mapping, KiB, before -> after: the `hod` binary's executable segment
  3776 -> 3932 (interp-g), 3532 -> 3672 (small-c), 3840 -> 4000
  (small-cxx-g); the heap 628 -> 584, 76 -> 72, 256 -> 232; libc and the
  rest unchanged. In `/proc/<pid>/status` terms: RssFile 5092 -> 5240,
  RssAnon 1092 -> 1060 (interp-g).

So the rise is 140 to 160 KiB more of the binary's own pages resident
(code and read-only data faulted in, rounded up by the kernel's
fault-around), and the heap is 4 to 44 KiB lower. The `.text` of the
binary grew by 20 KB (4,612,808 -> 4,632,920 bytes); under fat LTO the
functions a small input runs are laid out differently, and a few more
fault-around blocks are touched. The candidates the question named are
not it: the module kept with the object (`aa97f5da`) does not raise the
heap's peak (dhat equal), and the 64 KiB sink buffer is touched only as
far as the object is long (3.7 to 14 KB on these inputs). Nothing was
changed: there is no data to drop, and the binary's layout is not
something a local change controls.

1. **Member function attributes from the decoded node; no decode for
   parameters** (1d2204e6): `method_attrs` takes the decoded
   `DiSubprogram`: `type_die` has it already, `finish_types` decodes it
   once. `Writer::die` dispatches a formal parameter, unspecified
   parameters and the array index type to `type_die` before the decode
   (their writer reads the type's flags by view or nothing): 15 100
   decodes fewer there. WP-311 had put `method_attrs` on views; for
   eight fields of one node the whole decode is the cheaper read.
2. **One field for a record's scope and a scope's file** (ca084e0a):
   the verifier's check of a `#dbg_*` record reads its variable's or
   label's `scope` by view (the same two messages for an id that is not
   a node of that kind); `DebugLines::file_of` reads a local scope's
   `file` by view, by the scope's kind. Pays most on tiny-functions-g
   (−0.4%: a record per parameter).
3. **A definition decoded once; its declaration by view** (1f71dcfa):
   `seal_definition` takes the subprogram its caller
   (`finishSubprogramDefinitions`' loop) decoded; `subprogram_die`
   reads the declaration's `file`, `line` and `linkageName` by view.

## The SipHash table

The 14 M of SipHash (`DefaultHasher`, `<DefaultHasher as Hasher>::write`
9.3 M plus `hash_one` 5.1 M self on stl-heavy-g x86-64) is
`hod_cg::emit::section::Sections::by_name`
(`crates/hod_cg/src/emit/section.rs:225`, `HashMap<Box<[u8]>, ByName>`):
the calling instructions of the two `hash_one` instances that call
SipHash are in `Sections::entry` and `Sections::find`, and in the
table's rehash; together about 13 of the 14 M. `record`
(`section.rs:298-301`) hashes a name up to three times
(`contains_key`, `insert`, `get_mut`). The table is never iterated, so
its order cannot reach the output, but it is keyed by section names
(bytes from the input, comdat names of up to hundreds of bytes), not by
small integers or interned ids: outside what this package may change.
Not touched.

## What remains, ranked

1. **Member functions decoded three times**: at `create`, by
   `finish_types` (now a whole decode, 7 900 on stl-heavy-g) and by
   `Writer::die`. `MethodAttrs` but `cont` (which needs the containing
   types of `finish_types`) could be computed at `create` and kept,
   sorted by DIE, for both later readers: about 1.3 M of decodes and most
   of `method_attrs`' 2.4 M.
2. `Sections::by_name` (above): one hash per request instead of up to
   three, or a hasher that is not SipHash (needs a decision on keys
   from the input), about 13 M on stl-heavy-g.
3. The decodes that read most of their node: `constructing_node`
   (15 600, kept by WP-308), `create` (15 500), `Writer::die` for types,
   subprograms and globals (20 500), `func.rs:606` and `local_die`
   (8 700, 8 500), `template_param_die` (5 900). A cheaper whole decode
   would pay at all of them (the kind's match, one bounds check per
   field, the string lookups when a writer reads the id anyway);
   WP-318's decode with ids (`strx_of` reads the name again) is part of
   it.
4. Below 0.05% each: `is_unsigned` (1 900), `unit_of` (2 600), the
   lexical block walk `func.rs:385` (2 800).
