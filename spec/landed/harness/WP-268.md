# WP-268 — the hosted abseil job on AArch64: crash dumps and a phase's leftovers

Landed: every phase that runs a project's programs (configure, build,
test, and `oss-report.py rerun`) runs in a session of its own. Its core
size limit is 1 byte, and what it leaves running is killed and
reported. `oss-run.sh` logs `core_pattern` and the inherited core limit
once per run, and the load, available memory and free disk at the
start of each build (`spec/harness.md` "Real projects": "No core
dumps", "A phase's leftovers"). No change under `crates/`.

## The failure

Hosted run 43709093462 of `.github/workflows/oss.yml`: 30 of 32 project
jobs green; `oss aarch64 abseil` failed twice. In attempt 1 the lane's
step failed about 73 minutes in, and GitHub kept no log. Attempt 2 was
cancelled ("context canceled") 100 minutes in, with a 300-minute job
limit. In its log, O0 llc took 3 s to configure, 3m40 to build and
23m30 for the tests (rc 8). O0 hod took 6m40 to configure, 3m40 to
build and 17 min for the tests. O0 strict printed its first line and
nothing more for 42 minutes.

## What it was not

The supervisor's hypothesis was test programs (or their children) that
outlive ctest and starve the 4-core runner. It was checked on this host
(AArch64, native, the job's target) with the lane's scripts: abseil O0
`llc`, the lanes' jobserver pool, ctest at 4. The tests took 178 s and
gave rc 8: `absl_raw_hash_set_test` failed, and no test timed out. When
ctest returned, no process whose executable or arguments named the
build tree was alive (two samples 10 s apart). The hosted timings
refute it too: the build phase is not slower after a test phase. On
AArch64 `llc` and `hod` both built in 3m40. On x86-64 the build's wall
time is close to its CPU time: `llc` 1589 s wall / 1572 s CPU, `hod`
1804 / 1355.

## What the hosted data shows

Data: the x86-64 abseil job of the same run (green, 3h43): its log, and
its artifact's `test.log` and `compile.jsonl` for the six trees.

- Only configure is slow, and only after a test phase. cmake reports
  "Configuring done" in 2.2 s for the first build and 205 s for the
  second. The same kiln compile, `CMakeCXXCompilerId.cpp`, took 0.08 s
  wall / 0.08 s CPU in the first configure and 37 s / 8.9 s in the
  second, with 52-94 s per configure afterwards. A hundred times the
  CPU for the same work means a machine under memory or IO pressure,
  not a CPU taken by other processes. By the build phase, minutes
  later, it has passed.
- The tests that run death tests are 50 to 6000 times slower hosted
  than on this host. Hosted x86-64 O0 `llc` against local AArch64 O0
  `llc`:

| test | here (s) | hosted (s) |
|---|---|---|
| absl_check_test | 5.7 | 701 |
| absl_random_uniform_real_distribution_test | 1.2 | 266 |
| absl_cord_rep_btree_test | 3.6 | 246 |
| absl_random_uniform_int_distribution_test | 0.55 | 171 |
| absl_random_mock_distributions_test | 0.05 | 127 |
| absl_statusor_test | 0.03 | 95 |
| absl_substitute_test | 0.01 | 91 |
| absl_span_test | 0.01 | 61 |

  Test time in all: 430 s here, 4120 s hosted. A test without death
  tests is 1 to 7 times slower (`absl_btree_test` 93 s / 641 s,
  `absl_mutex_test` 90 / 267).

**Shown:** no process outlives the control's tests on this host. On
the runner, the build phase runs at normal speed. Configure, right
after a test phase, needs a hundred times the CPU for the same compile.
The tests that run death tests are the ones that are 50 to 6000 times
slower. The kept hosted trees hold no `core` files.

**Inferred, not proven** (the working explanation): every death test's
crashing child is handed to a pipe dump handler on the runner's host.
This host has `ulimit -c` 0 and `core_pattern` `core`; neither the
runner's limits nor its `core_pattern` is in the job's log. With a pipe
`core_pattern` the kernel ignores the limit except for the value 1
("No core dumps" in the spec). The crashing process waits until its
dump is consumed. A handler that reads and stores each core (apport is
serialized by a lock and may store cores on the host's disk) leaves a
backlog that keeps the machine under pressure after the test phase. On
the AArch64 runner that plausibly ended with the runner's agent losing
its connection. The next hosted run tests this reading. Its log now
gives `core_pattern` and the core limit once per run, and the load,
available memory and free disk at the start of each build. The death
tests' times will show whether the 1-byte limit removed the cost.

## Changed

- `scripts/oss/oss-build.sh`: configure, build and test run through
  `phase` (below);
  the lane's line for a phase ends with `; N left running, killed:
  <names>` when it left any.
- `scripts/oss/projects.py run-phase`: runs the command as the leader of
  a new session, with `RLIMIT_CORE` set to (1, 1) before exec and with
  `HOD_OSS_PHASE_TAG` (unique per run) in its environment. At its limit it sends SIGTERM to the process group,
  SIGKILL 10 s later, and gives status 124, as `timeout(1)` did. When
  the leader exits, it is left unreaped while the sweep runs, so its
  session number cannot be reused. The sweep finds every live process
  in the session or carrying the tag, re-checks each one through a
  pidfd, sends SIGTERM, then SIGKILL after 10 s. It names each
  leftover in the phase's log and appends the phase to
  `leftovers.jsonl`. The phase's status is the leader's.
  `projects.py leftovers` prints the lane's summary;
  `report-json` writes `leftovers`.
- `scripts/oss/oss-report.py`: the status and census pages show `(N
  left running: names)` after a tree's test count, never as a verdict.
  `rerun` runs ctest through `run-phase`.
- `scripts/oss/oss-run.sh`: `oss-run: core_pattern <pattern>; core
  limit soft/hard (bytes) <s>/<h>` once, and `oss-run: <p> <fl> <m>
  (time; load a b c, N MB available, N GB free)` per build.
- `.github/workflows/oss.yml`: comment only. Parsed with PyYAML 6.0.2
  (the sdist's pure-Python `lib/`, not installed): the same structure
  as at the base commit.
- `scripts/oss/oss-report-selftest.py`: eight new checks, 51 in all.
  `run-phase` keeps a phase's status (3), kills and records a forked
  `sleep`, gives 124 at its limit, and sets the core limit to (1, 1); `report-json` carries
  `leftovers`; a control's leftovers change no verdict (`check` exits
  0) and the census shows them.

Not changed: the per-test limit. Abseil includes CTest, whose default
per-test limit (`DART_TESTING_TIMEOUT`) is 1500 s, and its slowest
hosted pass is 979 s (`absl_btree_test`, O0g strict), so no shorter
limit is safe. The installed cmake 3.31 has no `CTEST_TEST_TIMEOUT`
environment variable. The whole test phase is still bounded by the
row's `test_timeout` (1800 s for abseil), which now kills the whole
session.
