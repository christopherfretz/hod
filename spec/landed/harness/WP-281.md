# WP-281 — mortar in the link matrix

Landed: the mortar linker (`https://github.com/christopherfretz/mortar`),
built from one pinned commit, is the fifth linker of every linking test,
optional as wild is, on both targets from the AArch64 development
machine. What it refuses by name is recorded as REFUSED cells, checked
against the refusal's text. Results and findings: `docs/status/linkers.md`
"mortar".

## How mortar is found and pinned

- The pin: `hod_testutil::linkers::MORTAR_COMMIT`
  (`ea9b94f42743d6772d690a374b5bf976e415f812`), the one place in the
  repository; `MORTAR_SHORT` is its short form for notes.
- `find_mortar`: `HOD_MORTAR` (a path that is not a file panics; empty
  means `PATH` alone), then `.toolchain/mortar/<MORTAR_COMMIT>/mortar` in
  the checkout or any directory above it, then `mortar`, then
  `ld.mortar`, on `PATH`. The workspace's provisioning script is to build
  the commit there (`cargo build --release -p mortar`, mortar's own
  `rust-toolchain.toml` asks for 1.95.0, the workspace's Rust).
- Optional: `MORTAR_REQUIRED` is false, so a missing mortar is a note
  (`note: mortar ea9b94f not found ...`) even under `HOD_REQUIRE_TOOLS=1`,
  and the matrix runs without it.
- Selected as `ld` in a `-B` directory (no driver knows
  `-fuse-ld=mortar`), with no further flag: it keeps unused sections by
  default. Its `.comment` signature is `mortar <version>` (`signer`;
  `xtask`'s `signature`). The harness (`xtask`) finds it the same way
  (`Search::from_env` searches the found mortar's directory first), names
  it in `--linker`, `LINKER_NAMES` and the debugger layer's
  `LINKER_WORDS`, and gives it `-Wl,--threads=1`.

## Cells

Every test that iterates the matrix gets mortar's cells (the same
`Toolchain::linkers`, `linkers::present`, `hod_mc_x64`'s `linkers()`).
With mortar available, `cargo test` of `hod_testutil`, `hod_obj`,
`hod_a64`, `hod_x64`, `hod_mc_x64`, `hod_dwarf`, `hod_eh`, `hod_cg`, `hod`
and `hod_cli` under `HOD_REQUIRE_TOOLS=1`: before the two findings were
recorded, 1372 passed and 5 failed, all five mortar refusals (below); no
program linked by mortar misbehaved. After: all pass.

## Refused kinds

`linkers::REFUSALS` (linker, version, what, text, finding) is the one
table; `refusal(linker, flags)` and `input_refusal(linker, case)` find a
row, `check_refused` requires the link to fail with the row's text and
prints `REFUSED`; a link that succeeds, or fails otherwise, panics.
`Toolchain::refuses` / `refuses_input` run such a cell and the test skips
the rest of it; `Toolchain::link_ok` panics for a refused flag, so a new
cell that forgets to ask fails loudly. Verified: `-shared` ("unsupported
option: -shared") and `-r` ("unsupported option: -r") exit 1 for hod's
objects (`hod_obj` `refused_kinds_are_refused_by_name`, the shared-object
cells of the call, constaddr, TLS and EH tests, `hod_mc_x64`'s shared
mode, `hod_dwarf`'s `type_debugger`).

## Findings

Evidence under `.build/findings/wp-281/<finding>/` on the development
machine (hod's commit, `.ll`, hod's and `llc`'s objects, the link line,
mortar's stderr, GNU ld's and mold's results):

- `section-start-option`: `--section-start` is refused ("unsupported
  option: --section-start") for an executable; `llc`'s object likewise.
  Cells: the far layouts of both `large_code_model` tests.
- `compressed-debug-input`: inputs with `SHF_COMPRESSED` `.debug_*`
  sections are refused ("unsupported feature: SHF_COMPRESSED input
  sections"); `llc`'s object compressed by `llvm-objcopy` likewise.
  Cells: the zlib objects of `hod_a64`'s `compressed` tests (their plain
  objects link and run).

Neither is about hod's objects (both refuse `llc`'s too); hod's code
generation is unchanged.

## Hosted CI

Not added. It would take, per job (or once per architecture, cached by
the commit): a checkout of mortar at `MORTAR_COMMIT`, `cargo build
--release -p mortar` (about two minutes on the development machine),
and `HOD_MORTAR` exported for the later steps, as the wild step does.
