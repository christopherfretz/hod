# WP-020 — bitcode on the text path

Landed: `spec/cli.md` "Bitcode conversion" (new), and its "hod's own
options", "Environment", "Reasons", "Exit status" and "Coverage log"
(fields 9 and 10); `spec/harness.md` "shim" (the converter in `bin/llc`).

## What it did

- `crates/hod_cli/src/convert.rs`: runs `llvm-dis -o - -` on a bitcode
  module over two pipes and judges what comes back. Five named ways to
  fail (`bitcode-converter-unavailable`, `-killed`, `-failed`, `-stderr`,
  `-output`).
- `driver.rs`: `--bitcode-via=<llvm-dis>` / `HOD_BITCODE_VIA`. When
  `hod::compile` declines with `bitcode-input` and a converter is named,
  the module is converted and `compile` is called again with the text. A
  failed conversion is a decline like any other: the fallback in hybrid
  mode, exit status 1 otherwise.
- `coverage.rs`: two fields appended, conversion microseconds (9) and the
  fallback's exit status (10). The first eight are unchanged.
- `xtask/src/shim.rs`: the generated `bin/llc` also sets
  `HOD_BITCODE_VIA` to the installation's `llvm-dis`.
- `xtask/src/irdiff/engine.rs`, `read_coverage`: reads a line of eight
  fields or more.
- `kiln_e2e.rs`: three programs that reach hod as bitcode (a coroutine, an
  `always_inline` function, `-O1`), with every supported LLVM installed.

`crates/hod/src/lib.rs` is unchanged: no seam was needed.

## Decisions, and why

- **hod runs the converter, not the shim.** A shell pipeline in `bin/llc`
  would need the input's kind before choosing a command, could not hand
  the fallback the original bytes after a failed conversion, and would
  not be in the coverage log.
- **Pipes, both served at once.** A thread writes the bitcode, a thread
  drains standard error, the main thread reads the text. No temporary
  file, and no module size at which either side blocks. Rust starts with
  `SIGPIPE` ignored, so a converter that leaves early is an `EPIPE` on a
  write hod does not care about.
- **The conversion is tried only for `bitcode-input`.** `compile` is
  asked first; its checks before the input's kind are cheap (`-filetype`
  today), and an invocation that would be declined anyway for one of them
  does not pay for a conversion. It also means the facade needed no
  change: the trigger is an answer it already gives.
- **A warning is a failure.** `llvm-dis` exiting 0 after writing to
  standard error may have changed the module: LLVM strips debug info it
  finds invalid with such a warning. hod cannot tell what a warning
  means, so the module goes to `llc` as it arrived.
- **The output check is `llvm-dis`'s own frame**, `; ModuleID = ` first
  and a newline last, verified with LLVM 19.1.7 and 22.1.8. It tells a
  whole module from a truncated or foreign one; validity is the text
  reader's business.
- **Another LLVM's `llvm-dis` is not detected, only reported.** LLVM 22
  bitcode of a trivial module is read by `llvm-dis` 19 without complaint;
  one `captures(none)` parameter is enough to make it fail (`Unknown
  attribute kind (102)`), which is `bitcode-converter-failed` and a
  fallback (`real_llvm_dis_of_another_major`). The shim therefore always
  names its own installation's and never lets a caller's through.
- **No time limit.** The fallback has none either; both are LLVM's tools
  on the build's own module, and a limit hod picked would be wrong for
  some module. The converter is always waited for.
- **`HOD_IN_FALLBACK` guards the converter too**, rather than a second
  variable: the meaning is the same ("a hod started you; do not start
  another") and one variable keeps the guard in one place. The
  converter's environment also loses hod's four settings, so a shim's
  `bin/llc` reached by mistake cannot log or fall back on the outer
  invocation's behalf.
- **Fallback status as `signal:<N>`**, not `128 + N`: an exit code of 137
  and a `SIGKILL` are different events (the first is the fallback's own
  choice), and the log should not merge them. hod's own exit status stays
  `128 + N`.
- **`read_coverage` takes eight fields or more.** The format now grows
  only at the end, and a reader needs no change when it does. This also
  keeps the stand-ins for hod elsewhere in the harness (which write eight
  fields, in files this work package does not own) readable.
- **The shim's `sh` hop stays** ("The shim's `sh` hop" below).

## Measurements

All on one shared aarch64 Linux container (24 CPUs, load 14 to 18 from
other work throughout), LLVM 22.1.8 and 19.1.7 as packaged by Debian
(`llc` and `llvm-dis` are small executables over a shared `libLLVM.so`),
release build of hod, 2026-11-12. Good for proportions, not for baselines.

### Conversion cost

Inputs, per LLVM: 94 bitcode modules exactly as kiln hands them to `llc`
(kiln's own tests that the corpus skips as `opt-first-*`: 31
`always_inline`, 25 coroutine, 30 optimized; and two
standard-library-heavy programs written for this, each at `-O0`,
`-O0 -g`, `-O1` and `-O2 -g`), captured by a program standing where hod
stands in a shim; and 9 corpus modules from 2 KB to 21 MB of text,
assembled with `llvm-as`. 8 optimized C tests were not captured.

Each module was given to hod on standard input with
`-O0 -relocation-model=pic -filetype=obj`, the converter and the fallback
of the same LLVM. The times are hod's own coverage fields: conversion
(9), and `llc`'s whole run on the bitcode (8). "`llc` on text" is the
same `llc` given the converter's output instead. Medians of 21 runs
(bitcode under 200 KB), 9 (under 2 MB) or 5.

By size, all 103 modules, LLVM 22 (LLVM 19 in parentheses):

|---|---|---|---|---|---|

| 4 to 16 KB | 38 (34) | 2.3 (5.1) | 9.9 ms (10.4) | 13.9 ms (13.4) | 73% (76%) |

What the numbers say:

- **There is a floor of 8 to 10 ms** (6.9 ms at best) however small the
  module: starting `llvm-dis`. `llc` has the same floor, so for the small
  modules that make up most of a test suite the conversion costs three
  quarters of an entire `llc` run.
- **Above the floor it is about 70 ms per megabyte of bitcode** with LLVM
  22 (15 ms per megabyte of text written), about 90 ms with LLVM 19.
- **On the modules a debug build of standard-library code produces**
  (150 KB to 3 MB of bitcode) the conversion is 22% to 50% of what
  `llc -O0` takes for the whole job with LLVM 22, 32% to 65% with LLVM
  19. Debug info makes it worse: more text per unit of code generation.
- **That is the printing half only.** The text still has to be parsed.
  hod's text reader is not wired in yet, so its share is not measured
  here; LLVM's own parser gives the scale: on the modules of 64 KB of
  bitcode and more, `llc` on the converted text takes 7% to 52% longer
  than on the bitcode (290 ms longer on the 13 MB module).
- Text is 3 to 7 times the bitcode above a few kilobytes (largest ratio
  seen 7.0; `convert.rs` reserves 8 times the bitcode's size for it).

Plainly: with the converter in the way, hod cannot be much faster than
`llc` on a bitcode module. Had hod's code generation cost nothing at
all, a small module would take three quarters of `llc`'s time, and a
large standard-library one a quarter to a half, before the text is even
parsed. kiln hands over bitcode for nearly every translation unit that
includes the standard library (`docs/design/0001-input.md`, point 6). So
the conversion is a bridge for correctness and coverage work, not for
speed; the speed case needs bitcode read natively (`hod_bc`) or modules
that never become bitcode (the in-process bridge, or `alwaysinline`
handled by hod so that kiln need not run `opt`).

### The shim's `sh` hop

`posix_spawn` to exit, 3000 interleaved runs of each, in microseconds:

| started | min | 10th percentile | median |
|---|---|---|---|
| `hod --help` directly | 701 | 1145 | 1814 |
| `hod --help` through the generated `bin/llc` (`/bin/sh` is dash) | 1019 | 1850 | 3003 |
| `hod --help` through a symbolic link | 693 | 1205 | 1929 |
| `/bin/true` | 217 | 320 | 400 |

The hop costs 0.3 ms at best and 1.2 ms at the median on this loaded
machine (an earlier run under less load: 0.3 and 0.8). That is more than
hod's own time to decline a module (below), and 3% to 10% of a small
translation unit's `llc` run; it will be a visible share of a small
translation unit once hod generates code.

It was left in place. The simple alternative is `bin/llc` as a link to
hod, with the fallback and the converter found beside the name hod was
started as. But `cargo xtask corpus capture` builds a shim around a
program of its own in hod's place, and that program takes the real `llc`
from the `HOD_FALLBACK_LLC` the script exports (`xtask/src/corpus/`,
outside this work package). Removing the script means changing that
first. Proposed mechanism, for whoever takes it: two links beside the
entry, `bin/llc.hod-fallback` and `bin/llc.hod-bitcode-via`, read with
`readlink` when the settings are not given otherwise; no parsing, no
environment, and `bin/llc` itself becomes a link.

### What the non-bitcode path pays

hod's own microseconds (coverage field 7) for a text module on standard
input with a fallback, 3000 interleaved runs, before this work package
and after:

| | min | 10th percentile | median |
|---|---|---|---|
| text input, before | 156 | 244 | 358 |
| text input, after | 148 | 243 | 360 |
| bitcode input, no converter, before | 145 | 276 | 542 |
| bitcode input, no converter, after | 141 | 271 | 543 |

No change: an invocation that converts nothing does nothing new (one
more environment variable read, two more fields in the log line).

## Left open

- **The conversion buys nothing until hod generates code.** Today every
  converted module is then declined as `codegen-not-implemented`, so a
  build through the shim pays the conversion on every bitcode translation
  unit and gains a triple in the log. That is the right default for the
  moment code generation is wired in (WP-043), and a cost until then. The
  shim has no switch to leave the converter out; a caller cannot turn it
  off either, because the shim's value wins. If the interim cost matters,
  the smallest change is an option of `cargo xtask shim`.
- **The native bitcode reader** (`hod_bc`) is what removes the cost; the
  table above is its case.
- **The `sh` hop**, as described above: needs the corpus capture's
  stand-in to stop depending on the script's exported variables.
- **`cargo xtask irdiff` does not clear `HOD_BITCODE_VIA`** from the
  environment of the hod it runs (`xtask/src/irdiff/engine.rs`,
  `HOD_VARIABLES`); its inputs are text, so nothing converts today.
- **Stand-ins for hod in the harness still write eight fields**
  (`xtask/src/corpus/capture.rs` `DECLINE_SCRIPT`, and the fake hods of
  `xtask/tests/irdiff_fakes.rs`, `irdiff_real.rs`, `jobserver.rs`,
  `corpus_fakes.rs`). They are readable under the append-only rule;
  bringing them to ten is tidying.
- **The corpus skips every `opt-first-*` translation unit** because `llc`
  was given bitcode. With `llvm-dis` on the path those could be admitted
  as text.
- The coverage log is still per translation unit (WP-022).
