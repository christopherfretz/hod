# WP-018 — `xtask bench` and `bench/`

Landed: `spec/harness.md` "bench" (the performance half of
`docs/VALIDATION.md`), the inputs in `bench/`, the first baseline in
`bench/baselines/`, the generated report `docs/status/perf.md`, and hod's
phase report (`spec/cli.md` "Phase report").

## What it did

- `bench/manifest`, `bench/src/`: ten sources written for this
  repository, each built with and without `-g`: 20 inputs in four size
  classes, from 10 KiB to 16 MiB of IR and from 3 to 5001 functions.
- `xtask/src/bench.rs`: the command (`parse_args`, `run(&Config) ->
  Result<Run, String>`), the measuring loop, the gate's re-measure loop.
- `xtask/src/bench/manifest.rs`: the manifest, the producers (clang or
  kiln), generating and caching an input's IR.
- `xtask/src/bench/measure.rs`: the measured child, the GNU `time` probe,
  the method's self-check (process floor, known allocation).
- `xtask/src/bench/record.rs`: records, ratios, throughput, the results
  file, the machine id.
- `xtask/src/bench/check.rs`: the gate's rule, the baseline and its log.
- `xtask/src/bench/report.rs`: the summary and `docs/status/perf.md`.
- `xtask/tests/bench_fakes.rs` (fake tools, every outcome and verdict),
  `xtask/tests/bench_real.rs` (real tools, gated).
- `crates/hod_cli/src/phases.rs` and 23 lines of `driver.rs`: hod appends
  its phase times to the file named by `HOD_TIME_PHASES`.

No new dependency, no `unsafe`.

## Decisions, and why

- **Peak memory comes from GNU `time`.** The kernel's resource record of
  a child (`wait4`) is not reachable from safe Rust without a dependency;
  `/usr/bin/time -f '%M %U %S'` is. The limits are set outside it, so its
  report is the program's alone. Every run checks the probe against a
  known allocation (`dd` with a 64 MiB block) and records the error.
- **The wall clock is read by a thread blocked in `wait`**, not by the
  polling loop of `irdiff::process::run`, whose interval would be added
  to every time. That is why `measure::run_measured` duplicates that
  function's limit wrapper instead of calling it.
- **The process floor is recorded, not subtracted.** Every time includes
  the shell, GNU `time` and a process start (1.5 to 3.8 ms on this host,
  depending on load). Subtracting a noisy estimate would add its noise to
  every figure; it is the same amount for every tool, and the header says
  how much.
- **Fastest of N for time, middle of N for memory.** Noise only adds
  time; it moves the resident set either way.
- **Rounds interleave the tools** (`llc`, hod, hod with fallback, then
  again), so a burst of load falls on all three.
- **hod is measured as built with the release profile**, by the command
  itself; `--hod` measures any other.
- **A decline is a status, not a time.** Its record keeps what declining
  cost, but has no ratio, no throughput, and no column among build times;
  the gate does not judge it. An error has no numbers at all.
- **`hod+fallback` is a third configuration.** It is what a hybrid build
  runs today, and the only one with a ratio to `llc` until hod generates
  code: the shim's overhead.
- **The phase report is a file named by an environment variable**, not a
  command-line option: hod's command line is `llc`'s, and the mechanism
  must not need a change to `args.rs` or be visible to a build system.
  The harness takes whatever phase names it finds; the code generator's
  own names are reserved in `spec/cli.md`.
- **The gate's control is `llc` in the same run** ("Drift"): the time
  threshold is scaled by how much slower `llc` is than in the baseline,
  never tightened, and past 25% the time is not judged.
- **A time whose runs disagree by more than 5% cannot fail the gate**
  ("Spread"), and NOISY is exit status 3, "the run cannot be trusted",
  not a pass. This came from measuring this host (below): without it the
  gate failed on noise in about one input of eight.
- **Memory is judged whatever the load**, with an absolute margin of 512
  KiB: the resident set of hod reading one module varied by up to 316
  KiB between runs.
- **A baseline is a results file**, per machine id, replaced only with a
  reason, which goes to a log beside it. On another machine or with
  another `llc` the check is advisory and compares ratios to `llc`.
- **The machine id** is architecture, CPU model and core count: no host
  name, no user.
- **Inputs are generated, not committed.** The IR is megabytes and
  depends on the installed libstdc++ headers; the sources and the
  manifest are pinned, and each record carries the size, function count
  and hash of what was measured. A baseline whose hash differs from the
  run's is advisory for that input.
- **`bench` is not a step of `cargo xtask ci`.** The gate's runs share
  the machine with seven other agents' builds; a time gate there would be
  noise. Its tests are in the gate (about 10 s of wall time on the loaded
  host, most of it sleeping fakes).

## Evidence

- `cargo xtask bench` on this host: 20 inputs, 3 runs, 24 to 39 s of
  wall time at load 10 to 18.
- The numbers are in `docs/status/perf.md`, generated from the baseline
  (`--runs 5`, 51 s). It was recorded at load 14: its times are 15% to
  40% above the fastest seen for the same inputs that afternoon (`llc` on
  `small-c`: 21.7 ms in the baseline, 13.1 ms at best), and 14 of its 20
  inputs have a spread above 5%, which the command says when it writes
  one. Its memory figures and object sizes are exact.
- `cargo xtask bench --check --judge hod+fallback` against it, with
  nothing changed: 17 ok, 1 improved, 2 NOISY after being measured again
  twice, no failure, exit status 3. `--check` (strict hod): 20 not
  judged, declined as in the baseline, exit status 0.
- `--llvm 19 --filter small-c`: measured with `llc-19` and `clang-19`.
- Probe error on a 64 MiB allocation over the runs made here: -56 to +84
  KiB (the stated bound is 655 KiB).
- hod with its fallback costs 1.02x `llc` in total (the sum of the
  fastest runs), about 3 ms per module, and no memory.

### Noise on this host

Five runs of the default command within five minutes, load average 10 to
18 on 24 cores:

| figure | variation across the runs, (largest - smallest) / smallest |
|---|---|
| `llc`, fastest of 3, per input | middle input 27%, worst 62% |
| `llc`, fastest of 15 (8 inputs, 4 runs) | middle 23%, worst 41% |
| hod declining (a 3 ms process), fastest of 3 | middle 110%, worst 256% |
| hod+fallback / `llc`, both fastest of 9 in the same rounds (4 inputs, 6 sets) | 5% to 21% |
| `llc`, peak memory, middle of 3 | at most 0.75% (500 KiB) |
| hod declining, peak memory | at most 316 KiB |

Judging each of these runs against each other as its baseline (400
input pairs, `hod+fallback`, nothing changed between them):

| rule | time failures | memory failures |
|---|---:|---:|
| 5% and 1 ms, no control | 158 (40%) | 0 |
| with `llc`'s drift | 53 (13%), 28 NOISY | 0 |
| with drift, fastest of 9 against a baseline of 3 | 11 (2.8%) | 0 |
| with drift and the spread rule at 5%, fastest of 3 | 14 (3.5%), 50 more NOISY | 0 |

What that means: on this host the memory half of the gate (2%) is
exact, and the time half cannot resolve 5%. More runs do not fix it: the
slowdowns last longer than a set of runs (the fastest of 15 moves almost
as much as the fastest of 3). The gate therefore reports NOISY, exit
status 3, where its own measurements disagree, and still catches large
time regressions (tens of percent on the inputs that take over 100 ms).
The 5% contract needs a quiet machine with its own baseline.

## What was ported from kiln

From kiln's `xtask` benchmark harness (read, not copied verbatim):
peak memory through GNU `time`; the wall clock taken by a waiting
thread; resource limits set outside the probe; FNV-1a as the identity of
an input; fastest of N with the spread shown beside it; a recorded
baseline per machine with advisory comparison elsewhere and when the
input or the reference tool changed; a status document generated from
the results.

## Not verified

- **kiln as the producer of the C inputs.** `--kiln` is implemented and
  tested with a fake; a full run with the real kiln was not made.
- **LLVM 19 beyond a run of the four small inputs.** No baseline is
  recorded for it, and `--update-baseline` refuses it.
- **The gate's time half on a quiet machine.** Every measurement here was
  made beside other agents' builds.
- **x86-64.** The machine id and the probe were exercised on aarch64 only.

## Left open

- `xtask/src/bench/measure.rs:114`: `run_measured` duplicates the limit
  wrapper of `irdiff::process::run`. After WP-024, fold both into one
  wrapper with a waiting thread, and take a jobserver token at
  `xtask/src/bench/measure.rs:143` (one line: the child is one process).
- `xtask/src/bench/measure.rs:27`: CPU time has GNU `time`'s 10 ms
  resolution; it is recorded but too coarse for the small inputs. A finer
  source needs `wait4` or `/proc/<pid>/stat` read at exit, neither
  reachable safely today.
- `xtask/src/bench/check.rs:33`: the gate's absolute margins and the 25%
  drift limit were chosen from one afternoon on one busy host. Revisit
  them with data from a quiet machine.
- `crates/hod_cli/src/driver.rs:217`: `compile` is one phase today. The
  code-generation packages split it into the reserved names (`ingest`,
  `analysis`, `emission`, `debug-info`, `object`) as each stage appears.
- The micro level of the task (per-function or per-pass benchmarks inside
  the crates) was not started: there is no code generator to measure. It
  belongs with the first code-generation package, and should report
  through the same results format.
- `bench/manifest`: no input is produced by kiln by default, and none
  comes from a real project. When kiln's IR differs in shape from
  clang's (it will, for `constexpr`-heavy code), add inputs captured by
  `xtask corpus` (WP-017).
- `spec/README.md:21` still says the rest of `harness.md` is planned.
