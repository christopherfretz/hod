# WP-027: the cost of classify

Landed in `crates/hod_ir/src/classify/{walk,support,mod}.rs`; the once
modes of `examples/classify_throughput.rs`; the census test in
`tests/classify_random.rs`. `spec/ir.md` §8.9 (census) and §8.11 (cost)
were changed. Base: f612aff (main plus WP-092 and WP-159).

## Method

Every count is callgrind's total instruction count for one strict run:
`hod --strict -O0 -filetype=obj -relocation-model=pic` with
`HOD_THREADS=1`, a release build, on the bench inputs from
`cargo xtask bench --generate`, both targets. The host is aarch64, so
the x86_64 runs are cross-target. The release profile uses fat LTO and
one codegen unit, so callgrind's inclusive costs per function are
meaningless (inlining moves cost across frames). Two measures are used
instead:

- the change in total count between two builds, which is exact and
  repeatable to the instruction (glibc malloc is the only noise, see cut 4);
- the classify share: the total of a build minus the total of the same
  build with a probe (`HOD_NOCLASSIFY`, never committed) that makes
  `Classifier::module` and `Classifier::body` return at once.

`examples/classify_throughput.rs` with `build` or `classify` as the third
argument builds one generated body, or builds it and classifies it once.
The difference between the two callgrind totals, divided by the
instruction count, gives the classify cost per IR instruction. Building
that same body costs 183 instructions per IR instruction.

From base to head, classify's own cost fell by 23 to 45% on every input
(tables 3.36 to 1.85; huge-function 9.74 to 6.00). The one exception is
aarch64 containers at 12%, where cut 4's malloc noise lands. Its share
of a run fell from 0.9–3.3% to 0.6–2.3%.

On a whole compile, classify was already a small fraction at base: 1 to
3.3% of the run. The example isolates it. At base, classifying an
accepted body cost 162 instructions per IR instruction, 89% of the 183
it took to build that body. After cut 3 it costs 92, 50% of building.
§8.11 used to say "about half"; that came from wall-clock timing
(WP-009) on a loaded host.

## Cuts

1. c383893: one `callee.kind()` read on the short way decides both
   `returns_twice` and the declared attrs; the short way used to look
   the callee up twice.
2. 09951bf: `accepts_operand` is `#[inline(always)]`. Without it,
   LTO left it out of line once for each operand.
3. dc6f6e2: `Support::short`, one word per opcode, built in
   `derived()`. It packs whether the short way may decide the op at
   all, whether the op is a call or memory op, its inline operand
   count, and the classes its row accepts, already masked by the type
   rows. `accepts` reads that one word in place of the row and
   the operand-shape match. Direct calls are memoised by
   (callee, fn type) in 8 slots, but only when the callee was accepted
   with no declared attrs, so the attrs check is never skipped.
4. b3ba15f: the constant walk does not recurse into leaf
   elements of an aggregate (`ConstTable::leaf_type`). When the
   aggregate itself sits at the nesting limit, every element is still
   walked, so `limit:constant-nesting` fires exactly as before. A none
   token is not a leaf.

Tried and dropped: a precomputed class bit per type in place of
`has_class(class_code(..))`, plus a plain operand loop (93 per
instruction against 92 in the example).

Cut 4's noise: aarch64 containers is +321k, and all of it is in glibc
`malloc_consolidate` and `unlink_chunk`, whose work depends on the order
of heap frees. No hod function changed by more than 2k.

## What is left

In the example at head, the 92 instructions per IR instruction go to:

- slice iteration over the instructions and operands;
- the `Value::kind` match on each operand;
- the `short` load;
- `Inst::operands` left out of line for list ops (`ptradd`, `ret`, `phi`);
- `CallSite::args` with its enumerate fold.

Each tiny body also costs about 400 instructions on its own: `Walker`
setup and the function's attrs, signature and linkage rows.

None of these can be cut without reaching outside classify. A per-type
class cache would remove the `class_code` match, but it belongs in
`TypeTable`, which this package may not touch (WP-170 owns it). That
cache is a follow-up.

## Identity

The tables were built after kiln's pin moved and the corpus was
recaptured. Both come from the same corpus: `corpus`, 6,454 entries
(aarch64), and `corpus-x64`, 6,450 entries (x86_64).

Each table runs release `hod --strict` with `HOD_CENSUS=1`, using the
entry's `llc` arguments from the manifest. There is one row per entry,
holding:
- the exit status;
- the object's sha256;
- the first 300 bytes of stderr, which carry the refusal and census lines;
- the run's coverage-log line without its times and output path.

The base table (f612aff) and the head table are byte-identical: 12,904
rows, sha256 `fd37fe89…2c746`.

| corpus | exit 0 | exit 1 | exit 2 |
|---|---:|---:|---:|
| `corpus` | 6,100 | 348 | 6 |
| `corpus-x64` | 6,041 | 380 | 29 |

12,141 rows carry an object.

Debug builds also check, on every instruction of every `hod_ir` test,
that the short way agrees with the long way.

## Seed 360

The finding in `tests/classify_random.rs` was that seed 360 reported a
`function:parameters/token` pair on iteration that the census of the
same Support lacked. Both sides follow §8.3. Under that Support,
`type:token` is off, so the census names the type row (`type:token`)
and stops there. The iteration turns `type:token` on and then meets the
pair. The test was the inconsistent side: its filter let any pair
through. Its replacement, `behind_type_rows`, accepts a pair missing from
the census only when the census holds the type row and the iteration met
that row first. The regression test is
`a_pair_is_found_only_behind_its_type_row`. §8.9 now states the rule.
