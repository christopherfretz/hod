# WP-140 — x86-64 ABI follow-ups and the rows no instruction group owned

Landed: `Target::for_function` in `crates/hod_cg/src/target.rs` (called
by `compile_function`, `crates/hod_cg/src/driver.rs`);
`crates/hod_x64/src/{abi.rs, target.rs, features.rs, reg.rs}`;
`crates/hod_x64/tests/abi/` and `tests/skeleton.rs` on WP-025's
`Toolchain`; `crates/hod_x64/tests/abi_followups.rs`; `spec/abi-x64.md`
§1.2, §1.3, §2, §5.1, §10, §11.1; `spec/codegen.md` §5.6.9 and §8.2;
`spec/cli.md` "The back half" and "Reasons" (`codegen-not-implemented`
retired); the support-matrix rows below.

## What is implemented

- **The function's features.** `X64` is `X64 { features: FnFeatures }`;
  the constant `X64` (no features) is the module-level value.
  `Target::for_function(module, body) -> Option<Self>` (default `None`,
  so AArch64 is unchanged) gives `compile_function` the target for the
  whole function; x86-64 returns `X64` with
  `features::of_function(target-cpu, target-features)`. The compiled
  function's features decide every signature in it, its own and each
  call's, as in `llc` (`spec/abi-x64.md` §1.3: the CPU tables
  `CPUS_WITHOUT_AVX`, `CPUS_WITHOUT_AVX512`, an unknown CPU counting as
  both, then the `+`/`-` items in order).
- **One walk.** `hod_x64::abi` classifies through `hod_cg::abi::Classify`
  (`Leaves`) and places through `walk`/`place_leaf`/`place_leaves`; its
  own copy of the walk, register numbering and DWARF table are gone
  (`hod_x64::reg` has `st0`, `st1` at 32, 33, DWARF 33, 34).
- **x87 places.** A `float`/`double` return piece that finds no `xmm`
  register is placed in `st0`/`st1` (`abi::x87_float_part`).
  `X64::assign` refuses such a signature as `x64:ret-x87-part`, and
  `call::guard` an `x86_fp80` part as `x64:todo:abi` (WP-131).
- **`-x87`** is refused (`attr:target-feature-no-x87`) only in a function
  with an `x86_fp80` value: `X64::assign` for a signature with one (it
  runs before `begin_function`), `begin_function` for an instruction
  with one (`features::uses_x86_fp80`). `hod::back` judges a function's
  `target-features` with `features::check_function`, which leaves `-x87`
  to the code generator; `-mattr=-x87` stays refused.
- **`fastcc`** is `ccc` (`spec/abi-x64.md` §1.2); **`sret`, `byval`,
  `uwtable`**, and **`insertvalue`/`extractvalue`** of `Int` and `Ptr`
  members needed no new lowering (WP-125 and WP-126 had it): their rows
  are flipped on the evidence below.
- `Construct::CodegenNotImplemented` is retired: nothing reported it
  since WP-116.

## Refused, by name

`x64:wide-vector-abi` (a vector wider than 16 bytes in a signature of a
function with AVX; a vector of `i1` with AVX-512), `x64:ret-x87-part`
(now `X64::assign`'s, no longer in `abi::UNSUPPORTED`),
`attr:target-feature-no-x87` (a function with `x86_fp80` under `-x87`),
`x64:nest` (`nest`, unchanged: the `attr:nest` row stays off), and
WP-118's other names unchanged. A vector of `i1` in a signature without
AVX-512 is placed and then refused by WP-128's stub as `x64:todo:vcall`.

## Matrix rows flipped (x86-64)

`cc:fastcc`, `attr:sret`, `attr:byval`, `attr:uwtable`;
`inst:extractvalue` and `inst:insertvalue` gain `int` and `ptr`.
`irdiff --llvm 22 --target x86_64` declines nothing else that is not
float, an intrinsic, a vector, x87, TLS, atomics or coroutines
(`const_operands.ll` is an AArch64 module). No seed newly runs:
`aggregate.ll` and `byval_sret.ll` now stop at `type:double` (WP-127).

## Evidence

- WP-118's grid against `llc` 19 and 22 (`-O0`, `-O0` SelectionDAG,
  `-O2`), both directions, under `qemu-x86_64` with the baseline CPU:
  13,691 signatures under `HOD_ABI_GRID=full` (3,689 systematic, 8,000
  random, 83 from `tests/abi/data`, 1,919 variadic), 22 more than
  WP-118's 13,669 (the `float`/`double` returns through `st0`/`st1`
  that were refused); a `float`/`double` NaN is quiet in the grid
  because an x87 load quiets a signaling one.
- `abi_followups::wide_vectors_follow_the_function`: hod's
  `<8 x i32>`/`<4 x i64>` functions call `llc`'s and are called by
  `llc`'s under five spellings of "no AVX", `llc` 19 and 22, bfd, lld
  and mold.
- `abi_followups::own_signature_takes_the_function_features`,
  `avx_signatures_are_refused_by_the_function` (14 attribute sets, the
  caller's features deciding a call to an AVX-512 callee).
- `abi_followups::cpu_tables_agree_with_llc`: 59 CPUs and feature
  strings, all agree with `llc` 19 and 22 on `xmm`/`ymm`/`zmm`.
- `abi_followups::rows_run_against_the_interpreter_and_llc`: a
  two-module program (`sret`, `byval` at alignments 1, 8 and 16, one at
  stack offset 8 that must move to 16, through a function pointer, `sret`
  and `byval` in one call, `fastcc` with an aggregate argument and a
  memory return, `insertvalue`/`extractvalue` of `i8`..`i64` and `ptr`)
  whose checksum `hod_interp` computes; hod/hod, hod/`llc`, `llc`/hod
  and `llc`/`llc` with `llc` 19 and 22, three linkers: 21 linked runs.
  Text bytes hod 3,593 against `llc` 22's 1,555 (ratio 2.31).
- `abi_followups::uwtable_gives_the_unwind_entries_llc_gives`,
  `no_x87_is_refused_only_with_x86_fp80` (and a function without
  `x86_fp80` gives the same object with and without `-x87`).
- AArch64 byte identity: `scripts/corpus-bytes.py` over the corpus, base
  and head `hod`: 6,451 modules, 6,441 objects and 10 declines
  identical, 0 differ.

## Mutations (each caught, then reverted)

1. `-avx` no longer clears AVX (`features::of_function`): four
   `abi_followups` tests fail, `cpu_tables_agree_with_llc` among them.
2. `X64::for_function` returns `None`: the AVX refusals and the own
   signature test fail.
3. A `byval` stack slot ignores its alignment (`abi::assign_argument`):
   the row program's checksum differs (`@sum_big9`'s copy lands at 8
   mod 16).

## Where hod differs from `llc`

- An unknown CPU is taken to have AVX and AVX-512 (`llc` falls back to
  `generic`): such a function's wide vectors are refused rather than
  placed.
- `-x87` in a function with `x86_fp80`: refused, where `llc` stops with
  an instruction-selection error.

## Follow-ups

- `-mcpu`/`-mattr` do not reach `hod_cg::Options`, so the command line's
  CPU never decides a convention (`crates/hod_x64/src/target.rs`
  `for_function`).
- `TargetStackArgs` (`crates/hod_cg/src/abi.rs:207`) assigns with the
  module-level target: a classifier stack-size estimate ignores the
  function's features (only matters for a wide vector under AVX, which
  is refused anyway).
- Vectors of `i1` in a signature: `x64:todo:vcall` until WP-128
  (`crates/hod_x64/src/vcall.rs:20`).
