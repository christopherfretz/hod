# WP-312 — the object written from its sections, not copied whole first

Base `edee2d1a`. Found by WP-303 step 3 (`spec/landed/ll/WP-303.md`,
"What remains" 3): `hod_obj::elf::to_vec` built the whole object in one
vector (5 MB on `stl-heavy-g`), and the tool then wrote that vector, so
every byte was copied twice and, at the copy, held twice. No emitted
byte changes.

## Measured first (base)

Bench inputs of `cargo xtask bench --generate` (clang 22), `hod -O0
-filetype=obj -relocation-model=pic`, `HOD_THREADS=1`.

- **Where the heap peaks** (massif): not at the copy. On `stl-heavy-g`
  the heap is 34.2 MB at the end of reading (the 16.4 MB input alive),
  15.9 MB once the input is freed, and peaks at 34.8 MB in the module
  emitter's `finish` (the DIE writer); during `to_vec` it is 30.6 MB.
  The same holds on `templates-g` (20.3 MB) and `tiny-functions-g`
  (17.1 MB); on `huge-function[-g]` the object is 0.36 MB and does not
  count.
- **Where the resident set peaks** (`/usr/bin/time` maximum RSS, the
  gate's measure): at the copy. glibc keeps the freed heap of `finish`
  resident, and the output vector (over the 128 KiB mapping threshold)
  is a fresh mapping on top of it. An experiment that wrote the object
  with `hod_obj::elf::write` straight to the file inside the facade,
  5 runs each, medians (KiB): `stl-heavy-g` 37 096 → 34 184 (aarch64),
  36 744 → 33 760 (x86-64); `templates-g` 24 104 → 22 604, 24 424 →
  22 604; `tiny-functions-g` 19 768 → 18 492, 18 944 → 18 036;
  `huge-function[-g]` unchanged within noise. Same bytes.
- **Instructions** (callgrind, inclusive of `to_vec`; the write is a
  few thousand instructions plus the syscall): `stl-heavy-g` 4.96 M of
  1 071 M (0.46%; x86-64 4.23 M of 1 092 M), `templates-g` 2.58 M of
  754 M, `tiny-functions-g` 0.48 M of 358 M, `huge-function` 9 k.
  WP-303 timed `to_vec` at 1.4 to 1.7 ms of `stl-heavy-g`'s ~120 ms.

So the cost worth removing was the resident set, about 3 MiB on the
largest input; the instructions were noise.

## What was built

- `hod_obj::elf::prepare(Object) -> Prepared`: the checks and layout of
  `to_vec`, kept with the object; `Prepared::write` / `to_vec` are
  `write` / `to_vec` past the checks, the same emitter (`emit`), so the
  two paths cannot disagree (`spec/object.md` "ELF writer").
- `hod::compile_object` (facade, an addition: `EMBED_API` unchanged)
  answers an `ObjectFile`: checked and laid out, `.dwo` written, the
  object's checks failing as before with the same `CompileError`.
  `write_to(&mut dyn Write)` writes it from the sections' buffers (the
  64 KiB batching of `elf::write`), with a panic contained as
  `CompileError::Panic`; `to_vec` is `compile_releasing`'s bytes.
  `compile_releasing`, `Session::finish` and `generate_with` keep their
  signatures and bytes (through `ObjectFile::to_vec`).
- The `hod` binary compiles with it (`driver::compile_hod`) and writes
  the file or standard output with `write_to`.

Two instruction costs showed in the first version and were removed:

1. Freeing the module and bodies before writing (the session ended in
   `compile_object`) made glibc consolidate their many small free chunks
   on the large frees of the sections after: +2.6 M instructions on
   `tiny-functions` (+1.4%, over the gate's 1%), +0.3 to +0.6% on
   `templates`. The `ObjectFile` now keeps the module and bodies, freed
   after the object when it is dropped, as they were when the object
   was copied out first.
2. The binary does not free a written object at all
   (`std::mem::forget`): only the coverage line follows and the process
   exits. Freeing it cost 1.4 M instructions on `templates` (x86-64). An
   object that failed to write is freed before any fallback runs.

A 64 KiB stack buffer instead of the heap one was tried and measured the
same; not kept (and clippy's `large_stack_arrays` refuses it).

## Errors and partial output, before and after

- Before: `std::fs::write` after the compile answered: the file created
  or truncated, then one `write_all`; a failure part way left the part
  written, no removal; standard output: `write_all` and `flush`, part
  written on failure. `output-unwritable`, exit 1, message `cannot write
  '<path>': <cause>` / `cannot write standard output: <cause>`.
- After: the same. The file is created only once the compile answered a
  checked object (an object the writer refuses is still a
  `CompileError` before any output is opened); then the pieces in file
  order; a failure part way leaves the part written, no removal; same
  reason, exit and messages. New: a panic of hod's while writing (a bug)
  is `internal-panic` and goes to the fallback as a compile's panic
  does, with the output possibly part written (the fallback rewrites
  the file; on standard output its object would follow the part).

## A bug found by the comparison, fixed

The first version asked `emitted.object.arch()` in
`back::generate_object` for every compile (to make an empty `.dwo` if
one were needed), and `Object::arch` panics on an i386 object, which
has no `Arch` (`crates/hod_obj/src/model.rs`): every i686 object was a
contained panic, and `tests/ir/odd_width_store.ll` (i686, plain) went
from exit 0 to `internal-panic`. The base had asked only on the
split-DWARF path. Now `generate_object` keeps the object's `Machine`
and `write_dwo` makes the empty companion with `Object::for_machine`.
Tests: `crates/hod/tests/object_file.rs`
`an_i386_object_is_written_through_every_path` (vector, whole sink,
4093-byte trickle and a file, each equal to `hod::compile`, ELFCLASS32
and `EM_386` checked); the facade comparison now runs i686 too and
refuses a refusal that is a contained panic; the `hod_cli` driver test
writes an aarch64, x86-64 and i686 object to a file and to standard
output. No other 64-bit-only assumption is in the package's diff: the
writer's `Prepared` keeps `Layout`, which already chooses the ELF32 or
ELF64 form from the machine.

## What remains

- The resident peak is now the DIE writer's heap in `finish` (34.8 MB of
  heap on `stl-heavy-g`), `crates/hod_dwarf` (WP-303's "What remains" 1).
- `ObjectFile::write_to` takes `&mut dyn Write`; a caller that writes
  to a file could use vectored writes for the large sections; not
  measured as worth it (the write is a few thousand instructions).
