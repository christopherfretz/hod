# WP-269: the constant fold never refuses a function

Spec: `spec/codegen.md` §5.6.8 "Folded constants and the blocks they
remove" (the paragraph after the description of step 4).

## Found

WP-261 refused a whole function, with one of four names, where
`markAliveBlocks` (step 4) would also rewrite something hod does not
model: `intrinsic:const-fold-null-access`, `-nounwind-invoke`,
`-noreturn-invoke`, `-indirectbr`. The survey of WP-261 (108 corpus
modules) never met one, but real code does:
`intrinsic:const-fold-nounwind-invoke` fired in 10 `std::basic_string`
tests of libc++ on each target (for example
`std/strings/basic.string/string.access/at.pass.cpp`, in
`basic_string::operator[]`) and in 21 of 159 translation units of the
fifth set of real projects on x86-64 (all in `main`: a `br` on
`llvm.is.constant.i1` and an `invoke` of a `noreturn nounwind` function
whose unwind edge goes to a landing pad). The previous release
candidate compiled those functions, so the refusal was a regression.

## Decision

The folding never refuses. In each of the four cases hod keeps the
instruction as written, with all its edges, and walks on: an `invoke` of
a `nounwind` callee stays an `invoke` with its landing pad; an `invoke`
of a `noreturn` callee keeps its normal destination; a non-volatile
store to, or a call or `invoke` through, `null` (and an `invoke` through
`undef`) is emitted as written; an `indirectbr` on a constant
`blockaddress` keeps all its successors. Each kept instruction is what
hod emitted for it before WP-261; a kept edge only keeps more blocks
reachable (a superset of `llc`'s), and no `phi` entry or edge is removed
for it (`remove_pred` is only called for the edges a folded terminator or
an ended block loses; `succs`, `reach` and `edge_live` all read the
terminator's own successors when its action stays `Emit`). The known
difference from `llc`'s object: hod's can hold a landing pad, a normal
destination, an `indirectbr` target or code after a `null` access that
`llc`'s does not, and the undefined symbols only those reference
(`__gxx_personality_v0` for a kept landing pad, which every C++ link
defines). Modelling the four rewrites exactly is a follow-up.

## Changed

- `crates/hod_cg/src/const_fold.rs`: the four refusals and their
  `pub const` names are gone (nothing else used them), and `no_unwind`
  with them; `mark_alive`, `alive_terminator` and `Lci::plan` cannot
  fail any more (`crates/hod_cg/src/driver.rs` drops the `?` of its one
  call; the public `analyse` keeps its `CgResult`).
- `crates/hod/tests/const_fold_blocks.rs`: `refusals` became
  `kept_rewrites`, and `kept_nounwind_invoke_unit` is new, with the input
  `crates/hod/tests/data/const_fold/kept_nounwind_invoke.ll` (the reduced
  unit of the finding, callee renamed).
- `spec/codegen.md` §5.6.8: the paragraph on the refusals became the
  rule above.

## Evidence

- The two evidence units of the real project (the reduced one and the
  full module) and the libc++ `at.pass.cpp` module: refused by the
  candidate at `e98267c0` (exit 2, `-nounwind-invoke`), compiled by
  this change in strict mode (exit 0), debug and release builds.
  `llvm-nm -u` against `llc-22` (x86-64, pic): the reduced unit adds
  only `__gxx_personality_v0` (the kept landing pad); the full module and
  `at.pass.cpp` have no undefined symbol that `llc`'s object lacks
  (`llc`'s has 5 `std::allocator<char>` members more in the first,
  emitted by hod as local `.alwaysinline` copies, a difference older
  than this change, and `memset` more in the second).
- `kept_rewrites`, on x86-64 (under `qemu-x86_64` here) and AArch64:
  for each of the four cases a function whose folded `br` deletes a
  block calling an undefined function, followed by the case; hod
  compiles it, its undefined symbols include all of `llc` 19's and
  22's and add at most `__gxx_personality_v0`, the program links
  without the dead arm's callee, and it prints what `llc` 22's program
  prints (the `nounwind` callee returns, the `noreturn` callee exits,
  the `null` access sits on a path the run does not take, the
  `indirectbr` goes to its constant target).
- `kept_nounwind_invoke_unit`: the reduced unit compiles on both
  targets; undefined symbols equal to `llc` 19's and 22's plus
  `__gxx_personality_v0`.
- Same bytes as `e98267c0` (its frozen candidate binary against this
  change's release build, `--strict -O0 -filetype=obj`, objects
  compared with `cmp`): 424 corpus modules (`.build/corpus` and
  `.build/corpus-x64`: every module that calls `llvm.is.constant` or
  `llvm.objectsize`, every 8th kiln module, every 40th gcc-torture
  module) and the 237 other `.ll` inputs under `crates/` and `tests/`
  (38 by their own triple; the 199 others, with `-mtriple`, once for
  x86-64 and once for AArch64): 792 objects, all equal. 47 corpus modules and 34 test inputs
  fail identically under both binaries (concatenated corpus files,
  other refusals and reader errors, same message); the only input whose outcome changed is the new reduced
  unit (refused before, compiled now).

## Not covered

- The kept `null` access and `indirectbr` cases run only on a path
  whose behaviour is defined; the libc++ tests and the real project's
  units were not rebuilt and run in full here (the supervisor's sweep).
