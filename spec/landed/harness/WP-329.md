# WP-329: the debug lane's i686 column

Brief: `spec/landed/codegen/WP-314.md` "The debug lane's i686 column".
Contract: `spec/harness.md` "debug", "Other targets", paragraph
**i686**. State: stage A done, stage B partly classified (one hod fix,
the rest listed below, open), stage C not done (see the end).

## What the column runs (stage A)

`cargo xtask debug --target i686`: each C and C++ test of `tests/debug`
built by clang 19 and 22 (`--target=i686-unknown-linux-gnu`), then by
`llc -O0 -global-isel=0 -fast-isel=0 -relocation-model=pic` and by hod;
linked by `i686-linux-gnu-gcc -pie` with GNU ld, lld and mold (wild and
mortar left out with a note: `linkers::EXCEPTIONS` case `elf-i386`);
run under `qemu-i386 -cpu <Target::I686's> -L /usr/i686-linux-gnu -R
<guest space> -g <port>`; gdb is `gdb-multiarch` (`set sysroot
/usr/i686-linux-gnu`, `target remote`), lldb is lldb-19 (`gdb-remote`).
The cross plumbing of WP-136 (`debug/cross.rs`, `irdiff::tools::
target_of`) already took the arch; what changed is in
`xtask/src/debug.rs` (the refusal removed for `run`; `debug verify
--target i686` still refused, no i686 corpus), `debug/directives.rs`
(`i686` a target word) and `debug/sessions.rs` (the linker filter, kiln
off, `KEPT_OFF_I686`).

**lldb's verdict**: lldb-19 through `gdb-remote` holds on i386: 183
hod sessions per run on the three linkers, 174 PASS; its 9 FAILs are line
or column differences (below), no crash, no attach failure. lldb-22 is
not installed in the container (as on the other columns).

kiln++ refuses i686 (`kiln++: error: unsupported target
'i686-unknown-linux-gnu' (kiln supports aarch64 and x86_64 Linux)`):
its units are SKIP with a note.

Kept off (SKIP, counted in the summary): 20 units by
`debug:dwarf-4-i386` (the `dwarf4_*` tests), 2 by
`debug:split-dwarf-i386` (`split.cpp`). Other SKIPs: IR tests (not run
on another target), `tls.c` / `tls_static.c` (`skip(remote)`: no
`qGetTLSAddr`), `sret_entry.c` (`target: x86_64 aarch64`).

  WP-252's `nop` at a `condbr` / `switch` on a constant folded to the
  next block (`spec/dwarf.md` §5.10), so `break 11` bound at line 12.
  `crates/hod_x86/src/control.rs` `folded_br` (as `hod_x64`'s), used by
  `cond_br`, `switch` and the wide switch (`int.rs`). Test
  `crates/hod_x86/tests/constant_branch_lines.rs` (`hod_x64`'s, for
  i686; `cond_false_unused` needs no `nop` on i386: its unused compare
  is written, line 12 has code). Only `hod_x86` changed: the 64-bit
  targets' objects are byte-identical (compare-binaries, below).
- **classes.cpp** (6 ERRORs, test text): the check named the vtable
  address point `<vtable for geo::Box+16>`, two 8-byte slots; on i386
  it is `+8`. The check now names the members (`kind = ...Box, static
  made = 1`); the transcript is still compared with `llc`'s.
- **kiln** (13 ERRORs, plumbing): kiln++ units SKIP with a note.

## Open FAILs (stage B, not classified further)

Each: count, one difference (`hod` / `llc`), class as far as known.
Reproducer: `cargo xtask debug --target i686 --keep tests/debug/<file>`
(the unit's directory keeps both programs and transcripts).

1. **coroutine.cpp, coroutine_ssp.cpp** (4): `hod declined module 0:
   coro:target`. hod refuses coroutines on i386 (in work, WP-327).
2. **stack_protector.c** (2), **stack_probe.cpp** (1): `x86:stack-protector`,
   `x86:probe-stack` (in work, WP-324).
3. **dbg_value_arglist.c** (6, gdb): `print q - p` hod `$1 = <optimized
   out>`, llc `$1 = 2`; `*q` and `d` likewise (llc `7`, `-5`). This is
   WP-314's open point: a `DIArgList` gets no location on i386
   (`hod_dwarf/src/loclists.rs` `fits_i386`, `spec/codegen-x86.md`
   §15), both for the pointer `q = p + i` and for `d = i - j` (32-bit
   operands). gdb prints `<optimized out>`, never a wrong value. The
   rule exists in codegen-x86.md, but no rule of `spec/dwarf.md` names
   the session difference, so no permitted entry: either lift the
   restriction when the arglist's width is at most 32 bits (llc's values
   are right here), or write the permitted class citing the rule.
4. **inlined.cpp** (6, gdb): after `finish` out of `observe` into the
   inlined `scale`: hod `0x? in scale (value=4, factor=5) at
   inlined.cpp:15`, llc `scale (...) at inlined.cpp:16`. hod pops the
   outgoing argument area after the call (`leal 0x10(%esp), %esp`, at
   the call's line 15), `llc` reserves it in the prologue, so hod's
   return address is mid line 15. Unknown: code shape, no wrong value;
   no rule names it.
5. **key_call.c** (9): gdb (clang-22) after `finish`: hod `main () at
   key_call.c:16`, llc `0x? in main () at key_call.c:16`; lldb (19 and
   22 front ends) `frame #0: ... main at key_call.c:16:3` against
   `17:19`. Rows at the return address (key instructions, §5.9).
   Unknown.
6. **call_sites_direct.c** (3, lldb, clang-22): `frame #0: ...
   middle(x=3) at call_sites_direct.c:14:11` against `14:7`: a column.
   Not a `step out` stop of `permitted::only_return_columns`? Unknown.
7. **exception.cpp** (2), **variable_twice.cpp** (1), mold only, gdb:
   hod `what = 0x? "too big"`, llc `what = 0x? <.L.str> "too big"`. The
   `<.L.str>` symbol is in `llc`'s program linked by mold only (not
   bfd, not lld): `llc`'s i386 object refers to the string through a
   `.L` local symbol that mold keeps in the symbol table. A difference
   of the ORACLE's program under one linker, not of hod's debug
   information; it would be a linker exception (`xlink::EXPECTED`)
   once measured with a witness. Plumbing / linker, open.

## Stage C (not done)

The lane at `-j 4` costs 110 s wall (82 s before the fixes) on the
development host: within the four-minute bound, but not green (the
FAILs above), so there is no `debug-i686` step. A hosted i686 lane
needs `gdb-multiarch`, `qemu-user` (`qemu-i386`), the i686 cross
toolchain and system root (`gcc-i686-linux-gnu`, `libc6-dev-i386-cross`,
`libstdc++-<N>-dev-i386-cross`), and lldb with the x86 target.
