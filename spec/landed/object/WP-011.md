# WP-011 — `hod_obj` follow-ups to WP-010

The contract is `spec/object.md`. This file records what the work package
did, what it measured, and what it left. It takes up the "Left for later"
list of `WP-010.md`.

## What landed

- **Linked sections** (`SHF_LINK_ORDER`): `Object::set_linked_section` and
  `Object::linked_section`; the writer sets the flag and `sh_link`; the
  deferred error `Error::LinkedToItself`. Spec: "Linked sections",
  "Caller's sections".
- **Convention helpers** in `crates/hod_obj/src/elf/conventions.rs`,
  exported from `hod_obj::elf`: `add_init_array`, `add_fini_array`,
  `DEFAULT_INIT_PRIORITY`; `gnu_property_note`, `add_gnu_property_note` and
  the feature constants `GNU_PROPERTY_AARCH64_FEATURE_1_{BTI,PAC,GCS}`,
  `GNU_PROPERTY_X86_FEATURE_1_{IBT,SHSTK}`. Spec: "ELF conventions".
- **Tests only, no code change needed**: thread-local storage through every
  access model, linked and run; initializer and finalizer arrays run in
  priority order; mergeable sections merged by the linkers; groups with
  members that are not loaded, `Plain` groups, references into a discarded
  COMDAT copy; x86-64 objects linked and run under emulation.
- Test support: `tests/common/linking.rs` (a `Toolchain` per target: the
  compiler driver, the linkers present, the emulator); the reader in
  `tests/common/mod.rs` now checks `sh_link`, `sh_info` and
  `SHF_LINK_ORDER` of every section it parses.
- New test files: `tests/link_tls.rs`, `tests/link_conventions.rs`,
  `tests/link_x64.rs`; new tests in `tests/link.rs`, `tests/structure.rs`,
  `tests/tools.rs` and the unit tests.
- `spec/object.md` updated throughout; nothing outside `crates/hod_obj` and
  `spec/` changed. `hod_testutil` is unchanged. No third-party crate; no
  `unsafe`.

## API added

    pub fn linked_section(&self, section: SectionId) -> Option<SectionId>;

Everything is additive. `Error` gained a variant, which breaks only a
caller that matches it exhaustively; there is none in the workspace.

## Decisions and why

- **The link is one more field of the section record, set by one call.**
  The smallest extension that expresses `SHF_LINK_ORDER`: no new section
  kind, no new constructor, and existing callers are unaffected. The
  writer translates the id to an ELF index when it emits the header; no
  pass was added.
- **The section record stays at 104 bytes.** The link is a `u32`, which
  would have grown the record to 112 bytes. The alignment, always a power
  of two, is now stored as its exponent in one byte, which makes the room.
  `record_sizes` asserts the size.
- **`SHF_LINK_ORDER` stays reserved in `SectionKind::Elf`.** The writer
  sets it from the link, so the flag and `sh_link` cannot disagree.
- **`sh_info` of a caller's section stays 0.** Nothing a compiler puts in a
  relocatable object needs it except sections that hold symbol table
  indices (`.llvm_addrsig`, call-graph profiles), and those would need the
  writer's symbol numbering as well, which is a different feature. It is
  listed under "Deliberately unsupported".
- **A linked section is not put into its target's group automatically.**
  LLVM does both for a function in a COMDAT; the model keeps the two calls
  separate and the spec says what the caller should do.
- **The helpers are free functions in `hod_obj::elf`, not `Object`
  methods.** Section names like `.init_array.101` and the property note
  are ELF conventions; the model stays format-neutral.
- **`add_init_array` takes the priority, not a name, and builds the name on
  the stack.** It adds a section on every call (as `add_section` does);
  the code generator keeps one id per priority it uses.
- **Priority names follow clang, not GCC.** clang names the section
  `.init_array.<n>` with `n` unpadded (`.init_array.101`, `.init_array.0`)
  and no suffix for 65535, `sh_entsize` 0. GCC 14 pads to five digits
  (`.init_array.00101`) and sets `sh_entsize` 8. The three linkers sort by
  the number either way; the test uses 200 and 1000, which sort the other
  way as text.
- **The TLS tests use a C driver compiled by the target's own compiler.**
  The accessors are hand-encoded and go through hod's relocations; the
  oracle for "the right address" is `&variable` as the C compiler computes
  it in the same thread. That is an external oracle, and it catches a
  wrong relocation kind or addend that a self-consistent hand-written
  program would not.
- **Code stays hand-encoded.** `hod_mc_a64` was not made a
  dev-dependency: the object writer's tests should not depend on the
  encoder they will later be used to test. The encodings were checked
  against `llvm-mc`/`llvm-objdump` while writing them.
- **No AArch64 general-dynamic test.** AArch64 toolchains use descriptors
  for the dynamic model by default, and `llvm-mc` 22 has no `:tlsgd:`
  operand to check a hand encoding against. `TlsgdAdrPage21` and
  `TlsgdAddLo12Nc` remain covered by name only (`tests/tools.rs`).
  x86-64 general dynamic is linked and run.

## What the linkers do

Observed with GNU ld 2.44, lld 22.1.8 and mold 2.37.1, and encoded in the
tests where the three agree or where the difference is stable.

| | GNU ld | lld | mold |
|---|---|---|---|
| `.init_array.<n>` order | by number | by number | by number |
| mergeable strings and constants across objects | merged | merged | merged |
| linked sections: output order | target order | target order | input order (flag ignored) |
| linked sections under `--gc-sections` | kept with target | kept with target | dropped unless referenced |
| `Plain` groups, same signature, two objects | both kept | both kept | both kept |
| `Plain` group under `--gc-sections` | members kept together | members kept together | per section |
| reference from `.debug_*`/`.eh_frame` to a local symbol in a discarded COMDAT copy | accepted; resolves to the kept copy | accepted; 0 | accepted; 0 |
| the same reference from `.data` | accepted silently when the kept copy has the same size | error: "relocation refers to a discarded section" | accepted silently |
| `.note.gnu.property`, all inputs marked | output marked (both targets) | output marked (both targets) | marked for x86-64; AArch64 property dropped |
| `.note.gnu.property`, one input unmarked | output unmarked | output unmarked | output unmarked |
| TLS descriptor access in `-shared`, variable also accessed by initial exec | descriptor turned into initial exec | kept | kept |

Consequences:

- The reference from a loaded section into a discarded group is documented
  as not portable ("References into a group from outside it") and has no
  control test: the brief asked for one only if the failure was consistent
  across the three linkers, and it is not.
- mold dropping the AArch64 property is mold's behavior with any
  compiler's objects (checked with gcc and clang objects built with
  `-mbranch-protection=standard`), not something in hod's note. The test
  checks presence where the linker propagates and absence everywhere when
  one input is unmarked.
- The shared-object TLS tests link each model set on its own and require
  the model's dynamic relocation in the result, so a silent conversion to
  another model would fail the test.

## The property note against the compilers

`.note.gnu.property` from clang 22.1.8 is 32 bytes, `SHT_NOTE`, `SHF_ALLOC`,
alignment 8: `04000000 10000000 05000000 "GNU\0" <property> 04000000
<features> 00000000`. Feature words seen:

| option | clang 22 |
|---|---|
| `-mbranch-protection=bti` | 1 |
| `-mbranch-protection=pac-ret` | 2 |
| `-mbranch-protection=bti+pac-ret` | 3 |
| `-mbranch-protection=standard` | 7 (BTI, PAC, GCS) |
| `-fcf-protection=branch` | 1 |
| `-fcf-protection=return` | 2 |
| `-fcf-protection=full` | 3 |

gcc 14 gives 3 for `-mbranch-protection=standard`.
`gnu_property_note_matches_clang` compares bytes and section header with
clang's for each option; for `standard` it takes clang's own feature word
and requires it to include BTI and PAC, so the test does not break when a
compiler version adds a bit.

## Left for later

- mold ignores `SHF_LINK_ORDER` and does not keep group members together
  under `--gc-sections`. A producer whose metadata must survive
  `--gc-sections` with mold needs another mechanism (a reference, or
  `SHF_GNU_RETAIN`). Decide when the first such section is emitted
  (exception tables are referenced from `.eh_frame`, so they are not
  affected).
- mold does not propagate the AArch64 feature property; recheck with newer
  mold versions.
- `wild` is not installed; none of this is tested with it.
- AArch64 general dynamic TLS (`TLSGD_*`) is not linked and run.
- TLS local dynamic (`TLSLD`, `DTPOFF32`) on x86-64 is written and named
  by the tools but not linked and run.
- The native x86-64 host path of the link-and-run tests is unverified.
- `sh_info` for caller sections and sections that hold symbol table
  indices (`.llvm_addrsig`).
- One heap buffer per section remains the dominant memory cost with
  function sections (from WP-010).
