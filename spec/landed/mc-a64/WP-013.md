# WP-013 — AArch64 scalar floating point, FP/SIMD loads and stores, and the SIMD subset

Landed: `spec/mc-a64.md` sections "FP/SIMD registers", "Immediates" (the
FMOV immediate), "Scalar floating point", "`fmov_const`", "FP/SIMD loads
and stores", "SIMD", and the FP/SIMD parts of "Fixups", "Not provided",
"Test method" and "Where hod and LLVM's assembler differ".

## What it did

- `src/reg.rs`: `VReg` (`V0`..`V31`) and the operand kinds that say which
  view of it an instruction uses: `FpSize`, `FpFormat`, `VecBits`, `Elem`,
  `Arr`, `FpArr`.
- `src/imm.rs`: `encode_fp_imm8` / `decode_fp_imm8`, the exact FMOV
  immediate predicate and its inverse.
- `src/fp.rs`: 49 scalar floating-point constructors (4 with a checked
  twin) and the constant materializer `fmov_const` with its `FmovSeq`.
- `src/fpmem.rs` (new module): `VMemSize`, `VPairSize` and 17 load/store
  constructors (15 checked) covering `B`/`H`/`S`/`D`/`Q` in the unsigned
  scaled, unscaled, pre-index, post-index and register-offset forms, the
  PC-relative literal load, and `S`/`D`/`Q` pairs in all three forms.
  `src/mem.rs` now shares its field packing with it (`pub(crate)` helpers
  that take a register field instead of a `RegZr`); the integer
  constructors encode exactly as before.
- `src/simd.rs`: 107 Advanced SIMD constructors (34 checked).
- `src/lib.rs`: the `family!` macro, for constructors that share a
  signature and an encoding-class helper.
- The crate now has 363 instruction constructors, 150 of them with a
  checked twin (190 and 97 before).
- `tests/l1`: the harness assembles and disassembles with
  `+fp-armv8,+neon`; four new groups (`scalar-floating-point`,
  `fp-constant-materialization`, `fp-simd-loads-and-stores`, `simd`); the
  tool-free `fpimm` tests; FP literal loads in the fixup tests; the
  coverage test reads `family!` entries and refuses duplicate names.

## Decisions, and why

- **One register type, `VReg`; the view is an operand.** `S0`, `D0`, `Q0`
  and `V0.4S` are one register, and the code generator tracks registers,
  not names. This is the rule `Size` already follows for `W`/`X`. Unlike
  the general-purpose registers there is no encoding with two meanings, so
  one type is enough.
- **Separate kinds for separate questions.** `FpSize` (S, D) is what scalar
  arithmetic takes; `FpFormat` adds H for the few places half precision
  exists without FEAT_FP16; `Arr` is a full arrangement; `VecBits` is for
  instructions where only the vector width matters (the bitwise ones, in
  assembly always `8B`/`16B`); `Elem` is for element access, where the
  vector width is not an operand at all. Each constructor takes the
  narrowest kind that states its operands, so most SIMD constructors are
  infallible by type. Where an instruction skips one arrangement (`mul`
  has no `2D`) it stays on `Arr` with a precondition rather than getting a
  type of its own.
- **Half-precision register moves are not provided.** The brief asked for
  `fmov` between H registers and to and from general-purpose registers.
  Those encodings (`ftype` = 11) are FEAT_FP16: LLVM 22 with `+fp-armv8`
  refuses each with "instruction requires: fullfp16", so there is no
  oracle for them under the WP's feature set and a base Armv8.0 core does
  not have them. Base floating point has half precision only in `fcvt`,
  in loads and stores of `H` registers, and in `fcvtl`/`fcvtn`; those are
  provided. A half value is moved as a single: `fmov(FpSize::S, ..)`
  copies bits 31:0.
- **`fmov_const` goes through a general-purpose register, never a literal
  pool.** A pool needs a second section or an island, a fixup, and a
  decision about where it lives, none of which belongs in an encoder; and
  a load is not faster to emit. `ldr_fp_lit` exists for a code generator
  that later decides to keep a pool. The cost is up to five instructions
  for a double with four distinct 16-bit chunks.
- **Zero is `MOVI <Dd>, #0` at every format**, as LLVM emits it: one
  instruction, no general-purpose register involved.
- **`fmov_const` takes the scratch register as an operand** and documents
  that it is written only in the general case, so a caller that has no
  register to spare can ask `encode_fp_imm8` (or look at `len() == 1`)
  first.
- **`fmov_const` takes a `FpFormat`, including `H`**, so the code generator
  has one entry point for `half`, `float` and `double` constants.
- **FP immediates are bit patterns (`u64`), not `f32`/`f64`.** The
  constructors are `const fn`, the IR hands the code generator bits, and a
  bit pattern says exactly which NaN is meant. For `FpSize::S` the pattern
  must have its upper 32 bits clear, the rule `encode_bitmask` has for
  `Size::W`.
- **Naming: the mnemonic; `_vec` only on a clash.** Everything is
  re-exported at the crate root, so `add` cannot be both. The scalar name
  was there first, the vector one gets the suffix, and a vector-only
  mnemonic (`cmeq`, `zip1`, `bsl`, `tbl1`) needs none. FP/SIMD loads and
  stores put `fp` after the mnemonic (`ldr_fp_off`) for the same reason.
- **`fpmem` is its own module** rather than more of `mem.rs` or `fp.rs`:
  the brief asked for a group per source module, and loads and stores of
  `Q` registers are not floating point. It shares `mem.rs`'s field packing
  instead of repeating it.
- **`family!`.** Sixty-odd SIMD constructors differ from a neighbour only
  in two or three opcode fields. The macro states the signature and the
  helper once and each member in one line, and generates the same
  `#[inline] pub const fn` (or `checked!` pair) the rest of the crate
  writes by hand. The coverage test reads its entries the way it reads
  `checked!`'s.
- **`tbl2` takes the first table register**; the second is the next one
  modulo 32, which is the architecture's rule. The code generator has to
  place its table in consecutive registers, and the signature cannot make
  that mistake for it.
- **The widening and narrowing constructors take the narrow element**
  (`sxtl(from, ..)`, `xtn(to, ..)`, `fcvtl(wide, ..)`), not two
  arrangements that would have to agree.
- **`ext` rejects an index beyond the vector** although LLVM's assembler
  accepts one (below): an index of 9 into an 8-byte vector is a caller's
  bug, not a request for index 1.

## What LLVM's assembler does that the sweeps had to learn

- Without `+fullfp16`, every scalar operation on an `H` register other
  than `fcvt` and a load or store is an error, including `fmov h0, h1`,
  `fmov w0, h1` and `fmov h0, #1.0`; so are FP operations on `.4h`/`.8h`
  other than `fcvtl`/`fcvtn`.
- `fmov <reg>, #value` rounds the decimal text to single precision before
  it checks encodability, at both precisions: `fmov d1,
  #1.0000000000000002` is 1.0. Rejection texts therefore have to be exact
  in single precision.
- `fmov d0, #0.0` is an alias of `fmov d0, xzr`; `#-0.0` and a vector
  `fmov v0.4s, #0.0` are errors.
- `fcmp d3, #0.0` needs the `.0` (`#0` is "too few operands"), while the
  vector floating-point compares with zero accept `#0` as well as `#0.0`.
- `ext` accepts any index and keeps its low bits: `#9` on `8b` assembles
  as `#1`, `#17` on `16b` as `#1`.
- A load pair into one FP register twice is diagnosed ("unpredictable LDP
  instruction, Rt2==Rt"), in all three forms; nothing is diagnosed for
  writeback, since the base cannot be an FP register.
- With `-M no-aliases` the disassembler still prints `mov` for DUP
  (element, scalar) (`mov s0, v1.s[1]`); it prints `ins` for both INS
  forms, `orr` for a vector move, `sshll`/`ushll` for `sxtl`/`uxtl`, `not`
  for `mvn`, and `umov` for the `mov w0, v1.s[1]` alias.
- `movi v0.16b, #1, lsl #0` is an error (the byte form takes no shift
  operand), while `movi v0.4h, #1, lsl #0` is fine.
- The across-lanes instructions refuse two-element arrangements
  (`addv s0, v1.2s`); `uaddlv d0, v1.4s` is the widest.
- `ldr b0, [x1, x2, lsl #0]` sets the `S` bit, as `ldrb` does.

## Follow-ups

- What the SIMD subset leaves out is listed, with the helper each belongs
  to, in `spec/mc-a64.md` "Not provided". The ones a code generator is
  most likely to want next are the two-element and floating-point
  reductions (`ADDP`, `FADDP`, `FMAXV`, ...: `src/simd.rs:63`), `MLA`/`MLS`
  (`src/simd.rs:21`), the vector conversions in the other rounding modes
  (`src/simd.rs:57`), and the upper-half widening forms
  (`src/simd.rs:115`).
- FEAT_FP16 (an `H` member of `FpSize`, `4H`/`8H` in `FpArr`) is a
  feature decision for the code generator's target model, not only an
  encoder change: `src/reg.rs:353`, `src/reg.rs:550`.
- `fmov_const` could use the one-instruction SIMD immediates (`MOVI`
  byte masks) for a few more constants. It would not change the
  signature.
