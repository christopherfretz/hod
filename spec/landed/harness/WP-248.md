# WP-248 — wild in the debugger layer (L7)

Landed: a new outcome of `cargo xtask debug`, XLINK, for a result whose
only problem is a linker exception on the oracle's side, and two new
exceptions of wild 0.11.0 (`spec/harness.md` "debug", "Linker
exceptions"; `docs/status/linkers.md` "Exceptions").

## What was measured

wild 0.11.0 joined the matrix in the previous landing. Three tests broke
the ORACLE's gdb session under wild alone (`llc`'s program misses a check
it meets with GNU ld, lld and mold): on hosted x86-64 the quick tier's
`tests/debug/tls_static.c` (clang 19 and 22), and on AArch64 in the full
tier `tests/debug/stack_protector.c` (clang 19 and 22) and
`tests/debug/hardening_a64.cpp`. In each, hod's program linked by wild
shows the same defect: in `tls_static.c` hod's transcript equals `llc`'s
(the "PASS" in the ERROR's detail is that equality: both print the wrong
word); in the two AArch64 tests both stop in `?? ()`. The evidence is
kept on the development machine under `.build/findings/wp-248/`
(objects, `repro.sh`, its output, the transcripts).

- `tls_static.c`, x86-64 (`tls-dtpoff-debug`). Both objects locate each
  `_Thread_local` variable as `DW_OP_const8u <R_X86_64_DTPOFF64 sym>,
  DW_OP_GNU_push_tls_address` (the same relocation type and symbol form in
  `llc`'s and hod's). Linked by GNU ld, lld and mold the operands are 0
  and 4 (the offsets in the module's TLS block, `PT_TLS` memsz 8); linked
  by wild they are `0xfffffffffffffff8` and `0xfffffffffffffffc`, the
  offsets from the thread pointer (TPOFF). gdb adds the operand to the
  block's address and prints the word 8 bytes before `global_ticks`.
  wild's defect; not reproducible here (qemu-user's gdb stub has no
  `qGetTLSAddr`), measured from the linked files. On AArch64 LLVM writes
  no location for a TLS variable, so the case does not arise there.
- `stack_protector.c` and `hardening_a64.cpp`, AArch64 (`plt-got-gdb`).
  wild writes every PLT entry as a `.plt.got` stub (`adrp x16; ldr x17,
  [x16, #off]; br x17`) through a `GLOB_DAT` slot, with `BIND_NOW` and
  neither `.plt` nor `.rela.plt`; GNU ld and lld write `.plt` and
  `.rela.plt` (`JUMP_SLOT`), mold both. BFD's synthetic symbols on AArch64
  come from `.rela.plt` only, so GNU objdump names the calls to `<x@plt>`
  with the other three linkers (9 in `stack_protector.c`) and none with
  wild, and gdb's `next` over
  `strcpy`/`snprintf` and `nexti` over `memset` stop in `?? ()`. The
  programs run correctly. In `stack_protector.c` hod's session also
  differs from `llc`'s afterwards, by the same cause: `finish` from the
  unnamed stub plants its breakpoint at a bogus return address that falls
  on a stack slot of hod's frame (`x` becomes `0xd4200000`, a `brk #0`,
  and the program prints `-736100305` = that + 47). An ABI-allowed form
  gdb does not understand: class (b).

## Decision

Both are linker cases, not hod's: hod's objects carry the same
relocations as `llc`'s and link correctly with the other three. Neither
test's checks were changed. `hod_testutil::linkers::EXCEPTIONS` gets
`tls-dtpoff-debug` and `plt-got-gdb`; `xtask/src/debug/xlink.rs`
`EXPECTED` lists (wild, `tls-dtpoff-debug`, x86_64, `tls_static.c`),
(wild, `plt-got-gdb`, aarch64, `stack_protector.c`) and (wild,
`plt-got-gdb`, aarch64, `hardening_a64.cpp`). A record is XLINK only for
a listed entry, when `llc`'s session lacks a check and the case's witness
holds on both linked programs; everything else is unchanged.

## Removing an exception

When wild is updated: run `cargo xtask debug --linker wild` on the
target. An entry whose `llc` session now meets every check makes hod's
PASS an XPASS naming it ("stale"): delete the `EXPECTED` row, and the
`EXCEPTIONS` row when no other test uses the case. For
`tls-dtpoff-debug` the fix is visible without a debugger:
`.build/findings/wp-248/x86_64/repro.sh` prints operands 0 and 4 for
`llc-wild`. For `plt-got-gdb` the case may also end by a gdb whose BFD
names `.plt.got` stubs on AArch64 (as it does on x86-64).

## Tests

`xlink::tests` (five unit tests: both witnesses on dumped text, which
entries are expected, an excepted ERROR is XLINK and an unexcepted one
stays ERROR, a passing listed case is a stale XPASS);
`xtask/tests/debug_real.rs` `quick_tier_matches_llc` also requires every
XLINK to be a listed entry. The x86-64 quick tier with native gdb runs
only on the hosted x86-64 lane.
