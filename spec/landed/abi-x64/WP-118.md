# WP-118 — `spec/abi-x64.md` and `assign` for x86-64 Linux

Landed: all of `spec/abi-x64.md` (§1 to §12), and `hod_x64::abi` that
implements it. `hod_cg/src/abi.rs` and `spec/codegen.md` are unchanged;
the gaps found in that interface are listed below.

## What it did

- `crates/hod_x64/src/abi.rs`:
  - `assign(types, sig, features, out) -> Result<(), AbiUnsupported>`
    (§3 to §6, §9, §10), with `Features { avx, avx512 }` (§1.3);
  - `classify(types, ty, features)`, the per-target leaf hook (§4), and
    a private copy of the aggregate walk, marked `TEMPORARY` until
    `hod_cg`'s lands (WP-117);
  - `cc_is_c` (§1.2); `Extension`, `produced_extension`,
    `assumed_extension` (§7); `dwarf_number` (§8.6);
  - the register numbering of §2 (`gpr`, `xmm`, `st`, `is_*`, `number`,
    `RAX`.., `ARG_GPRS`, `RET_GPRS`, `INDIRECT_RESULT`, `NEST_REG`),
    marked provisional until WP-116's `hod_x64::reg` exists;
  - `UNSUPPORTED`: the 19 names of §10.
- `crates/hod_x64/tests/abi/`: the cross-check against `llc` and its
  tool-free companions, ported from `hod_a64/tests/abi` (an AT&T emitter
  driven by the `Assignment` alone, x87 and mask-lane staging, a C
  driver, the qemu runner); `tests/abi/data/` is a copy of design 0006
  §3's experiments.
- `lib.rs`: `pub mod abi;`. `Cargo.toml`: `hod_ll` and `hod_testutil` as
  dev-dependencies.

## Test evidence

Commands, from the worktree after `source scripts/env.sh`, on an AArch64
host (x86-64 code linked with `x86_64-linux-gnu-gcc`, run under
`qemu-x86_64 -L /usr/x86_64-linux-gnu`):

- quick: `cargo test -p hod_x64` — 21 tests, about 35 s;
- full: `HOD_ABI_GRID=full cargo test -p hod_x64 --test abi --
  --test-threads 2` — the same tests, about 135 s.

Every run below passed with no failure and no `llc` crash. Each cell is
"hod calls LLVM / LLVM calls hod", and is the same for the three
configurations of a version (`-O0`, `-O0 -fast-isel=0`, `-O2`).

| grid | signatures | llc 22 | llc 19 |
|---|---|---|---|
| systematic | 3,670 | 3,010 / 3,670 | 2,705 / 3,286 |
| random, seed 1 (full) | 2,000 | 1,761 / 2,000 | 1,111 / 1,250 |
| random, seeds 2 to 4 (full) | 6,000 | 5,160 / 6,000 | 3,302 / 3,768 |
| design data (`tests/abi/data`) | 80 | 78 / 80 | 75 / 77 |
| variadic against C (full) | 1,919 | 1,919 / 1,919 | 1,066 / 1,066 |

The first number is smaller because a variadic signature runs with LLVM
calling only (the variadic grid does the other direction in C). LLVM 19
runs fewer because a signature holding an integer wider than 64 bits or
a vector of `i64`/`ptr` split element-wise is not run against it when
any of it is on the stack (§4.2); without that skip the systematic grid
fails 384 LLVM 19 runs, each of that kind. The systematic grid refuses
68 of its own signatures (`abi:cc` 16, `x64:mask-vector` 28, `x64:nest`
5, `x64:ret-x87-part` 19) and asserts that these are the only names.

Tool-free: `table::*` (11 tests: hand-written assignments, the §7
tables, conventions including `fastcc`'s third return register, DWARF
numbers), `errors::every_name`, `errors::any_signature_is_answered`,
`data::data_signatures_assign`, `perf::perf_of_assign`. With `llc` but
outside the grid: `cc::conventions_equal_to_c`, `cc::musttail_in_llvm`.

## Corrections to design 0006 §3

Listed in `spec/abi-x64.md` §12: the LLVM 19/22 differences for wide
integers (§4.2, §9.4); `{ i128 }` as two ordinary pieces; the `half`,
`fp128` and vector rows of the return table; `fastcc`'s third
`float`/`double` return register; `<N x i1>` scalarized outside 1, 2, 4,
8, 16; `<1 x half>` widened; `r10` not forwarded by the variadic
`musttail` thunk.

## Gaps in `hod_cg::abi`

- `Place`/`PReg` have no x87 class: `st(n)` is a private index 32 + n
  (`crates/hod_cg/src/abi.rs:47`, `crates/hod_cg/src/reg.rs:162`).
- `Target::assign` and `Sig` carry no target features, so a target
  object must hold `Features` (`crates/hod_cg/src/target.rs:118`,
  `crates/hod_cg/src/abi.rs:19`).
- `Assignment` cannot say "a `float` in `st0`" (it would need a
  conversion), hence `x64:ret-x87-part` (`crates/hod_cg/src/abi.rs:139`).
- Nothing selects the LLVM 19 behaviour of §4.2; hod follows LLVM 22.
