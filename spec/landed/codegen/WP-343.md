# WP-343: stack-protected coroutine bodies

## Where it comes from

WP-333 (`spec/landed/codegen/WP-333.md`) made a protected function copy
its wholly stack-passed arguments at entry into homes below the guard
(`spec/codegen.md` §5.6.24 rule 10), but left protected coroutine bodies
out (`hod_cg::driver::enter_arguments`, `self.coro.is_none()`): not
measured, not changed. This package measured them against `llc` and
closed the gap.

## What llc does (measured, 19 and 22, x86-64 and AArch64, after `opt -passes='default<O0>'`, `-O0`)

- CoroSplit's ramp, resume, destroy and cleanup functions keep the
  body's protector attribute and are protected as any function: the
  guard is written in each prologue and checked before each return (a
  suspend's return, the final return), never on unwinding. Under `ssp`
  and `sspstrong` each of them is guarded as soon as the body has a
  buffer on the machine stack (it is cloned into each).
- A slot whose scope holds a suspend is in the heap frame, which no
  guard watches; a buffer whose scope holds none stays on the machine
  stack.
- The split ramp is an ordinary function, so its stack-passed arguments
  are loaded at entry, before the guard store, into registers or spill
  slots below the guard (WP-333's finding), and an overflow of a ramp
  buffer followed by a store through a stack-passed pointer argument
  ends in `__stack_chk_fail` (SIGABRT, "stack smashing detected").

## What hod did before (built at `f20f08b6`)

- `victim.ll` (a protected ramp that overflows a 16-byte buffer, then
  stores through its 9th argument): hod died of SIGSEGV on x86-64 and
  AArch64 (the store went through the overwritten argument, read in
  place above the guard); `llc` aborts. In bounds, equal.
- Ramp and resumed-activation overflows of a machine-stack buffer
  (`overflow.cpp`): already equal to `llc` (the stubs write the guard,
  `guard::stub_enter`).

## What landed

- `crates/hod_cg/src/driver.rs` `enter_arguments`: the WP-333 copy below
  the guard applies to coroutine bodies too. Their arguments are read
  only in the ramp (`spec/xform.md` §3.4), whose machine frame holds the
  homes. One rule on all three targets.
- i386: `hod_x86`'s `ssp::copy_arguments` already copies the whole
  incoming area of a protected function below the guard
  (`spec/codegen-x86.md` §19.2, §18 "With §19") and redirects every
  access to it, so a ramp's home is now a second copy of that copy:
  redundant, harmless (both below the guard), and the same as i386's
  non-coroutine protected functions already had.
- `spec/codegen.md` §5.6.24 rule 10 (the coroutine and i386 sentences),
  new rule 11 (llc's rule for coroutine bodies, hod's mapping).
- No refusal added.

## Tests

`crates/hod/tests/coro_protected.rs`, data `crates/hod/tests/data/coro/`,
x86-64 and AArch64, each hod object plain and under stress against
`llc`'s: `protected.cpp` (clang 19 and 22, `ssp`, `sspstrong`, `sspreq`,
static and PIE; 32 runs per target), `overflow.cpp` (ramp and resumed
activation overflows; 48 per target), `victim.ll` (48 per target).

## Evidence

- Before, counted (the old condition put back, `cargo test -p hod --test
  coro_protected`): 2 of 3 tests pass; `a_ramp_reads_its_stack_arguments_below_the_guard`
  fails at its first comparison, `x86_64-22-ssp-exe ["overflow"]`: `llc`
  SIGABRT (smashed), hod SIGSEGV (not smashed). Head: 3 of 3.
- compare-binaries, `f20f08b6` (own target directory) against the head,
  over `tests/ir`, `.build/corpus/kiln`, `.build/corpus-x64/kiln`,
  `-j 4`: 14120 comparisons, 0 different, 0 changed outcome, 47 identical
  failures (aarch64 3, i686 38, x86_64 6). No module there has a
  protected coroutine body with a stack-passed argument.
- i386 by hand: `crates/hod/tests/data/i386/coro/protected.cpp`, clang
  19 and 22, `-fstack-protector-strong` and `-all`, static and PIE
  (8 objects): every object differs, only in `protected_gen`'s body (its
  frame grows by 32 bytes, 8 loads and stores copy the 8 argument words
  from the incoming area's copy into homes; the stubs share that frame);
  every other function is unchanged but for its position.
  `i386_coro` passes (`protected_bodies_run_as_llc_s` included).
- irdiff, head, LLVM 22 and 19: x86_64 480 PASS, aarch64 470 PASS,
  i686 171 PASS; 0 FAIL, 0 ERROR each (base counts).

## Not done

- The i386 double copy: removing the redundancy (the driver's home
  copying from `ssp::copy_arguments`'s copy, for every i386 protected
  function, not only ramps) is a possible later cut.
- A buffer in the heap frame is watched by no guard, in hod and `llc`
  alike.
