# WP-324 — i386: refusals clang's 32-bit output reaches

Landed: `crates/hod_x86/src/ibr.rs`, `ssp.rs`, `cet.rs`; one arm in
`call.rs` (`llvm.eh.unwind.init`). Behaviour: `spec/codegen-x86.md`
§19 (19.1 to 19.4; numbered 15 to 18 on the branch) and the §7 rows. Tests: `crates/hod/tests/i386_ibr.rs`,
`i386_ssp.rs`, `i386_cet.rs` (run harness `i386_i11b/mod.rs`), the
`tests/ir` seeds under `cargo xtask irdiff --target i686`.

## Step 0: what clang emits for i686 (clang 19 and 22, `-O0`)

| flags | what reaches hod | base hod |
|---|---|---|
| default (virtual classes, buffers, computed goto) | `frame-pointer=all`, `stack-protector-buffer-size=8`, no `ssp`, no `cf-protection-*`, no `stackrealign` | computed goto refused (`x86:indirect-branch`) |
| `-fstack-protector-strong -fcf-protection=full` | `sspstrong`, module flags `cf-protection-branch`/`-return` | `x86:cf-protection` (the first reached), then `x86:stack-protector` |
| `-mstack-protector-guard=global` | module flag `stack-protector-guard` | refused by the front half (`module-flag:stack-protector-guard`), unchanged |

Order taken: indirect branches, stack protectors, CET, then the
constant and the intrinsics.

## Per item

1. **`x86:indirect-branch`** (done). `llc`: `jmp *reg`; a label address
   is an absolute `R_386_32` in static code and `@GOTOFF` in PIC. hod: a
   label address in code is `call 0; pop r; lea r, [r + label - .]`
   (position-independent in both models), in data the existing block
   relocations; an `indirectbr` on a constant of its own function is a
   `br`. Another function's block in code: `x86:blockaddress` (new).
   Tests: 72 runs of `ibr/interp.c` equal `llc`'s.
2. **`x86:stack-protector`** (done). `llc`: guard `gs:[0x14]` (static
   and PIC), check before the epilogue and before a `musttail` jump,
   `call __stack_chk_fail@PLT` (never `__stack_chk_fail_local`), a
   `float`/`double` result live into the return is stored and reloaded
   around the check (rounded). hod: the same guard and fail call through
   `pic::emit_call`; the block placed last in the local area
   (`hod_cg::guard::GuardPlan`), the low guard at `Local(0)`; the x87
   rounding follows `llc`'s choice of protected functions
   (`ssp::checks_at_return`, an approximation: §19.2). Tests: 288 runs
   equal `llc`'s; 216 overflow runs abort with `*** stack smashing
   detected ***` as `llc`'s (cases 1 to 6).

   **The stack arguments of a protected function.** At first hod read the
   hidden struct-result pointer from the incoming area. That area lies
   above the guard and the return address, so an overflow that reached
   it made hod store the result through an overwritten pointer, and fault
   with SIGSEGV, before the check ran. Measured with `llc` 19 and 22 at
   `-O0`, CPU `generic` and `i686`, static and PIC, on a probe with
   `sret`, a `[20 x i8]` buffer passed to a call, and a stack `i32` read
   after the call and in a second block. `llc` loads every stack argument
   used after the entry block's first call at entry. It keeps the value
   in a spill slot below its protected arrays (`movl 48(%esp)` →
   `16(%esp)`/`8(%esp)` against the buffer at `20(%esp)` and the guard at
   `40(%esp)`), and the stores of the result and the `eax` result reload
   it from there. An argument used only before the call is read in place
   at entry. `byval` copies are addressed in place.

   hod now copies, in a protected function, every incoming word that
   holds the hidden pointer or a part that is not `byval`. The copy is
   made in the prologue (`ssp::copy_arguments`,
   `crates/hod_x86/src/ssp.rs:164`, called from `frame::begin`, scratch
   `esi`). It goes into one 16-aligned local slot, which lies below the
   guarded block like every slot outside it. `ssp::incoming`
   (`ssp.rs:199`, applied in `common::frame_inst`) sends every later
   access of those bytes to the copy. The exception is a `musttail`
   call's write of its stack arguments into the real area
   (`ssp::raw_incoming`, from `Target::copy`). Spec: §19.2, "The incoming
   stack arguments are copied below the guard". The weakness reproduced
   with the head before the fix: `ssp/args.ll` with `@over` = 200 gave
   SIGSEGV under hod and `*** stack smashing detected ***` under `llc`.
   Tests: `smash.c` case 6 (an overflow in `make`, whose result goes
   through the hidden pointer; static and PIE, `llc` 19 and 22, GNU ld,
   lld, mold, also `Stress::ALL`). `ssp/args.ll` covers the hidden
   pointer, a pointer argument and a scalar argument on the stack: 144
   runs, CPU `generic` and `i686`, static and PIE, `llc` 19 and 22. In
   bounds the output equals `llc`'s; with the overflow every build aborts.

   **The 64-bit targets (finding, not changed: byte-neutral package).**
   On both targets the hidden pointer arrives in a register (`rdi`, `x8`)
   and is spilled to a home below the guarded block. hod x86-64 keeps it
   at `[rbp - 0x38]`/`[rbp - 0x50]` with the block at `[rbp - 0x30]`, so
   the struct result itself is safe. But a STACK argument (the 7th
   integer argument on x86-64, the 9th on AArch64) keeps its incoming
   slot as its home (`hod_cg::driver::enter_arguments`, "Wholly on the
   stack"). That slot is above the guard, and it is read in place after
   the buffer is written. x86-64: `mov r12d, [rbp + 0x28]` after `call
   fill`. AArch64: `ldr x16, [x29, #0x10]` (the saved incoming `sp`) then
   `ldr w10, [x16]` after `bl fill`. `llc` x86-64 loads it at entry and
   spills it (`movl 88(%rsp), %eax` → `12(%rsp)`). A pointer-typed stack
   argument stored through after an overflow is therefore the same
   weakness on both 64-bit targets. Reproducer
   (`tests/ir/ssp_stack_arg_after_overflow.ll`, not added):

   ```llvm
   %struct.big = type { [5 x i32] }
   declare void @fill(ptr, i32)
   define void @make(ptr sret(%struct.big) %r, i32 %a1, i32 %a2, i32 %a3,
       i32 %a4, i32 %a5, i32 %a6, i32 %a7, i32 %a8, ptr %dst) sspstrong {
     %buf = alloca [20 x i8], align 1
     call void @fill(ptr %buf, i32 %a1)   ; writes past %buf
     store i32 1, ptr %dst, align 4       ; hod: %dst read from the
     ret void                             ; incoming area, above the guard
   }
   ```

   The fix belongs in `hod_cg` (a protected function's stack-argument
   homes in local slots, as on i386, or the same redirection in each
   target). It changes 64-bit bytes, so it needs its own package.
3. **`x86:cf-protection`** (done). `llc`: `endbr32` at entries (not
   `nocf_check`, not local functions whose address is not taken), at
   address-taken blocks and landing pads, after `returns_twice` calls;
   the 28-byte ELF32 note aligned to 4. hod: the same note byte for byte
   (`hod_obj::elf::add_gnu_properties` pads to the address size;
   `hod_cg`'s `gnu_property` writes it for i386); `endbr32` at a
   superset of `llc`'s places; an indirect `nocf_check` call refused
   (`x86:nocf-check-indirect-call`, new). Tests: 72 runs equal `llc`'s,
   12 objects' notes and landings compared, 24 freestanding links keep
   (or, with one unmarked object, drop) the property under GNU ld, lld,
   mold.
4. **`x86:constant`**: not done. The supervisor moved it out of this
   package; the facts and the next step are in `PARKED.md` at the tree
   root.
5. **`x86:intrinsic`** (part). `frame_intrinsics.ll` stopped at
   `llvm.eh.unwind.init` in `saving`: `llc` saves `ebp`, `ebx`, `edi`,
   `esi`, which every hod frame saves, so it is now a no-op and the
   seed passes. `drift_saturation.ll` stops at `llvm.fptosi.sat.*` /
   `fptoui.sat.*` with `float`/`double` sources (function `convs`):
   `llc` lowers them inline on the x87 (`fist`/`fistp` with clamping
   compares), a floating-point family `bits.rs` does not have at any
   width; it belongs to `x87.rs`, not touched here.
